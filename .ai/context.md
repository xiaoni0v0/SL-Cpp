# SL 项目协作上下文

这个文件不是语言标准（标准是 `SL.md`），是给"未来的我"或接手的另一个 AI 用的交接材料：记录 `SL.md`
里**没写**、但理解这门语言设计脉络所必需的东西——协作习惯、被否决的方案（及理由，避免重新提出）、
还悬而未决的问题、以及一些跟语言行为无关但重要的实现策略讨论。`SL.md` 本身只写行为契约，不写这些。

每次大改之后建议回来更新这个文件；`SL.md` 的具体条文以文件本身为准，这里只讲"为什么"和"还差什么"。

## 协作约定（durable，几乎不会变）

- **全程说中文**。
- **不准动 git**（不 commit、不 init、不查 log，任何 git 操作都不做）。
- 用户会在讨论中途**直接编辑 `SL.md`**（他自己的编辑器/IDE），出现过我的 Edit 因为文件已变化而失败、
  或者我前一轮的编辑被并发保存"冲字"回旧版本的情况。**每次回复前必须重新 Read 相关章节**，不能凭上一次
  读到的内容假设现状；系统会在文件被外部修改时给出提示，据此判断，不要反过来"纠正"用户的改动。
- 讨论节奏：用户抛出问题或疑虑 → 来回讨论权衡（我给意见、用户拍板或反驳）→ 用户说"写吧"/"改一下"才动手
  改 `SL.md`。**不要在讨论阶段就抢先写文件**；但如果用户已经把所有子问题都拍板、只是最后追问一句"这样对吧"，
  可以视作已授权直接写。
- 文风：要简洁，别啰嗦、别一次给一大段。用户多次说"你写得太啰嗦了"。```SL.md``` 里也一样，正交的可选项
  不要用"或"挨个穷举组合（见下面 `⟦⟧` 记号）。这条同样适用于本文件自己——只记"为什么"和"被否决的方案"，
  不记实现过程narrative、具体改了哪些文件/行号、测试用例数这类能从代码本身推出来的东西。
- 设计取舍的默认立场：显式优于隐式；不为"拼写错误/边缘场景"加机制（已否决 `@override`、强制访问控制、
  `__getattribute__`）；能复用已有机制就别发明新协议；标准里只写行为契约，不写具体算法/实现细节（已明确
  拒绝过：完整 C3 合并算法、复合赋值的临时变量展开式）。
- 优先级排序（用户原话）：数字字面量、`assert` 这类"加了也不会破坏什么"的功能可以往后拖；链式比较这类要
  设计的现在弄；`set`/文件 I/O/用户模块系统/内置库这些"不属于语言本身"的东西放到**最后**，语言核心先谈完。
- **构建与测试**：直接用 Bash 调 CLion 自带的 MinGW g++ 会失败（cc1plus 起不来），但用户提供了
  `.ai/run_test.bat`（脚本自带 CLion 的 MinGW/CMake/Ninja PATH，构建 cmake-build-debug 后跑 ctest）。
  在 Bash 工具里执行 `cmd //c "E:\Programs\SL-Cpp\.ai\run_test.bat"` 即可自己构建+跑全部测试，
  改完代码后自己跑它验证，不用再请用户代跑。

### 记号约定（2.2 开头定义）

`⟦X⟧` 表示 `X` 可选（出现 0 或 1 次），纯粹是**本文档**描述语法用的元符号，不是 SL 语法（SL 自己的方括号
`[]` 有实际语法意义：捕获列表、列表字面量、索引）。重复仍用 `...` + 文字说明，没有单独造记号。这是为了解决
"正交的可选项被挨个枚举组合"导致语法说明冗长的问题。

**什么时候能用这个记号收敛、什么时候不能**：如果几种写法之间是"同一条规则的复用"（没有交互效果），就能收成
一行模板（`if`/`for`/`try` 属于这种）。如果几种组合之间存在**只有同时出现才有的额外行为**，就不能硬收，
必须分情况说明——例子：`identifier : type = expr` 里"类型注解 + 默认值同时出现"会额外触发"检查默认值是否
符合类型注解"这一步（`TypeError`），这不是"类型检查"和"默认值"两条规则的简单叠加，所以 3.4.6 里这四种形参
组合的**语义**部分没有收成一行，只是**语法**收了。

## 动态作用域 → 显式捕获（3.10）

标识符解析收窄成"只查当前帧 `_L`，查不到退回 `_G`"，不再沿帧栈向外搜索——这个改动本身就解决了模块隔离问题
（动机：模块内函数被外部调用时不该意外搜到调用者的帧）。访问外层作用域需显式捕获：值捕获（建立时取值，等价于
旧用可变默认参数模拟捕获的写法）、引用捕获 `&x`（只记 (定义帧, 标识符)，读写转发到定义帧）。捕获不跨层自动
传递，中间每层必须显式转发。捕获列表里的标识符不能再被 `global` 声明。

`x op= expr` 的内部读取有特例：不适用"退回 `_G`"，未标记 global 时只查 `_L`，找不到直接 `NameError`——保证
这一步的读写落在同一帧，否则会"读到全局值却悄悄写出一个同名局部变量"。因此 `x op= expr` **不等价于**
`x = x op expr`（这个不等价此前判断错过两次，别改回去）。

**引用捕获内存模型**（推翻两版才定）：
1. 强引用整个帧对象——否，帧永远不回收；
2. 帧维护"谁引用了我"的通知列表、弹出时清空——否，对象拷贝时旁路账本不会自动同步，任何自定义的脱离统一
   引用机制的"账本"都没法兼容未来的拷贝；
3. **采纳**：定义帧字段就是对帧对象的普通引用，走统一引用计数/拷贝规则；帧弹出时只清空自己的局部字典为
   `None`（不清成空字典，区别于"活着但没有局部变量"），不管谁还持有该帧引用。判活/判死看局部字典是不是
   `None`。天然兼容以后的浅/深拷贝。

值捕获 vs 引用捕获：值捕获无生命周期限制但不能共享可变状态；引用捕获能共享但离开定义帧生存期后必
`NameError`——共享可变状态的经典模式必须用"值捕获 + 可变对象当盒子"，不是加专门的 `Box`/`Wrapper` 类型
（已讨论并否决，list-as-box 够用）。

## `finally` 跳转限制（3.4.5.7）

`expr3` 求值期间跳出这段范围的 `return`/`break`/`continue` 不合法，`expr3` 自己的循环/函数不受影响。机制：
跳转信号本来就是"向外传播、被最近循环/函数接住"，`expr3` 相当于包了一层拦截，能被自己消化的跳不到这层，
传到这层的必然是想跳出去的。编译期能查出的提前报错，`eval` 现场编译的由这层运行时拦截兜底。

（一度以为要给 `eval` 调用点挂静态上下文——**过度设计，已否决**，正确答案就是"信号自然向外传播"，`eval`
内联在当前帧跑，不需要特殊配合。）

字节码化后 `break`/`continue`/`return` 变成直接跳转指令，`eval` 现场编译的代码没法跳进外层已编译好的字节码——
不是严重冲突：只需在 `CALL eval` 后加一小段"检查跳转信号回传、有就跳"，复用异常传播基础设施即可，纯实现选择，
不写入 SL.md。

## `eval` 设计要点（4.1.10）

内联语义：不压新帧，直接在当前帧求值，让捕获/`global`/`finally` 规则不需要为 `eval` 开 special case。实现
提示：`eval` 被调用先压的那一帧要弹出暂存，求值完（含异常/跳转路径）必须用 RAII 保证压回去，维持帧栈平衡。

## 链式比较（3.3、3.4.2、2.1.5）

`< <= > >= != ==` 互相可链，`is` 单独一档优先级（比这六个松），不跟它们混链、也不共用节点类型（拆成独立
`AstNodeIs`）。**为什么 `is` 要分开**：`bool` 继承 `int`，如果和比较符混链或优先级更高，`a < b is c` 解析成
`a < (b is c)` 会把布尔值当整数比大小——类型上合法、静默出错，是最危险的一类。拆开后 `a < b is c` 解析成
`(a < b) is c`，即便碰巧不报错也是一眼假的写法。取值语义类比 `a OP1 b and b OP2 c and ...`：短路时返回该次
比较结果，全通过返回最后一次结果；求值顺序"求一个、比一对，假了立刻短路"。

## 开放式切片（`None..8` / `3..None`）

不加独立语法，靠 `..` 运算符 + `None` 表达开放端。`None` 本身不参与这个约定——是 `int` 的
`__op_range__`/`__op_rrange__` 把"另一侧是 None"识别成开放端，走普通运算符重载分派。开放 range 只能当切片
下标，直接迭代 `TypeError`。

## 装饰器语法（改了三轮才对）

`@decorator expr` 求值为 `decorator(expr)`；`@deco func f(){...}` 还需要把 `f` 重新绑定到装饰结果。判断
"该不该重新绑定"：
1. 判断值有没有 `__name__`（鸭子类型）——否，`@staticmethod outer` 会意外重新绑定 `outer` 这个名字；
2. 判断 `expr` 语法形状是不是直接的 `func`/`class`——否，嵌套装饰器 `@d1 @d2 func f(){}` 外层 `expr` 是
   装饰器表达式不是 func，外层不触发，`d1` 被丢弃；
3. 递归剥开装饰器表达式再判断——能用但丑，且"看 expr 长什么样决定有没有副作用"本身就是隐式的，跟"显式
   优于隐式"冲突。

**最终**：语法层面拆成两个东西，判据只看紧跟着的是不是 `func`/`class` 关键字（跟具不具名无关）：
- `@d1 @d2 ... func/class ...`：属于 func/class 表达式自己语法的一部分，`decorators_` 是节点自己的字段
  （不是外层包一个 `AstNodeDecorator`）。建立后按从近到远应用装饰器，命名的额外重新绑定 `identifier`。
- `@decorator expr`（expr 非紧邻 func/class）：永远只是 `decorator(expr)`，无副作用。

**教训**：一个规则的触发条件要靠不断打补丁才能覆盖各种嵌套情况，往往说明从一开始就不该用同一个语法形式
表达两种意图，该在语法层拆开让解析器确定性判断，而不是语义层"猜"。

（AST 上同理：一度用同一个 `AstNodeDecorator` 包 `Func`/`Class`，靠"target 是不是 Func/Class"区分语义——
被推翻，改成 `AstNodeFunc`/`AstNodeClass` 自带 `decorators_`，`AstNodeDecorator` 只留给真正的通用形式。
跟 `AstNodeCompare`/`AstNodeIs` 拆分是同一条原则："语义形状不同就不该共用节点"。）

## 命名决策：`match`/`case` → `when`

理由：`switch` 心智预期不对；`match` 常用词太易冲突；参考 Kotlin `when`，碰撞风险低。候选并否决：`where`
（LINQ/SQL 强关联过滤）、`given`（Scala 隐式参数）、`branch`（像名词）、`select`（Go/SQL 已占用）、`pick`
（太随意）。`case` 暂留，`when` 完整设计搁置（"有 if 可以代替，不着急"）。

## 其他设计点（补理由，SL.md 已写规则）

- 反引号原始字符串 `` `...` ``：不转义、天然多行。加了之后 `"..."`/`'...'` **永远不会**再加 `r` 前缀或
  三引号（反引号已覆盖"原始+多行"，双方都不支持多行是既定的，加 raw 语义是 no-op）——不要再提议 `r"..."`。
- 值捕获不加类型注解：形参注解有意义因为每次调用值可能不同；值捕获建立时就定死，真要校验用 `x = expr`
  值捕获形式包一层就够，不需要新语法。
- 文档字符串去缩进对齐 Python 3.14（编译器本身清理缩进，不是只有 `inspect.cleandoc` 才清理）。
- `SystemExit`/`KeyboardInterrupt` 挂 `BaseException` 不挂 `Exception`；讨论过要不要连
  `except BaseException` 也禁掉，否决——效果有限还破坏"任何 BaseException 子类都能被 except"的统一规则。
- 返回类型注解符号从 `-> type` 改成 `: type`：复用形参已用的记号，参照 TypeScript，牺牲跟 Python `->`
  的相似性换来的是整个函数签名"冒号=类型注解"的统一。
- 解构赋值 `*` 前缀不限于标识符，可以是任意左值（`*x.attr`、`*x[i]` 合法）——比"只能 `*` 标识符"更宽松，
  是用户自己拍板的，别以为是笔误。

## 字节码 / `Code` 对象设计（非语言语义，供以后字节码化参考，不进 SL.md）

这套设计通过了"是否有可观察语言行为差异"的检验——换一种实现完全可以不这么做而不改变任何 SL 程序的可观察
行为，所以只记在这里。

**整体模型**：源码编译产出 `Code`（字节码+常量池），文件/函数体/类体建立各对应一个 `Code`，边界基本等于
帧的边界，唯一例外是 `eval`——运行时现编译一个 `Code` 但内联在调用处当前帧跑，不新开帧。`eval` 不因此需要
对 SL 代码开放独立的 `compile()` 内置函数——`Code` 对 SL 完全不可见。

`Code` 装：字节码；常量池（字面量、名字字符串、嵌套 `Code`）；行号映射+来源标识（非规范，纯为报错）。
函数体的 `Code` 额外带形参形状元数据。

**明确不装进 Code**：装饰器（建立完函数对象之后的独立步骤）；形参默认值/类型注解的具体值（外层作用域、
建立时求值，算出来挂在 Function 对象上，Code 只需要知道"有没有"）；捕获列表怎么捕获的字节码在外层 Code
里。**但引用捕获了哪些名字必须作为函数体 Code 的持久元数据保留**（最初判断错了，被 `eval` 纠正：`eval`
运行时现编译，不经过原函数体编译期的指令选择过程，必须能现查"这个函数的引用捕获表里有没有这个名字"才能
正确路由）。值捕获不受影响，它们就在 `_L` 普通字典里，eval 直接查。

**"建立函数/类对象"指令（`MAKE_FUNC`）**：固定弹栈顶 6 项（捕获元组、形参注解/默认值元组、返回类型注解、
函数名、`Code` 常量、`doc`），不需要操作数、不需要运行时先查元信息才知道弹几个（推翻过"运行时先查再弹"的
提案，弹几个必须编译期确定）。
- 引用捕获不产生任何字节码指令（推翻了"CAPTURE_REF 压 (name, 当前帧)"的提案）——`MAKE_FUNC` 本来就在
  当前帧字节码里执行，天然知道当前帧是谁，直接抓一份引用挂到新对象上，跟 `LOAD_NAME` 隐式读当前帧 `_L`
  是同一类"用 ambient 当前帧"操作。
- 缺注解/缺默认值统一压 `PUSH_NULL`（不是 `object`，也不是 `None`——`None` 是合法真实默认值，拿它当哨兵
  会跟"默认值就是 None"撞车，这个坑在 `__hash__=None` 那次踩过）。`PUSH_NULL` 是纯内部、SL 层拿不到的
  哨兵，一造出来立刻被 `MAKE_FUNC` 消费。
- 弹出 6 项、构造对象之前要检查每个非 `PUSH_NULL` 类型注解是否满足 `isinstance(annotation,
  type|CompoundType)`，在全部 6 项都求值完毕之后才做（呼应"副作用都在完全求值完毕之前发生"）。

**装饰器求值顺序**（曾经以为不需要专门定规则，是错的）：最初把 `@deco func f(){}` 当 `deco(f)` 的语法糖去
套用调用求值顺序——站不住脚，因为装饰器前缀是 func/class 自己产生式的一部分，根本不存在外层的 `deco(...)`
调用表达式。正式规则：先按从前到后对各 decorator 求值，再进入捕获/形参/返回类型求值；装饰器的调用仍在建立
完毕后按从近到远进行。命名函数/类的绑定只在最终值确定后发生一次（不再是"先临时绑定、再重新绑定覆盖"的
两步）。

**Function 对象与 Code 的关系**：Code 编译一次可能复用多次（函数每次被调用新开帧但执行同一份 Code；循环体里
`func` 表达式求值多次产生的多个 Function 对象共享同一份 Code）。但"建立"这个操作每次执行都必须构造全新对象，
不能因为 Code 复用就连带缓存对象——`is` 比较的是对象身份，直接关系闭包正确性（循环里值捕获必须各自捕获到
当次的值）。

**Code 对语言用户隐藏**：不通过 `getattr`/`attrs()` 暴露（不像 Python `f.__code__`）——暴露就等于把字节码
格式钉成可观察行为，以后想换实现就是破坏性变更。

## Parser/AST 重写：审查旧 parser 时挖出的设计与 bug

旧 parser 照更早版本标准写的，`class`/`while`/捕获列表/返回类型注解/文档字符串槽位/链式比较全部缺失，
审查时顺带挖出两个真 bug：左结合运算符的 `rbp` 曾写成 `= lbp`（应为 `lbp + 1`），对可交换算子无影响，
但对 `-`/`//`/`%`/`<<`/`>>`/`..` 是真实算错值；`++`/`--` 原共用一元运算符优先级解析操作数，当时优先级
比 `**` 还高。

**AST 节点拆分原则**："语义形状不同就不该共用节点类型"这条这次会话反复用到：比较运算符
`< <= > >= == !=` 从 `AstNodeOpBinary` 拆成 `AstNodeCompare`（单个比较也用这个节点，不搞双表示，因为
链式比较的短路/单次求值语义跟普通二元运算完全不同）；`is` 又从 `AstNodeCompare` 里进一步拆成独立
`AstNodeIs`（`is` 不可重载、两组不能混链，独立节点天然满足这个约束，不用靠 parser 老实构造维持）。

**`++`/`--` 整体从语言里砍掉**（用户自己反悔的决定）：没有后缀形式，丢了 C 系"真正好用"的场景
（`arr[i++]`），剩下的前缀用法跟 `x += 1` 值语义完全一样，纯粹少打两个字符换来专门一档优先级+专门
节点+专门左值校验，投入产出不成比例，跟"不为图方便加机制"一贯取舍一致。

**`while` 没有单独 AST 节点**：`while [$] (cond) body` 语义上就是 `for [$] (; cond ;) body`，
`parse_while()` 直接构造 `AstNodeForCond{init=null, inc=null}`。`SL.md` 里 `while` 仍是独立关键字/
独立小节（可读性），纯内部化简。

**Dumper 改用 `AstNode::to_json()` 虚函数**（原来是 X-macro + `dynamic_cast` 链式分发的自由函数）：
`SemanticChecker` 有跨节点遍历状态（`Context`），留在外部合理；`Dumper` 纯粹"每个节点知道怎么描述自己"，
没有跨节点状态，虚函数更合适，且编译期强制补全（漏了直接编译失败），比 X-macro"忘加 case 运行时死循环
栈溢出"安全。代价是 AST 层依赖 `nlohmann/json.hpp`，接受。`SemanticChecker` 有意不对称，仍是外部 X-macro
分发。

**节点位置字段几经反复，最终版**：曾经给每个节点补完整的起止范围（Token 加 `end_row/col`、`AstNode` 加
`end_row_/end_col_`、`Parser::make_node<T>` 统一构造）——后来用户质疑"这真的有必要吗"，撤销：一个节点的
结束位置几乎总能从最右子节点递归推出，不需要现在就存；真正拿不回来的只是"运算符自己的位置"（夹在两个
子节点中间，不属于任何一个孩子）。改成窄版：只给"产生式里夹着一个不属于任何子节点的裸 token"的节点类型
各补一个位置点（`AstNodeOpUnary`/`OpBinary`/`CompoundAssign` 的 `op_pos_`，`AstNodeAttr` 的
`dot_pos_`，`AstNodeCall`/`AstNodeIndex` 的 `paren_pos_`/`bracket_pos_`，`AstNodeFunc`/`Class` 的
`decorator_positions_`，`Compare`/`Is` 的 `op_positions_`），用统一的 `struct Position{int row,col;}`
（不用 `pair`，避免 `.first`/`.second` 混淆）。**`AstNode` 基类的 `row_/col_` 最终也统一改成
`Position pos_`**（全部 ast_node_*.h、Parser.cpp、SemanticChecker.cpp 跟着改）；`Lexer`/`SyntaxError`
保留 `(row, col)` 两个 int 不变——lexer 那边一个 token 只有一种位置，不存在"歧义"，包一层 `Position`
纯粹多一层访问路径，零收益。

**`for` 迭代模式 target 放宽成任意左值**（类比 Python `for a, *b in iterable`），parser 不用改（本来
就走 `parse_expr()`），但顺手修了一个既有 bug：`check_lvalue` 从来没处理过 `AstNodeStar`（`*b`），
解构赋值带 `*` 的写法此前从未被真正校验过。

**判断"parser 该不该直接收紧到 token 级别"的标尺**：条文有没有把该槽位定义成一条独立、单一、不含表达式
递归的产生式（有→直接 `expect` 对应 token，不需要语义层）；有没有语法歧义需要拖到更后的 token 才能消解
（有→只能先按表达式解析，形状校验推迟到语义层）。`global identifier` 属于前者（直接
`expect(IDENTIFIER)`），`for` 迭代模式的 identifier 属于后者（`:`/`;`/`)` 要读到才能判断走哪条产生式）。
`del target` 语法上允许标识符或属性访问两种形状，也是"语法是表达式、语义层限定形状"的合理场景。

`global a.x` 解析成 `(global a).x`：**判定为预期行为不是 bug**——`global` 求值为 `None`，`(global a).x`
就是 `None.x`，运行时报错，跟其他任何"值为固定值的 primary 后面接后缀运算符"（`break.x`、`None.x`）是
同一种情况，专门拦截反而是在统一规则里挖洞。

**几个"跳换行容错 + 边界判定"的 bug，根因都是同一类**：提前做的换行/分隔符归一化操作，不小心把后续判别
要用的信号一并抹掉了。
- `for(a\nb\n)`：`consume_sep` 靠"回头比较行号"判断有没有分隔符，判不出"换行之后到底是下一槽内容还是
  压根没有下一槽"；修法是跳过换行后再看一眼是不是紧跟收尾括号。
- `{; a : b}`：入口无条件 `skip_terminator()` 把"见没见过前导 `;`"这个字典判别信号连同换行一起吃掉了；
  修法是拆成先 `skip_newline()` 再显式 `check(SIGN_SEMICOLON)`。
- `f({a\nb})`：块内换行被外层括号的续行规则（`skip_paren_newline` 靠 `paren_depth_ > 0` 判断）穿透，
  导致同一段文本在括号内外解析出不同结果；修法是进入 `{` 时暂存并清零 `paren_depth_`，出 `}` 后恢复
  （三处入口：`parse_brace`、`parse_func`/`parse_class` 的函数体/类体）。后来这个修法本身在字典分支又
  栽了一次同样的坑（`paren_depth_` 恢复得太早，写在 `finish_dict` **之前**而不是之后，导致
  `f({k: v\n+ w})` 又被误续行）——教训是"整个块内容解析完才恢复"必须严格执行到每一条分支。

**`parse_comma_list` 提取**：8 处"括号内逗号列表"（元组、列表、索引、类基类、异常列表、调用实参、捕获
列表、形参列表）共享同一套"跳前导换行→判空/解析第一项→逗号循环→尾逗号容错"骨架，提取成公共方法。设计上
否决过两个方向：复用 `parse_paren_or_tuple` 本身（它自带的"分组 vs 元组"二义性消解是表达式位置括号独有
的语义，其它语境不该继承这层隐含知识）；给一个"如何处理某种 item"的开关参数（否决，因为各处 item 类型
完全不同：`AstNodePtr`/`pair`/`OneCapture`/`OneParam`，改成让调用方传 `parse_item` 回调，通用骨架只管
逗号语法形状）。唯一没并入的是字典（判别"是字典还是复合表达式"要在进入逗号循环之前完成，且第一项判别
逻辑必须留在 `parse_brace_block` 自己手里）。

**字典展开项判定改为 AST 级**：原来判别"是不是展开项"看第一个 **token** 是不是 `**`，导致 `{(**d)}`
（分组括号包着展开）被误判成复合表达式——而 SL 里分组括号处处透明（`f((**d))` 与 `f(**d)` AST 完全
相同），字典的 token 级判别是全语言唯一一处"括号不透明"。改成解析完表达式后 `dynamic_cast` 判 AST 根
是不是 `AstNodeDoubleStar`，跟"分组透明"这条通用规则保持一致；`{**d + x}` 现在解析为复合表达式（根是
`OpBinary` 不是展开节点，展开节点本身位置不合法交给语义层按 3.6 拒绝）。

**消除"同一产物多出口构造"的短路径风格**：用户观察到最近两个 bug（`{; a : b}` 误判、`for(a\nb\n)`
误判）都是提前返回的特判路径孵出来的——同一种产物在多个出口分头构造，每条路径都是一块测试压不到的独立
状态空间。整改原则：合并"同一产物多处构造"，保留"产物本质不同"的分叉（字典 vs 复合表达式、分组 vs 元组
这些才是真正的二选一）。

**展开/装饰器的结合力、分组透明性补进 SL.md**：`*`/`**` 展开和 `@` 装饰器语义上是"变相的运算符"但不进
2.1.5 运算符表（结合层面像前缀运算符，但语义上不产生独立值、不可重载、只在特定父位置合法）。展开操作数
按单目优先级 140 解析（`*a.b` ≡ `*(a.b)`，属性/调用/索引/`?`/`!`/幂先结合，其余不结合）；装饰器串按
正常优先级贪心解析装饰器本身，被装饰的 `expr` 结合得比一切运算符都松（`@d x = y` ≡ `d(x = y)`）。2.1.5
补齐了分组（冗余括号）的正式定义：单元素无尾逗号的 `(expr)` 与 `expr` 完全同一个表达式，对一切"按表达式
本身判定"的场合（字典判别、展开位置判定）透明。

**其它零散 bug**（一句话记录，细节已在代码里体现）：
- `{k v}`（无分隔符）曾被静默接受成合法复合表达式——根因是判别第一项在 `parse_exprs()` 循环外解析，
  没过"两条表达式之间必须有分隔符"这道检查；后来提炼成独立的 `check_expr_terminator()` 方法（一个只
  服务于一处特例的参数不该泄漏进通用工具函数签名）。
- 零参数函数 `func f() {}` 完全解析不出来——`parse_func_param()` 没有"是否紧跟 `)`"的守卫，改成返回
  `optional`。
- `(1` 报错文案"expected ')' to close tuple"不准确（这时候分不清是元组还是分组）——加 `saw_comma`
  标记二选一措辞。
- `Lexer.cpp` 三处报错位置靠"当前 col_ 减几"现算，转义规则一变这些写死的减法就全错——改成进入可能
  变长的解析逻辑那一刻就存好位置变量，报错直接用，不再对 `col_` 做算术。
- `Parser::expect()` 报错信息曾直接暴露内部枚举名——新增面向用户的 `get_display_name_by_tokentype()`。
- 字符串转义截断报错文案统一成"unterminated escape sequence in string literal"跟其它"unterminated X"
  文案对齐。
- 几组"判断+转换"函数对（`is_compare_op`+`token_type_to_compare_op_type` 等），同一份 case 列表抄了
  两遍，合并成一个返回 `optional<OpType>` 的函数；`default: assert(false)` 换成 `return std::nullopt`
  （`-Wswitch` 要求有 default，`assert` 在 NDEBUG 下会被优化掉、实际是 UB）。

## Parser 码风统一（细节见对应 notes 文件）

`advance()` 全部改用 `expect()`（类型在调用点几选一的例外保留裸 `advance`）——防止"以为当前 token
一定是 X、实际不是"被静默吃掉变成下游报错，见 [[parser-prefer-expect]]。`finish_*` 系列的
`paren_depth_` 管理统一成"起始括号由调用方消耗、增减完全由 `finish_*` 自己管理、收尾永远先 `expect`
再 `--`"，见 [[parser-paren-depth-convention]]。`parse_chain_compare`/`parse_chain_is`/`finish_dict`
保留成独立方法不内联成 lambda（体量大、各自对应 SL.md 明确成节的语法概念），见
[[parser-member-vs-lambda]]。`skip_newline`/`skip_paren_newline`/`skip_terminator` 的空行布局原则：
一个 skip 调用永远只跟它后面的东西是一组（skip 只影响接下来的位置敏感操作，不为前面的事收尾），据此
删掉了 3 处证明为死代码的多余 skip 调用（判定方法：反向追问"到达这里的所有代码路径是不是都保证
`pos_` 已处于无分隔符状态"）。`consume_sep` 依赖的"回溯比较行号"逻辑最终提炼成独立方法
`separated_by_newline()`，跟 `check_over_newline`（正向扫描）成对放在一起——这两者是全项目仅有的
"处理换行容错的回溯/正向判断"，其余同类循环都不依赖这种判断。

## 字典展开项的存储方式：沿用"槽为空表示另一种形状"惯例

字典 `{k1: v1, **d2, ...}` 用 `vector<pair<AstNodePtr, AstNodePtr>>` 存 `items_`，`**expr` 展开项存成
`{expr, nullptr}`。讨论过要不要换成 `variant`——没换，因为"槽为空表示另一种形状"是整棵 AST 到处在用的
既有惯例（`AstNodeIf::else_expr_`、`AstNodeReturn::value_`……），换 variant 会成为全 AST 唯一一处用它
的地方，不划算。

## 空 `{}`：维持复合表达式语义

一度倾向改成空字典（Python 直觉、`()`/`[]` 为空都优先当空字面量集合）。但 SL.md 已有明确答案不需要改：
空字典本来就是 `dict()` 写的，不靠 `{}`；判别规则本身"要么 `**` 开头、要么第一个表达式后紧跟 `:`，否则
复合表达式"统一适用，空的情况自然落到"都不满足"分支。关键反例：`a = if (cond) {}` 里想表达"这个分支
什么都不做"的 `{}`，如果是空字典会让 `a` 变成空字典而不是 `None`，而空字典和 `None` 一样 truthy 上是
falsy，这类错误会长期潜伏。要空操作写 `None`，要空字典写 `dict()`，两者都有清晰写法，`{}` 不需要身兼
二职。

## if/while/for 条件槽拒绝裸赋值 `=`

防 `if (x = 5)` 手误坑（SL 是动态类型，赋值本身有值，没有 Swift/Rust 那种类型系统能免费防）。只限制
`if`/`while` 的 `cond`、`for` 三槽形式中间槽；不限制 `for` 的 `init`/`inc`（这两槽存在的意义就是赋值）；
只挡裸 `=`，不挡 `+=` 等复合赋值（没有跟 `==` 手误的风险）。真要在条件里赋值需要显式再套一层括号
`if ((x = y))`——外层用受限的 `parse_expr_pratt(11)`（卡住 lbp=10 的赋值类运算符），内层分组走不受限的
`parse_expr()`，两层括号天然形成边界。

（顺带发现并删掉一个未被 SL.md 授权的历史遗留分支：`for (cond) body` 这种"裸单槽纯条件形式"——
`while $ (cond) body` 已经能做到完全一样的效果，这个分支不提供任何 while 做不到的能力，反而削弱
"while 是纯条件循环专用关键字"的区分。）

之前大量 `CHECK_THROWS_AS` 只确认"会抛异常"，不管抛得对不对、指哪儿。补了两类：给全部 `error(...)`
调用点加"消息包含关键词 + 位置精确指向哪个 token"的断言；新增 `combination_test.cpp` 覆盖单章节测试
覆盖不到的"交互"场景（装饰器+类+捕获+`**kwargs`+`for $`+`is`+`try` 揉在一起，括号嵌套时 `paren_depth_`
一致性等）。（这里再次踩了 nlohmann brace-init 陷阱，已并入 [[json-test-brace-init-trap]] 笔记。）

## 架构边界：编译期 C++ 异常 vs SL 运行时异常对象

`builtins/exceptions/SyntaxError.h` 的 `SyntaxError`（纯 C++ 异常）和 SL.md 文档化的、暴露给 SL 用户
代码的异常类只是碰巧重名，现阶段完全不是同一个东西——`SlObject` 还是空壳，没有类系统。**这不是需要
二选一的问题，是本来就该分层**，SL.md 本身已经定性：`SyntaxError` 在编译期抛出，其余异常运行时抛出；
该编译期可能包含运行时（`eval` 动态编译）。`builtins/exceptions/*.h` 是"前端自己内部用的 C++ 报错
信号"，类比 CPython `PyErr_SyntaxError` 这层 C API 跟 Python 层 `SyntaxError` 类——同名同概念不同层。

唯一必须打通两层的地方是 `eval(code)`：现场编译产生的语法错误必须变成能被 SL `except (SyntaxError)`
捕获的运行时异常对象，`eval()` 内部 catch 住 C++ 异常、构造真正的 SL 异常对象再走正常 `raise` 传播
路径——不能让裸 C++ 异常类型泄漏到 `except` 类型匹配逻辑。这个"两栖"模式以后 `EncodingError`/
`FileNotFoundError` 也一样。

**字面量折叠必须用独立的、跟真正 VM 无关的超小型静态求值器**——不是偷懒抄近路，是 SL.md 本身"折叠不做
常量传播，一掺变量就不折"这条约束逼出来的：定义域天生排除名字查找/函数调用/副作用，`StaticEvaler`
完全不需要 `SlObject`/方法分派/继承查找，可以先立好骨架不用等 VM 写完。

VM 具体走"编译到字节码"还是"直接树遍历执行"仍未决定，两种路线都跟以上结论不冲突。

## 类型注解设计：从 `Self` 到否决，牵出"类没有捕获机制"的更底层漏洞

问题：没有泛型，没法表达"返回类型跟某个参数类型相同"；类型注解在类建立时求值，此刻类自己还没建好。
五版方案，全部否决前四个：

1. 引入内置单例 `Self`，类体收集属性那步把方法注解里的 `Self` 替换成类对象——否，解出来的是基类自己
   建立那刻冻死的具体值，子类继承时协变做不到。
2. `Self` 在方法调用时读"绑定给第一个参数的值"的类型——否，纯后门：绑定完成后这个信息早就丢了，得
   专门开新通道；且 SL 没有语法规定方法第一个形参必须是 self。
3. 用已设计的 `TypeVar` 顶替（`self: (T = TypeVar())`）——否，`MyInt.__op_add__("1", "2")` 这种不
   通过实例硬调的写法能通过检查，因为无约束 `TypeVar` 第一次出现只记基准，从没人验证这个基准对不对。
4. `TypeVar` 加 `bound` 参数锚定到具体类——技术上能堵住上面的洞，但否决：`TypeVar` 该管的只是"多个
   位置类型互相一致"，混进"是不是某个特定类实例"，职责不单一。
5. 字符串注解惰性解析，推迟到第一次调用时按名字重新查找——技术可行（期间还修过一次"定义帧一死就该
   NameError"的严重 bug），但否决：跟"建立时求值"两套时机并存不统一；按名字查找在"变量是引用语义"下
   不牢靠，名字随时可能被重新绑定。

**最终方案**：类型注解允许 `type | CompoundType | TypeVar`（正常检查）或 `str`（纯标签不参与检查，
运行时等价无注解）。真正需要自引用/前向引用检查时，改为函数体内手动 `isinstance`（调用时才执行，那时
类早建好），不再走注解机制。`TypeVar.bound` 同步简化为只能是 `type | CompoundType`（不再支持字符串，
也不能是另一个 `TypeVar`——一致性检查按调用时形参顺序单趟扫描"第一次出现定基准"，`bound` 若指向另一个
`TypeVar` 会依赖两者相对顺序，顺序理解错了类型检查悄悄放水，难排查）。

**牵出的更底层漏洞**：`class` 语法完全没有捕获列表（`func` 有），而"未捕获标识符只查当前帧与全局帧"
这条规则意味着类体、类体里任何方法体，都够不到外层函数的局部变量——不止字符串注解，普通代码也不行，
"局部定义一个类"这个模式完全走不通。**修法**：给 `class` 补上跟 `func` 一样的捕获列表语法，放在
`class identifier(BaseClass...)[ALL_CAPTURE]`——基类之后（基类在类体帧建立前的外层帧求值，捕获是新帧
建立之后处理的，文本顺序对应求值顺序；且基类/捕获是两个毫不相关的概念，特意不沿用 `func` 的
`[捕获](形参)` 视觉布局）。

**顺带化简**：引用捕获从"每个名字各存一份 (x, 定义帧)"改成"函数/类建立时无条件记住定义帧（不管有没有
捕获），引用捕获退化成只需要记名字集合"——因为一个函数/类只可能有一个定义帧，之前是重复存储。这个
"无条件定义帧"同时是让"模块"跨模块调用查全局作用域正确工作的必要前提（每个帧强引用自己所属模块的全局
帧，配合无条件定义帧，才能让跨模块调用依然在自己模块的全局作用域查名字）——目前只存在讨论里，等模块
章节展开时要写进 SL.md。

类体的引用捕获不会变成类属性（`_L` 只收集局部字典里的值捕获，引用捕获定义上不在 `_L` 里，是已有规则
的自然推论，不需要专门 `del`）。类的引用捕获链式转发也不会有死帧问题（引用捕获集合挂在函数对象自己
身上，不是挂在帧上）。

## int 高精度：`BigInt`——手写，双路径优化

放在项目顶层 `numeric/`（不是 `utils/`，那边是自由函数式工具，`BigInt` 是完整值类型）。**手写而非
引库**（Boost.Multiprecision/GMP）：GMP 需要独立构建链接，Windows 下历来不省心；Boost 头文件在严格
编译选项下容易冒警告；需求本身是"内存充足、无限位数"，用不着为此扛通用大库；`int` 四则运算是语言核心
语义本身，不像 `nlohmann_json`/`doctest` 只服务测试，值得完全自己掌握。

算法选"简单显然正确"优先于"渐进最优"：乘法朴素竖式；除法用二进制逐位长除法而非 Knuth Algorithm D
（后者"猜商偏大要修正"细节最容易埋 bug）；`~`/`<<`/`>>` 都用已有加减乘除组合表达（`~x=-x-1`，`x<<k`
恒等于 `x*2^k`，`x>>k` 恒等于向负无穷取整除以 `2^k`），只有 `&`/`|`/`^` 需要真正的"无穷位补码"转换。
`floor_div`/`mod` 的符号处理专门推导过（截断商余 `q,r`，`s=sign(a)*sign(b)`：同号或整除直接用截断
结果，异号则 `Q=-(q+1)`、`R` 补上"差的那一段"），用 SL.md 原文例子核对过。

**后来加了小路径优化**：内部表示改成"小路径 `int64_t` / 大路径 limbs"二选一，不变量是"只要数值能装进
int64_t 就必然走小路径"（每次产出新值后调 `shrink()`）。每个操作套一层"先试原生运算+溢出检测
（`__builtin_*_overflow`），溢出或本来就有一方是大路径才提升成大路径走原算法"。`INT64_MIN / -1`
特判（原生除法在这里溢出）。测试上刻意不手写巨大常量当预期值，改用"指数加法律"这类恒等式反过来校验，
避免测试 oracle 本身出错。

## StaticEvaler/ExprFolder：骨架、引用化、完整实现、范围收窄

**骨架**：按运算符语义家族分组（算术/位运算/比较/逻辑/is），避免类型×运算符组合爆炸。`ExprFolder`
管树的遍历/替换（拥有 `AstNodePtr` 槽位所有权），`StaticEvaler` 只管"给一个节点判断能不能折"，职责分开。

**`Analyzer`/`SemanticChecker`/`ExprFolder` 的入参从裸指针改成引用**：分派函数（`check`/`visit`）内部
试探类型时仍需要裸指针做 `dynamic_cast<T*>`（失败返回 nullptr；引用版失败是抛异常，拿异常当十几种类型
里挨个试的正常分派流程是反模式），但对外签名可以是引用。顺带统一了"槽位可能为空"的处理：`SemanticChecker`
新增 `check_optional`，跟 `ExprFolder::visit_and_replace` 一样统一在一层挡掉空指针。

**`StaticEvaler` 的入参不拥有所有权，但能移动子节点**：`fold_and_or` 直接 `std::move` 把没被选中的一侧
原地丢弃，不需要给 `AstNode` 加 `clone()`。但 `*` 的容器重复分支（`[1,2]*3`）确实需要产出多份独立内容，
`unique_ptr` 移动不出"同一份内容用 3 次"——加了 `clone_literal`，只处理字面量子集（不是给 `AstNode`
整体加通用多态 `clone()`，YAGNI：目前只有这一个场景需要）。`is_literal` 对容器是递归检查每个元素，不是
只看节点类型（`[x, 1]` 外层类型是 `AstNodeLiteralList` 但含变量 `x`，不该被当成编译期已知）。

**折叠范围两次确认之后收窄**：`is`、dict 的一切运算（含 `|` 合并）、str 的 `%` 格式化——虽然都是合法
语言特性，但"不是完全 static 的过程，得依赖 VM"（对象同一性、协议判等/类型转换），折叠不追求覆盖每个
运算符，交给运行时更老实。`float` 折叠结果的构造需要先把 `double` 转成合法 SL float 字面量文本
（`format_double` 逐步尝试精度，选第一个能精确 round-trip 的最短精度）；容器 `*` 重复次数、移位量转不
成 `long long` 就不折，没有另设人为上限（跟 `BigInt::pow` 对巨大指数不设上限是同一取舍）。

**`if`/`for`/`while` 死分支消除**：`if` 是 `clauses_`（if+elif）+`else_expr_` 的链式结构；跳过前导
确定 False 的 clause，遇到确定 True 就把对应 `body_` 整体移出替掉整个 `if`（后面全部丢弃），扫到不是
字面量的 cond 就先丢已确定 False 的 clause、重拼一个更短的 `AstNodeIf`（部分折叠，不要求一次知道最终
结果）。`for`/`while` 折 False 的替换值查 SL.md"表达式的值"规定（不带 `$` 是 int 0、带 `$` 是空
列表）；**`init_` 无论 cond 是否为真都会先无条件求值一次**，折叠时不能把这个副作用丢掉——`init_` 非空
时结果包成 `AstNodeCompound{init_, 0或[]}`。`for`/`while` 的 cond 折成 True 时刻意不折——`if` 折 True
能确定具体是哪个分支，循环折 True 只能确定"不会提前退出"，没有"换成什么"这个答案。

死分支消除复用了 and/or 已建立的"拿可变引用、`std::move` 走子节点"手法，印证了当初"用引用而不是指针"
那次设计选择的价值。

**check 与 fold 的调用顺序：维持 check 在前，fold 在后**（一度想倒过来配合死分支消除，未采纳）。反例：
`f(True and *args)`——check 先跑时，`*args` 作为 `and` 的右操作数永远在 `can_star=false` 语境下被检查、
正确报错；但如果 fold 先跑，`fold_and_or` 见左操作数为真直接把 `*args` 挪出来替掉整个 `and` 表达式，
`*args` 变成直接站在调用参数位置，`can_star` 在那个位置是 true，检查通过——**一段本该永远语法非法的
写法，因为死分支消除把受限位置的东西搬到了不受限的位置，就悄悄变合法了**。结论：不换顺序。

（顺带把 `doc` 规则改成纯语法检查：`doc` 必须**恰好**是字符串字面量，不再允许 `"a"+"b"`/`"x"*3` 这类
"编译期可折叠的组合"——因为这条规则本质依赖折叠结果，硬塞进"全程不碰值"的 `SemanticChecker` 会破坏设计；
Python 文档字符串本来就只能是单个字面量，SL 已有反引号字符串覆盖多行/免转义的实际需求，禁掉这个语法糖
损失很小。）

## `AstNodeProgram` 补一个值：SL"一切皆表达式"唯一被漏掉的角落

`eval_isolated` 的定义把自己的值甩给"函数体的值"，但 `AstNodeProgram`（唯一没定义值的节点）到底有没有
值、是什么，SL.md 里从来没写过。

**方案**：`Program` 只出现在三个固定语法位置（文件本身、func/class 元信息之后的 `{}`），用户没法手写
构造出一个 `Program`，纯解释器执行概念，Parser 不用改。**值**：从前到后依次求值，碰到 `return` 立即以
其值作为整个 `Program` 的值，跑到末尾没碰到则为 `None`（隐含末尾 `return None`）。**`return` 统一作用
于"离它最近的 Program"**，不再分函数体/全局两种情况描述——好处：`Program` 恰好和"帧"一一对应，"return
找最近的 Program"就是"退出当前帧"；天然正确处理 `eval` 内联语义（`eval` 展开是 `AstNodeCompound` 不是
`Program`，"最近的 Program"自然跳过它落到 eval 调用处真正所在的帧）。三处 Program 的值各自用途：函数体
是返回值；类体值被丢弃（但 `_L` 收集局部变量建属性表不受影响，是两条独立通道）；文件是 `__return__`/
退出码。

**`return`/`global` 允许出现在类体里，是真实的语义变更**（此前类体禁止两者，是我早前实现
`SemanticChecker` 时没跟 SL.md 原文逐句核对导致的既有 bug：SL.md 早就写"全局：立即退出当前文件"、"局部
作用域（函数体或类体）"两处，顶层 return、类体 global 本来就该合法）。`Context::func_depth` 改名
`local_scope_depth`（现在唯一用途是判断 global 合不合法），`check(AstNodeClass&)` 从清零改成 `++`。

`eval_isolated` 用新框架重新表述：不再说"等价于调用匿名函数"（这个说法跟"这次调用 `_L` 即 `_G`"本身
拧巴），改成"把 code 单独存成文件，`globals` 并入这个文件的 `_G`，当模块导入，返回值是这次导入所得
模块对象的 `__return__`"——`_L` 即 `_G`、不允许 `global` 都自然成立，不需要专门规则。

## `import` 语义 + 帧的"弹出/死亡/回收"三分

`import(module_name)` 找到源文件后：新建模块对象、新建帧、压栈；文件内容当 Program 在这帧上执行；
执行完弹出该帧——但帧的局部字典就是 `attrs(模块对象)` 本身，不是拷贝；Program 的值记入 `__return__`。
模块对象一旦建立永远存在（解释器停止前不回收），重复 `import` 同一名字返回同一对象、不重新执行文件
（不检测文件是否改过）。

（踩坑记录：模块源文件定义 `__op_call__` 不会让模块对象可调用——调用查的是 `type(x)` 的
`__op_call__`，模块对象类型是"模块"这个内置类，不是这份源文件本身；文件里的 `__op_call__` 只是
`attrs()` 里一个普通属性。）

**帧的三分**（这轮最容易踩坑，改了两次才理顺）：
- **弹出**：从帧栈移除，纯栈机制。
- **死亡**：局部字典置 `None`，通常跟弹出同时发生，**但文件级 Program 执行是例外**——弹出后不死亡，
  `_G` 一直保留（文件里定义的函数才能一直找到同一份文件里的其它东西），`eval_isolated` 临时构造的
  "文件"同样弹出不死。
- **回收**：帧对象内存释放，只要还有引用（含"定义帧"引用）指向就不发生，跟死活无关。

（第一版写岔：把"文件的帧弹出不死亡"和"import 模块永远不被回收"当成一回事——按三分定义，"不死亡"和
"不被回收"其实是独立的两条轴，import 模块能活到解释器停止是靠解释器自己的模块缓存强引用，不是"文件的
帧天生不死"这条规则本身在起作用；`eval_isolated` 构造的文件同样弹出不死，但没有缓存强引用，用完没人
再引用就正常回收。）

以后加生成器时（持有自己那个帧、可能重新压回帧栈），直接复用这套"弹出/死亡/回收互相独立"的框架，
不用另开概念。

`import(force=True)`：丢开缓存里的旧模块对象、建立全新对象存入缓存（不是 Python `importlib.reload()`
那种原地修改同一对象——原地修改会导致提前拿走的绑定不同步、`isinstance` 判定出岔子）。旧引用继续完整
可用，只是跟新 import 拿到的不是同一对象（`is` 为 False），旧对象没人引用后正常回收——跟
`eval_isolated` 的模块对象共享同一套"退出缓存后归入普通对象生命周期"规则。

## SemanticChecker 重构揪出的问题 + 全字段审计

用户自己重构 `SemanticChecker` 一遍后发现 6 处遗漏，其中三条有值得记住的教训：
- 形参顺序检查逻辑本身是错的：原来"见过 `*args` 之后任何普通形参一律报错"，但 SL.md 原文这条顺序
  规则**只管 `*args` 之前的位置形参部分**，之后是仅关键字形参，彼此之间有没有默认值不受约束
  （`func f(*x, y) {}` 合法，同 Python）。
- `check_lvalue`/`check_lvalue_pure` 对 `AstNodeIndex`/`AstNodeAttr` 只做形状判断就返回，没有递归进
  `object_`/`args_`——`a[break] = 1` 这种赋值目标内部的子表达式完全不会被检查。修法是形状判断通过后
  额外调一次完整的 `check(node)`。
- `AstNodeCall` 的 `args_`/`kwargs_` 是两个独立 vector，解析完就丢失原始书写顺序，导致 `f(a=1, 1)`
  这种理应报错的写法测不出来——不是 SemanticChecker 该补的检查漏了，是 `AstNodeCall` 结构本身不足以
  表达顺序，需要结构性重做（见下一节）。

新增了完整的 `SemanticChecker` 测试套件（此前完全没有专门测试，只在主程序里被间接跑到，这也是这些问题
潜伏这么久没被发现的原因）。

之后又做了一轮"每个字段都要检查"的全字段审计，揪出 5 处遗漏（`AstNodeClass.captures_` 没查空标识符、
`var_args_name_`/`var_kwargs_name_` 没查空字符串、`AstNodeIndex::args_` 没有"非空"防御性检查、
`AstNodeGlobal::identifier_` 没查空字符串、`AstNodeTry` 每个 except 子句的 `exceptions_` 没有"非空"
防御性检查）——共同点是这些字段在姊妹节点里有检查、这里被漏掉了，说明"照抄相似节点的检查逻辑"这个习惯
本身需要一份显式的字段清单来核对，不能靠肉眼扫。

（`=`/`op=` 左值范围延伸出的结论：解构赋值 `(a,b)=(1,2)` 合法，但 `(a,b)+=(1,2)` **不合法**——解构
目标没有单一"旧值"可读，`op=` 语义依赖"先读旧值算新值再写回"，两者矛盾。SL.md 正式区分"纯左值"
（标识符/属性/索引）和"左值"（纯左值∪其解构组合）：`=` 左边接受左值，`op=` 左边只接受纯左值。）

## 形参列表 / 调用实参重新设计：非法状态在数据形状层面就不可表达

裸 `*`/`/`（Python 风格仅位置/仅关键字分隔符）讨论后确定都不加——`*_` 已经能起到"强制后面形参仅关键字
传参"的效果，不需要为省这点新增语法。

**核心思路**：把"非法状态在数据形状层面就不可表达"，而不是在 SemanticChecker 里用状态机扫描去挡——
形参顺序那个 bug 的根源就是原来 `OneParam` 是打了 tag 的扁平 vector，`*args` 前后两个语义完全不同的
区域混在一起靠一个布尔标志人工区分，这类状态机代码正是最容易漏边界情况的地方。改法：`AstNodeFunc`
拆成 4 个字段对应形参列表的 4 段（`params_`、`var_args_name_`、`kw_only_params_`、`var_kwargs_name_`，
后来又收进嵌套的 `AllParams` 结构体），Parser 按这 4 段顺序解析，"至多一个 `*args`"等约束变成解析到
不该出现的 token 时的自然语法错误，SemanticChecker 的顺序检查大幅简化（无默认值必须排前面只需要对
`params_` 这一个 vector 线性扫）。

`AstNodeCall` 同一个思路但拆法不同（调用实参没有形参那种"显式 token 标记区域边界"，且必须严格保留
原始书写顺序求值）：拆成 `positional_args_`（位置实参+`*expr`展开）和 `keyword_args_`
（`OneKwArg{Kind::Keyword/DoubleStar; keyword_; value_}`）两个字段各自保持书写顺序。`finish_call`
改两阶段解析：一旦某项归类进关键字组，后面再出现位置实参直接在 Parser 报错——这是跟形参一致的选择
（原来 Parser 故意保持"傻"、留给语义层，这次改成阶段式解析直接保证）。判断一项是不是 `**expr` 展开
不能只看开头 token（分组括号透明，`f((**d))` ≡ `f(**d)`），必须先解析完整表达式再 `dynamic_cast`
看实际类型——这个坑第一版实现就踩了，被已有测试当场抓住。

## 新增 `InternalError`：区分"你的代码有问题"和"编译器自己有 bug"

之前"Bad AstNode: ..."开头的防御性断言（正常情况下永远不会触发，只有外部绕过 Parser 直接构造/篡改
AST 才会）全都走 `error()`，跟真正的 SL 语义错误一样抛 `SyntaxError`——这不合适，两者是完全不同性质
的问题。新增 `InternalError`。

第一版让它不继承 `SLException`（认为该跟"能被 SL except 捕获的异常"的 C++ 载体平级）；后来改主意：
能不能被 SL `except` 捕获，由"SL 层给不给它注册对应的 SL 类"这个注册表决定，不由 C++ 继承哪个基类
决定——所以继承 `SLException` 更一致（复用同一套构造/格式化逻辑），没有坏处，最终定案继承
`SLException`。`builtins/classes/exceptions/` 顺带改名成 `builtins/exceptions/`（去掉 `classes`
这层）。

`SL_Cpp_SemanticChecker_Tests` 并入 `SL_Cpp_Analyzer_Tests`（两边测试文件的 `TEST_SUITE` 名字和目录

## `to_json()` 加 `include_pos` 参数：NVI 模式，避开 clang-tidy 的"虚函数带默认参数"

`to_json()` 系列加了 `bool include_pos`（要不要把节点位置也 dump 进 json，默认 `false`）。直接在
虚函数上给默认值被 clang-tidy 拦了（默认值是按调用点静态类型决定的，虚函数场景下这条规则是对的，
不是误报）。改成 NVI：`AstNode` 基类留一个非虚的公开 `to_json(include_pos = false)`，转发给私有
纯虚 `to_json_impl(include_pos)`（无默认值）；各节点原来的 `to_json() override` 都改名成
`to_json_impl(...) override` 并挪到 `private:`，外部只能走基类那个非虚入口。

顺带把 json 输出的键名和字段名对齐了（去掉字段尾缀下划线后应该一致），改了几处历史遗留的不一致
（`capture_type`/`var_args_name`/`positional_args`/`keyword_args`/`keyword`/dict 的 `value`）。

## `StaticEvaler`：编译期常量折叠要防"编译炸弹"，不能无节制地折

折叠发生在编译期，跟运行时开销是两回事——`2 ** 100`、大次数的 `*` 重复这类，几十个字符的源码就能
让编译阶段本身被拖死或吃爆内存（CPython 的常量折叠器出过同类 bug）。参照 CPython 的思路定了几条
限制：

- **纯数值折叠改用 `int64_t` + 溢出检测，不再用任意精度的 `BigInt`**：折不动（操作数或结果超出
  `int64_t` 范围）就 `return nullptr`，交给以后的执行器用真正的任意精度整数处理，`int` 本身的
  语言语义不受影响。`==`/`<` 这类比较不受此限制，继续走纯字符串比较——比较结果只是个 bool，不会
  有"结果比输入还大"的爆炸风险。
- **str/tuple/list 的折叠结果大小设了上限**（`nMaxStrLength`/`nMaxContainerItems`，数值抄的
  CPython 实测值）。
- ~~**tuple 的 `*` 重复额外要求内容"深度不可变"**（`is_deeply_immutable`）~~——**这条判断错了，
  已经推翻，见 [[tuple 的 `*` 重复改成恒不折：`is` 让"深度不可变就能 clone 代替共享"这个假设不成立]]**。
  `+` 拼接不受此限制（`std::move` 子节点重新挂到新父节点，不产生新的共享/复制关系，天然安全），
  这条继续有效。

过程中测试顺带挖出一个真实 bug：`Pow` 分支在操作数解析失败时会误退化到 `float` 分支、返回错误
类型的结果（SL.md 规定"都是 int 且指数非负"必须出 int），已改成解析失败直接不折。

## 溢出检测最终用 C++26 `<stdckdint.h>`，不是手写也不是 SafeInt

手写的溢出检测测试全过，但这类代码历史上就是特别容易"看着对、边界抠错一位"，测试全过只能证明
"想到的边界都对"。查了 SafeInt 的实际接口，是抛异常的（`SafeIntException`），跟这个类"折不动一律
`nullptr`、从不抛异常"的风格不合，要用得自己包 try/catch，不够干净。最终选 C++26 的
`<stdckdint.h>`（`ckd_add`/`ckd_sub`/`ckd_mul`，`bool` 返回 + 指针出参，溢出不碰结果），确认项目
实际用的 Clang 工具链在 C++26 模式下对 `int64_t`/`size_t` 都支持后，把所有手写的溢出判断（含
`sum_exceeds`/`repeated_size_exceeds` 这两个辅助函数）都换成了它的薄封装。选它而不是直接用
`__builtin_*_overflow`，是因为前者是 C++26 里的标准接口而不是编译器专有名字，可移植性更好。

## 整数/浮点字面量禁止前导零（2.1.4）

`SL.md` 一直没规定 `007`/`00` 这类前导零字面量合不合法，是个真实的规范空白，本轮发现并补上。定为
**不合法**（单独一个 `0` 除外；float 的整数部分同样受限，`007.5` 不合法；小数部分不受限，`0.05`
合法）。理由：一是给以后要加的 `0x`/`0o`/`0b` 前缀预留解释空间——现在放开，以后加前缀就是破坏性
变更；二是避免"`0` 开头被当成八进制"这个 C 系语言的经典坑（Python 3 等也是这么处理的，不是凭空
发明）。**拦截点选在 Lexer**（`read_number()` 读完整数部分数字串之后，长度大于 1 且首字符是 `'0'`
直接报 `SyntaxError`）——这纯粹是"数字文本长什么形状"的词法判断，不需要语义层参与，跟"数字后紧跟
字母/下划线非法"是同一类检查，不是新开一种机制。

## `fold_compare` 曾错误地要求链上全是字面量才折叠，已修（利用短路语义）

原实现在真正比较之前先整体检查"所有 operand 是不是都是字面量"，不是就整体放弃——这是错的：链式
比较本身就短路（`a < b < c` 语义等价于 `a<b and b<c and ...`），一旦某一环确定为 `False`，后面
无论是不是字面量、有没有副作用（比如函数调用）都不会被求值。`1 < 0 < f()` 里 `f()` 根本不会被
调用，折叠没有理由因为 `f()` 不是字面量就放弃整条链，应该能直接折成 `False`。

**修法**：改成从左到右逐环扫描，边扫边判：某一环两个操作数都是字面量就直接算出真假；一旦算出
`False`，不管后面是什么，立即折成 `False` 返回（短路，`f()` 这类副作用节点被安全丢弃，因为它们
本来就不会被执行到）；扫到某一环因为操作数不是字面量而没法判定时才停下——如果停下时前面已经扫过
的环都确定为 `True`（纯字面量、无副作用，丢弃它们不影响后续求值和最终结果），就把这段确定为 True
的前缀丢掉，保留从第一个没法判定的操作数开始的缩短子链，构造一个新的、更短的 `AstNodeCompare`
返回（部分折叠，新节点自己的 `pos_` 取剩下的第一个操作数的位置，不是原链的 `pos_`——这是链式比较
节点"起始位置=最左操作数位置"这条既有约定的自然延伸）；如果第一环就没法判定，则整体没能折。

这跟 `fold_if`（确定为 False 的 clause 可以整体丢弃，遇到无法判定的 cond 停下、保留剩余部分）、
`fold_and_or`（`True and f()` 折成 `f()`，不需要 `f()` 本身可折）是同一条原则：折叠只需要保证
"被丢弃的部分本来就不会被求值"，不需要"被丢弃的部分本身可以折成字面量"——这两者是完全不同的要求，
之前的实现把两者混为一谈了。

## 全项目"隐含前提"排查：统一改成"调用方保证 X"+ 函数开头 assert，顺带挖出 BigInt 一个真实 bug

用户要求把散落各处措辞含糊的"要求 a>0"这类注释统一改成"调用方保证 a>0"（消除"这是函数自己检查的
还是靠调用方保证的"这层歧义），并给每一个真的有这种前提的函数在开头补 `assert`。明确要求不能只靠
grep（注释本来就不一定写全），要真的读函数语义。逐个模块过了一遍，结论：

- **`numeric/BigInt`**：补了 `sub_magnitude`（要求 a>=b）、`div_mod_magnitude`（除数不为 0）、
  `to_twos_complement`（要求走大路径、`limb_count` 留够安全余量）、`divmod_floor_big`（两个操作数
  都要走大路径）这几个内部函数的措辞+assert。**过程中挖出一个真实的、此前完全没被测到的 bug**：
  `shrink()` 直接读传入值的 `limbs_`/`negative_`，没考虑传入值本身就已经是小路径的情况——小路径对象
  这两个字段恒为空/`false`（从不写入），一旦发生"已经是小路径的值又被传进 shrink"，会把非零的
  `small_` 误读成 0。复现路径：`floor_div`/`mod` 对两个都超出 `int64_t` 范围、异号、但商本身装得进
  `int64_t` 的操作数（比如 `-300000000000000000007 // 100000000000000000000`），`divmod_floor_big`
  的"异号"分支内部先用 `operator+`/`operator-` 算出这个商（这一步会把结果正确 shrink 成小路径），
  结果又被 `floor_div` 外层再 shrink 一次，二次调用触发了这个 bug，实测返回 `0` 而不是正确的 `-4`。
  修法：`shrink()` 开头加一条"已经是小路径就直接原样返回"，把这个函数变成对任意路径输入都安全，
  不再是只能传大路径值的窄契约。这类"表面上是防御性 assert 的活，做起来才发现是真 bug"的情况，
  正是不能只满足于补注释、必须真的读函数体在干什么的原因。
- **`analyzer/expr_folder/StaticEvaler`**：`truthy`/`node_to_int64`/`node_to_double`/
  `clone_literal`/`is_deeply_immutable` 都要求 `is_literal_pure`/`is_int_family`/`is_numeric`
  成立；`literal_equal`/`literal_compare`（原来完全没写这条前提，纯粹是读函数体recursion 才看出来
  隐含要求两个操作数都是 `is_literal_pure`）、`literal_compare_int`（要求 `raw_` 非空，这条已经在
  之前一轮挪去 `SemanticChecker` 检查，这次只是把 assert 加回来）都补齐了。顺带发现
  `node_to_double` 的文档注释一直写着"node -> int64_t"（复制 `node_to_int64` 时改漏了返回类型），
  顺手修正。
- **`analyzer/semantic_checker/SemanticChecker`、`utils/string_utils`、`builtins/exceptions`**：
  这几处**故意不加 assert**——它们的"检查"本来就是通过抛 `SyntaxError`/`InternalError`/
  `EncodingError` 实现的，是要在 Release 构建里也生效的真实校验（`assert` 在 `NDEBUG` 下会被优化掉），
  跟"调用方保证、不检查"这个类别是两回事，不能混着改。
- **`parser/Parser`、`lexer/Lexer`**：两者的 `advance()` 都有"调用方保证 `pos_ <
  tokens_.size()`/`source_.size()`"这条隐含前提（内部直接下标访问，没有 `peek()` 那样的兜底），
  补了 assert；`Lexer::read_string(quote)` 补了"quote 是 `'` 或 `"`"这条。这两个函数此前完全没有
  任何注释提到这条前提，是纯粹靠读调用点（每处调用前都有 `!is_eof()`/`check()` 之类的守卫）反推出来
  的，grep 关键词根本搜不到。

## BigInt 该不该换第三方库：讨论后决定继续手写，改用代数恒等式批量测试查漏洞

`shrink()` 那个 bug 之后，讨论过要不要把 `numeric/BigInt` 换成第三方高精度库。排查过
`faheel/BigInt`（437 star，MIT，单头文件）——直接排除：README 自己标"Work in progress"，
**不支持位运算**（SL.md 3.4.2 要求 `int` 有 `& | ^ << >>`，这是硬需求），除法/取模对负数的符号语义
完全没文档（正是我们踩过坑的地方，换一个连这个都没说清楚的库等于把已知坑换成未知坑）。
Boost.Multiprecision 的几条引入路径（`FetchBoostContent`、vcpkg、手动 vendor 头文件）都讨论过，
但 vcpkg 需要引入新的包管理工具链、`FetchBoostContent` 本身也是个体量不大的个人维护胶水脚本，
可信度跟被排除的 `faheel/BigInt`是同一量级。最终决定：**继续手写**——`shrink()` 那次是"一个函数
假设输入已经是规范形式，但被套了一层调用后规范形式被破坏"这一类模式的 bug，不是加减乘除本身算错，
用同一模式去针对性复查+补测试，比引入一整条新依赖链更划算，符合本项目一贯的 YAGNI 取向
（对比 [[int 高精度：`BigInt`——手写，双路径优化]] 里最初选择手写而非 GMP 的理由）。

复查方式：不再靠手挑具体数字，改成拿一批"边界值"（0/±1、`int64_t` 边界内外、恰好卡在 `shrink()`
判定边界上的 `2^63` 附近、全 1 比特的 limb）两两/三三组合，批量验证数学上必然成立的恒等式
（加法交换律/结合律、乘法分配律、`a == (a//b)*b + a%b`、位运算的补码恒等式 `a&~a==0` 等、
`(a<<k)>>k==a`、`pow` 的指数加法律），外加专门的"规范化不变量"套件（同一个值走不同运算路径算出来
必须能用 `==` 判定相等）——这套方法论直接命中了第二个真实 bug，见下一条。

## 一元 `operator-()` 的第二个"没过 shrink()"bug：`+2^63` 取负后应该收缩成 `INT64_MIN`

跟 `shrink()` 那次同一类模式，靠上面的代数恒等式批量测试（`-(-x) == x`、`x*(-1) == -x`）直接测出来的：
`operator-()` 大路径分支只是把 `negative_` 取反就直接返回，没有过 `shrink()`。当时的推理是"绝对值
不变，只翻符号，输入已经是规范的大路径值，翻完符号还是规范的大路径值，不需要再 shrink"——这个推理
对绝大多数值成立，但漏掉了一个不对称的边界：`int64_t` 的表示范围是 `[-2^63, 2^63-1]`，`+2^63`
本身合法地装不下（只能是大路径），但取负后的 `-2^63` 恰好等于 `INT64_MIN`，是能装进小路径的。
`abs()` 不会踩这个坑（只会把负数变正数，而"负数留在大路径"这件事本身要求 magnitude 严格大于 `2^63`，
变正之后 magnitude 还是大于 `2^63-1`，仍然合法留在大路径），只有真正的取负 `operator-()`
会在这一个特定值上把"不能装小路径"变成"能装小路径"。修法：大路径分支返回前统一过一遍 `shrink()`。
这个 bug 沉默到什么程度：数值本身没算错（`-2^63` 的十进制字符串输出是对的），只有拿去跟另一个走
不同路径算出来的同值对象做 `==` 比较时才会因为 `is_small_` 标志不一致被误判为不等——这正是为什么
只有专门测"同一个值靠不同运算路径过一遍再互相比较"的规范化不变量套件才测得出来，光测数值对不对
（`to_decimal_string()`）测不出这类 bug。

## 用 deepseek 交叉审查 BigInt，又挖出 2 个真实 bug + 几处契约/可移植性问题

把 `numeric/BigInt` 整个丢给 deepseek 独立过一遍（它自己在 scratchpad 里编了个探针程序，用一套
完全独立于 `to_twos_complement` 的参考实现——靠 `floor_div(2)`/`mod(2)` 逐位剥补码位——交叉验证了
`& | ^`，核心算术/位运算判定没问题）。结论里 2 个是真 bug，都已修复并补了回归测试：

- **`operator>>` 大路径没有超大位移的短路**：小路径早就有"位移 >= 63 恒为 0/-1"的短路，大路径
  分支直接 `floor_div(BigInt(1) << k)`，`k` 上到十亿级会先老老实实把 `2^k` 这个天文数字造出来，
  轻则内存暴涨，重则 `std::bad_alloc`（头文件契约只写了 `k < 0` 抛 `domain_error`，没提过这个）。
  语义上 `x >> k` 在 `k` 超过 `x` 的比特长度时结果恒为 `0`/`-1`，是 O(1) 的事。修法：大路径分支开头
  加一句，`k >= limbs_.size() * 32` 就直接返回 `BigInt(negative_ ? -1 : 0)`。
- **`to_double()` 不是正确舍入，大数上会差 1 ULP**：原实现从最高 limb 往下逐 limb
  `result = result * 2^32 + limb` 累加，每加一次 limb 就舍入一次，且后面的 `* 2^32`
  会放大之前的舍入误差；`10^26` 这种量级的输入验证会差 1 ULP。改成只取整个数值最高的 64
  位（用 `std::bit_width` 定位真实比特长度），被舍弃的低位只要有一个非 0 就把 sticky 位
  or 进保留窗口的最低位，让 `uint64_t -> double` 这一次转换的舍入结果等价于对整个大数直接
  就近取偶，只舍入一次。测试改用 `std::strtod` 当 oracle 逐条对拍（不再靠手算期望值），
  另外扫了一遍 `10^k`（k=15..300）。

顺带清理掉几处"注释和代码互相矛盾"的隐患（deepseek 原话是"现在打不出来，但是雷"）：
`shrink()` 头文件注释里"除 `&`/`|`/`^` 外都要过 shrink"是错的——这三个慢路径其实都调了
`shrink()`，注释会误导后人删掉这几个调用，已改成不再有例外；`compare_magnitude`
所在那组 `*_magnitude` 静态函数，头文件契约写的是"允许多余高位 0"，但 `compare_magnitude`
自己按 `size()` 直接比较根本不容忍这种输入，而 `div_mod_magnitude`
的断言又是按"容忍"这个契约写的——查了一遍确认当前所有调用点传的都已经是 normalize
过的值，选择把契约收紧成"调用方保证已 normalize"（而不是反过来让 `compare_magnitude`
真的支持 padding），`div_mod_magnitude` 的断言相应简化成 `assert(!b.empty())`；顺带给
`add_magnitude`（唯一没在结尾剥高位 0 的 `*_magnitude` 函数，风格不统一）补了一致的剥零；
`to_decimal_string`/`to_double` 大路径分支开头加了 `assert(!limbs_.empty())`
防"规范化的 0 不该走大路径"这条不变量被破坏时的 UB。

另外把 `__builtin_add_overflow`/`__builtin_mul_overflow` 换成了 `<stdckdint.h>` 的
`ckd_add`/`ckd_mul`——这是 `CMakeLists.txt` 里 `SL_MSVC_LIKE_FRONTEND`
明确要支持的真·cl.exe 前端不认的编译器专有内建（clang-cl 有，纯 cl.exe 没有），跟
[[溢出检测最终用 C++26 `<stdckdint.h>`，不是手写也不是 SafeInt]]
里"选标准接口不选编译器专有名字，可移植性更好"的理由完全一致，只是当时漏了 `BigInt.cpp`
这一处，这次一并补上。

**没有动的一条**：`pow`/`operator<<` 对结果规模没有任何上限，`2 ** 10**9`
会真的去算一个十亿位的数。这不是 bug（无限精度数学本身就这样，Python 也一样），而是"要不要设一个
可配的位数上限、超了抛出去交给上层"这个设计问题；`StaticEvaler`
目前的纯数值折叠整个改用 `int64_t`（见 [[StaticEvaler：编译期常量折叠要防"编译炸弹"，不能无节制地折]]），
`BigInt` 实际没有调用方，等真的接到执行器上、`BigInt` 有了活的调用方时再回来定这个上限更合适，
现在设是无的放矢。

新增的用例覆盖了 deepseek 点名的几个盲区：`to_double` 的 oracle 对拍、大路径超大位移、
`<<`/`>>` 直接对着定义验证（不只是靠互相抵消这条弱恒等式）、大路径指数的 `pow`、比较的
三分性/传递性、除法的反向构造（从 `q`、`r` 反推 `a`，而不是从 `a` 反推 `q`、`r`）、
`|x % y| < |y|` 的量级边界、别名（`x.floor_div(x)`）、超长（500/2000 位）十进制往返、
更多脏输入。

deepseek 拿修好的版本又复查了一轮（随机大数对拍 `strtod`、刻意构造舍入平局、ASan/UBSan、
`-Wconversion -Wsign-conversion` 零告警等），确认这两个 bug 修对了、没有回归，又提了 4 点，
逐条决定：

- **`pow`/`operator<<` 没有规模上限**：用户明确拍板不管——"炸就炸呗，本来就是这么用的，VM
  还没设计"，跟上面"没有动的一条"是同一件事，维持不动。
- **`to_double` 的 sticky 位扫描是逐 bit 的，O(drop_bits)**：低位全 0 的输入（比如 `2^k`）会一路
  扫到底，是最坏情况，实测 `to_double(2^10000000)` 比 sticky 立刻命中的对照组慢 700
  倍。同意，改成按整个 32 位 limb 判断非 0（只有跨越 drop_bits 边界的那个 limb 需要位掩码），
  降到 O(drop_bits / 32)。
- **`to_double` 缺"刻意构造的舍入平局"用例**：之前的 `strtod`
  对拍虽然覆盖了不少大数，但没有一条是故意卡在两个相邻 double 正中间的。同意，加了一条：
  取 53 位尾数 `m`（分偶尾数 `2^52`、奇尾数 `2^52+1` 两种），构造 `(2m+1) * 2^(k-1)`——这个数在
  数学上精确等于 `m*2^k` 和 `(m+1)*2^k` 正中间那个整数，`m`、`m+1`
  在这个量级上正是相邻的两个可表示 double，所以这是一个不依赖 `to_double`
  内部实现细节的、纯数学意义上的舍入平局；再验证平局 ±1（明确偏向下/上一点点）必须分别舍成
  下/上两个方向，能确认 sticky 位真的在起作用。顺带补了 `DBL_MAX`
  精确边界（`(2^53-1)*2^971 == DBL_MAX`、`+1` 该舍回不该变 `inf`、明显越界才该
  `inf`）和 `kExponentClamp` 那条路径（`2^500000` 这种，指数本身会被截断，仍要能正确判出
  `inf`）。
- **位运算缺一条独立于 `to_twos_complement` 的参考实现**：之前只有恒等式自洽 + 几个手算小常量，
  deepseek 自己在 scratchpad 里验过一条"靠 `floor_div(2)`/`mod(2)`
  逐位剥补码位"的独立实现、全过，但没进我们仓库。同意这条能提供恒等式测不出来的新信息，搬了进来
  （非负数剥到 0、负数剥到 -1 收敛为止，高位按 `is_negative()` 统一处理，逻辑上等价于"无穷位
  补码"本身的定义），另外顺带补了 De Morgan（`~(a&b)==~a|~b` 等）、`a&(b|c)` 三元分配律、
  移位对位运算的分配律（`(a<<k)&(b<<k)==(a&b)<<k`）几条纯代数恒等式。

## `operator>>` 大路径改成直接右移 limb + floor 修正，不再委托给除法

用户追问：`limbs_` 明明是按二进制（2^32 进制）存的，`<<` 大路径也确实是直接搬 limb（`shift_left_magnitude`），
为什么 `>>` 大路径要 `floor_div(BigInt(1) << k)`，绕道走一整套二进制长除法？答案是纯粹图省事，没有
正确性上的顾虑：非负数右移直接截断 limb 就行，但负数要向负无穷取整，"截断商要不要再减 1"取决于被移出
的低位里有没有非 0——这条修正逻辑跟 `divmod_floor_big`"异号"分支的修正是同一件事，当时选择直接复用
已经测过的除法，图的是不用再为这一个特化场景单独写、单独测一遍。代价是真实的：长除法是 O(limb 数²)，
直接移位应该是 O(limb 数)。

改法：新增 `shift_right_magnitude(a, bits)`，只处理大小，返回"截断后的大小 + 被移出的位里有没有非 0"
（按整 limb 判断非 0、只有跨界那个 limb 需要位掩码，跟 `to_double` 的 sticky 位判断同一个模式，O(limb 数)
不是 O(bits)）。`operator>>` 大路径变成：直接调这个函数，非负数或者"负数但没有位被移出（整除）"直接用
截断结果；负数且真有位被移出，就把截断的商取负再减 1（`-(截断商 + 1)`）。原来"位移数超过总比特数就
短路成 0/-1"那条也顺带省了——`shift_right_magnitude` 内部扫"被移出的位"时天然被 `i < a.size()` 卡住，
不管 `bits` 传多大都是 O(limb 数)，不用再单独判断。

这轮没加新测试：之前"高强度测试"那轮已经在代数恒等式套件里对全部值池批量验证过
`a >> k == a.floor_div(2^k)`，改动后这批断言全过，直接当回归测试用了。

## tuple 的 `*` 重复改成恒不折：`is` 让"深度不可变就能 clone 代替共享"这个假设不成立

用户拿 Python 3.14 的反汇编发问：`((1, 2),) * 3` 折出来的常量里，`a[0] is a[1]` 是 `True`——三份
指向同一个 `(1, 2)` 对象，不是三份独立拷贝。查证：

- SL.md 3.4.2（522-526 行）本来就写对了："重复出来的各份中，对应位置的元素是同一个引用，而非
  各自独立的副本"——跟 Python 完全一致，不是新信息。
- 问题出在 `StaticEvaler::fold_mul` 的实现上：tuple `* n` 折叠时，对每一份都调用 `clone_literal`
  递归新建了 N 份**独立**的 AST 子树，不是共享同一份。当初（见上一条"编译期常量折叠要防编译炸弹"
  那条，第 3 点）的理由是"只要内容深度不可变，clone 和共享就没有可观察差异"——这个理由是错的，
  漏考虑了 `is`：SL.md 560 行把 `is` 定义成纯粹的"是否是同一个对象"、不可重载，跟内容是否可变
  毫无关系；哪怕内容完全不可变，"克隆出来的两份"和"共享的同一份"在 `is` 面前也能被区分出来。
- 更打脸的是代码库里已经有一模一样的顾虑，只是没推广到这里：`is` 表达式本身"恒不折"
  （`compare_is_test.cpp`，连 `1 is 1`、`None is None` 都故意不折，理由就是"对象同一性没法在
  编译期安全预判"）。tuple `* n` 折叠出来的克隆一旦以后被执行器求值，`is` 判定会跟真实语义
  （SL.md 自己写的"同一个引用"）对不上，是同一类问题。

**修法**：AST 是纯 `unique_ptr` 独占树，没有"共享/别名子树"的表示能力（要加是个大改动，且执行器
还没影，纯属为假设中的需求预先建设）。选择成本最低、最一致的方案——**tuple 的 `* n` 也改成恒
不折**，跟 `list`、跟 `is` 待遇一样，把这个折叠机会让给以后真正有对象模型的执行器。具体改动：

- `StaticEvaler::fold_mul`（`StaticEvaler.cpp`）删掉 tuple 分支，跟 list 一样直接落到末尾
  `return nullptr`。
- `is_deeply_immutable` 整个函数（连带 `.h` 里的声明和文档注释）删除——唯一调用点没了，纯粹的
  死代码。
- `StaticEvaler.h` 类头注释、`nMaxContainerItems` 的注释相应更新（这个上限现在只用于
  tuple/list 的 `+` 拼接，不再跟 tuple 的 `*` 有关系）。
- 测试：`container_ops_test.cpp` 里原来那个专门测"tuple 深度不可变才折"的 `TEST_SUITE`
  （连带里面按内容形状分的一堆用例：纯不可变基例、嵌套 tuple、含 Ellipsis、含 list、空 tuple）
  整个反过来，跟 `list * n 恒不折` 合并成一个 `TEST_SUITE`，断言这些形状现在**全部**不折
  （包括原来"深度不可变、应该能折"的那些用例，现在反而是重点回归测试——防止将来有人不小心
  把"深度不可变才折"这条逻辑加回来）；`大小上限` 套件里"tuple * 恰好等于上限折"那条用例
  直接删掉（tuple `*` 恒不折之后，"结果大小超没超限"这件事对 tuple `*` 已经没有意义了），换成
  一条"重复次数很大也不折"的轻量哨兵用例。

## 复合表达式 `{ expr1; expr2; ... }` 新增折叠：全体子表达式都是纯字面量时折成最后一条

用户发现的新折叠点：SL.md 3.4.1 规定复合表达式的值是最后一条子表达式的值、空复合表达式是
`None`；3.10 规定 `{}` 不引入作用域。之前 `StaticEvaler::fold()` 的 dispatch 完全没有
`AstNodeCompound` 分支（`ExprFolder::visit(AstNodeCompound&)` 只递归折子表达式本身，没有对
整个 Compound 节点尝试收缩），SL.md 这条"值等于最后一条"的语义压根没在编译期体现过。

补了 `StaticEvaler::fold_compound`：空复合表达式恒折成 `None`；非空时，只有当 `exprs_`
里**全体**子表达式都是 `is_literal_pure` 才折，折成最后一条（`std::move` 直接拿走，不需要
`clone_literal`——原节点马上就要被丢弃）。"全体"这个条件不能放松：`{}` 不引入作用域，前面的
子表达式如果不是纯字面量（赋值、函数调用……），可能带副作用或者被后面依赖，贸然丢掉不安全；
纯字面量本身求值没有任何可观察效果，扔了才稳妥。这跟 `fold_if` 对确定为 `False` 的 clause
前缀"安全丢弃"是同一类推理。

当时只做了"全体字面量"这一种情况，没做更宽松的"丢弃字面量前缀、保留非字面量的最后一条"（比如
`{1; 2; f()}` 折成 `f()`）。**下一条已经把这个推广补上了。**

`fold()` 的 dispatch 加了 `AstNodeCompound` 分支（在 `AstNodeForCond` 后面）。

## 复合表达式折叠推广成通用规则；顺带修好 `visit_and_replace` 只折一次的老毛病

用户追问两件事：（1）`{1; 2; f()}` 折成 `f()` 这个推广到底该怎么定规则；（2）`for (1; 0;) {}`
被折成 `{1; 0}` 就停了，没有继续折成 `0`，怀疑是"复合表达式折叠的产物没有再被折一次"。两个都对。

**规则推广**（`fold_compound`，`StaticEvaler.cpp`）：

1. 空复合表达式恒折成 `None`；
2. 只有一条子表达式：直接展开成那一条本身，不管是不是字面量——`{}` 不引入作用域，只有一条时
   压根不存在"评估顺序/副作用"这回事，跟裸表达式没有任何可观察差异（`{f()}` 也能展开成 `f()`，
   这条比用户的问题问的范围还宽，是同一个论证的自然推论）；
3. 否则，除最后一条外，逐条判断：纯字面量（`is_literal_pure`）就丢（求值无副作用、值也用不上），
   非字面量（赋值、函数调用、标识符……）就留，且相对顺序不能变（保留下来的这些之间的求值顺序
   /副作用关系不能打乱）；最后一条**永远保留**，不管它是不是字面量——它决定整个复合表达式的值，
   跟其余不同，不能套"是字面量就能丢"这条规则。丢到只剩最后一条，直接展开成那一条；丢完还剩不止
   一条，拼一个更短的 `Compound`；一条都没丢成，返回 `nullptr`（没法进展）。

实现上有个坑：判断"丢不丢得动"必须先只读扫一遍（只调 `is_literal_pure`，不碰 `node.exprs_`
本身），确认真能丢了再动手把元素 `std::move` 出来；如果反过来（边扫边挪、发现挪空了才发现其实
一条都没丢、要返回 `nullptr`），`node.exprs_` 里已经被挪空的那些槽位会变成悬空的 `unique_ptr`，
而 `fold()` 返回 `nullptr` 时调用方会继续用这个（其实已经被我们弄坏的）原节点——是那种"不触发
崩溃全靠运气"的伪缺陷，写测试也测不出来（因为测试只看返回值对不对，不会去戳被污染的原节点），
纯粹是审代码时自己反应过来的。

**`visit_and_replace` 只折一次的问题**：`ExprFolder::visit_and_replace` 原来是"visit 一次子节点、
`fold()` 一次自己"，`fold()` 成功就替换、不会再回头检查替换出来的新节点还能不能继续折。大多数
`fold_xxx` 没这个问题（它们拼出来的新节点，子节点要么是原树里挪过来的、早就被 visit 过了，要么是
现造的字面量叶子，没有"还能再折"的空间）；唯二的例外是 `fold_for_cond`：它会现拼一个
`Compound{init_, 退化值}`，这个 `Compound` 本身从没被当成"待折叠对象"处理过（`fold_compound`
这个折叠点是这次会话才加的，`fold_for_cond` 比它资历老得多），只调一次 `fold()` 会正好跳过它。
改法：`visit_and_replace` 的 `if` 换成 `while`，循环调 `StaticEvaler::fold`
直到返回 `nullptr`——不需要在循环里重新 `visit()`，因为上面那条"新节点的子节点必然已经被折过"的
不变量对所有 `fold_xxx` 都成立。回归风险低：唯一会多跑几轮循环的场景就是这次要修的
`for`+`Compound` 链，其它已有折叠的输出对 `fold()` 再调一次都是立即返回 `nullptr`，多一次
空调用，不影响结果。

测试：`compound_test.cpp` 补齐了新规则的全部分支（单条展开、字面量前缀丢弃收尾非字面量、
非字面量夹在中间时两侧都保留、最后一条是字面量时不能被误丢、一条都丢不动时不折）以及
`for (1; 0;) {} -> 0` 这条验证 `visit_and_replace` 循环生效的用例，另加了一条
`for (x = 1; False; x = 2)` 的对照组（`x = 1` 有副作用，不能被继续折掉），跟
`dead_branch_test.cpp` 里那条历史用例保持一致、确认没有回归。

## `AstNodeProgram` 也要按同一条规则精简，但不能走 `fold()` 替换节点这条路

用户追问：`fold_compound` 这套"丢弃非最后一条纯字面量"的规则，跟其他折叠（构造新节点、整个替换
掉原节点）比起来不统一；`AstNodeProgram`（模块顶层/函数体/类体，跟复合表达式同构，同样"值是最后
一条表达式的值"）要不要按同一条规则折？折的话又有问题：根节点可能变类型。

查证：`AstNodeCompound` 永远挂在通用的 `AstNodePtr` 槽位上（`left_`、`clause.body_`、
`program.exprs_[i]`……随便什么节点类型都能塞），所以 `fold_compound` 能把整个节点换成别的类型。
`AstNodeProgram` 不一样，有三处槽位按具体类型 `AstNodeProgram` 声明，不是通用 `AstNodePtr`：
`ExprFolder::root_`（`AstNodeProgram &`，引用，压根没法重新指向别的对象）、`AstNodeFunc::body_`
和 `AstNodeClass::body_`（都是 `AstNodeProgramPtr`）。这三处（Analyzer 的作用域检查、以后
Executor 的调用约定）都在按"函数体/类体/模块顶层就是一串语句"这个假设读，不是按"随便一个表达式"
读，节点类型不能变。

**结论（槽位类型这部分站得住，规则是否"统一"这部分错了，见下一条）**：机制不统一——这个不统一是
有明确、可讲清楚的结构性原因（槽位类型），不是两套随意不同的逻辑。用户确认理解后拍板：直接实现。

改法：新增 `StaticEvaler::prune_program(AstNodeProgram &node)`（公开方法，`ExprFolder` 要跨类
调用），**原地精简 `node.exprs_`，不返回替换节点、不通过 `fold()`**——哪怕精简到只剩一条也不像
`fold_compound` 那样展开成裸表达式，节点自身的地址/类型自始至终不变。因为是原地改、没有"改了发现
不该改、还要把原节点恢复"的回退顾虑，实现比 `fold_compound` 简单：不需要先只读扫一遍判断"丢不丢
得动"，就算一条都没丢成，把 `exprs_` 整个搬到新 vector 再搬回来也不会破坏节点（无论如何都会执行
`node.exprs_ = std::move(kept)` 这一步收尾，不存在"提前返回、原节点被移动了一半"的路径）。
`ExprFolder::visit(AstNodeProgram&)` 在子表达式各自 `visit_and_replace` 完之后调一下这个方法。
不需要循环/fixpoint（不像 `fold_for_cond` 那样会现拼一个从没被处理过的新节点，`prune_program`
处理的 `exprs_` 里的元素全部已经在前一步 `visit_and_replace` 里折到位了，精简一遍就是最终结果）。

测试新建 `test/analyzer/expr_folder/program_prune_test.cpp`，加了个新的测试工具函数
`fold_program_json`（`test/analyzer/test_utils.h`，跟 `fold_json` 的区别是保留 `Program` 这一层，
不要求恰好一条顶层表达式）。写测试时踩到一次那个老坑：`const auto j{nlohmann::json
类型的函数返回值}` 被 `nlohmann::json` 的 `initializer_list` 构造函数截胡，当成"用这一个元素
构造数组"，报 `operator[] with a string argument with array`——跟 `container_ops_test.cpp`
里注释过的坑完全同源，改成 `= ` 赋值初始化即可，顺手在新文件里也留了注释防止后人再踩。

**上面"规则跟复合表达式完全一样，只是机制不同"这个结论错了，下一条已经修正**，包括最后一条也要
保留这个假设是不成立的（Program 的值跟"最后一条表达式"没关系）。

## 上一条的推理错了：Program 的值不是"最后一条"，是 return（或 None），所以纯字面量不管在哪都能丢

用户追问一个具体例子：`prune_program` 为什么要"保留最后一条"？`func f() {1}` 跟 `func f() {}`
按理说应该是同一个东西吧，为什么不把这唯一一条也剪掉？——问住了，去翻 SL.md 才发现我把 Program
的取值规则想当然地类比成了复合表达式的规则，两者其实完全不是一回事：

- **复合表达式**（SL.md 3.4.1 第 489 行）：值是"块中最后一条表达式的值"——这条没错，
  `fold_compound` 保留最后一条是对的。
- **Program**（同一节第 490-492 行）：值完全由 `return` 决定——"一旦某个表达式的求值触发了
  `return`，立即以该 `return` 的值作为整个 Program 的值……若始终没有触发 `return`，则 Program
  的值为 `None`"，**跟最后一条表达式的值没有任何关系**。3.4.6 第 785 行对函数体又重申了一遍：
  "函数内需要显式使用 `return` 语句返回值，否则函数运行完毕后自动 `return None`"。

`func f() {1}` 里的 `1` 只是一条普通表达式，求值完不触发 `return`，函数照样返回 `None`，
跟 `func f() {}` 确实是同一个东西——用户是对的。

**修法**：`prune_program` 不再特殊保留最后一条，改成对 `exprs_` 里**每一个**位置（含最后一条）
统一判断：纯字面量（`is_literal_pure`）就丢，非字面量（可能含 `return`、可能有副作用）就留、
相对顺序不变。实现反而更简单了——不用再单独处理"最后一条"、不再需要 `.back()`、不再需要
`size() <= 1` 的提前返回（原来这个提前返回一部分是为了避免空 vector 上调用 `.back()` 的 UB，
现在整个函数就是一个纯过滤，天然不会有这个问题）。

这次修复暴露了一个连带问题：`test/analyzer/test_utils.h` 的 `fold_json`（几乎全部
expr_folder 测试都在用）内部是 `ExprFolder{*program}.fold()` 整份折——现在顶层
`AstNodeProgram` 也会被 `prune_program`，如果测试源码是"恰好一条顶层表达式，且这条折完是纯
字面量"（比如 `fold_json(U"1 + 2")`，`1+2` 先折成 `3`，`3` 是纯字面量），这条就会被剪空，
`fold_json` 接着访问 `program->exprs_[0]` 直接越界（`vector subscript out of range`，
实测导致 `SL_Cpp_Analyzer_Tests` 从第一个用例就崩溃）。根子在于 `fold_json`
真正想测的是"这一条表达式自己怎么折"，不是"这份只有一条语句的 Program 剪不剪得动"，
被 `prune_program` 这个新逻辑误伤了。

修法：给 `ExprFolder` 加一个新的公开静态入口 `fold_expr(AstNodePtr &node)`——只对单个
表达式节点做"visit + 折到不动为止"，不触碰 `AstNodeProgram`、不会触发 `prune_program`。
`visit`/`visit_and_replace` 这一整组方法本来就不碰 `root_`，顺手都改成了 `static`
（纯净的重构，行为不变）。`fold_json` 改成调 `ExprFolder::fold_expr(program->exprs_[0])`
而不是 `ExprFolder{*program}.fold()`，不再经过 Program 级别的剪枝；`fold_program_json`
（专门测 `prune_program` 本身的那个新工具函数）继续走原来的整份 `fold()`，两个工具函数分工
更清楚了：一个测"表达式怎么折"，一个测"Program 语句列表怎么剪"。

`program_prune_test.cpp` 里所有假设"最后一条被保留"的用例全部改了期望值（比如
`func f() {1;2;3}` 现在剪成空 body，不是剪成 `[3]`），新增一条最直接的回归测试：
`fold_program_json(U"func f() { 1 }") == fold_program_json(U"func f() {}")`——
就是这次讨论的原始例子，两边折完必须完全一样。

## `finally` 内 return/break/continue 拦截：deepseek 补的实现，review 后接受

3.4.5.7 定的"`finally` 体内拦截跳出该范围的 return/break/continue"这条规则设计完之后一直
没写实现，用户拿 deepseek 补上、要求 review。机制：`SemanticChecker::Context` 加
`finally_loop_depth`（进入 finally 时记下的 loop_depth，-1 表示不在 finally 内）：return
只要它 >= 0 就拦；break/continue 要求 loop_depth == finally_loop_depth（相等说明这层循环在
finally 外面，不相等说明是 finally 内部自己新开的循环，不该拦）；func/class 各自的 body 是新
Program，进入时都要把它重置成 -1（否则 finally 内定义的函数体自己的 return 会被误杀）。手动
推演过多种嵌套场景，判定实现正确，接受。

顺带清理：`check(AstNodeTry)` 里一行 `finally_loop_depth = -1` 紧跟着就被 `ctx_ = saved`
覆盖，是死代码，删除；deepseek 顺手把 `*` 的报错信息同步补上了 index 上下文（`can_star`
早就对 index 生效，报错文案一直没跟上），保留。

`StaticEvaler.h` 折叠范围表也有一处遗留：`D` 这一档原本同时标在 `(bool/int, str)` 跟
`(bool/int, tuple/list)`，是 tuple/list 的 `*` 还没改成恒不折之前的老结论。改法不是加新字母
（deepseek 的建议），而是把 `(bool/int, tuple/list)` 直接改标成 `E`——tuple/list 的 `*`
现在恒不折之后，这两格能折的运算符集合本来就跟 `E` 完全一样。

## `SemanticChecker`/`ExprFolder` 全面审查：2 个真 bug + 1 处死代码 + 大量测试空白

逐函数对照 SL.md 过了一遍 SemanticChecker/ExprFolder（含 StaticEvaler）全部
check(AstNodeXxx)/visit(AstNodeXxx)/fold_xxx。

**真 bug 1**：解构赋值里 `*` 后面允许接嵌套 tuple/list 解构（`(a, *(b, c)) = x` 未被拦截）。
SL.md 2.1.5 原文写的是"至多一个**纯左值**可以带 `*` 前缀"（标识符/属性/索引），不是"左值"，

**真 bug 2**：链式比较 `fold_compare` 遇到"操作数都是字面量但类型不可比"（比如

## `import` 语义定稿：module/package 概念仿 Python，见 SL.md 3.4.5

多段名字（`import os.path`）原来写的"等价于 `os = import('os.path')`"站不住：按"`import()`
不透明整串查找"这条流程，调用形态该返回叶子模块（`path`），绑给 `os` 就错了；反过来定义调用
形态返回顶层，又会让调用形态每次都要多写一段重复的 `.path`，糟蹋了它本该服务的动态导入场景。

中间讨论过一个更省事的方案：loader 永远不解析点号，`a.b` 能不能访问纯靠 `a` 模块自己有没有
挂对应属性——这条能自洽，但用户认为不如直接照抄 Python 的 module/package 模型来得实在，否决。

定稿：module 对应文件、package 对应目录（内容是 `__init__.sl`；没有则视同空文件，不报错），
两者产出同一种模块对象，没有独立的 package 类型。多段名字从左到右逐段导入，逐层把子模块挂为
上一级的同名属性（`os.path = <path 模块对象>`）。调用形态返回**最后一段**（跟
`importlib.import_module` 一致，服务动态导入）；关键字形态多段时只绑定**第一段**（跟 Python
`import` 语句一致，服务"之后写 `os.path.xxx`"这种最常见用法）——这是两种形态在多段情形下
唯一的差异，不是疏漏。链路中间某段不是 package、或同名文件与目录同时存在，统一抛新增的
`ImportError`。

搜索路径（名字怎么定位到具体文件系统位置）、循环 import、相对导入仍未设计，故意搁置。

## `import` 的 AST 表示：`AstNodeImportKw` + `AstNodeImportCall` 两个节点

两种语法形态**不**塞进一个节点里用 variant 分叉：仓库处理"同一关键字两种形状"的既定做法是拆成
两个节点类型（`AstNodeForCond`/`AstNodeForIter`），X 宏分发本来就一个类型一个重载，塞 variant
等于在下面再手写一层全代码库独一份的分发；何况两种形态字段交集为空。

调用形态一度打算复用 `AstNodeCall`，被调对象填 `AstNodeIdentifier{U"import"}`——理由是零下游
改动。**否决**，因为这条路要求运行期真的按名字查到一个 `import` 对象，而这带来两个问题：一是
SL.md 4.1 内置函数列表里根本没有 `import`（它早已从 4.1 挪进 2.2.5/3.4.5 成为语言构造），按
3.10.3 的解析规则（只查 `_L`→`_G`→NameError，无 builtins 兜底）这个标识符压根查不到，得专门为它
现造一层机制；二是造出来之后 `_G['import'] = print` 就能把调用形态劫持掉，而关键字形态不查名字、
不受影响——同一个语言构造两种写法一个能被劫持一个不能，这个分叉比劫持本身更坑。

也考虑过给被调对象加个零字段标记节点（类比 `_G`/`_L` 的 `AstNodeLiteralGL`）。同样否决：在"一切
皆表达式"的语言里，这个节点求值必须产出**某个值**，也就是一个 4.1 里不存在的"import 函数对象"；
要么把它加回 4.1（绕回劫持问题），要么规定"这个节点只能出现在被调位置"（开特例）。

最终：`AstNodeImportCall` 只有实参两组 + `paren_pos_`，**没有被调对象槽位**——`import` 是运算符
本身，不是能被取到的对象，所以根本不产生这个中间值。代价是 SemanticChecker 里位置组/关键字组那
十来行跟 `check(AstNodeCall)` 重复，按本文件既有风格（`check_lvalue`/`check_lvalue_pure` 本来就
各写各的）照抄即可，不抽公共函数。

解析层则**不**为此拆函数：`parse_import` 直接 `finish_call(nullptr, ...)`，再把实参从返回的
`AstNodeCall` 里拆出来重装成 `AstNodeImportCall`。曾把实参解析抽成 `finish_call_args` 出参版
供两边共用，理由是不想造出 `object_` 为空的临时节点；用户否决，理由是只留一个入口更统一，而且
`finish_*` 一族其余成员都是按值返回、没有出参风格。那个空 `object_` 的 `AstNodeCall` 只活两行、
就地拆完销毁，进不了 SemanticChecker，不构成实际风险。`finish_call` 返回类型顺势从 `AstNodePtr`
改成 `std::unique_ptr<AstNodeCall>`，拆孩子不用 `dynamic_cast`。

`OneKwArg` 从 `AstNodeCall` 里提出来变成自由结构体，照 `OneCapture` 被 func/class 共用时的先例
办；两者随后合并进 `ast_node_misc.h`，收录标准是"本身不是 AstNode、但被多个节点类型共用的小
聚合体"（写进文件头注释，免得变成杂物间）。

关键字形态存 `std::vector<std::u32string>`，不存 `AstNodeAttr` 链：`import os.path` 根本没对
`os` 做属性访问（它是两次导入 + 一次 `os.path = <模块对象>` 赋值），存成属性链会让泛型递归
`AstNodeAttr` 的消费者把被绑定的 `os` 当成一次读取，语义反了。而且文法只允许点号连接的裸标识符，
parser 用 `expect(IDENTIFIER)` 当场就能保证形状，不需要像 `del` 那样留通用表达式给语义层反查
（`del a[i]` 才真的需要通用表达式，这里不需要）——直接照搬 `AstNodeGlobal` 存裸字符串的做法。
逐段位置暂不存：`ImportError` 是运行期错误，节点自身 `pos_` 够用。

换行规则：`import` 后无条件允许换行（跟 `global`/`del` 一致），两种形态一视同仁；段名之间的 `.`
跟属性访问 `x.y` 逐字对齐——`.` 后无条件允许换行，`.` 前只在括号内允许。曾按"调用形态的 `(` 该像
普通调用那样绑定"把 `import\n(...)` 判成错误，被用户否决：拆成独立节点之后 `(` 不再是"接在某个
被调表达式后面的后缀"，而是 `import(...)` 这个整体的一部分，没有理由比 `global`/`del` 更严格。
