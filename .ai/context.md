# SL 项目协作上下文

这个文件不是语言标准（标准是 `SL.md`），是给"未来的我"或接手的另一个 AI 用的交接材料：记录 `SL.md`
里**没写**、但理解这门语言设计脉络所必需的东西——协作习惯、被否决的方案（及理由，避免重新提出）、
还悬而未决的问题、以及一些跟语言行为无关但重要的实现策略讨论。`SL.md` 本身只写行为契约，不写这些。

每次大改之后建议回来更新这个文件；`SL.md` 的具体条文以文件本身为准，这里只讲"为什么"和"还差什么"。

## 协作约定（durable，几乎不会变）

- **全程说中文**。
- **不准动 git**（不 commit、不 init、不查 log，任何 git 操作都不做）。

  或者我前一轮的编辑被并发保存"冲字"回旧版本的情况。**每次回复前必须重新 Read 相关章节**，不能凭上一次
  读到的内容假设现状；系统会在文件被外部修改时给出提示，据此判断，不要反过来"纠正"用户的改动。

  可以视作已授权直接写。

  不要用"或"挨个穷举组合（见下面 `⟦⟧` 记号）。
- 设计取舍的默认立场：显式优于隐式；不为"拼写错误/边缘场景"加机制（已否决 `@override`、强制访问控制、

- 优先级排序（用户原话）：数字字面量、`assert` 这类"加了也不会破坏什么"的功能可以往后拖；链式比较这类要

### 记号约定（2.2 开头定义）

`⟦X⟧` 表示 `X` 可选（出现 0 或 1 次），纯粹是**本文档**描述语法用的元符号，不是 SL 语法（SL 自己的方括号
`[]` 有实际语法意义：捕获列表、列表字面量、索引）。重复仍用 `...` + 文字说明，没有单独造记号。这是为了解决
"正交的可选项被挨个枚举组合"导致语法说明冗长的问题（`func`/`class`/`if`/`for`/`while`/`try`/`return` 的语法
都已经按这个记号收敛过）。

**什么时候能用这个记号收敛、什么时候不能**：如果几种写法之间是"同一条规则的复用"（没有交互效果），就能收成
一行模板（`if`/`for`/`try` 属于这种）。如果几种组合之间存在**只有同时出现才有的额外行为**，就不能硬收，
必须分情况说明——例子：`identifier : type = expr` 里"类型注解 + 默认值同时出现"会额外触发"检查默认值是否
符合类型注解"这一步（`TypeError`），这不是"类型检查"和"默认值"两条规则的简单叠加，所以 3.4.6 里这四种形参
组合的**语义**部分没有收成一行，只是**语法**收了。

## 动态作用域 → 显式捕获：这次会话的核心改造

**起因**：用户发现纯动态作用域（标识符读取沿帧栈向外找）让"模块"这个概念没法设计——模块内函数被别的模块
调用时，读取未声明 `global` 的标识符会不小心搜到调用者的帧，模块之间没有边界。

**最终方案**（已写入 `SL.md` 3.10）：

1. 默认标识符解析（3.10.3）收窄成"只查当前帧 `_L`，查不到再退回 `_G`"，**不再沿帧栈向外搜索中间的调用帧**。
   这个改动本身就顺带解决了模块隔离问题，不需要额外的模块级机制。
2. 想要访问定义处外层作用域的变量，必须显式**捕获**（3.10.4，类似 C++ lambda 但语义改造过）：
   - **值捕获** `x` 或 `x = expr`：函数建立时取值，绑成一个不参与传参的"隐藏默认值"，之后当普通局部变量用。
     语义上完全等价于早期用"可变对象当默认参数"模拟捕获的老写法（3.10.5 里还留着这个等价说明）。
   - **引用捕获** `&x`：函数建立时只记 (定义帧, 标识符)。之后读写都转发到定义帧上按 3.10.3 处理。
   - 捕获**不会跨层自动传递**：内层函数要访问外两层的变量，中间每一层都必须显式转发（`g` 自己也要 `&n`，
     `h` 才能在 `g` 里再 `&n` 一次）。这是刻意的，不是限制。
   - 捕获列表里的标识符（值/引用皆然）**不能再被 `global` 声明**；`global` 现在明确"只对纯局部变量有效"，
     形参、值捕获、引用捕获都不行（3.10.2）。
3. **引用捕获的内存模型**（这是这次会话里反复推翻重来的地方，最终版本见下一节）。
4. `++x`/`--x`/复合赋值 `x op= expr` 的内部读取有一条**特例**（3.10.3 末尾）：不适用"退回 `_G`"这条，未标记
   global 时只查 `_L`，找不到直接 `NameError`——这是为了保证这一步的"读"和随后的"写"落在同一帧，否则会出现
   "读到全局值、却悄悄写出一个同名局部变量"的坑。这条特例**不影响**手写的 `x = x op expr`（那是完全独立的
   两次标识符读取，各自按通用规则来）。也正因为这条特例，`x op= expr` **不等价于** `x = x op expr`（3.4.2
   有专门说明，别把这两个不等价关系的判断改回"等价"，之前反复错了两次）。

### 引用捕获的内存模型：三次推翻后的最终版本

这是这次会话里争论最激烈的点，按时间顺序记录演变，避免以后又绕回去：

1. **第一版**（我最初提议）：闭包直接强引用整个帧对象。被否：只要闭包活着，帧（含它全部局部变量）就永远
   不回收，等于变相带回了"延迟回收不可接受"的老问题。
2. **第二版**："通知列表"——帧维护一份"谁引用捕获了我"的列表，帧弹出时主动把列表里每个函数的定义帧字段
   清空为 `None`。**这版也被否**：以后要加对象的浅拷贝/深拷贝时，拷贝函数对象会复制"定义帧"这个字段，但
   拷贝件根本没登记进原帧的列表里，帧弹出时只会清空它认识的那些，拷贝件的字段变成没人管的悬空引用——任何
   自定义的、脱离语言统一对象引用/拷贝机制的"旁路账本"，都没法自动兼容未来任何形式的复制。
3. **最终版**（已写入 3.10.1/3.10.4）：定义帧字段就是对帧对象的**一个普通引用**，跟其他任何字段一样，
   走语言统一的引用计数/拷贝规则，不需要帧知道谁引用了自己。帧弹出时**只清空自己的局部字典为 `None`**
   （不是清空成空字典——要跟"活着但没有局部变量"区分开），不管外面还有没有人拿着自己。谁手里还攥着这个
   帧对象的引用，继续能摸到它，但摸到的只是一个局部字典为 `None` 的空壳，没有任何实际数据，代价可忽略。
   判活/判死就查局部字典是不是 `None`。**这个设计天然兼容以后的浅拷贝/深拷贝**，因为它没有引入任何自定义
   的旁路机制。

**值捕获 vs 引用捕获该怎么选**：值捕获（快照）没有生命周期限制，但对不可变对象（如 int）没法做"多个闭包
共享同一份可变状态"；引用捕获能共享同一个变量本身，但**逃逸出定义帧的生存期后必然 `NameError`**（定义帧
局部字典已被置 `None`）。所以"返回两个共享状态的闭包"这种经典模式**必须用值捕获 + 可变对象（一个单元素
list 当"盒子"）**，不能指望引用捕获——引用捕获只适合闭包不逃逸、在定义帧还活着时被同步调用完的场景
（3.10.5 有对照例子）。**曾经讨论过要不要专门加一个 `Box`/`Wrapper` 内置类型来包装不可变对象使其可变**，
最后否决了：list-as-box 完全够用，性能上没有实测支撑说明专门的 Box 会明显更快，不值得为这点便利多一个
内置类型（属于"不为不常见场景加机制"的一贯取舍）。

## `finally` 里的跳转限制：机制是什么、为什么这样设计

`try...finally` 的 `expr3` 求值期间，任何**试图跳出这段求值范围**的 `return`/`break`/`continue` 都不合法
（3.4.5.7），`expr3` 内部自己开的循环、自己定义的函数不受影响。

**实现机制**（3.4.5.7 已写、4.1.10 `eval` 里也呼应了）：`return`/`break`/`continue` 本来就得是"向外传播、
被最近的循环/函数调用接住"的机制（树遍历解释器下天然对应 C++ 递归调用栈 + 异常/信号传播）。`expr3` 求值
这段时间相当于包了一层"拦截"：能在 `expr3` 内部被自己的循环/函数消化掉的跳转，根本传不到这层；传到这层的
**必然**是想跳出 `expr3` 之外的，直接转 `SyntaxError`。字面代码里能在编译期直接查出来的（未跨函数的裸
`return`、目标循环在 `expr3` 外的裸 `break`/`continue`）会提前报错；查不出来的（比如 `eval` 现场编译出的
代码）由这层运行时拦截兜底，同样抛 `SyntaxError`——虽然发生在运行时，但对 `eval` 编译的那段代码而言，这仍
是它自己的"编译期"，跟 3.11"`SyntaxError` 只在编译期抛"不冲突。

**曾经的弯路**：一度以为这个检查必须给 `eval` 调用点"挂上下文"（编译器在每个 `eval(...)` 调用节点上记一份
静态元数据，运行时传给 `eval` 内部的编译过程）——这是**过度设计**，已经推翻。正确答案是上面这套"信号自然
向外传播、被最近处理者接住"，`eval` 不需要任何特殊配合，因为它内联在当前帧上跑，抛出的信号一样要经过同一
层拦截。

**树遍历 vs 字节码的差异**（这个问题还没最终定实现方案，先记着结论）：
- 树遍历下，`break`/`continue`/`return` 用异常沿着天然存在的 C++ 递归调用栈传播，"拦截"几乎是免费的。
- 字节码下，`break`/`continue`/`return` 通常编译成**直接跳转指令**（编译期烤死地址），没有天然的运行时
  传播通道；`eval` 现场编译出的小段字节码没法直接生成跳进外层、早已编译好的字节码中间的 `JMP`。
- 结论（已跟用户对齐）：这**不是**严重冲突，不需要放弃 `eval` 内联语义。字节码下只需在编译到 `eval(...)`
  调用点时，额外记一下"这里对应的跳转目标地址"，并在生成的 `CALL eval` 指令后面加一小段"检查有没有跳转
  信号回传、有就跳"；这个检查复用的是解释器本来就得有的异常传播基础设施（SL 的 `try`/`except` 本身就需要
  跨帧传播异常），不是另起炉灶。普通（不涉及 `eval`）的 `break`/`return` 依然是零开销的直接跳转，不受影响。
  这部分完全是**实现选择**，不改变语言语义，不写进 `SL.md`。

## `eval` 内置函数（4.1.10）设计要点

- **内联语义**：不压新帧，直接在调用处当前帧上求值，等价于把 `code` 原样写在调用处。这是为了让已经定好的
  规则（捕获的定义帧、`global` 的落点、`finally` 跳转限制）不需要为 `eval` 单独开 special case，全部自动
  成立——这些规则都是按"当前帧"/"AST 位置"定义的，内联恰好保持两者不变。
- **实现提示（非规范性，已写进 4.1.10）**：`eval` 被当普通函数调用会先压入一帧；`eval` 自己把这帧弹出暂存，
  在当前栈顶（即调用者的帧）上编译并求值 `code`，结束后（不管正常结束、发生跳转还是抛异常）都要把暂存的
  那帧压回去，再让调用机制正常弹出，以维持帧栈收支平衡。**这一步必须用 RAII/析构函数之类的手段保证异常路径
  也不会被跳过**，否则栈会失衡——这是唯一真正需要小心的实现细节。
- `eval` 目前还没有形式化"多语句/单表达式""能不能传 `_L`/`_G` 之外的东西"之类的边界细节，等真正需要时
  再补；核心的内联语义、跟捕获/`global`/`finally` 的关系已经定了，不会变。

## 链式比较（已写入 2.1.5、3.3、3.4.2）

- `<`、`<=`、`>`、`>=`、`!=`、`==` 六者互相可以链式（`a < b <= c`），`is` **单独一个优先级**（50，比这六个的
  60 松），链式只能跟自己链（`a is b is c`），不跟那六个混链。（优先级具体数值这次会话统一改成从 10 起、
  每级间隔 10，相对顺序不变——见 `Parser.cpp` 的 `infix_bp`。）AST 层面 `is` 也不与那 6 者共用节点类型，
  单独是 `AstNodeIs`（那 6 者是 `AstNodeCompare`），理由和优先级拆开是同一件事的两个侧面——见下面
  "Parser/AST 重写"一节。
- **为什么 `is` 要单独拆出去**：因为 `bool` 继承 `int`（4.2.2），如果 `is` 和其他比较堆在一起还允许混链或者
  `is` 优先级更高，`a < b is c` 解析成 `a < (b is c)` 会把 `is` 的布尔结果当整数去跟 `a` 比大小——类型上完全
  合法、不报错，是最危险的静默错误。定成 `is` 优先级更低，`a < b is c` 解析成 `(a < b) is c`，即便碰巧还是
  不报错，也是"拿一个布尔值去跟别的东西比身份"这种一眼就能看出不对劲的写法，危害小得多。
- 链式比较的取值**不强制是 `bool`**（比较运算符可重载，`3.8`），取值方式类比 `a OP1 b and b OP2 c and ...`：
  短路时返回那次比较的实际结果，全部通过时返回最后一次比较的结果。求值顺序是"求一个、比一对，假了立刻
  短路"，不是"全求完再比较"（3.3 里有过这个错误，已修正）。

## 开放式切片（`None..8` / `3..None`）

用户故意不加独立的开放式切片语法，靠现有的 `..` 二元运算符 + `None` 表达"开放端"。**关键设计取舍**：`None`
本身不参与这个约定、核心语言层面没有它的特殊地位——是 `int` 自己的 `__op_range__`/`__op_rrange__` 选择把
"另一侧是 `None`"识别成开放端（3.4.2），走的是普通运算符重载分派（`None..8` 先试 `NoneType.__op_range__`
失败，再退到 `int.__op_rrange__(8, None)`）。开放 range 对象只能当切片下标用，直接迭代会 `TypeError`。

## 装饰器：从"推断触发"改成"语法拆分"（改了三轮才对）

`@decorator expr` 求值为 `decorator(expr)`；但 `@deco func f(){...}` 这种"装饰刚定义的东西"还需要让 `f`
重新绑定到装饰结果。怎么判断"该不该重新绑定"，改了三版：

1. **第一版**（错）：判断"`expr` 的值有没有 `__name__` 属性"（鸭子类型、运行时判断）。`@staticmethod outer`
   （`outer` 只是引用别处定义的函数）会意外把 `outer` 这个名字在当前作用域重新绑一遍——写在类体里凭空多出
   一个 `outer` 类属性。
2. **第二版**（也错）：改判断 `expr` 的**语法形状**，要求 `expr` 直接是命名 `func`/`class` 表达式。修好了
   上面的问题，但嵌套装饰器 `@deco1 @deco2 func f(){}` 解析成 `@deco1 (@deco2 func f(){})`，外层的 `expr`
   是装饰器表达式而非直接的 `func`/`class`，按这版规则外层根本不触发——`f` 停在 `deco2(f)`，`deco1` 算出的
   `deco1(deco2(f))` 被扔掉。这是用户追问"这真的是好方案吗，感觉拆东墙补西墙"揪出来的。
3. **过渡版**（能用但被嫌丑）：把 `expr` 递归剥开装饰器表达式，剥到最内层再判断形状，链上每一层各自决定要不要
   重新绑定。逻辑上没错，但用户吐槽"递归上了更难看"，并且指出更根本的问题：**这整套"检查 expr 长什么样再
   决定要不要有副作用"的思路本身就是隐式的**，跟"显式优于隐式"的风格不符——读一行 `@deco expr`，光看语法
   看不出它会不会偷偷重新绑定别的名字，得看 `expr` 形状才能确定。

**最终版**（已写入 2.2.6/2.2.7/2.2.8、3.4.6/3.4.7/3.4.8）：**不再用同一个语法形式去猜两种意图**，直接在
语法层面拆成两个东西——而且拆分的判据**只看紧跟着的是不是 `func`/`class` 关键字，跟具不具名无关**（这点
我一开始还写错过一次：错误地把"匿名函数/类"排除在装饰器前缀语法之外、强推去走通用装饰器表达式，被用户指出
"这不对，都是函数/类表达式，该不该重新绑定是看有没有 `__name__`，这是两件事"才改对）：

- `@decorator1 @decorator2 ... func ⟦identifier⟧(...) {...}`（或 `class`）——一个或多个 `@decorator` **紧邻**
  在 `func`/`class` 定义前面（**命名、匿名皆可**），这属于 **`func`/`class` 表达式自己语法的一部分**
  （2.2.6/2.2.8），AST 最外层就是函数/类表达式本身，不是装饰器表达式包着它。语义（3.4.6/3.4.8）：建立函数/
  类之后，按从近到远依次应用装饰器得到最终值，**若是命名的**，额外把 `identifier` 重新绑定为这个最终值；
  匿名的没有名字可绑，但装饰器一样正常应用、一样影响表达式的值。这是对一个**列表**从近到远做顺序应用，不是
  递归剥皮，因为语法解析时就已经知道这里一共有几个装饰器、紧跟着哪个定义，不需要事后分析表达式树形状。
- `@decorator expr`（2.2.7）——`expr` 是除"紧邻的 func/class 定义"之外的任意表达式（标识符引用、属性访问、
  调用……），**永远、无条件**只是 `decorator(expr)`，没有任何副作用，不需要检查任何东西。

两者由**解析器**根据"`@` 后面一串装饰器紧跟着的是不是 `func`/`class` 关键字"来分派（不用看后面带不带名字），
是语法层面的确定性判断，不是语义层面的"推断"；具不具名只决定"分派到 func/class 语法之后，要不要多做一步
重新绑定"，是纯语义问题，跟分派到哪个产生式完全无关。代价是解析器看到 `@` 要往后多读一点才能确定走哪条
产生式，用户认为这个代价值得付。

**教训**：如果发现一个规则的"触发条件"要靠不断打补丁才能覆盖各种嵌套/边界情况（鸭子类型→语法形状→递归形状），
往往说明**从一开始就不该用同一个语法形式去表达两种不同的意图**，该在语法层面把两种用法分开，让解析器做确定性
判断，而不是在语义层面对着一棵任意的表达式树"猜"该不该有副作用。这比"把判断条件改得更精确"更重要。

## 命名决策：`match`/`case` → `when`

`match`/`case` 原本是 SL 保留字（照抄 Python 3.10 的结构化模式匹配命名）。讨论后改成 `when`（保留字列表已
更新），理由：
- `switch` 不合适：功能比 C 的 switch 强太多，会给错误的心智预期。
- `match` 本身作为常用英语词，太容易和现有代码里的变量/方法名（正则匹配、字符串匹配相关）冲突。
- 参考 Kotlin 用 `when` 替代 `switch`/`match` 的先例：碰撞风险低（"when" 不像名词，没人拿来当变量名），
  语义也贴切。
- 讨论过的其他候选（已否决）：`where`（LINQ/SQL 强关联"过滤"而非"分派"，语义容易跑偏）、`given`（Scala 3
  用来引入隐式参数，语义关联错）、`branch`（语义直白但读起来像名词，不像关键字）、`select`（Go/SQL 已有
  强关联，跟模式匹配不搭）、`pick`（太随意，碰撞风险中等）。
- `case` **暂时保留**未删（`when` 的具体分支语法——要不要 `case`、还是学 Kotlin 用 `pattern -> expr` 不需要
  引导关键字——留到正式设计 `when` 的时候再定，现在只是占位）。
- `when` 本身的完整设计（模式种类、guard、绑定变量等）**明确搁置**，用户原话："这个 when 很复杂而且完全
  有 if 可以代替，不着急设计"。

## 这次会话新增的其他设计点（SL.md 已写规则，这里补理由）

- **反引号原始字符串**（2.1.4）：`` `...` `` 不转义、天然多行，产出的还是 `str`（不是新类型，"一个类型多种
  接口"的老思路）。加了之后用户明确表态：`"..."`/`'...'` **永远不会**再加 `r` 前缀或三引号多行——反引号已经
  把"原始 + 多行"这个组合覆盖了，且 `"..."`/`'...'` 本来就不支持多行（2.1.4 写死的），所以给它们加 raw 语义
  对它们自己而言是纯粹的 no-op，不需要再开一条路。**不要以后又提议加 `r"..."`**，这个已经讨论过并关闭了。
- **值捕获不加类型注解**：讨论过要不要给 `[x: type]` 这种捕获加注解（对齐形参），**否决**——形参注解有意义是
  因为形参的值每次调用都可能不同，要在调用时动态查；值捕获的值建立时就已经定死，不会再变，真要建立时校验，
  直接用已有的 `x = expr` 值捕获形式包一层校验函数就够（甚至 `[x = x]` 语义等价于 `[x]`，也能塞进校验），
  不需要新语法。这是"复用已有机制，不为已经能做到的事再包一层专门语法"的又一个例子。
- **文档字符串去缩进跟 Python 3.14 对齐**：一度以为 Python 不做这个（`__doc__` 是原始值，只有
  `inspect.cleandoc` 才清理），被用户纠正——Python 3.14 起编译器本身就会清理文档字符串缩进。SL 索性也在
  `__doc__` 上做同款去缩进（3.4.6 有完整算法），不是凭空加的机制。
- **`hash`/`getattr`/`setattr`/`hasattr`/`exit` 等内置函数、`SystemExit`/`KeyboardInterrupt`**：`SystemExit`/
  `KeyboardInterrupt` 挂在 `BaseException` 下、不挂 `Exception` 下，讨论过要不要连 `except BaseException` 都
  禁掉（强迫必须显式 `except (SystemExit, KeyboardInterrupt, Exception)`），**否决**——效果有限（写全三个跟
  `except BaseException` 效果一样），还会破坏"任何 `BaseException` 子类都能被 except"这条无例外的统一规则，
  不值得为了防一个不常见的误用加特例。
- **调用/定义时的类型注解校验用 `PUSH_NULL` 不用 `object`**：细节记在下面"字节码 / `Code` 对象设计"一节，
  这里提醒一句这是**真实语义**（3.4.6 已写"建立时检查每个类型注解是否满足 `isinstance(annotation,
  type | CompoundType)`"），不是纯字节码实现细节——只是"缺注解时内部填什么占位"这个具体选择（`PUSH_NULL`
  还是 `object`）才是不影响语言行为的实现细节。
- **返回类型注解符号从 `-> type` 改成 `: type`**：理由是复用形参已经在用的"`identifier: type`"记号，整个
  函数签名里"冒号=类型注解"统一，`->` 之前是全局唯一、只为这一处开的符号。这个写法参照的是 TypeScript
  （`function f(x: number): string {}`），不是凭空发明；代价是牺牲了跟 Python `->` 的相似性，用户认为划算。
- **解构赋值**（`(a, b.attr, c[0], *rest) = expr`）：左值定义在 2.1.5（标识符/`target.attr`/`target[index]`
  三种"基本左值"，加上由左值组成、至多带一个 `*` 前缀元素的元组/列表，可嵌套），求值顺序在 3.3 第 4.6 条第 5
  款，值语义在 3.4.2。**注意**：`*` 前缀不限于标识符，可以是任意左值（`*x.attr`、`*x[i]` 都合法）——这是
  用户在并发编辑里自己拍板的，比"只能 `*` 标识符"更宽松，别以为是笔误改回去。

- **`local` 保留字的去留没有最终拍板**。用户说"不打算加功能了，要么一直当保留字留着，要么直接删了"，我
  建议保留（零成本、留着不影响现有代码，删了以后想加对称于 `global` 的东西还得重新占位），但用户没有明确
  回应确认，**不要假设已经决定**，需要的话再问一次或者提醒用户。
- **`when` 的完整语法/语义**：只占了保留字的位，具体设计完全没开始（模式种类、是否需要 guard 条件、分支
  怎么引导、`case` 到底要不要）。
- **`assert`**：只加了保留字，语义/语法完全没设计（用户明确说"先当保留字，不着急"）。
- **数字字面量扩展**（二进制/八进制/十六进制整数、科学计数法浮点、`complex` 字面量）：明确可以无损后加，
  故意拖后。`complex` 类本身已经加了（4.2.7，`numbers.Number` 直接子类），只是字面量写法还没设计。
- **LaTeX 内置类继承关系图**（4.4）：写的时候就说过我没法预览 MathJax 渲染效果，让用户看看有没有哪层嵌套
  渲染出来很挤/很丑，**至今没有收到反馈**，可能需要主动问一次或等用户实际渲染后反馈。
- **按用户明确说的优先级顺序，以下完全没有开始设计**（原话："这种不属于语言本身的东西，内置函数内置类
  内置模块最后设计"）：
  - 用户自定义模块系统（`import()` 目前只认 `math`/`time`/`numbers`/`protocols`/`exceptions` 几个内置模块，
    普通用户写多个 `.sl` 文件互相 `import` 的路径解析、模块缓存、循环 import 完全没设计——这次解决的是
    "作用域隔离"问题，不是"模块系统"本身，容易被混淆，需要提醒自己这是两回事）；
  - 文件 I/O（`IOError`/`EncodingError` 异常占了位置，但读写文件的 API 一个都没有）；
  - `set`（4.2.13，4.2 章节顺序已重排，见下方"结构速览"）方法列表（`add`/`remove`/`union` 等一个都没写，
    只有一句"继承 Iterable"）；
  - 字符串插值/f-string：**已讨论并否决**，用户和我都不喜欢 f-string，打算用 `%` 运算符重载
    （`str.__op_mod__`，复用已有运算符重载机制）+ `.format()` 方法代替，等设计内置类型时顺手定，不需要
    新语法/新词法特例。
- **多模块下 `_G` 该按定义处还是调用栈解析，尚未实际触及**：现在 `_G` 就是"帧栈栈底"（3.10.1），单模块下
  永远正确，不需要任何函数持有"定义帧"引用就能找到全局。但这是动态（调用栈）解析，不是词法（定义处）解析——
  一旦以后有了多模块 `import`，跨模块调用（比如把函数当回调传到另一个模块里执行）时，"栈底"就不一定是这个
  函数自己所属模块的全局帧了，行为会错。用户已经意识到这个隐患。现在**不需要改** SL.md（没有可观察的差异，
  改了就是提前发明用不上的机制），但设计模块系统时要记得：应该让每个函数对象在建立时就绑定一份"定义处所在
  模块的全局帧"引用（词法作用域），不要依赖调用时的帧栈底部。

## 架构 / 实现层面的既有共识（不影响语言语义，但重要）

- 分层：Lexer → Parser → Analyzer → Interpreter，外加一个 Executor 做整体调度。
- **字节码**：认同以后要加（性能考虑），但**不是现在**；当前先把树遍历版本的语言语义定完整。字节码化后
  `eval` 内联语义、`finally` 跳转拦截需要的额外工作量见上面对应小节，已确认不是致命冲突。
- **GC**：主要引用计数，堆大小达阈值时 STW 做一次全堆扫描处理循环引用（1 语言概述）。引用捕获的定义帧设计
  （帧弹出即清空局部字典）刻意设计成能被普通引用计数正确处理，不依赖弱引用或额外的旁路账本。
- **递归深度**：SL 的逻辑递归深度和 C++ 实际调用栈深度不是一回事，需要解释器显式 guard（对应 `RecursionError`，
  4.2.23 已有这个异常类型），防止 C++ 层栈溢出崩溃而不是抛出 SL 异常。这个 guard 怎么做（计数器阈值等）
  还没定具体数值/机制，只是原则上要有。

## 字节码 / `Code` 对象设计（提前想好的，供以后真正字节码化时参考——不是语言语义，SL.md 不收）

这套设计通过了"是否有可观察的语言行为差异"这个检验（同一个测试也用来判断 3.9 协议该不该用真继承）：
以下内容换一种实现（比如树遍历解释器）完全可以不这么做而不改变任何 SL 程序的可观察行为，所以定性为纯实现
细节，只记在这里，不进 SL.md。

**整体模型**：源码编译产出一个 `Code` 对象（字节码 + 常量池）。任何"能运行的地方"——整个文件、每个函数体、
每次类体建立——都编译成一个 `Code`。`Code` 的边界基本等于帧的边界，唯一例外是 `eval`：它在运行时现编译出
一个 `Code`，但按"内联语义"不新开帧，直接在调用处当前帧上跑这段字节码。`eval` 内部复用同一套通用编译流程
（这本来就是 3.11"该编译期可能包含运行时"暗示的），但**不**因此需要给用户开放一个独立的 `compile()` 内置
函数——`Code` 对象本身对 SL 代码完全不可见，`eval` 依然是"字符串进、值出"的黑盒，不泄露中间产物。

**`Code` 装什么**：
1. 字节码；
2. 常量池——字面量值、用到的名字字符串（不单独搞名字表，字符串本来就是常量池能装的东西，复用）、
   嵌套 `Code`（内部 func/class 编译结果，供外层"建立函数/类对象"指令引用）；
3. 行号映射（字节码偏移→源码行号）、来源标识（文件名，`eval` 用占位符如 `<eval>`）——非规范，纯粹为了报错
   信息，不影响语言语义但没有它给不出像样的报错位置。

函数体的 `Code` 额外带**形参形状元数据**（每个形参的名字、顺序、是否 `*args`/`**kwargs`、是否有注解/默认值）
——这个跟 Python 一样直接放 Code 里，因为调用时（不是建立时）就是靠它把实参灌进新帧，而调用本身就是在跑这份
`Code`，放这里最自然。

**明确不装进 Code 的东西**（各自的理由）：
- 装饰器：建立完函数对象之后才处理的独立后续步骤，跟 Code 无关；
- 形参的具体默认值/类型注解值：这些表达式在**外层**作用域、函数**建立时**求值（3.4.6 已有此规则），算出来的
  值挂在新建的 Function 对象上，Code 只需要知道"有没有"（形状），不需要知道"具体是什么、怎么算的"；
- 捕获列表的"怎么捕获"（求值默认值表达式那部分字节码）在外层 Code 里（建立指令的前置字节码）。
  **但引用捕获了哪些名字，必须作为函数体 Code 的持久元数据保留**——这点最初判断错了，后来被 `eval` 纠正：
  `eval` 是内联语义，运行时现编译一段全新代码，不会经过"编译这个函数体时"那次性烘录指令选择的过程；
  如果 eval 出来的代码里用到某个引用捕获的名字，运行时必须能现查"这个函数的引用捕获表里有没有这个名字"，
  才能按 3.10.3/3.10.4 正确路由——不能只体现在（原始函数体）编译期选中的指令种类里，那对 eval 不可见。
  值捕获不受影响：它们物理上就在 `_L` 里（普通运行时字典），eval 直接查 `_L` 天然就对，不需要枚举。
  引用捕获则数量有限、编译期就定死，所以能记、也必须记，供 eval 运行时按名字查。

**"建立函数/类对象"指令（示意名 `MAKE_FUNC`）的最终设计**：固定弹栈顶 6 项（原来是 5 项，`doc` 改成签名里
的显式语法槽位之后新增的第 6 项，见下），不需要任何操作数，不需要运行时先查元信息才知道弹几个（这是推翻的
第一版设计，被指出"很怪"——弹几个这件事必须是编译期就该确定的，元信息只用来解读弹出来的东西，不该用来
决定弹几个）：
1. **捕获元组**：捕获列表按声明顺序整体 `MAKE_TUPLE <编译期定好的 N>` 打包成一个元组。
   - 值捕获：求值、压栈，参与这次 `MAKE_TUPLE`；
   - 引用捕获：**不产生任何字节码指令**（推翻了"CAPTURE_REF 压 (name, 当前帧)"的提案）——一个函数的所有
     `&x` 都指向同一个东西（建立时唯一的"当前帧"），`MAKE_FUNC` 本来就在这个帧自己的字节码里执行，天然知道
     "当前帧是谁"，不需要谁显式压栈告诉它。有引用捕获时，`MAKE_FUNC` 直接抓一份自己当前帧的引用挂到新
     Function 对象上（这跟 `LOAD_NAME` 隐式读当前帧 `_L` 是同一类"用 ambient 当前帧"的操作，不算额外机制）。
2. **形参注解/默认值元组**：按 3.3.7 的顺序交替压栈（`type_1, default_1, type_2, ...`，一个参数占 2 个槽位，
   `*args`/`**kwargs` 不占槽位），`MAKE_TUPLE <编译期定好的 2×形参个数>` 打包。
   - 缺注解、缺默认值都统一压 `PUSH_NULL`（改过一次：缺注解最初想压 `object`，3.4.6 确实说"无注解等价于
     `object`"，但那只是行为上的等价，不要求真的存一个 `object` 值——Code 里的注解对 SL 完全隐藏，没有类似
     `__annotations__` 的内省接口能让用户翻出"存的到底是什么"，所以只要类型检查效果一致，压 `PUSH_NULL` 更
     省一次必然通过的 `isinstance` 调用，纯收益零成本）；
   - `PUSH_NULL` 产出的是一个**纯内部、SL 层永远拿不到**的哨兵（不是 `None`——`None` 是合法的真实默认值，
     拿它当"缺默认值"的哨兵会跟"默认值就是 `None`"撞车，这个坑之前在 `__hash__=None` 那次已经踩过一次）。
     这个哨兵活多久、具体是什么（C++ `nullptr` 还是内部对象）无所谓，反正一造出来立刻被 `MAKE_FUNC` 消费掉，
     从不流出到 SL 代码。
3. 返回类型注解（单值，缺省同样填 `PUSH_NULL`）；
4. 函数名（真实字符串，或匿名时的 `None`——`None` 在这里当哨兵是安全的，因为真实函数名永远是 `str`，
   不可能字面等于 `None`，跟上面默认值那个坑不是一回事）；
5. `Code` 常量；
6. **文档字符串**（`doc`）：单值，缺省同样填 `PUSH_NULL`。这是后来才加的——`__doc__` 的语法从"函数体折叠后
   第一条是字符串字面量就当文档字符串"改成了签名里 `⟦: type⟧ ⟦doc⟧ { ... }` 这样一个独立、显式的语法槽位
   （2.2.6/2.2.7），求值顺序排在返回类型注解之后（3.3 第 7/8 条）。改成显式槽位之后，原来"函数体不执行、
   类体立即执行，两者判断时机不一致，所以只能在编译期静态判断折叠结果"那一整套复杂度全部不需要了——`doc`
   跟形参注解/返回类型一样，在建立时按固定顺序求值，压根不用管函数体长什么样、什么时候执行。`doc` 的取值
   限制在"字符串字面量或其编译期可折叠的组合，不允许引用变量"（SL.md 3.4.6 已写），所以它的哨兵处理方式
   跟形参注解完全一样，不需要另外设计。

**`MAKE_FUNC` 现在还多一步语义校验（已写进 SL.md 3.4.6，不再是纯实现细节）**：弹出这 6 项、
构造 Function 对象之前，要检查每个非 `PUSH_NULL` 的类型注解（含返回类型）是否满足
`isinstance(annotation, type | CompoundType)`，不满足抛 `TypeError`。关键是这一步**在全部 6 项都求值
完毕之后**才做，不会因为第一个形参的注解就是坏的（比如 `func f(x: 1): 1 {}`）而提前中断——`1`、`'f'`、
`code` 等后续求值该跑还是照跑，跑完了才统一检查、统一报错，呼应 3.3 第 1 条"表达式的副作用都在完全求值
完毕之前发生"。

**装饰器求值顺序：曾经以为不需要专门定规则，是错的，已经在 3.3 第 7/8 条补上了。** 我最初想当然地把
`@deco func f(){}` 当成 `deco(f)` 的语法糖，套用调用求值顺序（先 callee 后参数）来说明 `deco` 先于函数
自身的构造（捕获/形参/返回类型）求值——但这个类比站不住脚：装饰器前缀在语法上是 `func`/`class` **自己产生式
的一部分**（2.2.6/2.2.8，AST 最外层就是函数/类表达式本身），根本不存在一个真正的、外层的 `deco(...)` 调用
表达式，所以 3.3.4.7 的调用求值顺序规则**并不会自动套用到这里**——这是用户自己审出来的真实缺口
（`@deco func f(x=g()){}` 里 `deco` 和 `g()` 谁先求值，改之前的 3.3 完全没说）。现在的正式规则（3.3 第
7/8 条）：**若有前缀装饰器，先按从前到后（离 `func`/`class` 越远越先）对各 `decorator` 求值，再进入捕获/
形参/返回类型（或基类）的求值**；装饰器的**调用**仍是建立完毕后按 3.4.6/3.4.7 从近到远进行，跟求值顺序是
两回事。这个最终结论恰好和我最初的直觉一致（`deco` 确实先于函数体求值），但推导过程之前是错的、且从未真正
写进 SL.md——记这条是为了提醒自己"结论对不代表推导对"，以后别再犯这类"想当然套用一个看起来像但实际不是的
已有规则"的错误。命名函数/类的绑定
**只在最终值确定后发生一次**（无装饰器时即建立完成时，有装饰器时即全部调用完毕时），不再有"先临时绑定、
再重新绑定覆盖"的两步（这是 3.4.6/3.4.8 已经落地的修改，旧版两步绑定是装饰器还是"函数外独立表达式、不好
识别"时代的遗留设计，现在装饰器已经是 func/class 表达式自己语法的一部分，一次绑定就够）。

**Function 对象与 Code 的关系**：Code 编译一次（对应源码里那一份 `func`/`class` 表达式文本），可能被复用
多次——函数每次被*调用*都新开一帧但执行同一份 Code；`func` 表达式在循环体里被*求值*多次时，产生的多个
Function 对象也共享同一份 Code。但"建立函数/类对象"这个操作，每次执行都必须构造全新对象，绝不能因为 Code
复用就连带把对象缓存/复用——`is` 比较的是 Function 对象身份不是 Code 身份，且这直接关系到闭包正确性
（循环里 `[i]` 值捕获必须各自捕获到当次的 `i`）。

**Code 对语言用户隐藏**：不通过 `getattr`/`attrs()` 暴露（不像 Python 的 `f.__code__`）——一旦暴露就等于把
字节码格式钉成语言可观察行为的一部分，以后想换实现就是破坏性变更，而且对 SL 用户代码没有实际自省价值，跟
3.9.1.2 那条"隐藏引用"是同一类处理。Code 内部引用（常量池→嵌套 Code）是树状无环的，光引用计数就够回收，
不需要环检测介入，但复用同一套通用对象表示（GC 意义上的 SlObject）没坏处，只是白跑一趟。

**引用捕获链式解析已经是对的，不需要新机制**：3.10.4 早就写了"改为对引用捕获表中 x 对应的定义帧按 3.10.3
的规则处理"——这本来就是递归的（如果在定义帧里 x 自己也是被捕获的，3.10.3 会再次转给 3.10.4 处理），能正确
处理多层嵌套引用捕获链。发现的唯一问题是 3.10.5
的例子里有条注释写错了（说"g 的 _L 里有 n"，但 g 对 n 是引用捕获，根据 3.10.1 引用捕获不进 `_L`）——已在
SL.md 里改成准确描述（n 不在 g 的 `_L` 里，是通过 g 自己的引用捕获表继续链到 f 帧）。

## Parser/AST 重写（这次会话，`parser/` 从旧标准跟上现在的 SL.md）

旧 parser 是照更早版本的标准写的，`class`/`while`/捕获列表/返回类型注解/文档字符串槽位/链式比较全部缺失，
审查时还顺带挖出两个和这次改造无关的真实 bug：

1. **左结合运算符的 `rbp` 写成了 `= lbp`，应为 `lbp + 1`**——Pratt 解析里右操作数用 `parse_expr_pratt(rbp)`，
   `rbp == lbp` 会把同优先级的下一个算子吞进右操作数，等效于变成右结合。对 `+`/`&`/`|`/`and`/`or` 这类
   可交换算子数值上不影响（求值顺序仍是从左到右，见 3.3 的"先左后右"规则，不受树形状影响），但对 `-`/`//`/
   `%`/`<<`/`>>`/`..` 是真实的算错值（`1 - 2 - 3` 原来会解析成 `1 - (2 - 3)`）。只有 `**` 和赋值类本来就该
   右结合，`rbp = lbp - 1` 是对的，没动。
2. `++`/`--` 原来跟 `+x`/`-x`/`~x` 共用同一档优先级解析操作数，但当时运算符表里 `++`/`--` 已经比 `**` 还
   高，共用会导致 `++x ** 2` 解析成 `++(x ** 2)`（这个问题现在已经不存在，见下面"`++`/`--` 整体砍掉"）。

**AST 节点设计上做了一处拆分**（用户明确要求，理由是"语义形状不同就不该共用节点类型"这条这次会话反复用到
的原则）：
- 比较运算符（`< <= > >= == !=`）从 `AstNodeOpBinary` 拆成 `AstNodeCompare`，**单个比较也用这个节点**
  （`operands_.size()==2` 的特例），不搞"单个用 OpBinary、链式才用专门节点"的双表示——链式比较的短路/单次
  求值语义（3.3.4.3）跟普通二元运算完全不是一回事，用同一个节点类型硬凑会是缝合怪。`is` 后来又从
  `AstNodeCompare` 里进一步拆出去成了 `AstNodeIs`，见下面专门一条。

**`++`/`--` 整体砍掉**（用户自己在写 parser 时反悔的决定，从语言里彻底删掉，不只是实现层面的事）：
理由是它没有后缀形式（当时的 2.1.5 就写明"均只有前缀形式"），丢了 C 系语言里 `++`/`--`真正好用的场景
（`arr[i++]` 这类）；剩下的"前缀自增"用法跟 `x += 1` 在值语义、副作用、求值顺序上完全一样，纯粹是少打两个
字符，换来的代价是专门一档全场最高优先级、专门的 AST 节点、专门的左值校验——投入产出不成比例，也不符合
项目一直在坚持的"不为图方便/边缘场景加机制"（`@override`、强制访问控制都是这么否掉的）。改动涉及
`SL.md`（2.1.5 表格与叙述、3.3 求值顺序、3.4.2 值语义、3.8 运算符重载表、3.10 特例）、lexer（去掉
`SIGN_DOUBLEPLUS`/`SIGN_DOUBLEMINUS` 两个 token 和对应的贪婪匹配分支，`+`/`-` 现在只贪婪到 `+=`/`-=`）、
parser（去掉 `AstNodeIncDec` 节点、对应的解析分支、优先级 170 这一档）。优先级表原来在 170（`++`/`--`）
和 180（索引/调用/属性）之间只差 10，砍掉 170 之后，180 直接下移填补成 170，其余 10~160 完全不用动——
不是巧合，是因为 `++`/`--` 恰好是当时最靠上的一档，删掉后正好补齐空缺，不需要重排整张表。

**`is` 进一步从 `AstNodeCompare` 拆成独立的 `AstNodeIs`**：这次会话早先设计 `AstNodeCompare` 时把
`is` 也塞进了同一个 `OpType` 枚举（`Lt, Le, ..., Is`），共用"链式、`operands_`+`ops_`"这一个节点形状。
回头看这也是共用不当：`is` 不可重载（2.1.5 第 3 点明确排除在外），另 6 个比较符可以走 3.8 的运算符重载；
两组还规定不能混链（3.3.4.3）。"同一节点内 `ops_` 只能全是一组"这个约束原来完全靠 parser 老实构造维持，
类型系统层面没有强制；拆开之后 `AstNodeIs`（`operands_.size()>=2`，不需要 `ops_`，因为运算符固定就是
`is`）天然满足这个约束，也不用担心以后写运算符重载分发时把 `is` 也顺手当可重载的走了同一条路径。`is` 的
优先级（50）和链式求值语义完全没变，只是内部表示从"和其他比较符共用一个节点、用 `OpType::Is` 区分"变成
"独立节点"——`SL.md` 不用改，纯 parser/AST 内部重构。

**`while` 没有单独的 AST 节点**：`while [$] (cond) body` 语义上就是 `for [$] (; cond ;) body`（`init`/`inc`
都为空），`parse_while()` 直接构造 `AstNodeForCond{init_=nullptr, inc_=nullptr}`，不建 `AstNodeWhile`。
`SL.md` 里 `while` 仍是独立的关键字/独立的 2.2.5.3 小节（面向用户的可读性理由，跟大多数语言一致），这纯粹是
"内部怎么表示"层面的化简，跟语言表面语法无关。

**运算符优先级数值这次会话统一重排过两次**：第一次是从 10 起、每级间隔 10（原来因为往表里插 `is`(45)、
`++`/`--`(155) 之类新行，出现了 5 为单位的不规则间隔），相对顺序完全没变，只是数值更规整；第二次是砍掉
`++`/`--` 后，170 这一档空出来，180（索引/调用/属性）直接下移填补成 170，10~160 都不用动。`SL.md` 2.1.5
的表和 `Parser.cpp` 的 `infix_bp()`/各前缀算符解析调用都已同步改过。

**Dumper 不再是访问者模式，改成 `AstNode::to_json()` 纯虚函数，每个节点自己实现**：原来 `Dumper.cpp` 里
一堆 `to_json(const AstNodeXxx*)` 自由函数，靠 `x_ast_nodes.h` 的 X-macro 做 `dynamic_cast` 链式分发——这
跟 `SyntaxChecker` 是同一套分发机制，但两者动机其实不一样：`SyntaxChecker` 手上有跨节点的遍历状态
（`Context`：`func_depth`/`loop_depth`/`can_star` 这些只有"正在遍历"这件事才有意义的东西），确实该留在外部；
`Dumper` 是纯粹"每个节点知道怎么描述自己"，没有任何跨节点状态，用虚函数直接放节点里更合适——而且虚函数是
编译期强制补全（漏了哪个派生类没实现会直接编译失败），比 X-macro 那套"忘了加 Dumper 里的 case 只会在运行时
死循环栈溢出"安全得多。代价是 `ast_node.h`（以及所有派生头）现在依赖 `nlohmann/json.hpp`，"纯数据、零依赖"
的 AST 层这条线被打破了——权衡下来接受了这个代价，因为 nlohmann::json 本来就是项目级依赖，且这类小项目不
存在"以后要把 AST 抽出去做独立零依赖库"的真实需求。`SyntaxChecker` **没有**跟着改，仍然是外部 X-macro 分发，
这是有意的不对称，不是漏改。

**几个查表用的 `static` 转换函数（`Parser.cpp` 里 `token_type_to_xxx_op_type`/`infix_bp` 这类）保持
`switch-case`，没有改成 `unordered_map`**：跟 lexer 阶段 `get_typename_by_tokentype`（稠密枚举→字符串，
直接数组下标）、`KEYWORDS_MAPPING`（字符串 key，无法数组下标，只能上 hash map）那两个选择不矛盾——那两个
是"定义域天然适合某种查表结构"，这里的定义域是 `TokenType` 里一个稀疏子集（比如一元运算符只有 6 个 token
命中，`TokenType` 总共几十个），既不适合建全量数组（大部分位置浪费），也没必要上 hash map（没有性能收益，
还多一次哈希开销和动态初始化成本），照抄 lexer 那套反而是生搬硬套。`switch` 的 `default` 分支还顺带保留了
"传入了不该出现的 token 类型就直接断言炸掉"这个安全网，用 map 的话得额外写 `.find()` 判断，没有优势。

**装饰器修正：`@deco func f(){}` 不该产出 `AstNodeDecorator` 包着 `AstNodeFunc`，而应该是 `AstNodeFunc`
自己带一个 `decorators_` 字段**——这是用户自己发现的一个真实设计 bug，之前实现（包括我在 `.ai/context.md`
自己写的评价里）一直下意识把"紧邻 func/class 的前缀装饰器"和"通用 `@decorator expr` 形式"（3.4.8，`expr`
可以是任意表达式）用同一个 `AstNodeDecorator` 节点表示，靠"target 恰好是不是 Func/Class"来区分两种语义。
但 2.2.6/2.2.7 的语法本来就写得很清楚：`⟦@decorator ...⟧` 是 `func`/`class` 产生式自己的一部分，压根不存在
一个独立的、外层的装饰表达式——这跟本文件前面"装饰器求值顺序"那条笔记的结论（装饰器前缀不是 `deco(f)` 的语法
糖，没有真正的外层调用表达式）其实是同一件事的两个侧面，早就该联想到 AST 形状也不该造出一个不存在的外层节点，
之前没推及到这一步。现在的正确形状：`AstNodeFunc`/`AstNodeClass` 各自有 `std::vector<AstNodePtr> decorators_`
（按书写顺序存放，离 func/class 越远越靠前），`AstNodeDecorator` 只保留给通用形式（`expr` 不是紧邻的
func/class，比如 `not_method = @staticmethod outer`），两种语义不再共用同一个节点类型——又是一次"语义形状
不同就不该共用节点"的例子，跟 `AstNodeCompare`/`AstNodeIs` 拆分是同一条原则。`Parser.cpp` 里
`parse_decorator()` 相应改成"先把连续的 `@decorator` 收集成一个列表，再看紧跟着的是 `func`/`class`（列表
整个转交给 `parse_func`/`parse_class` 存进 `decorators_`）还是别的表达式（退化成 `AstNodeDecorator` 链）"，
不再是"解析一个 decorator 就递归下探"的写法。

**语法层"合法目标是什么形状"该不该由语义层校验，取决于该槽位在语法上到底是不是表达式**：用户提出"parser 层
只管解析成表达式，具体形状（比如必须是标识符）留给 analyzer”，这个原则对一部分槽位是对的，但不是所有写着
"标识符"的槽位都该这样处理，关键要看 `SL.md` 语法条文本身把这个槽位定义成什么：
- `del target`（2.2.3）：条文原话是"`target` 的必须是标识符或属性访问"——用词是 `target`，且允许的形状不止
  一种（标识符、属性访问，属性访问本身还能递归出任意子表达式，如 `del get_obj().attr`），这就是真正意义上
  "语法上是表达式，语义上限定形状"，parser 只管 `parse_expr()`，形状交给 `SyntaxChecker` 天经地义。
  （顺带发现 `SyntaxChecker::check(AstNodeDel*)` 原来只放行 `AstNodeIdentifier`，没放行属性访问，跟条文
  对不上——已经改成两种都放行。）
- `global identifier`（2.2.4）：条文原话直接说是"`identifier`"，不是"`target`"，也没有"可以是标识符或
  别的什么"这种多形状描述——语法产生式本身就是一个 token，不是一条表达式产生式。这种情况下让 parser 走
  `parse_expr()` 再靠 `SyntaxChecker` 拒绝非标识符，等于凭空多解析了一整棵语法树、多做了一次动态类型判断，
  而这两步永远不可能有别的结果（`global` 后面除了标识符什么都不该被接受，也没有第二种合法产生式）——不是
  "延后到语义层"更干净，是根本不需要语义层参与，直接 `expect(TokenType::IDENTIFIER)`，`AstNodeGlobal` 也
  相应地把 `AstNodePtr target_` 换成 `std::u32string identifier_`，跟 `AstNodeFunc` 的名字/捕获/形参
  标识符是同一个做法。
- **`for` 迭代模式的 `identifier`（2.2.5.2 点 2）是唯一的例外，条文也写的是"标识符"，但 parser 没法在这里
  直接 `expect(IDENTIFIER)`**——因为 `for` 头部第一个槽在语法上有歧义：可能是迭代模式的 `identifier`（后面
  跟 `:`），也可能是条件模式的 `init`（后面跟 `;`/换行）或纯条件 `cond`（后面直接 `)`），三种产生式共享同一
  起始位置，要读到后面的分隔符（`:` / `;` / `)`）才能判断到底走哪条产生式。这种"提前无法区分、需要多 token
  前看"的情况下，只能先按最宽松的方式解析（`parse_expr()`），等看到 `:` 确认是迭代模式后，再在 `SyntaxChecker`
  里校验 `target_` 必须是标识符——这不是偷懒，是被迫的，不能照抄 `global` 那样直接 `expect`。
- 这条其实是判断"parser 该不该直接收紧到 token 级别"的通用标准：条文本身有没有把该槽位定义成一条独立的、
  单一的、不含表达式递归的产生式（有 → 直接 `expect` 对应 token，不需要任何语义层参与）；有没有语法上的
  先看歧义需要拖到更后面的 token 才能消解（有 → 只能先按表达式解析，形状校验推迟）。跟"该不该让 parser 干净"
  这种风格偏好无关，是纯粹由文法本身决定的，不能一刀切。

**`global identifier` 改成直接 `expect` token 之后带来一个连锁问题：`global a.x` 会解析成 `(global a).x`**——
因为 `parse_global()` 只消费 `global` 和紧跟的一个标识符就返回了，返回的 `AstNodeGlobal` 节点在外层 Pratt
循环里就是个普普通通的"primary"，后面紧跟的 `.x` 会被当成对这个 primary 的正常属性访问延续下去，没有任何特殊
拦截。判断下来这是**预期行为，不是 bug**，也没有针对 `global` 专门加拦截：`global identifier` 的值是 `None`
（3.4.4），`(global a).x` 就是 `None.x`，运行时会因为 `NoneType` 没有 `x` 属性报错——但这跟 `break`、`None`
字面量、`True` 字面量等所有其它"值为 `None`/固定值的 primary"完全是同一种情况（`(break).x`、`None.x` 现在
都一样能解析、都一样会在运行时因为访问不存在的属性报错），是 Pratt 文法里"任何 primary 后面都能接后缀运算符,
是否有意义交给运行时值本身"这条统一规则的自然结果。专门给 `global` 加一个"后面不能跟 `.`"的例外，反而是在
一条通用规则里挖了一个不一致的洞，没有真正解决什么问题（此类"合法但没意义、运行时才报错"的表达式到处都是，
`global a.x` 不是特例）。

**`for` 迭代模式的 target 放宽成任意左值**（用户要求，类比 Python 的 `for a, *b in iterable:`）：
`SL.md` 2.2.5.2/3.4.5.2 把 `identifier` 改成了 `lvalue`（定义引用 2.1.5），绑定规则改成复用 3.3 对赋值
运算符的规则（简单/属性/元素/解构赋值之一，视 `lvalue` 形状而定），不再单独定义一套。**parser 完全不用改**——
`parse_for()` 解析第一个槽时本来就是通过 `parse_expr()` 走完整的表达式语法（前面那条笔记解释过的、因为要等
`:`/`;`/`)` 才能消歧义而被迫的通用解析），`(a, b)`、`[a, *b]` 这些形状本来就能被正常解析出来，只是
`SyntaxChecker::check(AstNodeForIter*)` 原来专门写死了"必须是 `AstNodeIdentifier`"，现在换成直接调用
`check_lvalue`（和 `AstNodeAssign` 的目标校验复用同一个函数）。顺手发现并修了一个既有 bug：`check_lvalue`
原来完全没处理 `AstNodeStar`（`*lv`）——递归到 `*b` 这种条目时四个 `dynamic_cast` 全部不中，会直接报
"lvalue expected"，也就是说**解构赋值带 `*` 的写法（`(a, *b) = expr`）在这次修复之前从来没有真正被
语义层正确校验过**；顺带也补上了 2.1.5 第 4 点"至多一个左值可以带 `*` 前缀"这条一直没有被强制检查的约束
（新增 `check_lvalue_items` 辅助函数，扫描一层解构目标时数 `*` 的个数，超过一个直接报错）。

**`skip_newline()` 与 `skip_paren_newline()` 的区分，及 `parse_for()` 补上 `paren_depth_++/--`**：

这两个函数其实是把 `SL.md` 2.2.1（表达式分隔符）里那套"待定表达式贪心重试"算法，改写成了一次性前看、
不回溯的等价实现。2.2.1 的算法是：一行（软终止）先尝试独立解析成完整表达式——解析成功就默认到此为止
（除非是 if 缺 else/try 缺 finally 这两个特例，下一行是 elif/else/except/finally 时才继续合并）；解析
失败（比如运算符后面还没东西、括号没闭合）就说明这行本来不完整，强制合并下一行重试。Parser.cpp 没有真的
去重试，而是：

- `skip_paren_newline()`：对应"解析成功、默认止步"这条，只用在 Pratt 循环判断"当前表达式要不要继续
  延伸"的边界点（主循环、比较链、is 链这三处）。没有未闭合括号时换行就是终止信号不能吃；有未闭合括号时
  说明这行本来就没写完（对应"解析失败"分支），必须吃掉换行继续解析（如 `f(a,\nb)`）。
- `skip_newline()`：对应"解析失败、强制合并"这条，用在刚消耗掉一个语法上必然要求后面还有东西的 token
  之后（运算符本身、`.`、`=`、`global`、`del`……），此时无论有没有括号，当前待定表达式必然不完整，无条件
  跳过换行永远对（如 `a +\nb`、`global\na`）。

全文过了一遍后，`finish_call` 和 `parse_try` 的异常列表解析里用了 `skip_paren_newline()`，但那两处
`paren_depth_` 在调用前已经 `++` 过、函数退出前才 `--`，作用域内恒为正，跟 `skip_newline()` 完全等价，
纯属误导读者的冗余——已经统一改成 `skip_newline()`，和结构上完全类似的 `finish_index`/`finish_class_bases`/
`finish_func_captures`/`parse_func` 形参循环/`parse_paren_or_tuple`/`parse_list`/`parse_if`&`parse_while`
的 cond 解析保持一致。

`parse_for()` 之前解析自己的 `(...)` 头部时完全没碰 `paren_depth_`（`if`/`while`/`try` 都会为自己的
`(cond)` 做 `++/--`），当时给出的理由是"因为 for 头部的换行本身是槽之间的分隔符，`++` 了会被 Pratt 边界检查
的 `skip_paren_newline` 提前吃掉"——用户指出这个理由站不住脚，重新想过之后确认**应该 `++`**，原来的理由是
倒果为因：
1. `paren_depth_` 的本职是"当前有几层未闭合的 `(`/`[`"这一个全局不变量，只有两处读它：Pratt 边界检查、
   以及 [Parser.cpp:470](parser/Parser.cpp:470) 的 EOF 报错分支（`unexpected end of file (unclosed
   bracket)` vs `expected an expression`）。for 头部的 `(` 是真实存在的括号，不计入这个计数本身就是在
   破坏不变量——比如 `for (i = ` 后面直接 EOF，本该报"括号没闭合"，之前会因为 `paren_depth_` 是 0 而报出
   不太对路的"缺一个表达式"。
2. 不 `++` 也不是"必须如此"才能保住换行分隔符语义——`consume_sep()` 原来直接 `check(NEWLINE)` 来判断
   两个槽之间是否存在分隔符，这个检查本身写得比较脆弱：`++` 之后，槽末尾的换行确实会被上一个槽表达式自己
   内部 Pratt 循环的边界检查（`skip_paren_newline`）提前吃掉，导致 `consume_sep()` 再检查"当前 token 是不是
   NEWLINE"时已经找不到了。修法是把这个检查换成"当前 token 所在行是否与上一个已消耗 token 所在行不同"
   （`tokens_[pos_-1].row == peek().row` 则说明中间没有分隔符），这样不管换行有没有被提前消费掉，都能
   正确识别出"槽之间确实隔着至少一个物理换行"，同时仍然会对 `for(i=0 i<10; i+=1)` 这种真的一个分隔符都
   没有的写法正确报错——用一个具体反例验证过：如果不做这个修复、直接删掉 SEP 强制检查，`for(i=0 -1 i+=1)`
   会被静默地错误解析成 `i=(0-1)`、`i+=1` 两个槽（`-` 被当成延续上一槽的减法），而不是用户想要的三个独立槽，
   证明"两个槽之间必须有 SEP"这条硬性检查是真实需要的，不能因为 `++` 之后不好实现就干脆去掉。
3. `++` 之后顺带修好了一个之前没意识到的小限制：`for` 头部内某个槽自身的表达式如果想跨行写（比如
   `for (i=0; i<10\n and flag; i+=1)`），之前会因为深度恒为 0 而在遇到 `and` 前的换行处直接断开、报语法
   错误；现在跟 `if`/`while` 的 cond 一样可以自然地跨行延伸了。

**审查了全部 `start_row`/`start_col`（以及其它节点位置来源），发现并修了一个 bug，另外统一了一处此前不一致的
节点位置语义**：

1. **bug：装饰器的位置没有算进 `AstNodeFunc`/`AstNodeClass`**。`parse_decorator()` 收集 `@d1 @d2 func f(){}`
   时每个 `@` 自己的位置本来记在 `entries[i].row/col` 里，但走"紧邻 func/class"分支（装饰器归属函数/类自己
   产生式那次重构的成果）时只把表达式转移给了 `decorators`，位置被直接丢弃——`parse_func`/`parse_class` 自己
   重新用 `peek()` 取的是 `func`/`class` 关键字的位置，不是第一个 `@` 的位置。而通用形式（`AstNodeDecorator`
   链）是对的，外层节点用的就是第一个 `@` 的位置。既然 `decorators_` 现在是这两个节点自己的字段，按
   `ast_node.h` "开始的行和列"的约定，节点起始位置理应从装饰器算起。修法：给 `parse_func`/`parse_class`
   （[Parser.h:86-91](parser/Parser.h:86)）加了 `deco_row`/`deco_col` 两个默认为 0 的参数，`parse_decorator()`
   分发到 func/class 分支时把 `entries.front()` 的位置传进去；不带装饰器的独立调用不受影响，依然用自己的
   `peek()` 位置（`decorators.empty()` 作判断条件，不依赖参数默认值本身）。
2. **不一致：`AstNodeOpBinary`/后缀 `AstNodeOpUnary`（`?`/`!`）/`AstNodeAttr`/`AstNodeCall`/`AstNodeIndex`
   原来用的是运算符/括号自己的 `op_row/op_col`，跟 `AstNodeAssign`/`AstNodeCompoundAssign`/`AstNodeCompare`/
   `AstNodeIs` 用整个表达式起始位置的 `start_row/start_col` 不一样**。发现这个不一致的线索是 `AstNodeOpUnary`
   这一个结构体前缀用法（`-x`）和后缀用法（`x?`）对 `row_/col_` 的语义并不统一（前缀时运算符位置恰好等于
   起始位置，后缀时不等于）——问用户该往哪个方向统一时，用户把决定权交回来，给的判断标准是"哪种更利于未来
   编译到字节码时保留行号信息"。选的是**统一成 `start_row/start_col`**（整个表达式最左操作数的起始位置），
   理由：SL 从头到尾都在照着 Python 的语法习惯设计（`for`、链式比较、`*args/**kwargs`、装饰器……），而 Python
   `ast` 模块本身对 `BinOp`/`Call`/`Attribute` 等节点的 `lineno/col_offset` 用的就是整个子表达式的起始位置，
   不是运算符自己的位置；这也是一条更"扁平""可预测"的规则——字节码编译器只需要记住"每个节点的位置 = 它这棵
   子树覆盖的源码范围的起始位置"这一条不变量，不需要再对每种节点类型特判"这个该指向运算符还是指向左操作数"。
   已经把 [Parser.cpp:257-341](parser/Parser.cpp:257) 里所有原来用 `op_row/op_col` 构造节点的地方改成了
   `start_row/start_col`（后缀 `?`/`!`、`AstNodeAttr`、`finish_call`/`finish_index` 的调用、`AstNodeOpBinary`），
   `AstNodeAssign`/`CompoundAssign`/`Compare`/`Is` 本来就是对的，不用动；顺手把 `parse_expr_pratt` 里现在已经
   完全用不到的 `op_row`/`op_col`/`lexeme` 三个解构变量精简掉了，只留 `op` 本身。

**接着用户明确提出要往"每条字节码都有精确行列信息"（类似 Python 3.11+ 的做法）这个方向走，要求把 Parser
尽量改成适配这个目标，而且不止运算符相关的节点，各处都需要**。做法是给每个 AST 节点补上"结束位置"
（不只是 [ast_node.h](parser/ast_nodes/details/ast_node.h) 已有的"开始的行和列"），思路和落地方式：

1. **Token 本身先补上 `end_row`/`end_col`**（[token.h](lexer/token.h)）。关键设计：`Lexer::make_token`
   原来是文件作用域的 `static` 自由函数，改成了 `Lexer` 的私有成员函数，函数体直接读 `this->row_/col_`
   当作 end 位置——因为无论 `read_string`/`read_symbol`/`read_number`/... 里哪一处调用 `make_token`，
   调用时机永远是"这个 token 的字符刚被 `advance()` 消耗完"的那一刻，此时 `row_/col_` 天然就是结束位置。
   这个改法的好处是**全部约 60 处 `make_token(...)` 调用点一个字符都不用改**，只改了函数本身和它在
   `Lexer.h` 里的声明位置。
2. **`AstNode` 基类加 `end_row_`/`end_col_` + `set_end_pos()`**（不改动构造函数签名，默认值 `{0}`，构造完
   之后由外部补上）。这里故意不学 `row_/col_` 那样走构造函数参数——如果每个节点的构造函数都加两个参数，
   相当于要去改遍全部 ast_node_*.h 里三十多个 struct 的构造函数签名，属于纯体力活且极易出错。
3. **`Parser` 加了一个私有模板方法 `make_node<T>(Args&&... args)`**（[Parser.h](parser/Parser.h)/
   [Parser.cpp:226](parser/Parser.cpp:226)）：内部照常 `std::make_unique<T>(...)` 构造节点，再用
   `tokens_[pos_-1]`（当前已消耗的最后一个 token）的 end 位置调用 `set_end_pos`，然后返回。这样只需要把
   全文 `std::make_unique<AstNodeXxx>(...)` 这个写法整体替换成 `make_node<AstNodeXxx>(...)`
   （做法是 `replace_all` 全局替换 `std::make_unique<` → `make_node<`，注意 `make_node` 自己实现里那一行
   `std::make_unique<T>` 也会被连带替换成 `make_node<T>`——变成自己递归调用自己，替换完之后手动把这一行
   改回 `std::make_unique`），不需要逐个节点类型改构造函数。
   `tokens_[pos_-1]` 这个"上一个已消耗 token 的结束位置"之所以对任何节点都天然正确，是因为递归下降的
   不变量保证了：无论一个节点的产生式多复杂、嵌套了多少层子节点，等到真正调用 `make_node<T>(...)` 构造
   它自己的那一刻，它的产生式对应的全部 token（包括所有嵌套子节点消耗的）必然已经读完了，`pos_-1` 永远
   精确指向"这个节点自己应该到此为止"的最后一个 token，不需要对每种节点类型单独计算 end 位置。
   （唯一手动验证过的边界：`parse_func`/`parse_class` 里嵌套构造函数体的 `AstNodeProgram` 和外层
   `AstNodeFunc`/`AstNodeClass` 会拿到同一个 end 位置——这是对的，因为两者确实都在 `}` 处结束。）
4. 顺手在 `parse_non_op` 的 `switch (const auto &[type, row, col, end_row, end_col, lexeme]{peek()}; type)`
   （[Parser.cpp:405](parser/Parser.cpp:405)）补上了两个新绑定名（Token 结构化绑定必须绑定全部成员，多
   了两个字段就必须多写两个名字，即使用不到）。
5. 在 [position_tracking_test.cpp](test/lexer/common/position_tracking_test.cpp) 里补了几个 `end_row`/
   `end_col` 的用例：单字符/多字符 token 的结束列、跨行 token（反引号字符串）的结束行列、EOF 起止位置
   相同。

**上面这一整套（Token.end_row/end_col、AstNode::end_row_/end_col_、Parser::make_node）后来被撤掉了**，
用户回过头来质疑"这真的有必要吗"，讨论之后确认是想大了：

- 一个节点的"结束位置"（覆盖到源码哪里为止）几乎总能从它最右边的孩子节点递归推出来（`a+b+c` 最外层
  `AstNodeOpBinary` 的结束位置就是 `right_` 的结束位置，一路递归到最右叶子）——不需要现在就在每个节点上
  都存一份，真正要用（比如以后写字节码编译器要给报错画 Python 3.11 那种 `~~~^~~~~` 波浪线）的时候，
  在那时候的代码里递归一遍就能拿到。

## 字典展开项的判定归属：Parser 直接判定，不留给语义层（已实现）

字典字面量 `{k1: v1, **d2, ...}`，语法层用
`std::vector<std::pair<AstNodePtr, AstNodePtr>>` 存 `items_`，`**expr` 展开项存成 `{expr, nullptr}`
（`value` 侧为空表示"这项其实是展开，不是键值对"）。

**讨论过要不要换成 `std::variant`/带 tag 的联合体来存这两种形状**：没换，理由是这个"槽为空表示另一种形状"
的写法是整棵 AST 里到处在用的既有惯例（`AstNodeIf::else_expr_`、`AstNodeReturn::value_`、
`AstNodeForCond` 的三个槽……全是这个套路），字典展开项只是把这个套路用在 pair 的第二个位置上，风格上一致；
换成 `variant` 会成为全 AST 唯一一处用它的地方，为了这一处的类型安全破坏整体风格，不划算。

**但发现一个真 bug，跟"该不该用 variant"无关，已修复**：[Parser.cpp](parser/Parser.cpp) 的
`parse_brace_block()` 里，判断"这一项是不是展开项"，第一项和后续项原来不一致——第一项用
`first_is_doublestar` 直接检查是否以 `**` 开头（在解析之前就定了），但从第二项开始原来是"解析完 key 之后看
有没有冒号，没冒号就当展开项"，根本没检查这一项是不是真的以 `**` 开头。于是 `{k: v, x}`（`x` 只是个裸标识符，
既不是 `**expr` 也没有冒号）会被静默地当成合法展开项存进去（`key=x, val=nullptr`），而
`SyntaxChecker::check(AstNodeLiteralDict*)`（[SyntaxChecker.cpp:284](analyzer/syntax_checker/SyntaxChecker.cpp:284)）
也没有补上"val 为空时 key 必须是 `AstNodeDoubleStar`"这个校验，纯粹是漏检。

**修法**：第二项及以后也跟第一项一样，直接 `check(TokenType::SIGN_DOUBLESTAR)` 判断是否为展开项（解析 key
之前就决定），不再用"有没有冒号"反推；确认不是展开项后普通 `key: value` 分支用 `expect(SIGN_COLON)`
强制要求冒号，而不是像原来那样可选。这样这个不变式（`val==nullptr` ⟺ 语法上就是 `**expr`）由 Parser
结构性保证，不需要再让语义层补一道 `dynamic_cast` 检查——两边都做是重复劳动，选择让 Parser 一次性判定对，
不下放给语义层。`SL.md` 2.2.2 原本就写了"第一个表达式后紧跟 `:`"这条规则，这次修复只是让实现真正符合
已经写好的规则，规则本身没有变，所以没有改 `SL.md`。

## 空 `{}` 该解析成空字典还是空复合表达式：维持现状（复合表达式），已在 SL.md 明确写过

讨论时一度倾向于改成空字典（理由：Python 直觉、`()`/`[]` 为空时都优先按"空字面量集合"解析、`{}` 是唯一的
例外）。但重新看 `SL.md` 后发现这个问题**已经有明确答案，不需要改**：

1. [SL.md:82](SL.md:82) 早就写了"空字典 `dict()`"——空字典本来就不是靠 `{}` 拼出来的，已经有专门写法，
   所以"不把 `{}` 当空字典就没法写空字典"这个顾虑不成立。
2. [SL.md:224-229](SL.md:224) 的判别规则本来就是"要么 `**` 开头、要么第一个表达式后紧跟 `:`，否则就是复合
   表达式"，这条规则统一适用、不需要为空的情况特殊处理——`{}` 没有第一个元素，自然落到"都不满足"分支，
   判成复合表达式，跟规则本身完全一致，不是"忘了处理空的情况"。

**更关键的是用户指出的具体反例**：如果 `{}` 表示空字典，那 `a = if (cond) {}` 里想表达"这个分支什么都不做"
的 `{}` 会让 `a` 变成空字典而不是 `None`，反而制造了一个新的、更隐蔽的坑——空字典是 truthy 判断意义上的
falsy（跟 `None`一样），所以这类错误很可能长期不被发现（只有代码明确判断 `is None` 或调用 `None` 专属方法
时才会暴露），比"写错空字典、下一步用字典方法时立刻崩"这种坑更难排查。结论：维持现状（`{}` 空的情况判成空
复合表达式，值为 `None`），符合已经写好的规则，也天然避开了这个隐蔽坑；真要空操作分支直接写 `None`，
要空字典写 `dict()`，两者都有清晰、无歧义的专门写法，不需要让 `{}` 身兼二职。

## if / while / for 条件槽拒绝裸赋值 `=`（已实现）

经典的 `=`/`==` 手误坑（C/C++ `if (x = 5)` 那种）。SL 是动态类型、赋值表达式本身有值（不像 Swift/Rust 能靠
"赋值的类型是 `()`/`Void`，塞进要求 `bool` 的条件位置类型检查不过"这种机制免费防住），所以选择在语法层面
直接禁止：`if(...)`/`while(...)`/`for` 三槽形式的中间 `cond` 槽，禁止顶层出现裸的普通赋值 `=`；如果确实想
在条件里赋值，需要显式再套一层括号，如 `if ((x = y))`。`SL.md` 里 [2.2.5.1](SL.md:249)/[2.2.5.2](SL.md:259)/
[2.2.5.3](SL.md:275) 已经补了对应的"注"。

**明确只限制这三处**：`if`/`while` 的 `cond`、`for` 三槽形式（`init; cond; inc`）的中间槽。**不限制**
`for` 的 `init`/`inc`（这两个槽存在的意义本来就是赋值，`for (i = 0; ...; i += 1)` 是最常见的写法，限制了
反而堵死语言最常见的用法）。

**讨论过程中的一个错误，已订正**：我最初以为 `for` 还存在第三种"纯条件形式"`for (cond) body`（只有一个槽，
不写任何分号），语义上跟 `while (cond)` 地位相同，并以此为由主张不限制它。但这个"纯条件形式"根本不是
`SL.md` 授权的语法——2.2.5.2 明确只有两种形式：步进模式（三槽必须用 `;`/换行分隔，某槽为空也必须显式写
`;`）和迭代模式（`lvalue : iterable`）；本文件前面记录的 `while` 语义等价关系写的也是
`while [$] (cond) body` ≡ `for [$] (; cond ;) body`（三槽、显式分号、两头为空），不是裸的 `for (cond) body`。
`for (cond) body` 这种写法只是 [Parser.cpp](parser/Parser.cpp) `parse_for()` 里一个未被任何文档授权的分支
（历史遗留，具体哪次会话加的已不可考），而且完全冗余——`while $ (cond) body` 已经能建出一模一样的
`AstNodeForCond{init=null, cond, inc=null}` 节点，`for` 侧这个裸写法不提供任何 `while` 做不到的能力，反而
削弱了"`while` 是纯条件循环的专用关键字"这个既有区分（见上面 `while` 那条）。发现问题后已经把这个分支从
`parse_for()` 里删掉，只保留了一个`for ()`（头部彻底为空）的专门报错，提示改用 `for (;;)` 或
`while (cond)`；裸 `for (cond) body` 现在会在步进模式分支里被 `consume_sep()` 正常拦成语法错误。
`SL.md` 本身不用改——它从一开始就没有授权这第三种形式，这次只是让实现补上一直存在的欠账，不是新增规则。

**只挡普通 `=`，不挡复合赋值 `+=` 等**：`+=`/`-=`/... 没有"跟 `==` 长得像、容易手误"的风险，禁止裸写反而
没有实际收益、纯增加噪音，所以复合赋值可以裸写、不需要额外套括号。

**实现**（[Parser.cpp](parser/Parser.cpp) 新增 `Parser::parse_cond()`，声明见
[Parser.h](parser/Parser.h)）：不能简单地把 `parse_expr()` 换成"提高 min_bp 跳过整个优先级 10 这一档"，
因为普通 `=` 和所有复合赋值在 [`infix_bp`](parser/Parser.cpp:84) 表里共享同一个优先级（10），一刀切会连
`+=` 也一起挡掉。做法是：先用 `parse_expr_pratt(11)` 解析（`min_bp=11` 卡住 lbp=10 的赋值类运算符，
Pratt 主循环会在它们前面停下不消耗）；如果接下来紧跟的正好是普通 `=`，直接抛语法错误（并在报错信息里提示
"想这样写就多套一层括号"）；如果是复合赋值 `op=`，则手动重演 `parse_expr_pratt` 主循环里那一步该做的事
（`advance()` 消耗运算符、递归 `parse_expr_pratt(rbp)` 解析右侧、构造 `AstNodeCompoundAssign`），
构造出跟原来完全一样的节点。`if ((x = y))` 这种显式多套一层括号的写法之所以能"免费"继续工作：额外的这层
括号会走 `parse_paren_or_tuple()`，其内部对分组表达式用的是不受限的 `parse_expr()`（`min_bp=0`），赋值在
**内层**被正常吃掉；外层 `parse_expr_pratt(11)` 拿到的只是一个已经解析完、类型是 `AstNodeAssign` 的分组
结果，不会再往里看，两层括号天然形成"外层受限、内层不受限"的边界，不需要额外记录"用户是不是多写了一层
括号"这种信息。

`for` 头部原来只有一个 `parse_slot()` lambda（`init`/`cond`/`inc` 三槽通用），改造成
`parse_slot(bool restrict_assign)`，`cond` 槽传 `true`（内部走 `parse_cond()`），`init`/`inc`/
"纯条件形式"的单槽都传 `false`（内部走原来的 `parse_expr()`），互不影响。

## 写 parser 测试时挖出的真 bug：`{k v}` 曾被静默接受（已修复）

写 [test/parser](test/parser) 测试套件、测 2.2.2 的 `{}` 判别规则时发现的：`{k v}`（大括号内两条表达式
中间既没有分号也没有换行）本该跟顶层 `a b` 一样报 "expected newline or ';' after expression"，但实际会
静默解析成功，变成 `Compound{exprs:[k, v]}`。

**原因**：`parse_brace_block()` 为了判别"这是字典还是复合表达式"，得先把第一项 `first` 解析出来才能往下看
（有没有 `**` 前缀、后面紧不紧跟 `:`）。判别成复合表达式之后，原来的写法是手动
`exprs.push_back(std::move(first))` 再调 `parse_exprs()` 解析剩下的——但 `first` 是在 `parse_exprs()`
的循环**外面**解析、直接塞进结果数组的，没有过 `parse_exprs()` 内部"每条表达式解析完必须紧跟换行/分号/
EOF/`}`"那道检查（这道检查只发生在循环体**内部**每一轮的末尾）。所以 `first` 和 `parse_exprs()` 接下来
解析出的第一条表达式之间，这道检查被跳过了。顶层 `parse()`、函数体、类体都是直接从头调 `parse_exprs()`，
没有这种"先在外面偷偷解析一条塞进去"的操作，所以只有 `parse_brace_block` 这一条路径有这个漏洞。

**修法**：给 `parse_exprs()`（[Parser.h](parser/Parser.h)/[Parser.cpp:226](parser/Parser.cpp:226)）加了个
`AstNodePtr first = nullptr` 默认参数——传了就先 `push_back` 再走一遍终止符检查，跟循环体内部每一轮末尾
用的是同一个 `check_terminator` lambda（避免同一段检查逻辑抄两遍）。`parse_brace_block` 判别成复合表达式
后改成 `parse_exprs(std::move(first))`，让 `first` 也过这道检查。其余三个调用点（顶层 `parse()`、
`parse_func`、`parse_class`）都是原来的无参调用，默认参数保证它们不用改。

## 写 parser 测试时挖出的第二个真 bug：零参数函数 `func f() {}` 完全解析不出来（已修复）

写 [func_test.cpp](test/parser/2_2_6_func/func_test.cpp) 验证"形参列表为空"这个最基础的场景时发现的：
`func f() {}` 会直接抛 `SyntaxError`（"expected IDENTIFIER but got SIGN_RPAREN"），影响面极大——所有零参数
函数定义都解析不出来。这个 bug 之所以一直没被发现，是因为这是这个仓库第一次有 parser 级别的自动化测试。

**原因**：[Parser.cpp](parser/Parser.cpp) 里 `parse_func()` 解析形参列表用的是"先无条件解析一个，再看逗号
决定要不要继续"的写法（`params.push_back(parse_func_param()); while (check(COMMA)) {...}`），完全没有检查
"是不是紧跟 `)`（形参列表为空）"这道守卫——而 `parse_func_param()` 在形参不是 `*`/`**` 开头时会直接
`expect(IDENTIFIER)`，遇到 `)` 自然报错。同一个文件里其他"括号内列表"的解析函数都有这道"先检查是不是立刻
碰到右括号，空的话直接返回"的守卫（`finish_class_bases()` 的"空基类列表 ()"、`finish_func_captures()` 的
"空捕获列表 []"），唯独形参列表这里漏了。

**修法上的分歧**：我最初的想法是照搬 `finish_class_bases`/`finish_func_captures` 的写法，在 `parse_func`
里加守卫。用户认为这本质上是 `parse_func_param()` 自己的 bug（它没有优雅地处理"当前位置根本没有形参可解析"
这件事，只会用一个笼统的 IDENTIFIER-not-found 报错砸出来），要求改 `parse_func_param()`。最终做法：
`parse_func_param()` 的返回类型从 `AstNodeFunc::OneParam` 改成 `std::optional<AstNodeFunc::OneParam>`
（[Parser.h](parser/Parser.h)），函数开头先 `skip_newline()` 再检查——如果当前正好是 `)`，直接
`return std::nullopt`（不消耗任何 token）。`parse_func` 里两处调用点相应从"无条件 push_back"改成
"`if (auto p{parse_func_param()}) params.push_back(std::move(*p));`"（第一次调用，判断是否为空参数列表）
和"逗号循环内部直接 `*parse_func_param()` 解引用"（循环内已经用 `if (check(RPAREN)) break;` 排除了空的
情况，此处必然非空，不需要重复判空）。`parse_func_param()` 现在是"这个位置有没有形参可解析"的唯一权威，
调用处只需要处理它给出的 optional，不用自己关心"空列表"这个特例怎么识别。

## parser 测试套件实际跑起来之后：9 个失败用例，全部是测试自己写错了，不是 Parser 的问题

`SL_Cpp_Parser_Tests` 第一次实际编译运行后有 9 个 `TEST_CASE` 失败，逐一排查完确认没有新的 Parser 缺陷，
纯粹是测试代码本身的错误，已在对应文件里修正：

1. **`nlohmann::json` 花括号初始化的经典坑，5 处中招**：`const auto x{某个已经构造好的 json 值}` 这种写法，
   遇到"唯一的初始化项本身已经是个 json 对象"时，会被 `nlohmann::json` 自己的 `initializer_list<json>`
   构造函数当成"用这一个元素构造一个数组"，而不是拷贝这个对象本身，导致 `x` 变成包了一层数组的错误结果
   （对象没法再用 `x["key"]` 取字段，`x == 别的对象` 也永远不相等）。这是 nlohmann/json 库自己文档里明确
   警告过的陷阱：花括号初始化 vs 圆括号初始化在这个库里行为不同。踩坑的地方：
   [literals_test.cpp](test/parser/2_1_4_literals/literals_test.cpp) 两处"多元素元组/列表，尾逗号可选"、
   [func_test.cpp](test/parser/2_2_6_func/func_test.cpp) 三处"返回类型/文档字符串"相关用例。
   **以后写这类测试变量一律用 `=` 赋值初始化（`const nlohmann::json x = ...;`），不要用花括号**——已在
   踩坑的地方留了注释提醒，别再犯。
2. **`x.func()`/`(x\n.func()\n)` 两处用 `func` 当属性名**：`func` 是关键字不是普通标识符，`x.func()` 这种
   写法在 SL 里本来就无法解析（词法层面 `func` 就是 `KW_FUNC`，不是 `IDENTIFIER`）。这两处是照抄
   [SL.md 2.2.1](SL.md:185) 里的例子抄过头了——标准里那个例子只是为了说明续行合并规则，不是说"func"字面
   量本身在这个位置合法。已把属性名换成 `m`。
3. **`global x.y` 误判会报错，实际会成功解析成 `(global x).y`**：`parse_non_op()` 返回什么节点（哪怕是
   `AstNodeGlobal` 这种语法上是"固定两个 token"的特殊形式），回到 `parse_expr_pratt` 的主循环后都会被同一套
   通用的后缀运算符判定（`.`/`()`/`[]`/`?`/`!`）无差别处理——`global` 在 `SL.md` 里也确实被称为"表达式"，
   跟其他基本表达式一样能接后缀链，只是接出来的东西没什么实际意义（语义层大概率会拒绝，但语法层不管这个）。
   这不是 bug，是"每个表达式都能接后缀运算符"这个统一设计的自然结果，测试改成断言实际行为
   （`Attr{object: Global(x), attr: "y"}`），不再断言它会报错。
4. **`Parser`没有 `file_path` 的默认值，"<unknown>" 是 `Lexer` 独有的默认值**：`Parser.h` 里
   `explicit Parser(std::vector<Token> tokens, std::string file_path);` 的文档注释写着"默认为 <unknown>"，
   但函数签名根本没有默认参数——这条注释是从 `Lexer` 的构造函数注释照抄过来的，`Lexer` 才真的有
   `file_path = "<unknown>"` 这个默认值。`test_utils.h` 里 `parse_program` 自己又给了一个 `"<test>"` 的
   默认值，所以"不传 file_path 时默认是 <unknown>"这个测试从一开始就测不出 Parser 自己的行为。已删掉这条
   测试用例；`Parser.h` 那条过时的文档注释暂时没有动（不影响任何行为，只是注释抄错了对象，优先级很低）。

另外把 CMake 里两个测试可执行文件的名字对齐成同一套命名习惯：原来的 `SL_Cpp_Tests`（只测 lexer）改名成
`SL_Cpp_Lexer_Tests`，跟新加的 `SL_Cpp_Parser_Tests` 对称。

## `Lexer.cpp` 里报错位置靠"当前 col_ 减几"现算，用户指出这是脆的写法，已经全部改成提前存好的位置变量

用户看完上一轮的修复后自己发现的：`Lexer.cpp` 有三处报错位置不是直接用某个"这个 token/这个字符起始时"存好
的 `start_row`/`start_col`，而是在报错那一刻用当前 `row_`/`col_` 反着减一个固定数字倒推回去
（`col_ - 1`、`col_ - 2`）。这种写法今天算得对，是因为"从这个字符开始到报错这一刻，中间正好消耗了 N 个
字符"这个前提今天恰好成立；一旦以后转义规则变了（比如加 `\uXXXX` 这种多字符转义），中间消耗的字符数就不再
是固定的 1 或 2，这些写死的减法就全错了，而且没有任何编译期或类型上的信号提醒"这里也要跟着改"——纯粹靠人
记得，属于脆弱写法。

**修法**：不在报错的那一刻倒推位置，而是在"进入这段可能变长的解析逻辑"的那一刻就把当时的 `row_`/`col_`
存进一个专门的变量，后面不管这段逻辑本身消耗掉多少个字符，报错都直接用这个存好的变量，不再对 `col_` 做任何
算术。三处：
1. [`read_string`](lexer/Lexer.cpp:69) 里转义序列相关的两处报错（转义在字符串结尾被截断、未知转义序列）：
   在识别到反斜杠的那一刻新增 `const int esc_row{row_}, esc_col{col_ - 1};`（这一次减法只用来定位反斜杠
   自己——反斜杠固定占 1 个字符、不会是换行，这个减法本身不会因为转义规则变化而失效），两处报错都改用
   `esc_row, esc_col`，不再各自现算 `col_ - 1` / `col_ - 2`。
2. [`read_symbol`](lexer/Lexer.cpp:184) 里"完全不认识的字符"这个报错：这里更简单，函数开头本来就已经存了
   `start_row`/`start_col`（在 `switch(advance())` 消耗掉这个字符**之前**存的），报错那行却没用这两个
   现成的变量，反而重新写了一遍 `col_ - 1`——直接换成已有的 `start_row, start_col` 就行，不需要引入新变量。

三处修完之后，`Lexer.cpp` 里已经没有任何"报错时对 row_/col_ 做算术"的写法了（全项目搜过一遍确认）。
补了两条位置相关的回归测试：
[symbols_test.cpp](test/lexer/2_1_5_operators/symbols_test.cpp)（未知字符报错的列指向那个字符本身）、
[string_test.cpp](test/lexer/2_1_4_literals/string_test.cpp)（转义截断/未知转义序列报错的列指向反斜杠本身，
不是反斜杠后面那个字符）。

## `Parser.cpp` 里几组"判断是不是 X + 转成对应的枚举值"的函数对，合并成一个（用户要求）

用户观察到 `is_compare_op`/`token_type_to_compare_op_type` 和 `is_assign_op`/`assign_compound_to_binary`
各自都是同一份 `case` 列表抄了两遍（一份判 true/false，一份转枚举值），要求合并；顺带问了
`token_type_to_unary_op_type`/`token_type_to_binary_op_type` 的 `default: assert(false)` 能不能去掉
（前提是调用处能保证不传非法值）。

**先核实了"调用处能保证不传非法值"这个前提对不对**，逐个查了全部调用点：
- `token_type_to_unary_op_type` 两处调用都在已经判过 token 类型的分支内部（`SIGN_QUESTION`/`SIGN_EXCLAIM`
  各自一个 `if`，`SIGN_PLUS`/`SIGN_MINUS`/`SIGN_TILDE` 是同一个 `switch case`），成立。
- `token_type_to_binary_op_type` 唯一一处调用是主 Pratt 循环 `while` 的兜底分支，前面已经依次排除了
  赋值/复合赋值/`?!`/`(`/`[`/`.`/比较组/`is`，能落到这里的只剩它能处理的 15 种，成立。
- `is_compare_op`/`token_type_to_compare_op_type`、`is_assign_op`/`assign_compound_to_binary` 的每处
  调用也都成立（见下）。

**合并 `is_compare_op` + `token_type_to_compare_op_type`**：改成一个函数
`std::optional<AstNodeCompare::OpType> token_type_to_compare_op_type(TokenType)`，是比较组就返回对应枚举值，
否则 `nullopt`——"是不是"这件事和"转成什么"合并成一次判断。`Parser::parse_compare_chain` 的签名也跟着从吃
`TokenType first_op`（内部再转一次）改成直接吃已经转换好的 `AstNodeCompare::OpType first_op`，调用处
（[Parser.cpp:311](parser/Parser.cpp:311)）和链内部的循环条件（原来 `is_compare_op` + `advance` 两步，
现在 `token_type_to_compare_op_type(peek().type)` 一步判出"是不是、是哪个"）都相应简化。

**合并 `is_assign_op` + `assign_compound_to_binary`**：这两个函数原本管的范围不一样——
`is_assign_op` 连裸 `=` 也算 12 种，`assign_compound_to_binary` 只认 11 种复合赋值（裸 `=` 没有对应的
二元运算符，转不出来）。查了两处调用点（主 Pratt 循环、`parse_cond`），发现都是先单独判掉
`op == SIGN_ASSIGN`（要么直接构造 `AstNodeAssign` 返回，要么在 `parse_cond` 里专门报错）之后，
`is_assign_op` 才会真正派上用场——而这时候它的语义已经等价于"是不是这 11 种复合赋值之一"，跟
`assign_compound_to_binary` 的范围完全重合。于是把 `is_assign_op` 直接砍掉，`assign_compound_to_binary`
改成 `std::optional<AstNodeOpBinary::OpType>`，复合赋值分支用 `if (const auto compound_op{...})` 一次
判出"是不是复合赋值、是哪个二元运算符"。

**`token_type_to_unary_op_type`/`token_type_to_binary_op_type` 的 `default: assert(false)` 没法简单删掉，
解释了原因、换了个更合适的做法**：这两个函数的 `switch` 是对着 `TokenType` 这个大枚举（约 92 个值）写的，
只覆盖其中 6 个/15 个；如果直接删掉 `default` 什么都不加，`-Wswitch`（`-Wall` 的一部分）会把其余没覆盖到的
七八十个枚举值全部当"没处理"报警告，这两个测试可执行文件的 `-Werror` 是无条件开着的（不分 Debug/Release），
等于编译不过。另外 `assert(false)` 本身在 `NDEBUG`（Release）下会被优化成空语句，那时候这个 `default` 分支
其实是"函数摔到结尾却不返回值"的未定义行为——只是因为调用处保证走不到这里，这个隐患才一直没暴露出来。
最终做法：跟上面两组一样，也改成 `std::optional` 返回、`default: return std::nullopt;`（`optional` 天然
满足 `-Wswitch` 要求"有 default"这一条），三处调用点（[Parser.cpp:282](parser/Parser.cpp:282)/
[325](parser/Parser.cpp:325)/[469](parser/Parser.cpp:469)）改成 `*token_type_to_xxx_op_type(...)` 直接
解引用——调用处已经确认过类型，解引用不会踩空。这跟原来"assert 不可能发生"的自信程度是一回事，只是换了个
能通过编译检查的写法。

**顺带发现一处小的死代码，没有动，仅记录**：`token_type_to_unary_op_type` 的 `switch` 里有
`case TokenType::KW_NOT: return AstNodeOpUnary::OpType::Not;`，但全项目搜过，没有任何调用点会真的传
`KW_NOT` 进来——`parse_non_op` 里 `KW_NOT` 分支是直接手写 `AstNodeOpUnary::OpType::Not` 构造节点，压根没走
这个函数。这个 `case` 分支本身够不成问题（多一个 case 而已），只是从来没被执行过，不属于这次改动请求的范围，
没有主动删。

## `parse_exprs(AstNodePtr first = nullptr)` 这个参数：用户觉得怪，改成更干净的写法

用户直接问"这个参数为什么存在、是不是必要、能不能换种方式实现"——这是个很中肯的疑问，`parse_exprs` 本来是个
"尽可能多解析表达式"的通用工具函数，四个调用点（顶层 `parse()`、函数体、类体、`parse_brace_block`）里只有
最后一个会传参数，其余三个全部无参调用，一个只服务于一处特例的参数确实显得突兀。

**这个参数当初为什么会加进去**：`parse_brace_block()` 判别"这是字典还是复合表达式"必须先把第一项 `first`
解析完才能往下看（有没有 `**` 前缀、后面紧不紧跟 `:`——这是语法本身决定的，无法只靠 peek 几个 token 就
判断出表达式在哪结束，`{a + b: c}` 这种键本身可以是任意表达式，只有真的解析完才知道 `:` 在哪）。判别成
复合表达式之后，`first` 需要跟 `parse_exprs()` 循环体内部解析出的其余表达式享受同一套校验（"两条表达式之间
必须有合法分隔符"，这条正是上一轮从 `{k v}` 那个 bug 里补上的）。当时图省事，直接把这道校验逻辑本身搬进
`parse_exprs`、让它多接一个可选参数，两边共用一份检查代码。

**问题出在哪**：这么做把"`parse_brace_block` 自己的特殊需求"泄漏进了一个本该是纯通用工具的函数签名里——
`parse_exprs` 的另外三个调用点完全不知道、也不关心这个参数的存在，读到这个签名的人得去翻 `parse_brace_block`
才能明白这个参数是干什么用的，职责不清晰。

**改法**：把"检查当前位置是不是一条表达式合法的终止符"这件事本身拆成一个独立的小方法
`Parser::check_expr_terminator()`（[Parser.h](parser/Parser.h)/[Parser.cpp:193](parser/Parser.cpp:193)），
`parse_exprs()` 恢复成纯无参函数，循环体内部调这个方法；`parse_brace_block()` 判别成复合表达式之后，自己先
显式调一次 `check_expr_terminator()`（对 `first` 做校验），再手动 `push_back(first)`，再调无参的
`parse_exprs()` 拼剩下的。校验逻辑本身没有重复（还是只有一份实现），只是从"塞进 `parse_exprs` 的参数"
变成"提取成一个两边都能调的小方法"——`parse_exprs` 恢复干净，`parse_brace_block` 自己的特殊处理留在自己
身上，不去污染通用工具函数的签名。行为完全不变（`{k v}` 依然正确报错，其余场景都照原样跑过一遍确认过）。

## `(1` 报错"expected ')' to close tuple"，措辞不准确（用户发现，已修）

`(1`（只有一个元素、没有逗号、没闭合）现在会报"expected ')' to close tuple"，但这时候根本推导不出用户是想
写元组 `(1, ...)` 还是纯分组 `(expr)`——两者在解析到这一步为止的语法完全一样，只有真的出现过 `,` 才能确定
是元组。用户明确说了不能简单地把"to close tuple"这几个字直接删掉/换掉，因为 `(1, 2`（已经出现过逗号，确定
是元组）这种场景下这句话是准确的，删了反而变差。

**修法**：[`parse_paren_or_tuple`](parser/Parser.cpp:494) 里加一个 `bool saw_comma` 标记，见过 `,` 才置
`true`；报错时按这个标记二选一——见过逗号（已确定是元组）用原来的"expected ')' to close tuple"，没见过
（分不清是分组表达式还是元组）用新的"expected ')' to close the parenthesized expression (or ',' to make it
a tuple)"，同时提示了两种可能的写法。补了对应的位置区分测试
（[literals_test.cpp](test/parser/2_1_4_literals/literals_test.cpp)）。

## `for` 头部的换行分隔符检测有真 bug：能骗过"是否有分隔符"的判断，把没写的第三槽悄悄当成合法的空槽

用户报的：`for(a\nb\n) {}` 这种写法——按 `SL.md` 2.2.5.2，步进模式的三个槽之间必须用 `;` 或至少一个换行分隔，
但"某个槽为空必须显式用 `;`"，光凭换行判不出"这一槽本来就打算空着"还是"用户没写完"。这份输入实际上只写了
两个槽（`a`、`b`），第三槽（`inc`）压根没写内容也没有 `;`，理应报错，但当时会静默解析成
`ForCond{init=a, cond=b, inc=null}`，把"没写第三槽"和"第三槽显式留空"混为一谈。

**根因**：[`parse_for`](parser/Parser.cpp:697) 里 `consume_sep()`（判断两个槽之间的分隔符是否合法）用的是
"比较当前 token 所在行和上一个已消耗 token 所在行是否不同"这个间接的行号判断——之所以要绕这么一圈，是因为
每个槽自己的表达式在 Pratt 循环里（`skip_paren_newline`，括号内无条件跳过换行方便多行链式调用）可能已经把
槽末尾的换行提前吃掉了，这时候再直接 `check(NEWLINE)` 会误判成"没有分隔符"（这段历史在代码注释里写着）。
但这个行号比较只能回答"这两个 token 之间原文里有没有换行"，回答不了"换行之后紧接着的到底是下一个槽的真实内容，
还是压根没有下一个槽、直接就是收尾的 `)`"——`for(a\nb\n) {}` 里 `b` 和 `)` 之间确实隔着一个换行（行号不同），
这个判断就认为"分隔符合法"，然后 `inc` 槽自己检测到紧跟 `)` 就当成"合法的空槽"接受了，两层判断各自都"合理"，
组合起来就成了 bug。

**修法**：`consume_sep()` 在"确认是换行分隔（不是显式 `;`）"这条分支里，跳过换行之后再多看一眼——如果紧接着
就是 `)`，说明后面这一槽根本没有内容，而这一槽的"空"没有被显式的 `;` 标记过，直接报错
（"an empty slot in a for header must be marked with ';', a newline alone is not enough"）。这个检查只加在
"非显式 `;`"这条分支里，`;` 标记的空槽（`for (;;)`、`for (a;b;)` 等）完全不受影响，也不影响三槽都有真实内容、
纯换行分隔的合法写法（`for (a\nb\nc)`）——只有"换行分隔之后紧跟着 `)`，且这段没有 `;`"这一种组合被拦下来。

**关于测试强度**：这个 bug 之所以没被已有的 233 条用例覆盖到，是因为之前"换行分隔符"相关的测试只测了"三槽都有
内容、纯换行分隔"这一种正面场景（[for_test.cpp](test/parser/2_2_5_control_flow/for_test.cpp) 的"分隔符可以
用换行代替分号"），没有测"换行分隔到一半、槽没写完就收尾"这类边界组合——只测孤立的正反面场景、不测场景的
组合，是这次漏测的直接原因。补充了三组回归测试：两槽换行分隔后直接收尾（原始 bug 场景）、退化到单槽的同类
写法、前面槽用 `;` 显式标空但最后一槽只有换行的组合，外加一条"补上显式 `;` 后重新合法"的对照。

## 用户要求主动复查 `parse_for`/`parse_paren_or_tuple` 这类"换行容错 + 边界判定"的逻辑，逐个过了一遍

用户对上面那个 bug 的反应是"这至少说明测试强度不够"，要求主动、仔细地把 `parse_for`、`parse_paren_or_tuple`
以及同类逻辑（依赖换行容错、需要提前看一段才能判定语法形状的地方）过一遍，不是被动等他继续报 bug。逐个手工
过了以下函数，重点找"换行被提前吃掉之后，某个判定条件被骗"这一类问题：

**`parse_for`**：除了已修的那处，又手工推演了这些场景，没有发现新问题：
- 头部开头的换行（`(` 之后直接换行）：会被 [Parser.cpp:714](parser/Parser.cpp:714) 那行无条件 `skip_newline()`
  吃掉，这是**有意为之**（跟 `()`/`[]`/`{}` 开头允许换行是同一惯例，纯格式，不代表"第一槽为空"），不是 bug。
  补了一条测试锁定这个行为（`for (\ni=0; i<10; i+=1)` 等价于不带开头换行的版本）。
- 连续多个空行（两个换行之间夹了好几个 NEWLINE token）：`consume_sep` 的行号比较和新加的 RPAREN 检查都是
  "比较两个具体 token 的行号"/"检查跳过换行之后紧跟的 token"，不依赖"恰好一个换行"，多个空行不影响判断。
  补了测试确认。
- `for (;)`（只有一个显式 `;`，缺第二个分隔符和第三槽）：会在第二次 `consume_sep()` 里因为"当前 token 和上一个
  已消耗 token 同一行"而正确报错——本来就该报错（三槽形式怎么都得有两个分隔符），行为正确，补了测试锁定。
  确认过 [`check_over_newline`](parser/Parser.cpp:152)（迭代模式判 `:`、空头部判 `)` 用的）是"从当前位置向前
  扫描、跳过 NEWLINE"的正向扫描，不依赖"是否已经被消耗"这种回溯式判断，天然不会被提前吃掉的换行骗到——这跟
  `consume_sep` 用的"回头比较行号"的间接判断是两种不同机制，后者才是那个 bug 的根源，前者本来就没有这个问题。
- `paren_depth_` 在每条 `error()` 抛出路径上确实没有配对递减，但整个 Parser 遇到异常就是整体废弃、不会捕获后
  继续解析（这是全项目的既有设计，不止 `for`），所以不算是这次审查范围内的新问题。

**`parse_paren_or_tuple`**：本身不依赖行号比较，分组/元组判别和逗号检测都是"显式 `skip_newline()` 之后直接
`check()`"这种直接判断，不受"换行被提前吃掉"影响（因为不管谁提前吃掉换行，显式 `skip_newline()` 都会把剩下
的一并吃干净，然后 `check()` 直接看当前 token，没有"回头看是否有换行"这一步）。逐个推演过：换行在逗号前/后/
两边、单个元素本身横跨多行（末尾二元运算符触发续行）后面还有更多元素、开头换行加尾逗号、开头换行加纯分组
（无逗号）——都正确。补了对应的测试组
（[literals_test.cpp](test/parser/2_1_4_literals/literals_test.cpp)）。

**同类的其他逗号列表**（`parse_list`、`parse_brace_block` 字典分支、`finish_call`、`finish_index`、
`finish_func_captures`、`finish_class_bases`、`parse_func` 形参循环、`parse_try` 的异常列表）：结构上都是
"先解析/判空、再 `while (check(','))` 循环、循环体内先 `advance` 再 `skip_newline` 再判尾逗号"这同一套模式，
没有使用行号比较这种间接判断，逐个读过没有发现类似问题。`parse_try` 的 `except`/`finally` 续行判断用的是
`check_over_newline`（正向扫描），同上，机制上不会有这个问题。

**结论**：`parse_for` 那处 bug 是唯一一处依赖"回头比较行号来推断有没有分隔符"的地方（全项目搜过
`tokens_[pos_ - 1]` 只有这一处），根源在于这个函数需要"两个具体 token 之间有没有换行"这个回溯式信息，而
`check_over_newline` 这类正向扫描机制解决不了这种回溯式问题，只能退而求其次用行号比较，这也是它比其他函数
更容易出这类 bug 的原因。其余函数没有这种回溯式判断需求，没有发现同类问题。

## 提取 `parse_comma_list`：统一"括号内逗号列表"这一族重复的解析循环

上面的审查已经指出 `parse_paren_or_tuple`、`parse_list`、`finish_index`、`finish_class_bases`、
`parse_try` 的异常列表、`finish_call`、`finish_func_captures`、`parse_func` 的形参循环这八处
共享同一套"跳过前导换行 → 判空/解析第一项 → `while (check(','))` 循环、循环体内消耗逗号、跳过换行、
遇到收尾符号就当尾逗号处理、否则解析下一项"的循环骨架。这次把这套骨架提取成公共方法：

```cpp
// 假定起始括号已消耗、paren_depth_ 已自增；不消耗、不检查收尾的右括号（留给调用方，
// 因为每处"未闭合"的错误文案不同）；是否允许列表整体为空也不在这里处理，
// 见下面"为什么空值判断也下沉了"
bool Parser::parse_comma_list(TokenType close, const std::function<void()> &parse_item);
```

**设计过程中几个明确否决掉的方向，记录一下为什么**：

1. **最初想复用 `parse_paren_or_tuple` 本身**（调用它、检查返回值是不是非空非分组的元组）被否决：
   `parse_paren_or_tuple` 自带"分组 (expr) vs 元组 (expr,)"这层二义性消解，这层逻辑是表达式位置的
   括号独有的语义，`except (...)`/`class (...)` 这类语境里的括号从来不存在"是不是在分组"这个问题——
   `except (ValueError) body` 里的 `(ValueError)` 从头到尾就是"一个元素的列表"，把它套进
   "元组语义 + 事后 unwrap" 的框架里，反而是把不该存在的隐含知识（"拿到非 tuple 说明只有一项"）
   散布到好几个调用点。

2. **给一个"如何处理 `x = expr`"的开关参数**（用户最初设想的方向）也被否决：这种开关只能覆盖
   item 类型统一是 `AstNodePtr` 的那几处（tuple/list/index/class-bases/except/call），但字典的 item 是
   `pair<AstNodePtr, AstNodePtr>`、捕获列表的 item 是 `OneCapture`、形参列表的 item 是 `OneParam`——
   这些完全不是"给 `AstNodePtr` 加个开关"能覆盖的。最终改成让调用方直接传一个 `parse_item` 回调，
   通用骨架只管"逗号 + 跳换行 + 尾逗号容错"这部分语法形状本身，不关心每一项具体怎么解析、解析结果
   塞进什么容器——`finish_call` 的回调内部自己判断 `at_kwarg()`，是就塞进 `kwargs`，不是就塞进
   `args`，通用骨架完全不知道"kwarg"这回事。

3. **为什么空列表的判断也下沉了**：起初以为"空的时候有的要返回完整 AstNodePtr 字面量、有的要返回裸
   vector，行为差异太大不适合塞进公共逻辑"，后来发现这是个假象——不管列表最终是空还是非空，调用方
   都是"把 `items` 包装成结果"这同一句代码（`make_unique<AstNodeLiteralList>(start_pos,
   std::move(items))` 在 `items` 为空时天然就是空列表字面量），从来不需要为空另写一条路径。真正
   需要在 helper 外面单独处理的只有"根本不允许空"的场景（`finish_index`、except 异常列表）——这两处
   现在是调用完 `parse_comma_list` 之后自己加一句 `if (items.empty()) error(...)` 的后置检查，
   而不是给 helper 塞一个 `allow_empty` 参数。

4. **`parse_paren_or_tuple` 的分组判定最终也没有特殊对待**：把 `parse_comma_list` 的返回值定义成
   "循环期间是否真的消耗过至少一个 `,`"（`saw_comma`），`parse_paren_or_tuple` 调用完之后用
   `items.size() == 1 && !saw_comma` 就能准确复现原来的三态判断（`()` 空元组 / `(x)` 分组 /
   `(x,)` 单元素元组）——包括"尾逗号强制识别为元组"这条容易漏掉的规则（`saw_comma` 在看到逗号的
   那一刻就置位，不管随后是不是紧跟收尾括号）。验证过 `()`/`(x)`/`(x,)`/`(x, y)`/`(x, y,)` 五种组合，
   跟原来手写的行为完全一致。

**唯一没有并入这套体系的是字典**（`parse_brace_block` 里 `{k: v, ...}` 那部分）：`{}` 这个 token
到底要解析成字典还是复合表达式/空复合表达式，取决于解析完第一项之后往后看是不是紧跟 `:`——这个
消歧决策发生在"进入逗号循环之前"，且决定权要留在 `parse_brace_block` 自己手里，不能交给一个"直接
处理第一项"的通用 helper。字典的其余部分（`items.emplace_back` 那段 while 循环）本质上还是同一种
"逗号 + 尾逗号容错"形状，但因为要保留手写的第一项判别逻辑，没有强行套进 `parse_comma_list`。

**顺带修掉的一处不一致**：`parse_func_param()` 原本因为要检测"是不是紧接 ')'（形参列表为空）"，
被迫改成了 `std::optional<AstNodeFunc::OneParam>` 返回、靠返回 `nullopt` 表示"没有下一项"——这是
全项目唯一一处用"返回空值表示列表为空"来处理这件事的地方，其它同类函数都是"调用前先 `check`
收尾符"。现在空值判断统一移到 `parse_comma_list` 的 `if (!check(close))` 门槛里，`parse_func_param()`
退回普通的 `AstNodeFunc::OneParam` 返回值，不再需要 `std::optional`，跟其它"单项解析函数"
（`parse_func_capture()` 等）保持一致的调用约定。

**一处有意的行为变化（不是回归）**：`except` 的异常列表原来完全没有专门处理"空列表"这件事——
`except ()` 会让 `excs.push_back(parse_expr())` 直接对着 `)` 去解析表达式，报出的是 `parse_expr()`
内部某个通用 fallback 错误（具体措辞取决于 `parse_non_op()` 走到 default 分支的"unexpected token"
消息），不是针对"异常列表为空"这件事本身设计出来的措辞。改用 `parse_comma_list` 之后顺手补了一条
明确的 `error("except requires at least one exception type")`，测试
（[try_test.cpp:71](test/parser/2_2_5_control_flow/try_test.cpp:71)）只断言抛出 `SyntaxError`，
没有锁定具体文案，所以这次改动没有破坏任何测试，属于顺带的错误信息改进。

**测试跑出的唯一失败跟这次重构无关，是老熟人**：
[literals_test.cpp:126](test/parser/2_1_4_literals/literals_test.cpp:126)（上一轮审查新加的换行边界测试）
写成了 `const auto pair{nlohmann::json::parse(...)}`——又是那个 nlohmann brace-init 陷阱：花括号
初始化一个已经构造好的 json 对象，会被 `initializer_list<json>` 构造函数当成"用这一个元素构造
数组"，实际拿到的 `pair` 是包了一层数组的错误值，跟 parser 返回的裸对象自然对不上。改成
`const auto pair = nlohmann::json::parse(...)`（拷贝初始化）即可，`parse_comma_list` 那次重构涉及
的所有函数本身没有问题。

## `parse_brace_block` bug：前导 ';' 被 `skip_terminator()` 连同换行一起吃掉，丢失了"这必然不是字典"的信号

**现象**：`{; a : b}` 被静默解析成了字典 `{a: b}`，而不是报错。

**根因**：[Parser.cpp:553](parser/Parser.cpp:553) 原来一进函数就无条件 `skip_terminator()`（同时跳过
NEWLINE 和 `;`），然后才开始"是不是以 `**` 开头 / 第一项后面紧跟 `:`"这套字典判别。但字典字面量的
第一项永远不可能是裸 `;`——`;` 是复合表达式专属的语句分隔符，只要开头出现了它，就已经确定这必然是
复合表达式，不管后面的内容长得再像 `k: v` 也不该再被判成字典。原来的写法把"见没见过前导 `;`"这个
判别信号和"跳过多余的前导换行"这个纯格式化操作混在了一次 `skip_terminator()` 调用里，调用完之后
两者都不留痕迹，导致 `{; a : b}` 里的 `;` 被吃掉之后，剩下的 `a : b` 就被按普通"先解析第一项、
再看后面是不是 `:`"的流程走了一遍，误判成字典。

这跟 `parse_for` 那次的 bug 是同一类根因："提前做的换行/分隔符归一化操作，不小心把后续判别要用的
信号也一并抹掉了"——只是这次丢的不是"有没有换行"，而是"有没有见过 `;`"。

**修法**：把无条件的 `skip_terminator()` 拆成两步——先 `skip_newline()`（换行本来就不影响字典/
复合表达式判别，两者开头都允许换行，可以放心跳过），再显式 `check(SIGN_SEMICOLON)`：一旦是 `;`，
直接短路进复合表达式分支（`parse_exprs()` 起手也会自己 `skip_terminator()`，所以这个 `;` 本身
还是会被正常吃掉，只是不再在"判断是不是字典"之前就被吃掉）。见
[Parser.cpp:553-573](parser/Parser.cpp:553)。`{; a : b}` 现在会在强制走复合表达式分支之后，
因为 `a` 后面紧跟 `:` 不是合法的表达式终止符而正确报 `SyntaxError`。补了三条测试
（[compound_dict_test.cpp](test/parser/2_2_2_basic_exprs/compound_dict_test.cpp)）：`{; a : b}`
必须报错、`{; a}`/`{; a; b}` 这种前导 `;` 后面跟合法复合表达式的情况不受影响。

## `parse_brace_block` 全面复查：发现并修复"块内换行被外层括号续行规则吃掉"的 bug

用户要求对 `parse_brace_block` 再做一轮彻底审查。逐 token 手工推演了 50+ 个对抗性输入
（空/纯分隔符/前导 `;`/前导 `**`/各种残缺键值对/字典与复合表达式的边界组合/嵌套/EOF 截断），
其中发现一个真 bug：

**bug：`{}` 的内部没有屏蔽外层括号的续行语境。** 复现：`f({a\nb})` 报错
"expected newline or ';' after expression"，而顶层的 `{a\nb}` 是合法的两语句复合表达式。
根因：解析块内第一条语句 `a` 的 Pratt 循环里，`skip_paren_newline()` 看到 `paren_depth_ == 1`
（来自 `f(` 的括号），把 `a` 和 `b` 之间的换行按"括号内续行"吃掉了，导致后续的
`check_expr_terminator()` 直接撞上 `b`。同理受害的还有函数体/类体（`parse_func`/`parse_class`
直接 `expect(LBRACE) + parse_exprs()`，没经过 `parse_brace_block`）：`f(func() {a\nb})` 一样误报错。
更隐蔽的是不报错的变体：`f({a\n+ b})` 当时被续行成 `Compound{a + b}`，而顶层 `{a\n+ b}` 是
`Compound{a, +b}`——同一段文本在括号内外解析出不同结果。

**规范依据**：SL.md 2.2.1 开头写明分隔规则"对于**一个块的内部**"适用，即按块递归；
`(x\n.func())` 的续行靠的是"表达式不完整→合并下一条待定表达式"这个外层机制。`{}` 一旦开启一个块，
其内部的换行就重新是语句分隔符，不该被外层括号的续行规则穿透。所以这是实现 bug，不是规范空白，
SL.md 无需改动。

**修法**：进入 `{` 时把 `paren_depth_` 暂存到局部变量并清零，消耗完 `}` 后恢复
（error 路径不恢复——Parser 报错即整体废弃，全项目既有设计）。三个入口都改了：
- `parse_brace_block`：拆成薄壳（存/清/恢复 `paren_depth_`）+ `finish_brace_block`
  （原函数体，命名跟随 `finish_call`/`finish_class_bases` 的"起始符已消耗"惯例）；
- `parse_func` 函数体、`parse_class` 类体：`expect(LBRACE)` 后同样暂存清零、`parse_exprs()`
  完恢复。
这个修法同时保证了 `}` 之后回到外层语境：`f({a; b}\n.c)` 里 `}` 后面的换行仍按括号规则续行成
`Attr(Compound, c)`（有测试锁定），而顶层 `{a; b}\n.c` 照旧报错（SL.md 2.2.1 的 `x\n.func()` 规则）。

**复查中确认正确、无需改动的行为**（都有测试锁定）：
- `{;}`/`{;;}`/`{\n;\n}` → 空复合表达式；`{a;}`/`{a\n}` → 单语句复合表达式；
- `{a, b}` 报错（SL 没有集合字面量，也不是合法复合表达式）；
- 字典项分隔只认逗号：`{k: v; k2: v2}`、`{k: v\nk2: v2}`、`{**d; x}` 都报错;
- 残缺键值对 `{k:}`/`{: v}`/`{k: v,,}` 都报错；
- `{**\nd}` 合法（`parse_non_op` 统一跳过前导换行）；
- `{k\n: v}` 判成字典的 `check_over_newline` 逻辑在括号内外行为一致（新增括号内版本的测试）。

**观察到但判定为"语法层放行、语义层校验"、不算 bug 的**：`{**d + x}` 会解析成
key=`OpBinary(DoubleStar(d), x)`、val=nullptr 的字典项——`**` 在 `parse_non_op` 里操作数按
单目优先级 140 解析，后续更低优先级的二元运算符会把整个 DoubleStar 节点当左操作数包进去。
"val 为空的项 key 必须是 DoubleStar 节点"这类形状校验按项目分层惯例归语义层，与调用实参里
`f(*args + x)` 的处理方式一致。
（此条结论后被推翻，见下面"字典展开项判定改为 AST 级"一节：`{**d + x}` 现在解析为复合表达式。）

## 消除"同一产物多出口构造"的短路径（short path）风格

用户点名批评了到处散落的提前返回特判（如 `finish_brace_block` 里空 `{}` 的专用出口），
认为"代码不统一 + 容易藏不易发觉的 bug"。同意，且有实证：最近两个 bug 全是特判路径孵出来的——

`consume_sep` 的特判分支。同一个产物在多个出口分头构造时，每条路径都是一块测试压不到的独立状态空间。

**整改原则**：合并"同一种产物多处构造"，保留"产物本质不同"的分叉（字典 vs 复合表达式、

1. `finish_brace_block`：原来空 `{}`、前导 `;`、带 first 三条路各自构造 `AstNodeCompound`
   （共 3 个出口），现在统一为一条收尾路径（`exprs` 可能为空、可能已含 first，最后统一
   `parse_exprs()` + `expect('}')` + 构造）。判别条件反转成"既不是 `}` 也不是 `;` 才需要做
   字典判别"——`;` 只 check 不消耗的关键信号语义保留（有注释+测试锁定）。字典分支抽成
   `finish_dict(start_pos, first, is_first_doublestar)`，两个函数各自扁平。
2. `parse_if`：else 分支原来提前 return（`AstNodeIf` 构造写了两遍），改为 `else_expr` 局部变量
   默认 nullptr、单一构造点。
3. `parse_try`：finally 同理，`finally_expr` 变量 + 单一构造点。
4. `parse_return`：裸 return 特判原来两处构造 `AstNodeReturn`，改为 `bare ? nullptr : parse_expr()`
   单一构造点。
5. `parse_decorator`：func/class 两个分支重复了 10 行一模一样的 decorators 向量搬运代码，
   合并成一个 `if (func || class)` 块，只在最后一步三元分派给 `parse_func`/`parse_class`。

## 字典展开项判定改为 AST 级：`{(**d)}` 是字典（语言设计决定）

用户发现设计歧义：`{(**d)}` 被解析成复合表达式，因为字典判别看的是第一个 **token** 是不是 `**`，
而 `(**d)` 的第一个 token 是 `(`。用户直觉认为应该是字典。讨论后同意，论据：

1. **分组括号在 SL 里处处透明**：`parse_paren_or_tuple` 对 `(x)`（单元素、无逗号）直接解包返回
   内部节点，所以 `f((**d))` 与 `f(**d)` 的 AST 本来就完全相同、`[(*a)]` 与 `[*a]` 也相同。
   字典的 token 级判别是全语言唯一一处"括号不透明"，是不一致而非原则。
2. **token 级区分在下游不可执行**：正因为分组解包，`(**d)` 与 `**d` 产出的 AST 一模一样，
   语义层根本无法区分两者——想学 Python 把 `(**d)` 判非法只能在 parser 里做 token 记账，
   而调用/列表/索引各处都没做、也不该做。SL.md 3.6 的"`**expr` 只能出现在字典字面量、函数调用中"
   按 AST 层解读（展开**节点**只能作为字典/调用的直接项）才是可实施的规则，实施就是一个父槽检查。
3. 顺带消除怪状：原来 `{k: v, (**d)}` 是解析错误而 `f((**d))` 合法；原来 `{**d + x}` 被解析成
   "key 为二元加法、val 为空"的畸形字典项（见上一节被推翻的观察）。

**实现**：`finish_brace_block` 删掉 `is_first_doublestar` token 标志，改为解析完第一个表达式后
`dynamic_cast<AstNodeDoubleStar *>` 判 AST 根；`finish_dict` 去掉 bool 形参，第一项和后续项统一
走一个 `emplace_item` lambda（根是 DoubleStar → 展开项无 value；否则 expect ':' 后解析 value），
这也顺带消除了第一项/后续项两套并行代码。**行为变化**：
- `{(**d)}`/`{((**d))}`/`{k: v, (**d2)}` → 字典，AST 与不带括号的完全相同（新增测试锁定，
  包括与 `f((**d)) == f(**d)` 的一致性对照）；
- `{**d + x}` → 复合表达式（根是 OpBinary 不是展开节点；其中的展开节点位于非法位置，
  归语义层按 3.6 拒绝）；`{k: v, **d + x}` → 解析报错（比原来"畸形字典项"更早暴露）；
- `{(**d): v}` 与 `{**d: v}` 一样报错（展开项不能带 value）。

**SL.md 同步**：2.2.2 判别规则措辞改为"第一个表达式本身是 `**` 展开项（分组括号不影响判定）"；
3.6 加注说明位置判定按表达式本身而非书写形式（`(expr)` 与 `expr` 是同一个表达式），
并给出 `{(**d)}` ≡ `{**d}`、`**d + x` 中的展开不在合法位置两个例子。

`.ai/run_test.bat` 验证：Lexer 133 + Parser 265 全部通过。

## 补齐标准：展开/装饰器的结合力、分组（冗余括号）的定义与透明性、装饰器求值顺序

用户指出：`*`/`**` 展开和装饰器 `@` 在语义上成了"变相的运算符"，但它们的优先级、装饰器求值顺序、
"冗余括号"的定义与完全透明性在标准里都没写。定位共识：**语法结合层面像前缀运算符，但语义上不产生
独立可用的值、不可重载、只在特定父位置合法，所以不进 2.1.5 运算符表，改在各自章节写明结合规则**，
并在运算符表后加一条"这些不是运算符"的指路注。全部内容按 parser 实际行为核对后写入（不是拍脑袋定的，
是把既有实现行为升格为标准条文）：

1. **2.1.5**：条目 1 扩为分组的正式定义——单元素且无尾逗号的 `(expr)` 为分组（冗余括号），与 `expr`
   是完全同一个表达式，可任意嵌套，除改变结合顺序、参与 2.2.1 跨行合并外无任何效果，也不影响一切
   按"表达式本身"进行的判定（字典判别、展开位置判定）。表后加注：展开与 `@` 不是运算符、不可重载、
   不列入表中。
2. **3.6 加"结合力"注**：展开操作数按单目一档（140）解析——高于此档的（属性/调用/索引/`?`/`!`/幂）
   先结合进操作数，其余不结合。例：`*a.b` ≡ `*(a.b)`、`*f(x)` ≡ `*(f(x))`、`**d ** e` ≡ `**(d ** e)`、
   `**d + x` ≡ `(**d) + x`。对应实现：parse_non_op 里 Star/DoubleStar 的操作数用 parse_expr_pratt(140)，
   与一元 +/-/~ 完全同档。
3. **2.2.8 加注**：decorator 部分按正常优先级贪心解析（`@d(args) target` 的装饰器是 `d(args)` 整体）；
   被装饰的 `expr` 是 `@` 串之后的一整条表达式、结合得比一切运算符都松（`@d x = y` ≡ `d(x = y)`，
   已有测试锁定）；`@` 可连用，`@d1 @d2 expr` ≡ `d1(d2(expr))`。
4. **3.4.8**：补链式等价（`d1(d2(expr))` 以此类推）和求值顺序——由等价形式按 3.3 展开：先从前到后
   求各 decorator，再求 expr，最后由近及远逐层调用；并点明与 3.3 第 7/8 条（函数/类定义的前缀装饰器：
   "离 func 越远的越先求值"=同样的从前到后，调用同样由近及远）完全一致。这个"一致"验证过：
   `d1(d2(expr))` 按 3.3 规则 4.7（先 callee 后实参）展开正是 d1 → d2 → expr → 调 d2 → 调 d1。

测试：precedence_test.cpp 新增"展开操作数按 140 档解析"用例，把 3.6 结合力注里的四个例子逐个锁定
（`[*a.b]`、`[*f(x)]`、`{**d ** e}`（顺带覆盖 AST 级字典判定与幂的组合）、`*a + b`）。
装饰器的范围论断原本就有测试（`@dec x = 1`、链式包裹、带参装饰器），未重复添加。

## 用户重构 Parser.cpp 后复查：发现字典分支 `paren_depth_` 恢复时机错误的新 bug

用户自行重构了一版 Parser.cpp（函数改名、`parse_paren_or_tuple`/`finish_call` 等大量方法合并调整、

`f({k: v + w})`（`+w` 被续接进 value），而没有外层调用包裹的顶层 `{k: v\n+ w}` 正确报错——同一段

跟另外两个分支（空/`;'`、复合表达式）"整个块内容解析完才恢复"的既有惯例保持一致。
补了回归测试（[compound_dict_test.cpp](test/parser/2_2_2_basic_exprs/compound_dict_test.cpp)）：
`f({k: v\n+ w})` 必须报错。

的双重检查写法、`finish_func_params`/`finish_func_captures` 把原本独立的 `parse_func_param`/
`parse_func_capture` 方法内联成局部 lambda、`parse_chain_compare`/`parse_chain_is` 纯改名）逐个

用户要求做三件统一码风的事，外加确认上一轮我提的两个疑问。逐项记录：

**1. 确定的 `advance()` 全改 `expect()`**：用户确认这是刻意的（对应我上一轮问的"check+expect 双重检查
是不是规矩"），理由是防止"以为当前 token 一定是 X、实际因为别处 bug 不是"这种情况被静默吃掉、变成远离
真正错误位置的下游报错；一次 enum 比较的性能损耗可忽略。全文逐个 `advance()` 调用点过了一遍，区分
"类型在该调用点唯一确定"（换成 `expect(X)`，约 30 处，覆盖 `parse_non_op` 的字面量/标识符/`*`/`**`/
`not`/`break`/`continue` 分支、`$`/`:`/`;`/`@`/`is`/`,`/`&`/`=`/`(`/`)`/`[`/`]` 等各处的确定消耗）
和"类型是几选一"（保留裸 `advance()`，只有 3 处：Pratt 循环里消耗任意中缀运算符、`parse_cond` 消耗
11 种复合赋值运算符之一、字面量解析里 `+`/`-`/`~` 三个 case 共用一段代码）。`expect()`/`skip_newline()`
等自身内部的 `advance()` 是最底层原语，不套用此规则（套了就是无意义的自我调用）。记进了
[[parser-prefer-expect]]。

**2. `finish_*` 系列的 `paren_depth_` 约定统一**：整改前 `finish_call`/`finish_index` 是"调用方在调用前
`paren_depth_++`、函数自己只减不增"，`finish_func_params`/`finish_func_captures` 是"函数自己全权管理"，
两种写法混用；收尾顺序也是约一半"先减后消耗收尾括号"、一半"先消耗后减"（后者是本轮才发现的额外不一致，
原来以为只有前一半需要统一）。统一成：**起始括号永远由调用方消耗，`paren_depth_` 的增减完全由
`finish_*` 函数自己管理，收尾永远是"先 `expect(close)` 再 `paren_depth_--`"**（跟开头"先消耗起始括号
再 `++`"对称）。为此把 `finish_call`/`finish_index` 改成自己 `paren_depth_++`，`parse_expr_pratt`
里两处调用它们之前的 `paren_depth_++` 删掉；把 `finish_func_params`、`parse_try` 的异常列表、`parse_if`/
`parse_while` 的 cond、`parse_for` 两处收尾的"先减后消耗"顺序全部倒过来。`finish_dict` 保持例外
（`{}` 的深度由 `parse_brace` 整体管理，是"开启全新语句语境"而非"多一层括号"的不同机制，见前面
`parse_brace` 那次修 bug 的记录），不碰 `paren_depth_`。两种顺序在行为上完全等价（`expect()` 抛异常时
Parser 整体废弃，不会有代码在"减了但还没消耗"或反过来的窗口期里读到 `paren_depth_`），纯粹是风格选择。
Parser.h 里这几个 `finish_*` 的文档注释同步改成统一措辞。记进了 [[parser-paren-depth-convention]]。

**3. `parse_chain_compare`/`parse_chain_is`/`finish_dict` 要不要内联成局部 lambda**：上一轮我拿不准
这仨该不该跟 `parse_func_param`/`parse_func_capture` 一样被"类成员 vs 局部 lambda"的标尺收编，用户说
这是他自己也没想清楚的偶然情况，让我自己判断。结论：**继续保留成独立方法，不内联**。理由：这仨体量都
不小（带自己的局部状态、循环），且都对应 SL.md 里明确成节的语法概念（链式比较、链式 `is`、字典字面量），
单凭这点就够格在类的"词汇表"里占一行，不需要为了机械贯彻"单调用点就内联"而牺牲 `parse_expr_pratt`/
`parse_brace` 这两个全文件最核心的调度函数的精简——把 30~40 行的 lambda 塞进本就是全文件最复杂函数的
函数体，只会让最需要保持清晰的地方变得更难读。这个判断也补进了 [[parser-member-vs-lambda]]。

**4.（第一次尝试，未完成）** skip_newline 等周围的空行是否正确表达"先做事再 skip"还是"先 skip 再做事"
——第一次尝试是"从已有空行反推规律"，没能归纳出自洽的规则，按用户"没听懂就先不干"原话没动，留给下次。

## 第二次尝试：skip_* 空行——从语义反推分组，而不是从已有空行反推规律

用户纠正了第一次的方法论错误："让你根据 skip 和周围语句关系、逻辑总结它应该跟前边是一组还是跟后边
一组，然后来修改空行，而不是根据已有空行总结规律"，并提示"可能存在某些多余的 skip 导致你不好总结规律，
如果确信某个 skip 多余，可以删掉"。

**结论（不是猜的，是从 skip_* 的唯一职责推出来的）**：`skip_newline`/`skip_paren_newline`/
`skip_terminator` 唯一的作用是"清掉分隔符噪音，让**接下来**的位置敏感操作（`check`/`peek`/解析调用）
看到干净的输入"——它对"前面已经发生的事"没有任何影响，也不为前面的事"收尾"。所以结构上，一个 skip 调用
**永远只跟它后面的东西是一组，从不跟前面是一组**。由此得到一条可机械核查的规则：**一个 skip 调用和它
后面紧跟着的、真正读取当前位置的语句之间不该有空行**（哪怕文本上紧跟着的是一行说明性注释或者一行不碰
`pos_` 的纯声明，也算"紧跟"，因为注释/声明本身不产生分隔）。但如果紧跟着的是一个**有份量的独立单元**
（比如一整个 lambda 定义、一段跨多行的结构体定义）——这种情况下这个单元本身值得单独成段，跟 skip 之间
留不留空行是另一个问题，不套用这条规则（唯一一处：`parse_for` 消耗 `(` 之后的 `skip_newline()`，后面
跟着 `parse_slot` 这个 lambda 的定义，保留了空行）。skip 前面要不要留空行，是"这一段跟上一段是不是同一
逻辑步骤"的独立问题，这条规则不管。

**验证方法**：对每个 skip 调用，从它出发反向追问"到达这里的所有代码路径，是不是都保证 `pos_` 已经处于
无分隔符状态"——如果是（不管是靠"刚执行完另一个 skip，中间只有纯读取/纯声明"，还是靠调用点单一且唯一
调用路径也是如此），这个 skip 就是死代码，删掉；如果只是**部分**路径冗余（比如 `for`/`while` 里
`if (collect) expect($); skip_newline();`，`collect` 为假时这个 skip 确实什么都不用跳，但为真时是
真的在跳 `$` 后面的换行），那就不是死代码，两种路径都要能应付，必须留着。

**结果——删掉了 3 处真正的死代码**（全部验证过：删掉后所有测试仍然通过）：
1. `finish_dict` 收尾前多余的 `skip_newline()`：紧跟在它前面的 `while` 循环每一条退出路径（条件为假、
   或遇到尾逗号 `break`）都已经紧跟在另一次 `skip_newline()` 之后，pos_ 必然已经干净，这个是纯粹的
   历史遗留——`finish_dict` 是手写的逗号循环（因为要处理 `**` 展开项的特判，没法直接复用
   `finish_comma_batch`），复用 `finish_comma_batch` 的其它调用点从来没有这个问题（`finish_comma_batch`
   自己的循环收尾时从不额外补一次 `skip_newline()`）。
2. `finish_func_params` 里 `parse_one_param` 这个局部 lambda 开头的 `skip_newline()`：它是私有 lambda，
   唯一调用路径是 `finish_comma_batch` 的 `parse_item` 回调，而 `finish_comma_batch` 自己在每次调用
   `parse_item()` 之前都已经 `skip_newline()` 过（无论是循环外的首次调用还是循环内的后续调用）。
3. `finish_func_captures` 里 `parse_one_capture` 同理。

（`parse_non_op` 开头的 `skip_newline()` 一开始怀疑也是这个模式——它也经常在另一个 `skip_newline()`
刚跑完之后被调用——但排查出至少一条真实依赖它的路径：`parse_if`/`parse_while` 的 `expect(LPAREN);
paren_depth_++; parse_expr_as_cond();` 之间没有插入任何 skip，`if (\ncond) ...` 这种写法就是靠
`parse_non_op` 自己这个"防御性"的开头换行处理撑住的。`parse_non_op` 调用点太多、太分散，不像
`parse_one_param`/`parse_one_capture` 这种私有单一调用点的 lambda 能证明"所有路径都冗余"，所以留着。）

**空行调整**（约 16 处，逐一验证紧跟其后的是不是真正的位置读取操作）：`parse_exprs`/`parse_expr_pratt`/
`parse_non_op`/`parse_expr_as_cond`/`parse_brace`/`parse_for`（3 处）/`parse_while`（2 处）/`parse_func`
（2 处）/`parse_class`（1 处）/`finish_dict`（1 处，随死代码删除一起处理）/`finish_func_params`
（1 处）/`finish_func_captures`（1 处）——全部去掉了 skip 和它真正服务的下一条语句之间的空行；
`parse_for` 里那处紧跟 lambda 定义的、以及各函数里"skip 是某个可选 if 块内最后一条语句、真正的下一步
在块外"的情况（这种 skip 的"下一步"隔着一个 `}` 和一段新段落的开头，不适合机械去掉空行）保持不变。

`.ai/run_test.bat` 验证：Lexer 133 + Parser 267 全部通过，行为不变（纯删除死代码 + 空行调整）。

## `expect(括号)` 与 `paren_depth_` 合并成一行；finish_call/finish_index 收编开括号消耗

用户要求三件事：(1) 确认所有 `expect(括号)` 和 `paren_depth_++/--` 的相对顺序一致后，合并成一行
`expect(X), paren_depth_++; // 消耗 'x'`（逗号表达式）；(2) 所有没有 `// 消耗 'xxx'` 风格注释的
`advance()`/`expect()` 补上（几选一的场景枚举出来，范围很大/不确定的不写）；(3) `finish_*` 系列的
开括号消耗和 `paren_depth_++` 尽量放在一起，允许调整调用处结构，`finish_dict` 这种确实没法放的算例外。

**(1) 顺序检查**：逐个核对后确认——开括号侧"先 `expect` 消耗、再 `++`"、闭括号侧"先 `expect` 消耗、
再 `--`"这个顺序在全文所有已经共处一处的场景里都是一致的（这也是上一轮"统一 paren_depth_ 约定"那次顺带
定下来的），可以放心合并。合并后用逗号表达式写成一行，`expect()` 的返回值本来就没被用过（不是
`[[nodiscard]]`），丢弃合法；这个写法本来就是全文一直在用的既有习惯（`return expect(X), make_unique<...>();`
这类 return 语句早就在用逗号表达式丢弃 `expect`/`advance` 的返回值）。

**(2) 补注释**：把全文每一个 `expect()`/`advance()` 调用点过了一遍，区分三档——单一确定类型补
`// 消耗 'x'`（字面量类的 token 因为没有固定符号，改用描述性文字，比如"消耗整数字面量"/"消耗标识符"）；
小范围几选一的枚举出来（`+`/`-`/`~` 三选一、`<`/`<=`/`>`/`>=`/`==`/`!=` 六选一）；范围很大或不确定的
不加（Pratt 循环里消耗任意中缀运算符——跨度几乎是整张运算符表；`parse_expr_as_cond` 里消耗 12 种
复合赋值运算符之一——判定成"太多不逐个列"，只留一句"允许裸写复合赋值"的既有注释）。`expect()`/
`skip_newline()`/`skip_paren_newline()`/`skip_terminator()` 自己内部的 `advance()` 是最底层原语，
不套用这条规则。

**(3) `finish_*` 收编开括号消耗**：`finish_func_params`/`finish_func_captures` 直接把调用处原本的
`expect(LPAREN)`/`expect(LBRACKET)` 挪进函数体自己开头，跟 `paren_depth_++` 合并成一行——这两个的
调用处本来就没有更复杂的分支要处理，挪动很直接。`finish_call`/`finish_index` 麻烦一些：它们的开括号
原来是在 `parse_expr_pratt` 的 Pratt 循环里，被"消耗运算符"那行通用 `advance()` 顺带吃掉的（这行
`advance()` 对赋值/复合赋值/`?`/`!`/`(`/`[`/`.`/比较/`is`/普通二元运算符全部通用，为的是共享同一次
消耗）。解法是把 `op == LPAREN`/`op == LBRACKET` 这两个分支挪到通用 `advance()` **之前**判断——
命中就直接把 `left`/`start_pos` 交给 `finish_call`/`finish_index`，自己去 `expect` 开括号、算自己的
`paren_pos`/`bracket_pos`（原来是调用方通过 `op_pos` 传进去的，现在改成被调用方自己 `peek()` 一次），
不再走后面统一的 `advance()`；其余分支不受影响，仍然共享同一次 `advance()`。这样 `finish_call`/
`finish_index` 的函数签名也简化了（去掉了 `paren_pos`/`bracket_pos` 参数）。副作用是 Pratt 循环里
原本靠结构化绑定 `[op, op_row, op_col, lexeme]` 从 `peek()` 拿运算符信息的写法，改成先用 `peek().type`
单独拿 `op`（用于判断分支和绑定力），再在通用 `advance()` 处直接从它的返回值 `const Token&` 里取
`.row`/`.col`（`lexeme` 全程没被下面任何分支用到，顺手也不再绑定）。

**唯一保留的例外仍是 `finish_dict`**：它的 `'{'` 从来不归它自己管（`parse_brace` 整体存/清/复原
`paren_depth_`，跟"多一层括号嵌套"是不同的机制，前面 bug 修复那次已经解释过），所以 `expect(RBRACE)`
没有配对的 `paren_depth_--` 可合并，在函数里补了一句注释点明这是"为数不多的例外之一"。

**一段过程中的插曲，跟这次改动本身无关**：中途 `.ai/run_test.bat` 意外报过两次跟本次修改完全无关的
失败——一次是 `executor/Executor.cpp` 的 `-Werror=range-loop-construct`（跟 Parser.cpp 无关，Parser.cpp
两个编译单元当时都已经编译成功）；一次是重新单独构建 `SL_Cpp_Parser_Tests` 目标时链接报错，但 `ninja`
在这个 Bash 环境下没能把真实的链接器诊断文本传回来（只看到被截断的命令行和"subcommand failed"，手动
重放链接命令时的输出也是乱码，怀疑是这个环境下调用链接器时的流捕获问题，不是新增的稳定故障）——重新
跑一次完整的 `.ai/run_test.bat` 后两个问题都消失了，判断是构建目录里的过期/半失败中间状态，不是代码
本身的问题。

`.ai/run_test.bat` 最终验证：Lexer 133 + Parser 267 全部通过。

## 用户自己重构完全文件后，唯独 `parse_for` 觉得"写法怪、容易藏 bug"，重新优化

用户自己把其余所有函数都重构完了（`parse_brace`/`parse_func`/`parse_class` 的 `paren_depth_` 恢复都
合并进了 `expect(RBRACE)` 那一行；`parse_decorator` 从"struct + 一个 vector"改成了两个平行 vector +
`std::views::zip`；`finish_dict` 收尾也不用再单独判 `paren_depth_` 了）。唯独 `parse_for` 他没动，
点名要求重新优化。

**先确认了问题出在哪**：全文唯一一处直接管 `tokens_[pos_ - 1]`（绕过 `peek`/`check` 这套统一的 token
访问抽象、裸手指向数组）的地方，就是 `consume_sep` 里那句 `tokens_[pos_ - 1].row == peek().row`。这是
之前那次 `for(a\nb\n)` bug 修复时加的，用来回溯判断"两个槽之间是不是真的隔着换行"——因为 `parse_slot`
内部走的是 `parse_expr`/`parse_expr_as_cond`，这两者最终都会进 `parse_expr_pratt` 的 Pratt 循环，循环
每轮开头无条件 `skip_paren_newline()`（只要 `paren_depth_ > 0` 就跳换行，不管跳完之后到底要不要继续），
所以槽末尾的换行经常在 `consume_sep` 看到之前就已经被内层循环"顺手"吃掉了，直接 `check(NEWLINE)` 会
判不出来。

**认真考虑过从根上修（让 Pratt 循环变成"先探路、确定要继续了再吃换行"的懒惰版本，这样 `consume_sep`
就能直接 `check(NEWLINE)` 了），但放弃了**，原因：`parse_chain_compare`/`parse_chain_is` 各自也有一份
一模一样的"无条件 `skip_paren_newline()` 再判断要不要继续"循环——真要从根上修，这三处得一起改，牵动的
是全文件用得最频繁的核心解析路径，风险和改动范围都远超"优化一下 `parse_for`"这个请求本身；而且就算
现在全改对了，以后随便谁新加一个类似的循环、忘了套这个"懒惰"套路，同样的 bug 还会长出来——这个坑不是
靠改一次就能填死的，靠调用方（`consume_sep`）自己不依赖"换行有没有被吃掉"这个假设反而更稳：不管换行
是被哪层循环、什么时候吃掉的，"上一个已消耗 token"和"当前 token"的行号只要不一样，就说明中间确实隔着
至少一次真实换行——这个结论不依赖"换行具体在哪一步被吃的"，天然就对所有内层循环的吃换行行为免疫。
所以维持现在这个回溯比较行号的策略，但改善"表达方式"：

1. 把 `tokens_[pos_ - 1].row == peek().row` 从 `consume_sep` 内部的裸表达式，提取成一个新的私有方法
   `bool Parser::separated_by_newline() const`，跟 `check_over_newline` 放在一起（両者算一对——一个
   往前看跳过换行，一个往回看有没有跨过换行），在方法自己的注释里把"为什么不能直接 check(NEWLINE)"
   这段解释讲清楚，`consume_sep` 里只留一句指过去的引用，不用重复贴一遍。这样裸数组下标访问只出现在
   一个专门、有名字、有文档的地方，不再是埋在大 lambda 里的一行不明所以的表达式。
2. 顺手清理了 `parse_for` 里两处编号注释的"1. / 2. / 3."——"1."那处之前已经被去掉了（用户自己重构时
   删的），只剩"2."/"3."孤零零地跳号，看着不完整；这次统一去掉编号，改成跟文件里其它函数一致的自然
   语言过渡（"否则为步进模式：..."），不再假装这是一份编号列表。

`parse_slot`/`consume_sep` 两个内部 lambda 的其余部分（结构、参数、控制流）没有发现需要改的地方——
`parse_slot` 已经很薄；`consume_sep` 的两个报错分支各自对应 SL.md 2.2.5.2 两条不同的规则，不是重复。

`.ai/run_test.bat` 验证：Lexer 133 + Parser 267 全部通过，行为不变（纯提取 + 注释/编号整理）。

## 加强测试覆盖：报错消息/位置的精确断言 + 语法组合场景

用户反馈测试强度不够：一是"各种语法的组合没有大面积测"，二是"报错定位、错误信息是否表达清晰"没有

**写这批测试时踩了一个坑，记一下根因**：一开始所有从 `parse_json(...)` 拿到整棵树后要多次 `["field"]`
取值的地方，都写成了 `const auto root{parse_json(source)};`（花括号初始化）。结果运行时
`root["type"]`/`root["items"]` 这类取值全部抛 `[json.exception.type_error.305] cannot use operator[]
with a string argument with array`——`root` 本身变成了"一个只有 1 个元素的数组，元素是本该长这样的
对象"。

根因：`nlohmann::json` 同时有"拷贝/转换构造函数"和`initializer_list<json>` 构造函数，`T x{expr};` 这
种花括号初始化语法在两者都可行时**优先选 `initializer_list` 版本**——`{expr}` 被当成"一个元素的列表"，
再套用 nlohmann 那条"列表里每一项是不是 `[字符串, 值]` 这样的二元数组"的启发式来判断整体是数组还是
对象：这里列表只有 1 项（`expr` 本身，一个完整的 json 对象），它不满足"自己是二元数组"，于是整个列表被
判成数组，`root` 就变成了 `[expr]`。用 `const auto root = parse_json(source);`（拷贝初始化，不走花括号）
就没这个问题——这条坑其实 `literals_test.cpp`/`func_test.cpp` 等文件里早就有注释提醒过（"注意：这里
必须用 = 而不是 auto j{...}"），但那些注释只覆盖了"expected 字面量"场景，这次在"从 `parse_json` 返回值
本身取值"这个新场景又踩了一次——统一起见，往后任何 `const auto x = parse_json(...);` 都必须用 `=`，
只有绑定"已存在对象的子字段"的 `const auto &x{...}`（引用，不走构造函数）不受影响，可以放心用 `{}`。

`.ai/run_test.bat` 最终验证：Lexer 133 + Parser 281（新增 14 个用例，全部通过）。

## 架构讨论：编译期 C++ 异常 vs SL 运行时异常对象；整条前端流水线跟 VM 的边界在哪

用户发现一个容易被忽略的问题：现在 `builtins/classes/exceptions/SyntaxError.h` 里的 `SyntaxError`
（`: public SLException : public std::runtime_error`，纯 C++ 异常）和 SL.md 4.2.23 里文档化的、
将来暴露给 SL 用户代码的异常类 `SyntaxError`（`BaseException > Exception > SyntaxError`），只是碰巧
重名，现阶段完全不是同一个东西——`SlObject`（`builtins/object/SlObject.h`）目前还是个空壳，没有任何
字段、没有类系统，两者没有任何继承/构造关系。

**结论：这不是需要二选一的问题，是本来就该分层，SL.md 自己已经把这件事定了性**：

- 1184 行：`SyntaxError` 在编译期抛出；其他所有异常均在运行时抛出。
- 1186 行：该编译期可能包含运行时，因为可以使用 `eval` 函数动态编译。
- 632 行：`try` 的 `finally` 段里检测不出来的违规（比如来自 `eval` 现场编译出的代码）"由这层运行时
  拦截兜底，同样抛出 `SyntaxError`"。

也就是说：**解析器（Lexer/Parser/Analyzer）保持"很静态"是故意的、正确的设计**——纯文本→AST 的变换，
不需要一个跑起来的 VM 才能工作，`Executor.cpp` 现在的样子（三段各自 `try { ... } catch (SLException&)
{ 打印到 stderr; return 1; }`，压根没有第 4 步"执行"）正好体现了这一点。`builtins/classes/exceptions/
*.h` 这一整套的定位就是"前端自己内部用的 C++ 报错信号/栈展开载体"，类比 CPython 的 `PyErr_SyntaxError`
这层 C API 跟 Python 层真正暴露给用户代码的 `SyntaxError` 类——同名、同概念、不同层，本来就不该是同一个
东西。

唯一必须把这两层打通的地方是 **`eval(code)`**（4.1.15）：它是一个在已经在跑的 SL 代码里调用的内置
函数，内部会现场再跑一遍词法+语法（可能还有语义分析）。这次现场编译产生的语法错误，必须变成一个能被
SL 层 `except (SyntaxError)` 正常捕获、正常传播的**运行时异常对象**，不能是从 C++ 里裸传上来的东西。
设计上：`eval()` 的实现内部 `catch` 住这些 C++ 异常，用其中的消息/位置信息构造出真正的 SL 异常对象
（到时候基于 `SlObject`/SL 类系统），再通过 Executor 正常的 `raise` 传播路径抛出去——和其他内置函数
（比如将来 `open()` 抛 `FileNotFoundError`）走同一条路，不能让裸的 C++ 异常类型直接泄漏到 `except`
的类型匹配逻辑里。程序最外层的三段 `try/catch` 保持现状：直接打印到 stderr、非零退出，因为那个时刻
压根没有"正在跑的 SL 程序"能去 catch 它。这个"两栖"模式不止 `SyntaxError` 一个——`EncodingError`/
`FileNotFoundError` 以后也一样：`Lexer` 读文件编码错了是编译期 C++ 异常，但 SL.md 4.3.3 也把 `IOError`
一类列进了运行时异常表，将来 `open()` 在运行时抛同名异常时，也得走同一座桥。

**整条前端流水线跟 VM 的边界**：`SL some_code_file.sl` 的完整流程应该是 Lexer → Parser → Analyzer
（内部又分 `SyntaxChecker` 静态语义检查 + `LiteralFolder` 字面量折叠）全部跑完、确认没有编译期错误之后，
才轮到执行/VM 这一步接手——这几步全程不需要 `SlObject`/类系统/VM 存在，纯粹是 C++ 数据结构上的变换，
跟"字节码解释 vs. 直接对 AST 树遍历执行"这个后续选择完全正交、互不影响。

**字面量折叠（`LiteralFolder`/`StaticEvaler`）必须用一个独立的、跟真正 VM 无关的超小型静态求值器**，
不是偷懒抄近路，是 SL.md 1188 行本身划定的范围逼出来的：折叠"不做常量传播，一掺变量就不折叠"，也就是
`LiteralFolder` 只会把纯字面量、不含任何标识符引用/函数调用的闭合子表达式交给 `StaticEvaler` 求值（
`doc` 字符串的折叠规则 668 行也是同一条约束的具体应用：必须是字符串字面量或其编译期可折叠的组合，不
允许引用变量）。既然定义域天生就排除了名字查找、函数调用、任何副作用，`StaticEvaler` 就完全不需要
`SlObject`/方法分派/继承查找这些真正 VM 才需要的机制，可以直接在字面量对应的原始值（大整数、浮点、
`std::u32string`、bool 等）上做一个纯递归的 AST 求值，比未来的真 VM 小得多、也不会跟 VM 的实现进度
产生依赖关系——这也是为什么 `analyzer/literal_folder/` 现在能先立好 `LiteralFolder`/`StaticEvaler`
两个空壳类，而不用等 `SlObject`/VM 先写完。

**尚未决定、留白**：VM 具体是"编译 AST 到字节码再跑字节码解释器"还是"直接对 AST 做树遍历执行"，现在
代码里（`Executor.h`/`SlObject.h` 都还是空壳，没有 `bytecode`/`vm` 之类的目录或文件）完全没有定论，
两种路线都跟前面这几条结论不冲突，等真正要写执行这一步时再定。

## 类型注解设计：从 `Self` 到彻底否决，再到发现"类没有捕获机制"这个更底层的漏洞

用户发现两个语言设计层面的问题：1）没有类似泛型的东西，没法表达"返回类型跟某个参数类型相同"；
2）类型注解在类建立时求值，此刻类自己还没建好，连自己都引用不了。讨论过程反复推翻了好几版方案，
记一下每一版为什么被否决，免得以后又想回去重新试一遍。

**方案一（已否决）：引入内置单例 `Self`，在类体收集属性那一步（3.4.7 原第 4 步）顺手把方法注解里的
`Self` 替换成刚建好的类对象本身。** 被用户指出"凭空给类建立过程加了一步"，不优雅——而且这样解出来的
`Self` 是在**基类自己**建立那一刻冻死的具体值，子类继承这个方法时不会变成子类，协变根本做不到，等于
白白多绕一圈还没拿到协变这个好处。

**方案二（已否决）：`Self` 改成在方法调用时读"绑定给第一个参数的值"的类型。** 这版被指出是纯粹的
后门——类型检查这一层本来只处理"每个已声明形参对应的实参值"，"第 0 个位置的实参就是被绑定的实例"
这个信息在 `MethodDescriptor.get(obj)`（3.9.1.2/764）那一层完成绑定后，往下传到类型检查这层时早就
丢了，想读出来必须专门开一条新通道；而且 SL 压根没有语法层面规定方法第一个形参必须叫 `self`、必须在
第几个位置，这条规则是我凭空加的。

**方案三（已否决）：用已经在设计的 `TypeVar` 顶替 `Self`**——`self: (T = TypeVar())`（注解表达式的
副作用顺手把 `T` 存成类体局部变量），`other: T`，`del T` 清理。这版复用的都是已经拍板的机制（注解
求值有副作用、`TypeVar` 按调用绑定、`del`），不用任何新概念，而且返回类型协变是白送的（查的是
`type(self 实际值)`，不是写死的类）。但用户用一个例子直接戳破：`MyInt.__op_add__("1", "2")` 这种
不通过实例、直接拿字符串当参数硬调的写法，检查竟然能通过——因为无约束的 `TypeVar` 第一次出现只负责
"记下基准"，从来没人验证过这个基准本身对不对，`self` 和 `other` 只是互相一致，压根没被锚定到 `MyInt`
这个具体类上。

**方案四（部分否决）：给 `TypeVar` 加 `bound` 参数，`self: (T = TypeVar(bound='MyInt'))`，`bound`
本身还是走字符串惰性求值那条路。** 这版技术上是对的（验证过能堵住上面那个洞），但用户指出这是在
"锚定到具体类"这件事上又多绕了一层——`TypeVar` 该管的只是"多个位置的类型要不要互相一致"，混进"这个
类型是不是某个特定类的实例"，职责不单一。

**方案五（已否决）：字符串注解惰性解析——推迟到第一次调用时按名字重新查找（先查定义帧、查不到/帧已
死退到全局帧），解析成功后永久覆盖回注解位置。** 技术上可行（期间还修过一次"定义帧一死就该 `NameError`
不能照抄引用捕获"的严重 bug），但用户复查后否决：这套"建立时求值"与"字符串则推迟到调用时按名字查找"
两套时机并存，本身就不统一；而且按名字查找在"变量是引用语义"的前提下不牢靠——名字随时可能被重新绑定，
查到的不保证还是"当初想指的那个类"。

**最终方案（采纳）：类型注解允许 `type | CompoundType | TypeVar`（正常参与类型检查）或 `str`
（纯标签，不参与任何类型检查，运行时等价于无注解，只是把字符串原样存起来给以后的静态分析工具/
`metadata` 模块用）。** `TypeVar` 保持不变，职责仍只是"多个位置类型互相一致"。真正需要自引用/
前向引用类型检查时，不再走注解机制，改为在函数体内手动 `isinstance` 检查（函数体在调用时才执行，
那时类早已建好、名字也已绑定，没有"建立时类还不存在"的问题），或者等拿到真实类型对象后手动改写
字符串元信息。`TypeVar.bound` 同步简化为只能是 `type | CompoundType`（不再支持字符串），因此也不再
需要 `TypeVar` 自己的"建立帧"。已写入 SL.md 3.4.6、4.2.24。

**这个过程中，`self: 'MyInt'` 到底该在哪一帧求值这个问题，牵出了一个远比"注解怎么写"更严重的漏洞**：
`class` 语法完全没有捕获列表（`func` 有 `[ALL_CAPTURE]`，`class` 没有），而 3.10.3 规定任何一帧对
未捕获的标识符"只涉及当前帧与全局帧，不查找帧栈中的其他帧"——也就是说类体本身、类体里任何方法的方法
体，只要不是全局名字，从语法层面上压根够不到外层函数的局部变量，不止字符串注解，普通代码也不行。这
使得"局部定义一个类"这个模式（比如工厂函数动态造一个绑定了配置的类）在当前设计下完全走不通。

**修法**：给 `class` 补上跟 `func` 完全一样的捕获列表语法（值捕获、引用捕获都要）。位置上没有照抄
`func` 的 `[CAPTURE](PARAMS)` 布局，放在 `class identifier(BaseClass1, ...)[ALL_CAPTURE]`——基类
之后——理由是 3.4.7 规定基类要在类体自己的帧建立**之前**、在外层帧里求值，而捕获是新帧建立之后才
处理的东西，文本顺序正好对应求值顺序；而且基类（继承，参与 MRO）和捕获（把外层的值/引用带进来）是
两个毫不相关的概念，紧挨着放容易让人错误联想成"跟 func 的 [捕获](形参) 一样是一对"，所以特意没有
沿用 func 那个视觉布局，还在 SL.md 里专门注明两者互不相关。已写进 2.2.7（语法）、3.3 第 8 条
（求值顺序）、3.4.7（类建立步骤，新增"处理 ALL_CAPTURE"一步，在帧建立之后、类体求值之前）、3.10.4
（捕获机制的表述从"函数建立时"泛化成"函数、类建立时"）。

**顺带做的一个化简（用户提出）**：3.10.4 原来的引用捕获是"把 (x, 定义帧) 记进引用捕获表"——每个
捕获的名字各自存一份帧引用，但一个函数/类只可能有一个定义帧，这么存是重复的。改成：**每个函数/类
建立时都无条件记住定义处所在的那一帧（下称"定义帧"），不管有没有捕获、有没有捕获列表，这是固定动作**；
引用捕获退化成只需要记一个**名字集合**，因为这些名字对应的定义帧永远是同一个，不用重复存。这个改动
不只是省了点存储——"定义帧"现在是一个正式命名、随时可复用的概念，前面讨论的"字符串注解该在哪一帧
求值"直接就是复用这同一份东西，不需要另外发明一套"记住封闭作用域"的机制。3.10.1 里"帧对象为什么可能
在弹出后还继续存在"那句也同步改成"只要还被某个定义帧引用持有（不要求有引用捕获）"。

**类体的引用捕获会不会变成类属性？——不会，而且这个结论不需要任何新规则，是已有规则的自然推论**：
3.4.7 的属性收集规则（760/770）只收集类体这一帧**局部字典 `_L`** 里剩下的变量；而 3.10.1（1050 行）
早就写明"`_L` 只包含...值捕获，不包括引用捕获"——引用捕获从定义上就不在 `_L` 里，属性收集这一步压根
看不到它，自然不会被收进去，不需要专门 `del`（也没法 `del` 出"类体自己的"这份，因为压根没有——对
引用捕获的名字做 `del`，按 3.10.4 的重定向规则，删的是**定义帧**里的那个变量，不是类体自己的局部
变量）。值捕获则完全相反：它就是类体的一个普通局部变量，不 `del` 就会被收集为类属性，跟自己在类体里
手写的其他局部变量没有任何区别——这个不对称（值捕获默认进属性、引用捕获永远不进）是两种捕获本身的
定义差异带出来的，不是额外加的特殊规则。

**类的引用捕获链式转发不会有死帧问题**：比如 `class Local[&count] { func increment[&count](self) {...} }`
这种链式转发，推演过不会碰到死帧问题——`increment` 的引用捕获集合是挂在 `increment` 这个函数对象
自己身上的元信息，不是挂在某个帧上；查找 `count` 时先看是否被类体自己的引用捕获集合转发，是的话
直接递归转到来源帧，类体自己这一帧死没死不参与判断，只有链条最终落地的那一帧死没死才决定成败。跟
3.10.5 里 `h[&n]` 嵌 `g[&n]` 嵌 `f` 那个例子原理一致。

（此前设计过一版"字符串注解惰性解析"，连带发现并修过"定义帧一死就该 NameError 不能照抄引用捕获"
的 bug；这版方案后来被整体否决，具体细节不再保留，见上面"方案五"。）

**收尾时复查发现的三处遗留问题，已修**：

1. `3.10.1` 里"帧对象为什么可能在弹出后还继续存在"那句在改"无条件定义帧"时被删掉了、没补上替换句——
   已补回：只要还被某个定义帧引用持有就会继续存在（不要求有引用捕获），跟 `3.10.4` 的表述对齐。
2. `4.2.24` `TypeVar.bound` 那句 `isinstance(bound, type | CompoundType ? )` 里的 `?` 不是没删干净

   type | CompoundType | TypeVar)` 的显式 `|` 写法保持一致，改写成了 `type | CompoundType | None`。
   顺带明确了 `bound` **不能是 `TypeVar`**：一致性检查是按调用时形参从前到后单趟扫描、"第一次出现
   定基准"的，`bound` 若指向另一个 `TypeVar`，其基准是否已确定就依赖两者在形参列表里的相对顺序，

   排查——跟 `Self` 那几版被否决的方案是同一类"看似能扩展、实际引入隐藏时序依赖"的坑，不值得为了这点
   表达力去冒这个险。
3. `3.3` 第 8 条（类定义求值顺序）原来写的是"先文档字符串、再基类"，比基类和捕获都早，但 `doc` 在

   这次给"捕获放在基类之后"的理由正是"文本顺序应该对应求值顺序"，`doc` 的位置就成了这条原则唯一的
   反例。已把 `doc` 挪到最后求值，跟基类之后、捕获之后的语法顺序对齐，也跟第 7 条（函数定义，`doc`
   本来就是最后求值）保持一致写法。这处改动不影响任何可观察行为——`doc` 被强制限定为字面量或编译期
   可折叠、不许引用变量（3.4.6/674 行），所以它相对基类/捕获求值的先后顺序本来就没有可观察差异，
   纯粹是为了文档本身的一致性、不让读者去猜"这处顺序是不是故意的"。

**顺带确认了一条没有写在 SL.md 里、但支撑"无条件定义帧"这个设计的关键原因**：每个帧都强引用着"它
自己所属的全局帧"（不是当前调用者的全局帧，是这个函数/类**定义时所在模块**的全局帧）；配合"每个

污染。如果只有"存在引用捕获"的函数才记定义帧，没有任何捕获的函数在跨模块调用时就会找错全局帧——所以
这不是可选的优化，是让"模块"这个概念本身能正确工作的必要前提。这条目前只存在于讨论过程里，SL.md 还
没有模块/`import` 相关的章节可以挂靠，等那部分设计展开时需要把这条也写进去。

## int 高精度：`numeric/BigInt`——手写还是引入库，以及几处容易出错的算法细节

在写字面量折叠器之前，先把 `int` 的高精度运算单独实现成一个跟上下文/运行环境完全无关的类型
`numeric/BigInt`——静态求值器和以后的 VM（运行时 `int` 的实现）都用同一份，不属于 parser/analyzer/
executor 中任何一层，所以放在项目顶层新开的 `numeric/` 目录下，不是塞进 `utils/`（`utils/` 现在放的
是字符串/文件这类自由函数式的工具，`BigInt` 是一个有完整行为的值类型，性质不一样）。

**手写还是引入库（Boost.Multiprecision 的 `cpp_int`、GMP）**：选了手写。理由：
1. 用户刚为了 Clang 工具链的折腾把 GCC 换掉，这时候再引入 GMP（C 库，需要独立构建/链接，Windows 下
   历来不省心）风险很不划算；Boost.Multiprecision 虽然 `cpp_int` 默认后端是纯头文件、不需要链接，
   但 fetch 下来还牵连好几个 Boost 子库（config/core/type_traits 等），CMake 接线比现在 `nlohmann_json`/
   `doctest` 这种单仓库 FetchContent 复杂不少，而且 Boost 头文件在 `-Wall -Wextra -pedantic -Werror`
   这套严格编译选项下历来容易冒出各种警告，属于新引入一个不确定因素。
2. 需求本身写在这次的设计里就是"暂时按内存充足、无限位数设计"——不是要一个渐进最优实现，用不着
   为了这个去扛一个通用大型库。
3. 这个项目到目前为止唯一的第三方依赖（`nlohmann_json`、`doctest`）都只服务于测试/AST 序列化，
   不在"语言核心语义"这条路径上；`int` 的四则运算恰恰是语言核心语义本身，不引入额外依赖、完全自己
   掌握实现，风险和收益的账算下来更划算。

**用到的算法，都选了"简单、明显正确"优先于"渐进最优"的版本**（符合上面第 2 条的设计前提）：
- 乘法：朴素竖式 O(n·m)，不是 Karatsuba/FFT。
- 除法（`div_mod_magnitude`）：**二进制逐位长除法**（从最高位到最低位，边移边比较边减），不是更快
  但出错率高得多的 Knuth Algorithm D（"猜商偏大要修正"那套细节最容易埋 bug）。二进制长除法只需要
  比较、减法、移一位这三个已经写过的原语，正确性几乎是"显然"的，代价是比 Algorithm D 慢一个数量级
  （按位而不是按 limb 迭代），但对当前的设计前提完全够用。
- 位运算（`&`/`|`/`^`）：`~`/`<<`/`>>` 其实都不需要真的按位实现——`~x` 就是 `-x-1`；`x << k` 恒等于
  `x * 2^k`；`x >> k` 恒等于 `x.floor_div(2^k)`（向负无穷取整右移，`-1 >> 任意位数` 恒为 `-1` 正是
  这条的推论），全部能用已经写好的加减乘除直接表达，不用碰"无穷位补码"那套机制。真正需要"无穷位
  补码"的只有 `&`/`|`/`^` 这三个二元位运算——通过 `to_twos_complement(limb_count)`/
  `from_twos_complement` 这对函数，在"两个操作数里较长的 limb 数 + 1"这个安全宽度下转成补码视角、
  逐 limb 做位运算、再转回符号-大小表示；这个"+1"是必要的安全余量（防止刚好在 limb 边界上误判符号位）。

**`floor_div`/`mod` 的符号处理**——这是最容易出符号错误的地方，专门推导过一遍再实现，不是照感觉写的。
设 `q, r` 是 `|a|` 除以 `|b|` 的向零截断商和余数（`0 <= r < |b|`），记 `s = sign(a) * sign(b)`：
- `r == 0`（整除）：直接 `Q = s * q`，`R = 0`，两种取整方式没有区别；
- `s == +1`（同号）：`Q = q`，`R = sign(b) * r`——截断结果本来就是对的，不用调整；
- `s == -1`（异号）：`Q = -(q + 1)`，`R = sign(b) * (|b| - r)`——floor 比截断多向下（更负）一格，
  余数补上"差的那一段"。

用 SL.md 3.4.2 原文举的例子核对过：`-7 // 2 == -4`、`-7 % 2 == 1`（异号，`q=3,r=1`，`Q=-(3+1)=-4`，
`R=1*(2-1)=1`，对上）；`7 // -2 == -4`、`7 % -2 == -1`（同样异号，`Q=-(3+1)=-4`，
`R=(-1)*(2-1)=-1`，对上）。测试里额外加了一条"恒等式 `x == (x//y)*y + x%y` 在正负交叉组合下都成立"
的通用检查，不只测孤立的几个例子。

**测试里刻意没有手写超大常量（比如 2^100 的完整 31 位十进制展开）当预期值**——除了 2^32/2^64/2^128
这几个多次在别处见过、记得非常确定的常量，凡是记不准的大数验证一律改成"用指数加法律
`x^(a+b) == x^a * x^b` 之类的自洽关系反过来校验"，而不是自己拍脑袋写一串数字再让测试去凑它——测试
oracle 本身错了比实现错了更难发现，缩小"需要我记对一个几十位数字"这件事的依赖面。

`.ai/run_test.bat` 验证：新增 `SL_Cpp_Numeric_Tests`（42 个用例、135 个断言）第一次真正跑起来就全绿，
Lexer 133 + Parser 285 不受影响。

## BigInt 加小路径：值能装进 int64_t 就走原生运算，装不下才退到大数

用户要求：确信装得下 int64_t 的就走原生整数运算（更快），装不下的才走上面写的大数逻辑。

**内部表示改成"小路径 + 大路径"二选一**（`is_small_` 判别）：小路径就是一个 `int64_t small_`；大路径
是原来那套符号-大小 `limbs_`/`negative_` 表示。**不变量：只要数值能装进 int64_t，就必然走小路径**——
每一处产出新值的地方（构造、四则运算、位运算、移位……）算完之后都会检查结果是否收缩得回小路径
（`shrink()`），所以"当前走哪条路径"本身就等价于"这个值是否超出 int64_t 范围"，调用方不需要关心，
也没有开放任何接口能查——两条路径纯粹是内部实现细节，对外行为必须完全一致。

**改法是给每个公开操作套一层"先试小路径、不行再退大路径"，大路径原来的算法完全不用重写**：
- `+`/`-`/`*`：两个操作数都是小路径时，用 `__builtin_add/sub/mul_overflow` 做原生运算 + 溢出检测，
  没溢出直接返回；溢出了（或者本来就有一方是大路径）就把两边都提升成大路径（`promoted()`），照抄
  原来验证过的 `add_magnitude`/`sub_magnitude`/`mul_magnitude` 算完，再 `shrink()` 一次——如果这次
  运算的结果碰巧又回到 int64_t 范围内（比如大数减大数得到一个小结果），会被收缩回小路径，不会因为
  "曾经大过"就一直拖着大数表示不放。
- `floor_div`/`mod`：小路径下用 C++ 原生的截断除法/取模 + 一次"转成向负无穷取整"的符号修正
  （`r != 0 && (r 和除数异号) 则商减一、余数加上除数`），这是教科书写法，用 SL.md 原文的例子核对过
  跟大路径那套符号-大小推导出来的公式结果一致。唯一的坑是 `INT64_MIN / -1`——数学结果是 `2^63`，
  原生 int64_t 除法这里会溢出，特判成"两个操作数都是 -1 和 INT64_MIN 这个组合"时直接跳过小路径。
- `&`/`|`/`^`：两个都是小路径时直接用原生按位运算——两个 int64_t 按位运算的结果显然还是能装进
  int64_t（补码位运算不会让量级变大），不需要 `shrink()`。**这里踩了一个坑**：一开始算安全 limb
  数（`to_twos_complement` 要用多少个 limb 才够）时，是拿两个操作数"提升前"的 `limbs_.size()` 取
  `max`——小路径的操作数 `limbs_` 压根没用过、是空的，读出来是 0。巧合的是这不会实际出错（能落到
  这条慢路径，必然至少有一方是真正的大数，它的 limb 数至少是 2，`max` 不会被那个 0 带偏），但这个
  "巧合不出错"依赖一条不太直观的不变量、没必要冒这个险，改成先 `promoted()` 两边、再用提升后的
  `limbs_.size()` 算 `n`，正确性不用绕这么一圈推理就能看出来。
- `<<`：`k <= 62` 且走小路径时，`int64_t{1} << k` 本身不会碰到符号位、可以安全地当乘数去做
  `__builtin_mul_overflow` 检测；不满足就退大路径（原来的 `shift_left_magnitude`不变）。
- `>>`：小路径下 `k >= 63` 直接返回 `-1`（负数）或 `0`（非负），因为再往上的位全是符号扩展出来的；
  `k < 63` 直接用原生 `>>`——C++20 起有符号整数的算术右移是标准保证的行为，恰好就是"向负无穷取整
  除以 2^k"，不用再自己实现一遍。大路径分支保持原来的写法（`floor_div(1 << k)`，组合出来的，不需要
  单独维护）。
- `~`/`pow`：完全没改，因为它们本来就是通过 `-`/`+`/`*`/`floor_div` 组合出来的（`~x = -x-1`，
  `pow` 是逐位快速幂），这些被组合的操作各自已经有快慢路径分发，组合出来的操作自动跟着受益，不用
  再单独处理。
- 比较（`<=>`/`==`）：两边都小路径时直接比较 `int64_t`；否则提升成大路径再用原来的量级比较逻辑。

**测试**：原来 42 个用例（135 断言）在改完之后不改一行、原样全部通过，是对这次重写的第一道验证
（这些用例本来就覆盖了小数值、跨 limb 边界的大数值，任何一条快路径算错了大概率会被原有用例绊倒）。
另外专门加了一组"小路径/大路径边界"用例：恰好在 `INT64_MAX`/`INT64_MIN` 边界上下的加减法、乘法溢出、
`INT64_MIN` 取负/取绝对值、`INT64_MIN / -1` 这个除法溢出特例、小路径与大路径操作数混着运算、以及
"算出来的结果又缩回小路径范围"这几种情况——因为这些正是这次改动新增的代码路径，原有用例大多没有
专门针对"刚好在边界上"这个场景设计过。

`.ai/run_test.bat` 验证：`SL_Cpp_Numeric_Tests` 48 个用例、153 个断言全部通过（原 42 个 + 新增 6 个
边界用例），Lexer 133 + Parser 285 不受影响。

## StaticEvaler/LiteralFolder 骨架 + Analyzer 全面引用化 + StaticEvaler 完整实现

这一整段是同一条主线上的三步，分别记录。

### 第一步：LiteralFolder/StaticEvaler 骨架

按运算符语义家族分组，避免类型×运算符组合爆炸：算术（+ - * / // % **）、位运算（& ^ | << >>）、
比较（链式 < <= > >= != ==）、逻辑（not/and/or）、is。`LiteralFolder` 负责树的遍历/替换（拥有
`AstNodePtr` 槽位的所有权），`StaticEvaler` 只负责"给一个节点判断能不能整体折成字面量"，两者职责
分开。当时留了一个悬而未决的问题：`and`/`or` 的结果可能是"原封不动挪用一个已有子节点"（不一定是
新构造出来的值），而 `StaticEvaler` 当时的入参是 `const AstNode*`，没有所有权、搬不动子节点，所以
这两个折叠分支先留空恒返回 `nullptr`。

### 第二步：`Analyzer`/`SyntaxChecker`/`LiteralFolder` 的 `root_` 和分派入参从裸指针改成引用

用户提议：这几个类的 `root_` 成员改成引用，分派函数（`check`/`visit`）内部需要 `dynamic_cast` 试探
时再取地址转成裸指针，试出来以后传引用往下走。判断可行：分派函数本身必须留一份裸指针做
`dynamic_cast<T*>`（失败返回 nullptr）——引用版 `dynamic_cast` 失败是抛 `bad_cast`，拿异常当十几种
类型里挨个试的正常分派流程是反模式；但分派函数的入参签名本身可以是引用（因为调用时已知非空），内部
自己 `&node` 取指针去试。三个类的 `root_` 从 `T *const` 换成 `T &`——这两者对"能不能被赋值"这件事
效果一样（`T *const` 本来就不可再赋值），换引用不损失任何能力，纯语义收紧。

改的时候发现 `SyntaxChecker::check` 和 `LiteralFolder::visit_and_replace`（当时叫 `visit_and_replace`）
对"这个槽位可能是空"的处理方式不统一：`LiteralFolder` 一律靠 `visit_and_replace` 这一层统一挡掉空
指针；`SyntaxChecker::check(const AstNode*)` 却是自己在分派函数内部 `if (!node) return;`，导致代码
里到处混着"调用前 `if (x) check(...)`"和"不判直接传、靠 `check` 内部兜底"两种写法。既然改成引用之后
`check` 不可能再收到空的，就借这次机会加了个 `check_optional(const AstNodePtr&)`（照抄
`visit_and_replace` 的模式），把所有真正可能为空的槽位统一走这一个函数，顺带把散落各处多余的
`if (x) check(...)` 判断也删掉了——两个类现在对"槽位可能没东西"这件事处理方式完全一致。

### 第三步：`StaticEvaler` 完整实现

**入参设计（用户明确问过"指针还是引用，替换这一步要不要也搬进 StaticEvaler"）**：跟第二步的结论
一致，`fold`/`fold_binary` 等入参统一收非 const 引用，内部分派需要裸指针时自己取地址。但"替换到
`AstNodePtr` 槽位里"这一步**没有**搬进 `StaticEvaler`——那样会让它从"纯函数：给输入返回新值或
nullptr"变成需要感知"我在改一个被谁拥有的槽位"，职责会混在一起。真正需要的能力只是"把某个已有子节点
移动出来当结果用"，而这只需要输入是非 const 引用（能对 `node.left_`/`node.right_` 做 `std::move`），
根本不需要碰 `unique_ptr` 本身的所有权语义；"折完之后塞回槽位"这一步依然完全留在
`LiteralFolder::visit_and_replace` 里，跟原来一样。

这个设计顺带解决了骨架阶段悬而未决的 and/or 问题：`fold_and_or` 拿到的是 `AstNodeOpBinary&`（可变），
只要左操作数是字面量、能判出真值，就直接 `std::move(take_left ? node.left_ : node.right_)`
把没被选中的那侧原地丢弃——不需要给 `AstNode` 加 `clone()`。

**但 `*` 的容器重复分支意外地真的需要"深拷贝"**：`[1,2] * 3` 要产出 3 份独立的 `[1,2]` 内容，
`unique_ptr` 没法复制、只能移动一次，移动不出"同一份内容用 3 次"。这是设计骨架时没预见到的新问题
（当时只想到 and/or 需要"搬子节点"，没想到重复也需要"复制子节点"）。加了一个
`clone_literal(const AstNode&)`，只处理 `is_literal()` 认可的字面量子集（None/bool/int/float/str/
Ellipsis/tuple/list/dict，容器递归克隆），因为调用方（+ 拼接、* 重复、dict 合并）都已经确认过操作数
`is_literal`，克隆这个子集总是良定义的，不需要给 `AstNode` 整体加一个通用多态 `clone()`。

**`is_literal` 对容器是递归的，不是只看节点类型**：`AstNodeLiteralTuple`/`List`/`Dict` 这几个节点
类型名字叫"Literal"，但语法上它们就是元组/列表/字典**显示**语法（`[x, y+1, f()]` 一样是
`AstNodeLiteralList`），元素可以是任意表达式，不一定是常量。`LiteralFolder.h` 类注释里写的是
"纯字面量组合的子表达式"——所以 `is_literal` 对容器必须递归检查每个元素（tuple/list 每个 item，
dict 每个 key、非空 val）都满足 `is_literal`，只看外层节点类型是不够的。反例：`[x, 1] + [2]`，外层
两个操作数都是 `AstNodeLiteralList` 节点，但左边包含变量 `x`，不该被当成"编译期已知的值"去折。
副作用：`AstNodeLiteralGL`（`_G`/`_L`）从 `is_literal` 的候选列表里删掉了——骨架阶段的旧列表里
误把它当成字面量收录了，但 `_G`/`_L` 的值是运行时的实时字典视图（SL.md 3.4.1），不是编译期能确定
的东西，这是骨架留下的一个小疏漏，完整实现时顺带修掉。

**发现两处 SL.md 没定义、跟用户当时口头描述对不上的语义，找用户确认过要不要正式加进语言**：
1. 字符串的 `%` 格式化——SL.md 原来 `%` 只对数字定义（取模）。用户确认要加：Python 风格 printf 的
   一个子集（`%s`/`%d`/`%f`/`%%`，可选 `0` 前缀 + 宽度 + `%f` 的精度），不追求 100% 复刻 Python
   （不支持 `%(name)s` 具名替换、`%r` 等），写进了 SL.md 3.4.2。
2. `dict` 的 `|`——SL.md 原来 `|` 只对 int/set 定义。用户确认要加：仿 Python 3.9+ 的 dict 合并语义
   （重复 key 用右操作数的值，位置留在左操作数原来的位置，右操作数独有的 key 按序追加在末尾），
   同样写进了 SL.md 3.4.2。

这两处都是"语言设计决策"级别的新增（不是单纯把 StaticEvaler 该实现的东西补全），所以没有自己决定，
是先问清楚再动手实现 + 补文档。

**`//`/`%` 掺了 float 时的语义是从 SL.md 原文推出来的，不是照抄"都是 int"那条**：SL.md 3.4.2 原文
只显式写了"`x`、`y` 都是 int 时：`//`、`%` 结果仍是 int"，没有直接写"掺了 float 怎么办"。按上下文
（先说"对于数字，返回…向下取整商、余数"这个通用规则，再对"都是 int"这个子情形单独澄清"仍是 int"），
推断掺了 float 的情况走通用规则、结果是 float，同 Python（`7.5 // 2 == 3.0`）。手写了 Python 语义
一致的向负无穷取整 `%`/`//`（`fmod` 算完如果余数非零且跟除数异号，就把余数加上除数），没有去猜/发明
新语义。

**float 折叠结果的构造需要先解决"怎么把 double 转成合法的 SL float 字面量文本"**：SL.md 2.1.4
规定 float 字面量目前不支持科学计数法、且整数/小数部分都不能省略（`1.`、`.1` 都不合法），所以折叠出
的新字面量必须是形如 `"3.14"`、`"3.0"` 这种恒带小数点的定点文本，不能用 `%g`/科学计数法。`format_double`
从 0 位小数开始逐步尝试 `%.*f`，选第一个能精确 round-trip（`strtod` 转回来位级相等）的最短精度，
没有小数点的话补 `.0`。任何折叠结果如果不是有限数（`±inf`/`NaN`——理论上只会出现在极端的
溢出/`0**负数`这类场景），`make_float` 直接返回 `nullptr`（当前语法写不出这两种值），交给运行时处理，
不在这里硬编码"抛异常"。

**容器 `*` 的重复次数、`<</>>` 的移位量都要先能转成 `long long`，转不下就不折**：`try_to_ll` 把
`BigInt` 转 `long long`，失败（数值太大装不下）直接返回 `false`，调用方视为"折不动"、绝不抛异常。
没有另外加一个"重复次数不能太大"的人为上限——这跟 `BigInt::pow` 对巨大指数不设上限是同一个取舍
（"内存充足、无限位数"的既有设计哲学），能装进 `long long` 但数值依然大到不现实（比如重复 10^15 次）
不会被这道检查拦下来，这是故意的，不是遗漏。

**测试**：新增 `SL_Cpp_Analyzer_Tests`（48 个用例、116 个断言），按语义家族拆成
`arithmetic_test.cpp`/`bitwise_test.cpp`/`container_ops_test.cpp`/`str_format_test.cpp`/
`compare_is_test.cpp`/`logical_test.cpp`，测试工具复用 `test/parser/test_utils.h` 的
`parse_program`，新增 `fold_json` 直接跑 `LiteralFolder{*program}.fold()` 后转 JSON 比对（不经过
`Analyzer`/`Executor`——`Executor.cpp` 里 `to_json()` 转储发生在 `Analyzer::analyze()` 之前，没法
从那条路径观察折叠结果，这也是一开始手工用 `SL.exe` 跑 smoke test 时"完全没有任何东西被折叠"、一度
以为实现有 bug 的原因，后来才意识到是转储时机的问题，不是折叠逻辑的问题）。覆盖：SL.md 原文的
floor div/mod 例子、bool 提升不改变结果类型（`+True` 是 `int` 不是 `bool`）、除零/负数移位/负数重复
次数不折、str/tuple/list 的拼接与重复（含"重复出来的每一份是独立节点"）、dict 合并的位置/覆盖规则、
str 格式化的宽度/精度/`%%`/参数数量不匹配、链式比较/跨类型比较、`is` 只对 `None` 折、and/or 不短路
但能整体挪用非字面量的一侧（如 `True and f()`）。`.ai/run_test.bat` 验证四个测试目标全绿：
Numeric 48/153、Lexer 133/358、Parser 285/511、Analyzer 48/116（新增）。

## StaticEvaler 折叠范围收窄：砍掉 dict/is/str%，加上 if/for/while 死分支消除

上面那版 StaticEvaler 写完不久，用户重新设计了一遍折叠范围，画了张"哪些类型的一元/二元运算参与折叠"
的表，比原来的窄很多，同时额外要求 if/elif/else、for/while 的 cond 也要参与死分支消除。核对确认后
按这版重写了 StaticEvaler，是一次纯粹的收窄+新增，不是推翻重来。

**砍掉的三样——`is`、dict 的一切运算（含刚加的 `|` 合并）、str 的 `%` 格式化**：用户的说法是
"字典的拼接、字符串格式化不是完全'static'的过程，得依赖于 VM，所以不折"——这比我自己最初的理由
（复杂度收益比不划算）更准确地指出了本质：折叠是个优化，不是必须覆盖语言定义的每一个运算符，这几个
要么根本没法在编译期安全预判（`is` 的对象同一性），要么实质上要靠 VM 的对象模型/协议才能算准
（dict 合并的 key 判等、`%` 格式化的类型转换协议），不如老实交给运行时。**这几个运算符本身仍然是
合法的语言特性**（`%`、dict `|` 都已经写进 SL.md 了），只是编译器不再尝试替你在编译期算出来——SL.md
不用跟着改回去，改的只是 `StaticEvaler` 这一处实现范围。

**保留的部分核对了一遍，跟原来的实现完全对得上**，不需要改逻辑：数字之间的算术/位运算/六个比较符
（含 bool/int/float 任意组合提升）、str×str/tuple×tuple/list×list 各自的 `+`/六个比较、
数字×(str/tuple/list) 的 `*`（非负 int 重复）、跨类型 `!=`/`==`（恒可折，因为跨类型必不相等）。
`is_literal`/`clone_literal`/`literal_equal`/`literal_compare`/`truthy` 里原来的 dict 分支全部删掉
（`is_literal` 不认 dict 之后，含 dict 元素的 tuple/list 也会因为递归检查失败而不再是"整体已知"，
这是自然的连带效果，没有特殊处理）。

**新增 if/elif/else、for/while 的死分支消除**，用户给的规则原话："`if(真值为False的字面量)` 是
直接删掉整个它，`if(真值为True的字面量)` 是把后边的东西拿出来替掉 if。for 和 while 是 False 就删掉
整个，是 True 则不折叠"。落实时确认/推导出几个原话没覆盖到的细节：
- `if` 是 `clauses_`（if + 各 elif）+ `else_expr_` 的链式结构，不是简单二选一。实现按顺序扫
  `clauses_`：跳过前导的确定 False（cond 是字面量且假），遇到确定 True 就把对应 `body_` 整个
  移出来当结果（后面的 clause/else 全部丢弃）；如果扫到某个 cond 不是字面量，前面已经跳过的那些
  False clause 依然可以先丢——重新拼一个更短的 `AstNodeIf`（用剩下的 clause + 原 `else_expr_`）
  返回，这是"部分折叠"，不要求一口气知道最终结果；如果全部 clause 都确定 False，整体值退化成
  `else_expr_`（没有则 `None`，SL.md 3.4.5.1 原文）。
- `for`/`while` 折成 False 时的替换值不是随便选的，是查 SL.md 3.4.5.2/3.4.5.3 "for/while 表达式
  的值"这段原文查出来的：不带 `$` 是"实际循环次数"（一次都不跑就是 `int 0`），带 `$` 是"收集到的
  结果列表"（一次都不跑就是空 `[]`）。
- **这里发现一个原话没提、但如果忽略会引入真 bug 的情况**：`for` 的 `init_` 无论 `cond` 是否为真
  都会无条件先求值一次（SL.md 3.4.5.2："先对 init 求值并丢弃，然后不断重复：对 cond 求值……"），
  哪怕循环一轮都不跑，`init_` 的副作用（比如 `x = 1` 这个赋值）依然发生了，不能因为整体在折叠就
  把这个副作用悄悄丢掉。处理方式：`init_` 非空时，折叠结果不是直接换成 `0`/`[]`，而是用
  `AstNodeCompound{init_, 0或[]}`（复合表达式，SL.md 3.4.1："复合表达式的值为块中最后一条表达式的
  值"）把 `init_` 的副作用接在前面、最终值仍是 `0`/`[]`；`init_` 为空时才直接换成常量，不用包一层。
  `inc_`/`body_` 不用管——它们在语义上只有循环真的至少跑了一轮才会被执行到（`inc_` 在 `cond` 判断
  之后才轮到），`cond` 从一开始就是 False 时它们连一次都不会被摸到，折叠时直接丢弃是安全的。
- `for`/`while` 的 cond 折成字面量 True 时刻意不折——这跟 `if` 不对称：`if` 折 True 时"知道具体
  是哪个分支"，可以直接换成那个分支的整个内容；但循环折 True 只能确定"不会提前退出"，循环本身要跑
  几轮、每轮 `body_` 算出什么、最终值是什么，都不是编译期能知道的东西，没有"换成什么"这个答案，
  所以就是不折——这不是漏做，是这条规则的题中之义。

**`clone_literal` 要不要升级成 `AstNode` 全体的通用多态 `clone()`，用户明确交给我决定**：保留原来
"只处理 `is_literal` 认可的字面量子集"这个范围小的静态函数，没有给 `AstNode` 基类加虚函数
`clone()`。理由是 YAGNI——目前整个代码库里只有 `*` 的容器重复这一个场景需要"同一份内容用多次"，
这个场景已经被 `clone_literal` 完全覆盖；给全部几十种节点类型（包括 `AstNodeFunc`/`AstNodeClass`
这种复杂结构）都加一个 `clone()` override 是量级完全不同的工程量，而且现在没有第二个场景会用到，
纯粹的投机通用化。等真的出现新的需求（比如宏展开、内联）再加不迟。

死分支消除复用了 and/or 已经建立的"拿可变引用、`std::move` 走某个子节点"这个手法（`fold_if`/
`fold_for_cond` 跟 `fold_and_or` 一样收 `AstNodeIf&`/`AstNodeForCond&`），架构上不需要任何新突破——
这也印证了当初（决定用引用而不是指针传参、把 and/or 的所有权问题解决掉）那次设计选择的价值：一次
性解决的不只是 and/or 一个运算符，后续任何"折叠结果是挪用某个已有子节点"的新场景都能直接复用。

**测试**：删掉了 `str_format_test.cpp`（功能整个不要了），`container_ops_test.cpp`/`compare_is_test.cpp`
里 dict 相关的用例改成断言"不折、原样返回"，新增 `dead_branch_test.cpp` 覆盖 if 的直接命中/退化到
else/部分折叠/第一个 clause 不能判定这四种情况，以及 for/while 的 False 退化值（含 `init_` 副作用
保留）、True 不折、cond 缺失或非字面量不折。`.ai/run_test.bat` 验证四个测试目标全绿：
Numeric 48/153、Lexer 133/358、Parser 285/511、Analyzer 47/111。

## check 与 fold 的顺序：维持 check 在前，理由是一个具体的健全性反例；顺带把 doc 规则改成纯语法检查

用户一度想把 `Analyzer::analyze()` 里 `SyntaxChecker`/`LiteralFolder` 的调用顺序倒过来（先 fold
再 check），主要动机是刚做完的 if/for 死分支消除——觉得死代码不该被语法检查卡住。

**没有采纳，原因是一个具体反例，不是泛泛的"死代码要不要检查"这种取舍**：`f(True and *args)`。
`SyntaxChecker::check(AstNodeOpBinary&)` 检查 `and`/`or` 的操作数之前，无条件把 `can_star`/
`can_double_star` 强制置成 `false`——这个重置只跟"当前正在检查的是 and/or 自己的操作数"这件事有关，
跟这个 and/or 表达式整体站在树的什么位置无关。check 在 fold 之前时，`*args` 作为 `and` 的右操作数
永远会在 `can_star=false` 的语境下被检查到，报错，无论 `True` 的值是什么——这是对的，`True and *args`
本来就是没意义的写法。但如果 fold 先跑：`fold_and_or` 见左操作数 `True` 为字面量、真值为真，`and`
的语义是"左真取右"，于是把 `*args` 整个原封不动挪出来，直接替掉了 `True and *args` 这一整块，树变成
`f(*args)`。check 随后只看得到挪动之后的树——`*args` 现在直接站在调用参数的位置，`can_star` 在这个
位置本来就是 `true`，检查通过，**不报错**。这不是"死代码里的 bug 没被抓到"（`True` 那部分是必定
执行的活代码），而是**一段本该永远语法非法的写法，纯粹因为死分支消除把受限位置的东西搬到了不受限的
位置，就悄悄变成合法的了**——`if` 的死分支消除同理（`if(True) *x else y` 类推）。`for`/`while` 那条
路径反而没这个问题，因为 `init_` 挪进 `AstNodeCompound` 时，`check(AstNodeCompound&)` 自己也会重置
`can_star=false`，跟原来 `ForCond` 的效果一致。要在 fold-first 顺序下堵住这个洞，得让 `StaticEvaler`
感知"这个子节点是不是 `*`/`**` 前缀、能不能被搬走"这种语法层面的限制，会把本该纯粹按 AST 形状判断
"能不能折"的 `StaticEvaler`，跟 `SyntaxChecker` 的语境规则耦合在一起，破坏两者目前干净的职责分离。
结论：维持 check 在前、fold 在后，不换。

**顺带发现并解决了一个真实存在的别扭之处**：func/class 的 `doc` 槽位有一条规则（SL.md 3.4.6）
"`doc` 必须是字符串字面量或其编译期可折叠的组合（`"a" + "b"`、`"x" * 3` 等）"——这条规则本质上依赖
折叠结果，不是纯语法/作用域规则，硬塞进 `SyntaxChecker` 就会出现"先 check 就得在 doc 这一个槽位单独
先 fold 一次"这种特例，跟"check 全程不碰值、不摸树"的整体设计不符。考虑过三条路：
1. 把这条规则挪到 `LiteralFolder` 里，紧跟着它本来就有的 `visit_and_replace(node.doc_)` 之后做——
   不用额外跑一遍折叠，但 `LiteralFolder`/`StaticEvaler` 一直以来"折不动一律返回 nullptr、从不抛
   异常"这条约定就被破了个例外，且 `LiteralFolder` 得额外收一个 `file_path_` 才能拼出规范的
   `SyntaxError`；
2. 在 `SyntaxChecker` 里对 `doc_` 单独调 `StaticEvaler::fold` 做"试探"——被否决：`fold_and_or` 会
   真的 `std::move` 走子节点，"只是试探"这个动作本身就会实际改动原树，等于在只读的 check 阶段
   偷偷做了不可逆的变更；
3. **改语言规范本身**：`doc` 必须恰好是一个字符串字面量，不再允许 `"a"+"b"`/`"x"*3` 这类"编译期可
   折叠的组合"。

选了第 3 条。理由：Python 的文档字符串本来就只能是单个字符串字面量（连 Python/C 那种"相邻字面量自动
拼接"都没有，SL.md 2.1.4 也明确说 SL 不支持这个），允许 `"a"+"b"` 反而是比 Python 更宽松的 SL 自创
扩展；SL 已经有反引号原始字符串覆盖"多行/免转义"这个 `+`/`*` 拼接在文档字符串场景下唯一站得住脚的
实际需求，禁掉之后losses 很小。换来的是：`doc` 的检查退化成一条纯形状检查（`dynamic_cast` 到
`AstNodeLiteralStr` 就完了，不需要知道任何值），`SyntaxChecker` 新增 `check_doc(const AstNodePtr&)`
辅助函数，不依赖折叠结果、不需要碰 `StaticEvaler`；`LiteralFolder`"从不报错"这条约定完整保留；
check 在 fold 之前这个顺序也完全不用因为 doc 这一个槽位破例。

`.ai/run_test.bat` 验证四个测试目标不受影响：Numeric 48/153、Lexer 133/358、Parser 285/511、
Analyzer 47/111；手工用 `SL.exe` 验证 `func f() "a" + "b" { 1 }` 现在正确报
`SyntaxError: doc must be a string literal`，`func f() "a plain doc" { 1 }` 正常通过。

## 给 AstNodeProgram 补一个值：`eval_isolated` 别扭的真正根源

用户回头复查 `eval_isolated`（4.1.16）设计，觉得"很怪、无法接受"，让先讨论、别急着改。诊断过程：
`eval_isolated` 的定义一直是"等价于调用 `func(){code}`……函数体的一般规则照常适用，不为
`eval_isolated` 单独定义"——这句话把 `eval_isolated` 自己的值完全甩给了"函数体的值"，但"函数体
（`AstNodeProgram`）到底有没有值、是什么"这件事在 SL.md 里从来没被定义过。`eval_isolated` 本身没写
错，是它脚下的地基（`AstNodeProgram` 的值）一直没浇——**这是 SL"一切皆表达式"这条设计原则下唯一一个
被漏掉的角落**：几乎所有 AstNode 都有定义好的值（3.4.1/3.4.2/3.4.5……），唯独 `AstNodeProgram`
没有。

**最终方案**（跟用户来回对了两轮才定下最精确的表述）：

- **`AstNodeProgram` 只出现在三个固定语法位置**——整个文件本身、`func` 元信息之后的 `{ }`、`class`
  元信息之后的 `{ }`；这三处的 `{ }` 内容固定解析成 `Program`（不是复合表达式，尽管写法上一样是花括号
  包起来的一串表达式）。用户没法在源码里手写构造出一个 `Program`——它不是字面量、没有对应语法——
  所以这条值规则纯粹是解释器执行到 `Program` 时才用得上，不涉及编译期折叠，**Parser 完全不用改**
  （现状本来就是这样解析的，这次只是把"这是有意为之、不是实现细节"这件事显式确认下来）。
- **`Program` 的值**：从前到后依次求值；一旦碰到 `return` 就立即以它的值作为整个 `Program` 的值，
  不再往后求值；始终没碰到 `return`、跑到末尾，则值为 `None`（等价于末尾隐含一条 `return None`）。
- **`return` 的作用对象统一成"离它最近的那个 `Program`"**，不再分"函数体内/全局"两种情况单独描述。
  这条统一规则有两个好处：
  1. `Program` 恰好和"帧"一一对应（SL.md 3.10.1 早就是这么定义帧栈的：函数调用、类体执行、文件
     本身各自对应一个帧）——"return 找最近的 Program"就是"return 退出当前帧"，没有例外要谈；
  2. 天然正确处理 `eval` 的内联语义：`eval(code)` 展开成 `{code}` 是 `AstNodeCompound`，不是
     `Program`，"最近的 Program"自然跳过它，落到 `eval` 调用处真正所在的函数/类体/文件上——跟
     现有 4.1.15"若中途被 return 提前带出，使外层函数返回"这句话严丝合缝，不需要为 `eval` 单独
     写规则。
- 三处 `Program` 的值各自怎么用：函数体——这次调用的返回值；类体——值被丢弃（但类体执行期间收集到
  `_L` 里的名字**不受这个"丢弃"影响**，仍然照常用于建类的属性表——这是两条独立的信息通道，用户
  专门强调"这跟收集局部变量不是一回事"）；整个文件——`__return__`/退出码（SL.md 3.4.5.6 原来就有
  这条，这次只是把它纳入统一框架）。

**`return` 允许出现在类体里，是一次真实的、有意为之的语义变更**——现在（改之前）类体里 `return`
是禁止的：SL.md 3.4.5.6 原来只定义了"函数体内"和"全局"两种情况，压根没提类体；
`SyntaxChecker::check(AstNodeClass&)` 也显式把当时叫 `func_depth` 的计数器清零（我自己当时写的
注释是"类体执行更像顶层脚本：不允许裸 return/break/continue"）。这次把类体正式纳入"合法 return
的三种 Program 之一"。

**顺带揪出并修掉两处跟"顶层 Program"直接相关的既有 bug**（都是我自己早前实现 `SyntaxChecker` 时
没有跟 SL.md 原文逐句核对导致的）：
1. `check(AstNodeReturn&)` 一直写的是"`func_depth == 0` 就报 return outside function"——但
   SL.md 3.4.5.6 从最早的版本开始就写了"在全局：立即退出当前文件"，**顶层 `return` 本来就该合法**，
   之前的实现一直是错的。既然"离它最近的 Program"这条统一规则下 `return` 处处合法（哪怕在文件
   顶层，最近的 Program 就是文件自己），`check(AstNodeReturn&)` 现在直接不再做任何上下文判断，
   只递归检查 `value_`。
2. SL.md 3.4.4 原文明明写的是"只能在局部作用域（**函数体或类体**）中使用"——`global` 本来就该在
   类体里合法，但 `check(AstNodeClass&)` 把 `func_depth` 清零，把 `global` 也一起误禁了。

**`func_depth` 这个名字本身也不对了**（用户原话："至少 func_depth 这个名字就不对了"）——它现在
唯一剩下的用途是判断 `global` 合不合法（`return` 已经不需要它），而 `global` 合法的条件是"身处
func 体或 class 体的局部作用域"，改名成 `local_scope_depth`；`check(AstNodeFunc&)`/
`check(AstNodeClass&)` 进入各自的体时都是 `local_scope_depth++`（原来类体是清零，现在改成 `++`，
一次性把"类体里 return 合法"和"类体里 global 合法（修 bug）"两件事一起做对，`loop_depth` 依然清零，
break/continue 该有的限制不受影响）。

**`eval_isolated` 的重新表述彻底解决了它自己的问题**：不再说"等价于调用一个匿名函数"（这个说法
跟"这次调用的 `_L` 即其 `_G`"本身就有点拧巴——正常函数调用的 `_L` 该跟 `_G` 不同，只有顶层/全局
作用域才 `_L` 即 `_G`，3.10.1 原文如此），改成"把 `code` 单独存成一个文件，`globals` 并入这个文件
的 `_G`（不传则新建空 `dict`），当模块导入，返回值是这次'导入'所得模块对象的 `__return__`"（语义
等价，非实现）——`_L` 即 `_G` 自然成立（文件/顶层作用域本来就是这样），不允许 `global`（顶层不能
`global`，2.2.4）也自然成立，不需要专门为 `eval_isolated` 说明或判断。

**SL.md 改动位置**：3.4.1 新增 Program 的值这条规则（连同它只出现在三处、跟 return/帧的关系一起
写清楚）；3.4.5.6 `return` 改成统一按"最近的 Program"描述，新增类体这一种情况；3.4.7 类体执行步骤
里补充 return 可以提前中止、值丢弃、局部变量收集不受影响；3.5 函数调用里补一句"函数体是一个
Program，这次调用的返回值就是这个 Program 的值"；4.1.16 `eval_isolated` 按上面的新框架重写。

**`SyntaxChecker` 改动**：`Context::func_depth` 改名 `local_scope_depth`；
`check(AstNodeReturn&)` 去掉上下文判断（处处合法）；`check(AstNodeClass&)` 从
`local_scope_depth = 0` 改成 `local_scope_depth++`；`check(AstNodeGlobal&)` 判断条件和报错文案
跟着改名同步更新。

`.ai/run_test.bat` 验证四个测试目标不受影响：Numeric 48/153、Lexer 133/358、Parser 285/511、
Analyzer 47/111。手工用 `SL.exe` 验证：顶层 `return 5` 不再报错；类体里 `global x`、`return None`
都不再报错；类体里裸 `break`（没有真的在循环里）依然正确报 `break outside for/while loop`
（`loop_depth` 不受这次改动影响）。

## 补全 `import` 语义 + 帧的"弹出/死亡/回收"三分

上面 Program 的值定的框架刚落地，用户接着让把 `import`（4.1.14）的语义也补完整，顺带把帧模型里
"弹出"和"死亡"这两件事分开讲清楚。

**`import(module_name)` 找到 SL 源文件之后的语义**（查找规则本身留空，以后再定）：新建模块对象、
新建帧、压栈；把文件内容当一个 Program（3.4.1）在这帧上执行；执行完（或被 `return` 提前结束）后
弹出该帧——但帧的局部字典（即这次执行的 `_G`）直接就是 `attrs(模块对象)` 的内容，两者是同一个
`dict`，不是拷贝；Program 的值记入模块对象的 `__return__`。

**模块对象的缓存语义**：一旦建立，在解释器停止之前永远存在、永远不被回收（哪怕调用处不再持有引用）；
对同一个 `module_name` 重复 `import`，返回同一个（`is` 意义上）对象，不重新执行文件——哪怕文件在
两次 `import` 之间改过，也用缓存的旧结果，不检测、不失效。

**顺手记了一条真实踩过的坑**（用户原话是自己在 Python 里真的干过这事，"还到处搜资料"）：模块源
文件里定义一个 `__op_call__`，不会让模块对象本身可调用——调用 `x(...)` 查的是 `type(x)` 的
`__op_call__`（3.8），模块对象的类型是"模块"这个内置类，不是这份源文件本身；文件里的 `__op_call__`
只是 `attrs()` 里一个普通属性，跟"模块类有没有 `__op_call__`"是两件事。这条按用户的要求，用了比
SL.md 其余部分略轻松一点的语气写（"这是个经典的坑……翻多少资料都绕不开这一条"），其余地方保持
SL.md 一贯的干燥技术文风，没有到处加调侃。

**帧的"弹出/死亡/回收"三分**（3.10.1 补写）——这是这轮最容易踩坑、来回改了两次才理顺的部分：

- **弹出**：从帧栈移除，栈机制层面的事。函数调用返回/异常传播退出/类体执行完毕/一份文件执行完毕，
  都会弹出对应的帧。
- **死亡**：局部字典置为 `None`，跟"弹出"通常同时发生（函数调用、类体执行结束时立刻死亡），
  **但文件级别的 Program 执行是例外**——弹出后不会死亡，局部字典（`_G`）一直保留，文件里定义的
  函数才能一直找到同一份文件里的其它函数/全局变量。这条不区分"是不是被 `import` 缓存的模块"，
  `eval_isolated` 临时构造出的那种"文件"同样弹出不死。
- **回收**：帧对象本身的内存被释放，垃圾回收层面的事，只要还有引用（含 3.10.4 的"定义帧"引用）
  指向它就不会发生，跟这个帧是死是活无关。

**第一版写岔了的地方，回头自己发现并改掉**：最早把"文件的帧弹出不死亡"和"`import` 模块永远不被
回收"这两件事写成了一回事（"模块对象……永远不死"），但按上面三分的定义，"不死亡"（局部字典是否
被清空）和"不被回收"（帧对象本身是否还占内存）其实是两条独立的轴——`import` 缓存的模块能活到解释
器停止，靠的是解释器自己维护的模块缓存一直强引用着它，不是"文件的帧天生不死"这条规则本身在起作用；
`eval_isolated` 构造出的"文件"同样弹出不死，但没有这份缓存强引用，用完之后没人再引用就跟普通对象
一样被回收——这也是为什么 4.1.16 里补了一段"`eval_isolated` 不进模块缓存、不享受这条特殊待遇"的
澄清，不然读者会以为每次 `eval_isolated` 调用都永久漏内存。

顺带在 3.10.1 里留了一句面向未来的话：以后加生成器，生成器对象持有自己那个帧的引用，也是"弹出但
不死亡"、甚至可能被重新压回帧栈的情况，直接复用这套"弹出/死亡/回收互相独立"的框架即可，不需要
另开概念——纯粹是为了不在加生成器的时候又把这几个概念混到一起返工一遍。

这轮是纯 SL.md 修订，没有触及任何 C++ 代码，`.ai/run_test.bat` 跑过确认没有回归（构建工具显示
"no work to do"，符合预期）。

## 定了 `import(force=)`

**`import` 新增 `force` 参数**：`force=True` 时丢开缓存里的旧模块对象（不再持有它）、重新完整走
一遍导入流程、建立一个全新的模块对象（不是原地复用/修改旧对象）存入缓存。用户明确选的是"整个换一个
新对象"而不是 Python `importlib.reload()` 那种原地修改同一个对象——原地修改会导致
`from module import x` 这类提前拿走的绑定不同步、`isinstance` 对着旧类对象判定出岔子这些 Python
自己都没根治好的坑；换新对象则简单直接：旧引用（谁在 `force` 之前存下来的模块对象）继续完整可用，
只是跟新 `import` 拿到的不再是同一个对象（`is` 为 `False`），旧对象一旦没人再引用就跟其他不被
缓存的对象一样正常回收——这套"退出缓存后归入普通对象生命周期"的行为，跟 `eval_isolated` 的模块
对象是同一套规则，两个功能因此共享同一套说明，没有另开一套概念。

`.ai/run_test.bat` 确认没有回归（纯 SL.md 修订）。

## 用户重构一遍 SyntaxChecker 后揪出的 6 个问题，加上专门的 SyntaxChecker 测试套件

用户自己动手把 `SyntaxChecker` 重构了一遍（`check_optional` 拆成 `check_not_null`/`check_nullable`
两个更明确的助手，`require_not_null` 加了不少调用点），过程中发现 6 处我之前遗漏/写错的地方。
逐条记录问题和修法：

1. **`AstNodeClass` 的 `captures_` 完全没被检查**——既没有递归 check 各 `value_expr_`，也没有查重复
   名字。之前给 `AstNodeFunc` 加捕获/形参重名检查时漏了 class 这一侧（class 只有 captures_，没有
   params_，逻辑该更简单，结果直接漏掉了）。修法：照抄 func 那套 `unordered_set<u32string>` 查重
   逻辑，去掉 params_ 相关的部分，单独给 class 的 captures_ 补上。

2. **形参顺序检查的逻辑本身是错的**：原来的代码是"见过 `*args` 之后任何普通形参一律报错
   `normal parameter after *args`"，但 SL.md 2.2.6 的原文是"1. 无默认值的形参；2. 有默认值的
   形参、可变长位置形参（这两种之间顺序不限）；3. 可变长关键字形参"——**这条顺序规则只管
   `*args` 之前的位置形参部分**，`*args` 之后的形参是仅关键字形参（3.5 原文："出现在可变长
   位置形参之后的槽位标记为仅关键字"），按名字匹配、不按位置，彼此之间有没有默认值完全不受
   这条顺序约束（同 Python：`def f(*x, y)` 合法，`y` 是必须以关键字方式传入的形参）。反例
   `func f(*x, y) {}` 之前会被误判为"普通形参跟在 *args 后面"直接报错，但这明明是合法语法。
   修法：把"无默认值必须先于有默认值"这条检查的适用范围收窄到"还没见过 `*args`"这个阶段，
   `*args` 之后完全不再检查默认值顺序。

3. **字典字面量的 `**expr` 展开项和 `val` 是否为空这两件事没有互相校验**：`{**d: v}` 这种
   `key` 是 `**` 展开、`val` 又不是 `nullptr` 的组合，理论上不可能通过 Parser（`{**d: v}` 在
   Parser 层面就已经是 SyntaxError，见 `test/parser/2_2_2_basic_exprs/compound_dict_test.cpp`），
   但原来的 `check` 完全没有对这层结构性关系做任何断言——只要 C++ 层真造出这种畸形组合（比如
   将来 Parser 改出 bug），会被静默放过。修法：`key` 是 `AstNodeDoubleStar` 时要求 `val` 必须是
   `nullptr`，否则 `error()`；这属于"Parser 结构性保证、只是防御性断言"的一类，跟 `clauses_`
   非空那条是同一个性质。

4. **`check(AstNodeAssign&)`/`check(AstNodeCompoundAssign&)` 里左值检查在重置 `can_star`/
   `can_double_star` 上下文之前做**，跟其余所有 `check(...)` 函数"先存/重置上下文、最后再恢复"
   的统一模式不一致。深入看了一下发现：`check_lvalue`/`check_lvalue_pure` 根本不读取
   `ctx_.can_star`（它们对解构里的 `*lv` 用的是自己直接 `dynamic_cast<AstNodeStar>` 判断，不走
   `ctx_.can_star` 那条路），所以这个顺序目前**不影响任何实际行为**，纯粹是风格不统一。按用户
   要求统一改成"先重置上下文，左值检查和右值检查都放在重置之后"。**顺带在这次深入排查里额外
   发现一个真的会导致漏检查的 bug**：`check_lvalue`/`check_lvalue_pure` 对 `AstNodeIndex`/
   `AstNodeAttr` 只做了"是不是这个类型"的形状判断就直接 `return`，完全没有递归进
   `object_`/`args_`——意味着 `a[break] = 1` 这种赋值目标内部的子表达式，只要外层形状合法
   （确实是 Index/Attr），内部无论写了什么都不会被检查。修法：形状判断通过后额外调一次完整的
   `check(node)`（复用 `check(AstNodeIndex&)`/`check(AstNodeAttr&)` 里本来就有的
   `require_not_null` + 递归逻辑），`check_lvalue`/`check_lvalue_pure`/`check_lvalue_items`
   都因此改成非 const（因为要调非 const 的 `check(...)`）。

5. **`AstNodeCall` 的 `args_`/`kwargs_` 是两个独立 vector，一旦解析完就丢失了原始书写顺序**，
   导致 `f(a=1, 1)`（关键字参数后面又跟位置参数）这种理应报错的写法完全没法在 `SyntaxChecker`
   里检测出来——不是 `SyntaxChecker` 该补的检查漏了，是 `AstNodeCall` 这个结构本身就不足以
   表达"顺序"这件事。用户提议参照 `AstNodeFunc::OneParam` 的做法：改成一个按书写顺序排列的
   vector，每项带类型标签（位置/关键字/`*`展开/`**`展开），再交给 `SyntaxChecker` 按顺序校验。
   **这个我同意，但没有在这轮动手**——这是 AST 节点定义（`ast_node_postfix.h`）+ Parser 的调用
   参数解析逻辑（`parser/Parser.cpp`）+ 现有 Parser 测试里 Call 相关用例的 JSON 断言，三处一起
   牵动的改动，比这轮其余几条纯 `SyntaxChecker` 内部的修正大得多，留到用户确认细节后单独一轮做。

6. **`check(AstNodeDel&)` 完全不递归**：只做了"target_ 是不是 Identifier/Attr"的形状判断，
   连 `require_not_null`/`check_not_null` 都没调用过——如果 `target_` 恰好是 `nullptr`，
   `error()` 里紧接着的 `node.target_->pos_` 会直接空指针解引用崩掉；即便 `target_` 非空，
   `del (f()).attr` 这种 `target_` 是 `Attr` 且 `object_` 里嵌了复杂表达式的情况，`object_`
   里的问题也完全不会被检查到。修法：先 `check_not_null(node.target_, node.pos_)`（顺带完成
   非空断言 + 递归 check），再做形状判断，两个问题一次解决。

## 上面第 4、6 条的后续收尾 + `=`/`op=` 左值范围在 SL.md 里补齐定义

上面"用户重构一遍 SyntaxChecker 后揪出的 6 个问题"那节里，第 4、6 条当时只是给了修法，没记后续
讨论的结论；这里补上：

- **第 6 条（`check(AstNodeDel&)` 不递归）**：修法本身没变（先 `check_not_null(node.target_,
  node.pos_)` 再做形状判断），但按用户要求，整个函数额外包了一层"先存/重置 `ctx_`、最后再恢复"
  的标准写法，跟其余所有 `check(...)` 函数保持一致——单纯风格统一，不影响行为。
- **第 4 条（`=`/`op=` 左边能放的东西范围是否一致）**：讨论延伸出一个新问题——既然已经允许
  `(a, b) = (1, 2)`（解构赋值），那 `(a, b) += (1, 2)` 该不该也允许？结论是**不允许**，理由：
  解构目标没有单一的"旧值"可读，而 `op=` 的语义（3.4.2）依赖"先读旧值、算出新值、再写回"，两者
  矛盾；即便硬要定义"读成元组再做 `+`"，元组的 `+` 是拼接不是逐元素相加，算出来的结果再拿去解构
  几乎必然对不上元素个数，是个纯粹的坑。也符合 Python 的先例（`a, b += 1, 2` 在 Python 里就是
  `SyntaxError`）。
  由此在 SL.md 2.1.5 的运算符表里正式把"左值"拆成了两个概念：**纯左值**（标识符 /
  `target.attr` / `target[index, ...]`）和**左值**（纯左值 ∪ 由纯左值组成的元组/列表解构，
  至多一个纯左值可带 `*` 前缀）。`=` 左边接受左值，`op=` 左边只接受纯左值。"纯左值"这个词此前
  在 SL.md 里完全没定义过（`SyntaxChecker.h` 里 `check_lvalue_pure` 的注释倒是已经在用这个词了，
  代码比文档先行一步），这次一并把定义补齐，3.3 节复合赋值的求值顺序描述也改成显式点名"纯左值"。

## 形参列表 / 调用实参重新设计：解决 item 2、item 5（`OneParam`/`AstNodeCall` 结构性缺陷）

上面第 6 个问题清单里的 item 2（函数参数顺序逻辑错误）和 item 5（`AstNodeCall` 的
`args_`/`kwargs_` 丢失书写顺序）当时都只是临时应付或干脆没动，用户明确说"准备要大改"。这次借着
讨论"要不要引入裸 `*`/`/`"的机会把两处都推翻重做了。

**裸 `*`/`/` 讨论的结论：都不加。** 参考 Python 的 `ast.arguments`（`posonlyargs`/`args`/
`vararg`/`kwonlyargs`/`kw_defaults`/`kwarg`/`defaults` 分组存储）来对比 SL 现状，SL 目前形参
只有 `a`/`*b`/`**c` 三种形状（`a` 独有 `: type`/`= expr`），用户的原话："`/` 在 SL 里没有存在的
意义，裸 `*` 不加新语法，直接用 `*_` 代替"——`*_` 已经能起到"强制后面的形参必须仅关键字传参"的
效果（虽然还是得接受一个永远不用的位置形参收集元组，但语义上跟 Python 的裸 `*` 等价），没必要
为了省这一点再引入新语法。**这条决定不动语法本身，只动"形参列表允许的顺序在标准里怎么写、
AstNode 里怎么存、Parser 怎么解析、SyntaxChecker 怎么检查"这四处。**

**核心设计思路：把"非法状态在数据形状层面就不可表达"，而不是在 SyntaxChecker 里用状态机扫描去
挡。** item 2 那个 bug（`func f(*x, y) {}` 应该合法却报错）的根源就是原来 `OneParam` 是一个打了
`ParamType` tag 的扁平 `vector`，`*args` 前后两个语义完全不同的区域（受"无默认值排前面"约束 vs
不受约束）混在同一个 vector 里，靠一个 `has_seen_star` 布尔标志位在扫描时人工区分——这类状态机
代码正是最容易漏掉边界情况的地方（事实也确实漏了一次）。改法：

- `AstNodeFunc::OneParam` 去掉 `param_type_`/`ParamType`，只保留 `identifier_`/
  `type_annotation_`/`default_value_`（`*args`/`**kwargs` 各自只是裸标识符，不需要这个结构）；
- `AstNodeFunc` 新增 4 个字段对应形参列表的 4 段：`params_`（`*args` 前）、
  `var_args_name_`（`optional<u32string>`）、`kw_only_params_`（`*args` 后、`**kwargs` 前，
  仅关键字形参，形状跟 `params_` 一样支持类型注解/默认值）、`var_kwargs_name_`；
- **`Parser::finish_func_params`** 按这 4 段的顺序解析（`ast_node_func.h`/`Parser.h`/
  `Parser.cpp`），"至多一个 `*args`""`**kwargs` 必须是最后一项"这两条现在是解析到不该出现的
  token 时的自然语法错误（直接 `error(...)`），不再是 SyntaxChecker 的状态机检查；
- **`SyntaxChecker::check(AstNodeFunc&)`** 大幅简化：查重覆盖
  `captures_ ∪ params_ ∪ {var_args_name_} ∪ kw_only_params_ ∪ {var_kwargs_name_}`；
  "无默认值形参必须排在有默认值形参前面"只需要对 `params_` 这一个 vector 线性扫一遍，不再需要
  `has_seen_star` 跨区域标志位；`kw_only_params_` 不做任何顺序检查（结构上已经保证在正确的
  区域）。

**`AstNodeCall` 同一个思路，但拆法不同**：调用实参没有形参那种"由一个显式 token（`*args`）
标记的区域边界"，位置组/关键字组是按每一项自己的形状（`identifier=value` 还是别的）判定的，且
3.3 节 453 行"从前到后逐个求参数的值"要求严格按书写顺序求值——这意味着不管怎么设计，AST 都必须
完整保留原始书写顺序。改法：拆成 `positional_args_`（`vector<AstNodePtr>`，位置实参 + `*expr`
展开，复用已有的 `AstNodeStar` 包裹节点，不新增 tag）和 `keyword_args_`
（`vector<OneKwArg>`，`OneKwArg` 是 `{Kind::Keyword/DoubleStar; keyword_; value_}`）两个字段，
各自内部保持书写顺序。

`finish_call` 改成两阶段解析：一旦某一项归类进关键字组（`identifier=value` 或 `**expr`），后面
再出现位置实参（含 `*expr`）就直接在 Parser 里报 `"positional argument cannot appear after
keyword argument"`——这是跟形参那边讨论后达成一致的选择（原来的实现里 `finish_call` 注释明确
写着"参数顺序合法性由语义层校验"，即刻意让 Parser 保持"傻"，这次讨论后决定改成跟形参一致的
"Parser 阶段式解析直接保证"，不再需要 SyntaxChecker 检查这条顺序）。**一个容易踩的坑**：判断
一项是不是 `**expr` 展开不能只看开头是不是字面的 `**` token——分组括号是透明的（`f((**d))` ≡
`f(**d)`，`test/parser/2_2_2_basic_exprs/compound_dict_test.cpp` 里就有这条回归用例），必须
先 `parse_expr()` 解析完，再 `dynamic_cast<AstNodeDoubleStar*>` 看解析结果的实际类型，不能用
"先 peek token 决定分支、再解析"的写法（第一版实现就是这么栽的，被已有测试当场抓住）。

`SyntaxChecker::check(AstNodeCall&)` 因此也不再需要检查顺序（结构上已保证），只需要对
`positional_args_`/`keyword_args_` 分别设置正确的 `can_star`/`can_double_star` 上下文再递归；
`keyword_args_` 里 `Kind::DoubleStar` 的那一项才允许 `can_double_star`，普通 `Kind::Keyword`
的 `value_` 跟其他任何"纯粹是个值"的位置一样，不允许 `*`/`**` 前缀。

`var_args_pos_`（曾经打算给 `*args` 单独存一个位置字段方便报错）最后没加——现有代码里连普通
形参、capture 都没有单独的位置字段，报错全靠整个函数节点的 `node.pos_` 兜底，单独给 `*args`
加位置纯属跟这条既有惯例不一致的多余设计。

item 2、item 5 都在这轮里彻底解决了；测试同步更新（`test/parser/2_2_6_func/func_test.cpp`、
`test/parser/2_1_5_operators/precedence_test.cpp`、`test/parser/common/combination_test.cpp`、
`test/syntax_checker/func_class_test.cpp`、`test/syntax_checker/dict_call_test.cpp`、

## SyntaxChecker 全字段审计：先判空再解引用 + 每个字段都要检查

用户要求做两件事：1. 在 `Parser.cpp` 的 `finish_func_params`/`finish_call`/`finish_captures` 里
明确写注释，说清楚这几个函数各自保证了什么、把什么留给语义层（SyntaxChecker）；2. 把
`SyntaxChecker.cpp` 里**每一个**节点类型的**每一个**字段过一遍，确认：(a) 每个 `AstNodePtr` 字段
都是先判空（`check_not_null`/`check_nullable`/`require_not_null`）再解引用，明确假设"外部可能
直接篡改了 AST"、Parser 自己的保证不能作为唯一防线；(b) 纯 `Position` 字段不用检查，但凡是
"跟着一个正文数组配对的位置数组"（比如 `decorator_positions_` 配 `decorators_`）都要用
`require_same_size` 查一遍长度。

**结论**：null-check-before-deref 的顺序本身通读一遍下来是对的（`check_lvalue_items` 里
`dynamic_cast` 前有 `require_not_null`、`AstNodeDel` 里 `error()` 消息取 `pos_` 前 `target_`
已经被 `check_not_null` 确认过等等），没找到真正的"先解引用再判空"的顺序错误。但"每个字段都要
检查"这条揪出了 5 处此前遗漏的字段：

1. `AstNodeClass` 的 `captures_`：只查了重名，没查 `capture.identifier_` 本身是不是空字符串——
   跟 `AstNodeFunc` 那边（已经在查）不一致，明明两者共用同一套捕获列表语义；
2. `AstNodeFunc` 的 `var_args_name_`/`var_kwargs_name_`：这两个是 `optional<u32string>`，跟
   `name_` 结构完全一样（要么 `nullopt` 要么非空），但只查了重名（`ensure_unique`），没查空
   字符串这条（`name_` 有查）；
3. `AstNodeIndex::args_`：`a[]` 语法上不允许（Parser 的 `finish_index` 已经
   `if (args.empty()) error(...)`），但 SyntaxChecker 这边从来没有对应的防御性 `require_not_null`
   （跟 `AstNodeIf::clauses_`/`AstNodeCompare::operands_` 这些"Parser 保证最小个数"的既有模式
   不一致）；
4. `AstNodeGlobal::identifier_`：完全没有检查过是不是空字符串——`AstNodeIdentifier` 那边同名字段
   有查，`AstNodeGlobal` 这边彻底漏掉了；
5. `AstNodeTry` 每个 `except` 子句的 `exceptions_`：SL.md 2.2.5.7"每个 except 内 Exception 有
   1 个或多个"，Parser 的 `parse_excs_and_body` 已经 `if (excs.empty()) error(...)`，但
   SyntaxChecker 从来没有对应的防御性 `require_not_null`。

5 处都补上了对应检查，`test/syntax_checker/defensive_test.cpp` 各加一个手工搭畸形 AST 的测试
用例验证。`.ai/run_test.bat` 全绿：SyntaxChecker 49/109（新增 5 个 test case / 6 个 assertion）。

`Parser.cpp` 里 `finish_func_params`/`finish_call`/`finish_captures` 也按要求加了注释，说明各自
在 Parser 层保证了什么、留给语义层检查什么——这样以后再有类似"到底该 Parser 查还是 SyntaxChecker
查"的疑问，直接看这几个函数的注释就有答案，不用重新推一遍。
