## 语言设计决策

### 动态作用域 → 显式捕获

标识符解析收窄成"只查当前帧 `_L`，查不到退回 `_G`"，不沿帧栈向外搜索（动机：模块内函数被外部调用时
不该意外搜到调用者的帧）。访问外层作用域需显式捕获：值捕获（建立时取值）、引用捕获 `&x`（只记
(定义帧, 标识符)，读写转发到定义帧）。捕获不跨层自动传递，中间每层必须显式转发。

`x op= expr` 的内部读取有特例：不适用"退回 `_G`"，未标记 global 时只查 `_L`，找不到直接
`NameError`——保证这一步的读写落在同一帧。因此 `x op= expr` **不等价于** `x = x op expr`。

**引用捕获内存模型**：定义帧字段是对帧对象的普通引用，走统一引用计数/拷贝规则；帧弹出时只把自己的
局部字典置为 `None`（不是空字典，区别于"活着但没有局部变量"），不管谁还持有该帧引用。判活/判死看
局部字典是不是 `None`。**否决过**：强引用整个帧对象（帧永远不回收）；帧维护"谁引用了我"的通知
列表、弹出时清空（对象拷贝时旁路账本不会自动同步）。

值捕获无生命周期限制但不能共享可变状态；引用捕获能共享但离开定义帧生存期后必 `NameError`——共享
可变状态用"值捕获 + 可变对象当盒子"，不加专门的 `Box`/`Wrapper` 类型（list-as-box 够用）。

### `finally` 跳转限制

`expr3` 里跳出这段范围的 `return`/`break`/`continue` 不合法。这项检查纯在编译期完成，不需要运行期
兜底：`expr3` 的内容编译期全部可见；唯一能在运行期往里塞代码的 `eval`，其 `code` 顶层不可能出现
这三者（见下），跳不出 `code` 自身；`eval_isolated` 编译出的代码只作用于它自己那份文件。

`raise` 允许。对齐 Python：`try`/`except` 里的 `return`/`break`/`continue` 以及待传播异常，都等
`finally` 正常结束再生效；`finally` 再抛则新异常取代待完成的跳转或原异常。语言没有
`__context__`/`__cause__`，不做异常链。

### `eval(code)`：共享调用帧，靠"空的静态外层环境"划出可用子集

绕了一圈：最初设计成完全内联 → 因下述几条整体删除、只留 `eval_isolated` → 现在以受限形式回归。

**回归的理由**：`eval_isolated(code, _L)` 顶替不了 `eval('x = 0')`。前者把 `_L` 当作一份新文件的
`_G`，其中的 `x` 只能是那份文件的全局变量；而内联的 `x = 0` 里，`x` 是局部变量、全局变量还是引用
捕获，只有调用帧当时的状态说了算，这件事没有任何写法能替代。

**定稿**：`code` 必须恰好解析出一个表达式（要多条自己写 `{ a; b }`，`{ }` 不引入作用域）。`eval`
跟任何调用一样压帧（执行器的 CALL 无特例），但它自己那一帧全程空着、对 `code` 不可见，`code` 在
调用帧（压 `eval` 这帧之前的栈顶帧）里求值——"等价于没有新帧"是 `eval` 的语义，不是压帧规则里挖洞。

**关键设计**：不列"禁止 `return`/`break`/`continue`"这三条禁令，而是规定 `code` 的**静态外层环境
为空**——不在任何 Program 内，也不在任何循环内。于是现有规则自己把子集切出来：`return` 要求有"离它
最近的 Program"，`break`/`continue` 要求外层有 `for`/`while`，都不满足 → `SyntaxError`；`raise`/
`global`/`import`/赋值/`del`/`try` 不要求任何外层构造 → 照常可用。好处是零新增规则，且嵌套情形
自动正确（`code` 里自己写的 `func` 体是 Program，里面的 `return` 合法；自己写的循环里 `break`
合法；但复合表达式不是 Program，`eval('{ return 1 }')` 仍非法）。

**当初的否决理由，逐条对照**：
- "内联要求'调用点'是编译期概念，但 `eval` 是一等函数值"——不成立了。调用帧是纯运行期概念（压
  `eval` 帧之前的栈顶帧），`f = eval` 照常可用，语义不含糊。
- "跳转信号要跨调用边界回传"——被空外层环境根除，`code` 顶层根本产生不了向外的跳转。
- "堵死'局部变量编译成槽位下标'这类未来实现"——**依然成立，是明知并接受的代价**。`_L` 必须始终是
  真字典（3.10.1 本来就这么规定），换取的正是 Python 做不到的"`eval` 里赋值真的生效"。
- "反面教材 Python `eval`/`exec`/`locals()`"——它烂恰恰是因为函数局部变量是编译期槽位、`locals()`
  只是快照。SL 没这个前提，所以不会重蹈。

`eval` 是普通内置函数（不做成关键字），可以 `f = eval` 传递。

### 链式比较

`< <= > >= != ==` 互相可链，`is` 单独一档优先级（比这六个松），不跟它们混链、也不共用节点类型。
**为什么 `is` 要分开**：`bool` 能跟 `int` 比大小（它实现了 `numbers.Real` 要求的比较，见下面
"`bool` 不再继承 `int`"），若和比较符混链，`a < b is c` 会解析成 `a < (b is c)`，把布尔值当数字比
大小——类型上合法、静默出错，是最危险的一类。拆开后 `a < b is c` 解析成 `(a < b) is c`，即便碰巧
不报错也是一眼假的写法。（注意这条理由不依赖"`bool` 是 `int` 的子类"，那层继承后来去掉了，理由
照样成立。）

### 开放式切片（`None..8` / `3..None`）

不加独立语法，靠 `..` 运算符 + `None` 表达开放端。`None` 本身不参与这个约定——是 `int` 的
`__op_range__`/`__op_rrange__` 把"另一侧是 None"识别成开放端，走普通运算符重载分派。

### 装饰器语法

`@decorator expr` 求值为 `decorator(expr)`；`@deco func f(){...}` 还需要把 `f` 重新绑定到装饰
结果。判断"该不该重新绑定"，否决过两条：①判断值有没有 `__name__`（鸭子类型）——`@staticmethod
outer` 会意外重新绑定 `outer`；②判断 `expr` 语法形状是不是直接的 `func`/`class`——嵌套装饰器
`@d1 @d2 func f(){}` 外层 `expr` 是装饰器表达式不是 func，外层不触发，`d1` 被丢弃。

**最终**：语法层面拆成两个东西，判据只看紧跟着的是不是 `func`/`class` 关键字：`@d1 @d2 ...
func/class ...` 属于 func/class 表达式自己语法的一部分（`decorators_` 是节点自己的字段）；
`@decorator expr`（expr 非紧邻 func/class）永远只是 `decorator(expr)`，无副作用。

**教训**：一个规则的触发条件要靠不断打补丁才能覆盖各种嵌套情况，往往说明从一开始就不该用同一个
语法形式表达两种意图，该在语法层拆开让解析器确定性判断，而不是语义层"猜"——跟"节点拆分原则"
（见 [architecture.md](architecture.md)）是同一条原则的两个应用。

### 命名决策：`match`/`case` → `when`

理由：`switch` 心智预期不对；`match` 常用词太易冲突；参考 Kotlin `when`，碰撞风险低。候选并否决：
`where`（LINQ/SQL 强关联过滤）、`given`（Scala 隐式参数）、`branch`（像名词）、`select`
（Go/SQL 已占用）、`pick`（太随意）。`case` 暂留，`when` 完整设计搁置。

### `++`/`--` 整体从语言里砍掉

没有后缀形式，丢了 C 系"真正好用"的场景（`arr[i++]`），剩下的前缀用法跟 `x += 1` 值语义完全一样，
纯粹少打两个字符换来专门一档优先级 + 专门节点 + 专门左值校验，投入产出不成比例。

### 空 `{}`：维持复合表达式语义，不是空字典

一度倾向改成空字典（`()`/`[]` 为空都优先当空字面量集合）。**否决**：空字典本来就是 `dict()` 写的，
不靠 `{}`；判别规则"要么 `**` 开头、要么第一个表达式后紧跟 `:`，否则复合表达式"统一适用，空的情况
自然落到"都不满足"分支。关键反例：`a = if (cond) {}` 里想表达"这个分支什么都不做"，如果 `{}` 是空
字典会让 `a` 变成空字典而不是 `None`，而空字典和 `None` 一样 falsy，这类错误会长期潜伏。要空操作
写 `None`，要空字典写 `dict()`，`{}` 不需要身兼二职。

### `if`/`while`/`for` 条件槽拒绝裸赋值 `=`

防 `if (x = 5)` 手误坑（SL 是动态类型，没有类型系统能免费防）。只限制 `if`/`while` 的 `cond`、
`for` 三槽形式中间槽；不限制 `for` 的 `init`/`inc`（这两槽存在的意义就是赋值）；只挡裸 `=`，不挡
`+=` 等复合赋值。真要在条件里赋值需要显式再套一层括号 `if ((x = y))`。

**因此"冗余括号没有任何效果"这个说法必须收窄**：冗余括号不改变值/类型/求值顺序，但它是实实在在写
在源码里的语法结构，凡是按**写出来的形状**给的语法限制都看它在不在——这条裸赋值限制就是唯一的现存
例子（`if (x = y)` 非法、`if ((x = y))` 合法）。以后再加这类纯语法限制，记得一并想清楚括号算不算。

`for (cond) body` 这种单槽纯条件形式**故意不提供**——`while $ (cond) body` 已经能做到完全一样的
效果，多一个入口只会削弱"`while` 是纯条件循环专用关键字"的区分。

### 类型注解设计

问题：没有泛型，没法表达"返回类型跟某个参数类型相同"；类型注解在类建立时求值，此刻类自己还没建好。
五版方案，否决前四个：

1. 内置单例 `Self`，类体收集属性那步替换成类对象——否，解出来的是基类自己建立那刻冻死的具体值，
   子类继承时协变做不到。
2. `Self` 读"绑定给第一个参数的值"的类型——否，绑定完成后这个信息早就丢了，且 SL 没有语法规定
   方法第一个形参必须是 `self`。
3. 用 `TypeVar` 顶替（`self: (T = TypeVar())`）——否，`MyInt.__op_add__("1", "2")` 这种不通过
   实例硬调的写法能通过检查，因为无约束 `TypeVar` 第一次出现只记基准，没人验证这个基准对不对。
4. `TypeVar` 加 `bound` 参数锚定到具体类——技术上能堵住上面的洞，但否决：`TypeVar` 该管的只是
   "多个位置类型互相一致"，混进"是不是某个特定类实例"，职责不单一。
5. 字符串注解惰性解析，推迟到第一次调用时按名字重新查找——技术可行，但否决：跟"建立时求值"两套
   时机并存不统一；按名字查找在"变量是引用语义"下不牢靠，名字随时可能被重新绑定。

**最终方案**：类型注解允许 `type | CompoundType | TypeVar`（正常检查）或 `str`（纯标签不参与
检查，等价无注解）。真正需要自引用/前向引用检查时，改为函数体内手动 `isinstance`（调用时才执行，
那时类早建好）。`TypeVar.bound` 只能是 `type | CompoundType`（不支持字符串，也不能是另一个
`TypeVar`——一致性检查按调用时形参顺序单趟扫描，`bound` 若指向另一个 `TypeVar` 会依赖两者相对
顺序，理解错了会悄悄放水）。

**牵出的更底层漏洞**：`class` 语法完全没有捕获列表（`func` 有），而"未捕获标识符只查当前帧与全局
帧"意味着类体、类体里任何方法体都够不到外层函数的局部变量——"局部定义一个类"这个模式完全走不通。
**修法**：给 `class` 补上跟 `func` 一样的捕获列表语法，放在基类之后（基类在类体帧建立前的外层帧
求值，捕获是新帧建立之后处理的，文本顺序对应求值顺序；且基类/捕获是两个毫不相关的概念，特意不
沿用 `func` 的 `[捕获](形参)` 视觉布局）。

**顺带化简**：引用捕获从"每个名字各存一份 (x, 定义帧)"改成"函数/类建立时无条件记住定义帧（不管
有没有捕获），引用捕获退化成只需要记名字集合"——一个函数/类只可能有一个定义帧，之前是重复存储。
这个"无条件定义帧"同时是让跨模块调用正确解析全局作用域的必要前提（见下面帧栈一节）。类的引用捕获
不会变成类属性（`_L` 只收集局部字典里的值捕获），类的引用捕获链式转发也不会有死帧问题（引用捕获
集合挂在函数/类对象自己身上，不是挂在帧上）。

### `import` 语义：module/package 概念仿 Python

多段名字（`import os.path`）原来写的"等价于 `os = import('os.path')`"站不住：按"`import()` 不
透明整串查找"这条流程，调用形态该返回叶子模块，绑给 `os` 就错了。中间讨论过一个更省事的方案：
loader 永远不解析点号，`a.b` 能不能访问纯靠 `a` 模块自己有没有挂对应属性——能自洽，但用户认为不如
直接照抄 Python 的 module/package 模型来得实在，否决。

定稿：module 对应文件、package 对应目录（内容是 `__init__.sl`；没有则视同空文件，不报错），两者
产出同一种模块对象，没有独立的 package 类型。多段名字从左到右逐段导入，逐层把子模块挂为上一级的
同名属性。调用形态返回**最后一段**（跟 `importlib.import_module` 一致）；关键字形态多段时只绑定
**第一段**（跟 Python `import` 语句一致）——这是两种形态在多段情形下唯一的差异，不是疏漏。完整
规则见 SL.md 对应章节。搜索路径、循环 import、相对导入仍未设计，故意搁置。

### `import` 的 AST 表示

两种语法形态**不**塞进一个节点里用 variant 分叉，拆成 `AstNodeImportKw`/`AstNodeImportCall` 两个
节点（理由见 [architecture.md](architecture.md) 的节点拆分原则）。

调用形态一度打算复用 `AstNodeCall`，被调对象填 `AstNodeIdentifier{U"import"}`——**否决**：这要求
运行期真的按名字查到一个 `import` 对象，但 `import` 是语言构造不是内置函数，既不在 4.1 里也不在
内置表里，这个标识符压根查不到；而且造出来之后 `_G['import'] = print` 就能把调用形态劫持掉
（内置名字本来就可以被 `_L`/`_G` 里的同名项 shadow），关键字形态不查名字、不受影响——同一个语言
构造两种写法一个能被劫持一个不能，这个分叉比劫持本身更坑。也考虑过给被调对象加个
零字段标记节点，同样否决：在"一切皆表达式"的语言里这个节点求值必须产出某个值（一个 4.1 里不存在
的"import 函数对象"）。

最终：`AstNodeImportCall` 没有被调对象槽位——`import` 是运算符本身，不产生这个中间值。

关键字形态存 `std::vector<std::u32string>`，不存 `AstNodeAttr` 链：`import os.path` 根本没对
`os` 做属性访问（是两次导入 + 一次 `os.path = <模块对象>` 赋值），存成属性链会让泛型递归的
`AstNodeAttr` 消费者把被绑定的 `os` 当成一次读取，语义反了。

换行规则：`import` 后无条件允许换行（跟 `global`/`del` 一致），两种形态一视同仁；段名之间的 `.`
跟属性访问 `x.y` 逐字对齐。调用形态的 `(` 不比 `global`/`del` 更严格（曾按"该像普通调用那样绑定"
判 `import\n(...)` 为错误，被否决：拆成独立节点之后 `(` 不再是接在某个被调表达式后面的后缀，而是
`import(...)` 整体的一部分）。

### 真值统一到 `__bool__`

原文只列了一张"哪些内置对象为假"的清单，读起来像是真值由解释器写死的。改成：任意对象 `x` 的真值
就是 `type(x).__bool__(x)` 的返回值（必须是 `bool`，否则 `TypeError`）；`object` 自带一个无条件
返回 `True` 的 `__bool__`，所以任何对象都有真值，自定义类不重载就恒为真。原来那张清单降级成"部分
内置类型对 `__bool__` 的重载结果"。

`__bool__` 没有进协议那一章：那章的判定标准是"方法存不存在决定对象能不能参与某机制"，而 `__bool__`
因为 `object` 兜底永远存在，不存在"满足与否"的问题。也不属于运算符重载表（不对应任何运算符，`not`
明确不可重载）。

### 内置名字放在一张独立的"内置表"里，不放 `_G`

`print` 等内置名字原先没规定住在哪，塞进 `_G` 很不合适（每份文件的 `_G` 都得预先灌一份、还会被
`del` 掉）。定稿：单独一张固定、全局唯一、只读的**内置表**，只在按标识符**读取**且当前帧与它所属
全局帧都没有该名字时兜底（`_L` → `_G` → 内置表）。写和删永远不碰它：`print = x` 只是在 `_L`/`_G`
新建一项来 **shadow**，`del print`（没被 shadow 过时）照常 `NameError`。

**4.3 内置模块不在内置表里**：模块名只能靠 `import` 主动导入才绑定到标识符，没 `import` 过直接写
`numbers` 就是 `NameError`。（`import` 找不到同名源文件/目录时才去内置模块名里找，那是加载算法的
事，跟标识符解析是两回事。）

### `bool` 不再继承 `int`，改继承 `numbers.Real`

继承 `int` 会把位运算等一堆"只有 `int` 才讲得通"的东西带给一个只有两个值的类型，`isinstance(True,
int)` 成立也是 Python 被诟病过的历史包袱。改成继承 `numbers.Real`：混算行为几乎不变（`True == 1`、
`True + 1 == 2` 照旧），但不是靠继承白拿，而是 `bool` 自己实现 `numbers.Real` 要求的四则运算与
大小比较，参与运算前把 `True`/`False` 折算成 `1`/`0`，再复用 `int` 的实现；
结果类型与对应的 int 运算相同（不是 `bool`）。因此 `True + 1` 是 int，`True / 2` 是 decimal。

**没继承 `object` 而是继承 `numbers.Real`**：`bool` 确实能正确参与四则运算和比较，让
`isinstance(x, numbers.Real)` 对它成立符合通用数值代码的预期；要甩掉的只是 `int` 特有的那部分。

**连带后果（都是有意的）**：位运算 `~ & ^ | << >>`（SL.md 写的是"对于 int"）对 `bool` 变成
`TypeError`；容器重复次数（"非负的 int"）也不收 `bool`，`'a' * True` 是 `TypeError`；`FuncGroup`
分派时 `f(True)` 不再命中 `x: int` 那条候选。折叠器里对应地把"是不是 int"拆成 `is_int`（真 int）和
`is_int_family`（bool 或 int）两个谓词，强迫每个调用点显式选一次。

### 复合类型 `[]`：tuple 与 list 完全平行

`tuple[T1, T2, ...]` / `list[T1, T2, ...]` 定长、按位置检查；一个类型参数即定长 1（`list[int]`
不是任意长的 int 列表）。齐次用 `tuple[T, ...]` / `list[T, ...]`。`dict` 只有 `dict[K, V]`，
`set` 只有 `set[T]`。

### `unsupported` 从"打标记的内置函数"改成 `Descriptor` 子类

原设计 `unsupported(v)` 把 `v.__is_unsupported__` 置 `True` 再原样返回 `v`——一边骗
`isinstance`/协议检查说这个方法不满足，一边又保留 `v` 的可调用性，语义分裂；而且这个标记是"活的"
（每次协议检查都要重新扫），随时可能被 `attrs` 绕开。

改成内置类 `unsupported(name=None)`，`Descriptor` 子类，`get` 无条件抛 `AttributeError`。类体里写
`some_meth = unsupported`（收集属性那步自动补成 `unsupported(name)`，不用手写两遍名字）或
`unsupported('自定义消息')`，存进**描述器表**。于是"标记"和"行为"是同一个东西，不存在被绕开的窗口。

**优先级不用单独规定**：它进的是描述器表，自动遵守"MRO 上第一个命中的描述器表项获胜"，子类的
`unsupported` 正常盖住祖先类里的真实方法描述器。`protocols` 的鸭子类型检查也不再单独扫标记，改成
复用同一次 MRO 查找："查到的那一项是不是 `unsupported` 的实例"。

**`abstractmethod` 不跟着改**：它只在类建立那一刻被读一次、烤进 `__abstractmethods__` 就定型，
事后改标记没人再看，不存在 `unsupported` 那种被绕开的漏洞。两者还能正交组合：
`foo = abstractmethod(unsupported)` 天然表达"没有默认实现、子类必须重写"。

### 帧栈允许多个全局帧，`_G` 不再是"栈底"

原文写"栈底为全局帧"，跟已定稿的 `import`/`eval_isolated` 语义矛盾：这两者都会在栈的任意位置再压
一个文件级的帧，运行期同时存在多份 `_G`。

改法：帧显式分成**全局帧**（执行一份文件压入）与**局部帧**（函数调用、类体执行压入），每个帧再记
一条"所属的全局帧"——全局帧属于自己，局部帧属于"建立它的那个函数/类的定义帧所属的全局帧"。`_L` 是
栈顶帧的局部字典，`_G` 是当前帧所属全局帧的局部字典。

关键是这条链走**定义帧**、不走栈：一个函数不管从哪份文件里被调用，它的全局变量始终是它自己那份
文件的（等价于 Python 把 `__globals__` 绑在定义处的模块上）。若按"从栈顶往下找最近的全局帧"定义，
A 文件里的函数被 B 文件调用时全局变量会跑到 B 上去，是动态作用域灾难。定义帧这个概念本来就为引用
捕获而存在，直接复用，没有新增机制。

### 描述器移出类的属性表，单独一张描述器表

起因：属性协议一边把属性做成字典，一边靠描述器插一嘴、还兼着"防御"（方法描述器不实现 `set`，所以
`int.__op_add__ = f` 抛 `AttributeError`），但这层防御被 `attrs` 一扯就开——
`attrs(int)['__op_add__'] = f` 直接改掉 `int` 的行为。

比较过四条路：①黑名单锁住某些东西禁用 `attrs`（`__slots__`/`__dict__` 那套，无原则性答案）；②类的
属性表只读（"怎么只读"要新造只读视图类型，且挡住了合法的类级写入）；③`attrs` 返回一个继承 dict
但在 `[]` 上加检查的实例（继承 dict 却撒谎，破坏映射协议可替换性）；④**描述器全部搬到另一张表**。
选④，它顺带把②吃掉了：危险槽位根本不在 `attrs` 里，`attrs` 就能继续是一个诚实的、可读可写的普通
`dict`，类和实例一视同仁。

定稿：①描述器表只在类建立时确定，此后不变（类建立完之后再 `C.p = property(...)` 只是写进属性表、
成为普通类属性，不参与绑定）；②描述器表整体优先于属性表，同名时属性表那份是死项；③描述器表既不
通过属性名暴露，`attrs` 也取不到（唯一例外：`property.get` 经由类访问时故意返回自己供内省）。
因此实例不能用同名属性覆盖类上的方法：方法在描述器表里，写入走 `MethodDescriptor.set`，默认
`AttributeError`。不引入 Python 那套数据/非数据描述器区分。

实例侧不分两张表：查找规则只查 `type(o)` 的 MRO，实例属性表里放个描述器对象就只是个普通值——实例
属性表里没有任何解释器依赖的不变量，被旁路写也只会写出个被描述器遮蔽的死项。

**读/写/删三条规则的第 1 条必须对称**：都得先判"`o` 本身是类就查它自己 MRO 的描述器表"。曾经只有
读有这条特判，于是 `int.__op_add__ = f` 查 `type(int)`（即 `type`）的描述器表、查不到，静默写进
`int` 的属性表变成死项——那层"方法描述器不实现 `set` 所以报 `AttributeError`"的防御等于没有。

**`get(self, obj)` 不传属主类**（不像 Python 的 `__get__(self, obj, objtype)`）：靠
`isinstance(obj, type)` 一个判据区分经实例访问/经类访问。成立的前提是 `type` 是唯一元类且 final
（用户定义不出元类），因此"`obj` 是类"⟺"经类访问"；经实例访问时属主类就是 `type(obj)`，不用传。
**唯一的边界**：给 `type` 自己加需要绑定的普通方法或 `property` 会破坏这个等价（类是 `type` 的
实例，此时经实例访问的 `obj` 也是个类）。已在 SL.md 3.9.1.1 写死"别给 `type` 加这种成员"；运算符
方法不受影响，它们本来就是 `type(a).__op_xxx__(a, ...)` 显式传第一参数。

**描述器表的开放方式**：不新开 `descriptors()` 内置函数（用得极少却要长期占一个内置名字）；不做成
`cls.__descriptors__`（任何类在类体里定义同名的东西就会遮蔽它）。最终给 `attrs` 加参数
`attrs(obj, table='attributes')`，`table='descriptors'` 返回 `frozendict`（只读）。**`attrs` 保持
自由函数，不做成方法、也不给它配 `__attrs__` 钩子**：`attrs` 的全部价值在于它是唯一一扇不经过属性
协议的窗，做成方法就等于放回它本该绕开的机制里（能被 `__getattr__`/子类重载拦截）。

`frozendict` 只冻表、不冻值：拿到 `MethodDescriptor` 之后 `attrs(它)['func'] = evil` 照样能改
`int` 的行为。故内置描述器（`MethodDescriptor`/`property`/`classmethod`）持有的函数不放进自己的
属性表，走解释器内部引用；`staticmethod` 不在此列，它不是描述器，`v.func` 是货真价实的属性。

**`MethodDescriptor` 不是内置类**：它是 SL 本体（类体收集属性那步）产生的类，不在 4.2、也不在内置
表里，源码中写不出这个名字，只能通过 `attrs(cls, 'descriptors')` 拿到它的实例。凡是这种"解释器
自己造、用户按名字够不到"的类都别往 4.2/4.4 里加——那两处是"内置表里有哪些名字"的清单，不是"运行期
存在哪些类"的清单。

`MethodDescriptor.get(self, obj)` 跟 `property`/`classmethod` 一样必须分 `isinstance(obj, type)`
两路：经由实例访问才把 `obj` 绑成第一参数，经由类访问（`C.method`）不绑定、直接返回持有的函数。
早期写成无条件绑定，会让 `C.method` 拿到"把类 `C` 绑成 self"的东西，已改正。

### `for`/`while` 收集模式扩展：`$ *`、`$$`、`$$ **`

补上字典推导式的空缺。最好的说法不是"`$` 后面若有则必须是 `*`"这条规则，而是**两个记号各管一个
轴**：第一个（`$`/`$$`）定结果容器（list/dict），第二个（`*`/`**`）定每轮的值怎么进容器（整体一项
/ 展开一批）。配对约束是推出来的——展开方式必须跟容器种类匹配，复用展开语法里 `*` 对可迭代、`**`
对映射的既有分工。

**记号挂在 `for` 上而不是挂在被收集的表达式上**（不写成 `for $ (i : xs) *e`）。后者看着更贴合展开
语法的老位置，实际不行：`expr` 可以是 `{ ...; e }` 或 `if (c) a else b`，`*` 就得允许出现在复合
表达式末项、`if` 各分支里，规则变成"收集模式的 expr 及一切能成为它的值的子表达式"，非局部、难写
难查。挂在 `for` 上它就是这个循环的一个静态事实。代价：这个 `*` 不再是展开语法（没有操作数），是
模式修饰符。

**`$$` 每轮 `expr` 的形状定为"相当于 `(k, v) = expr`"**，即恰好产出 2 个元素的可迭代对象，不必是
`tuple`。决定性理由：迭代模式 `for (k, v : pairs)` 已经在按解构赋值规则拆每个元素了，同一个构造里
不能对"一对"有两套判定。已知后果并接受：两字符 str 会被当成合法 pair（同 Python 的
`dict(['ab'])`）。

### `float` → `decimal`：十进制、任意精度；二进制浮点降级成 `raw_float`

`int` 早就是高精度的，`float` 是数值塔里唯一"精度取决于硬件"的异类；而且字面量是十进制写的，
`0.1` 在词法分析那一刻就已经不是 `0.1`——这是所有浮点惊吓的源头。SL 定位是脚本、方便优先于速度，
于是换成十进制浮点 `decimal`（`符号 × 系数 × 10^指数`，系数任意精度）。原来的 double 以后以
`raw_float` 身份回来（跟 `raw_int` 一桌），价值只剩速度和与 C/文件格式互通。

**改名而不是沿用 `float`**：老 float 迟早以原生身份回来，两个类型不能都叫 float；而且各语言里
`float` 都背着"`0.1 + 0.2 != 0.3`"的包袱，这次改动的全部意义就是干掉这个默认假设。

**否决了有理数（分数）**：`1/3` 精确、`1/3*3 == 1` 成立，看着更"精确"，但显示两面派（打印 `1/3`
就不是小数类型了，打印截断小数又破坏往返）、无理运算照样得舍入（等于同时背两套精确性模型）、
分母静默膨胀（累加 `1/k` 几百项就是几千位的分母）。

**代价，别忘了**：超越函数得自己写。SL.md 允许 `x ** y` 的非整数指数，也就是 `2 ** 0.5` 必须算得
出来——任意精度下要靠牛顿迭代开方 + `exp(y·ln x)`，还得带保护位。精度固定这一点帮了大忙：保护位
数量有界，不用写通用实现。

### 科学计数法字面量：尾数带不带小数点决定 int 还是 decimal，纯语法判定不求值

语法：尾数（int 或 decimal 字面量）后面跟 `[eE][+-]?digits`，指数部分同样遵守"不允许前导零，
单独一个 `0` 除外"。`+` 可省略，`-` 不可省略。整体值是"尾数 × 10^指数"。

**类型只看尾数带不带小数点，不看指数正负、更不看数值算出来是不是整数**：尾数不带小数点时，
必须搭配非负指数，整体是 int（`1e9` 是 int，值 `1000000000`）；尾数带小数点时指数可正可负，
整体恒是 decimal（`1.0e9`、`1.0e-9`）。跟 `float → decimal` 一节同一个精神：类型是字面量写下的
样子决定的静态事实，不是运行时/编译期求值算出来的——`100e-1` 数值上恰好是整数 `10`，也不例外，
一律走"尾数不带小数点 + 指数为负 = 不合法"这条。

**尾数不带小数点、指数为负（如 `1e-9`）直接判成不合法，不是自动退化成 decimal**：曾经考虑过让
它退化成 decimal（跟 Python "只要有 `e` 就是 float" 一致，也更宽松），否决了——那样"是不是 int"
就得同时看两个信号（尾数带不带点 + 指数正负）才能判定，且两个信号还能互相覆盖（点决定，点没有
时指数说了算），概念上不干净；改成"不合法"之后，规则退化成一句话："尾数带小数点 ⟺ decimal"，
指数的正负只决定"这条 int 字面量合不合法"，不参与决定类型本身。代价是想写一个很小的 decimal
时不能省 `.0`（`1e-9` 不行，必须 `1.0e-9`），换来的是类型判定规则没有例外、不需要读指数才能确定
一个字面量是 int 还是 decimal。

**int 分支的指数上限定为 65536，decimal 分支不设限**：`decimal` 的系数指数分开存，指数再大也不会
真去材料化一个天文数字（`1.0e999999999` 不炸内存）；但 `int` 只有裸值，`1e999999999` 得真造一个
十亿位的 `BigInt`，那是小时级/爆内存。**一度决定"跟 `BigInt::pow` 一样不设上限、留给 VM 资源
guard"，后来推翻了**——`pow` 的操作数可以是变量、上限只能是运行时策略；而字面量的指数是写死在
源码里的静态常量，编译期就能判，没有理由拖到运行时。

**限制只针对 `e` 记法，手写的长字面量不受限**（`1` 后面手写 70000 个 `0` 合法，`1e70000` 不合法）。
这不是双标，是两种写法的代价本来就不对称：手写 n 位数，源码里就得有 n 个字符，长度即成本、
一眼看得见；`e` 记法几个字符就能要一个天文数字。

**65536 这个数是量过的**（本机 `/O2`，naive O(n²) 的 `BigInt`）：

| 量级 | `1e{k}` 走 `pow` 展开 | 手写等长字面量解析 |
|---|---|---|
| 10^10000 | 0.3 ms | 3 ms |
| 10^65536 | 11 ms | 138 ms |
| 10^200000 | 124 ms | 1.3 s |
| 10^1000000 | 3.8 s | 26 s |

选它的硬理由不是"够大"，是**在这个边界上被限制的写法（11 ms）比不受限制的写法（138 ms）还便宜
12 倍**——于是这条限制不可能被指责成"比放行的路径更严"。同时它确实挡住了危险区间：10^10⁶ 已经
是肉眼可见的卡顿。顺带一提，展开要走 `mantissa * BigInt(10).pow(exp)`，别拼出数字串再解析：
`from_decimal_string` 是逐位 `*10` 的 O(n²)，同量级下比 `pow` 慢一个数量级（表里两列就是这个差）。

**这条限制归 lexer 管，不下沉到 `BigInt`**（因此 `BigInt::from_decimal_string` 接受任意大的指数，
只在文档里注明风险）。理由有三条，都指向同一处：这是**源码形态的政策**，不是数值库的不变量。
其一，已有先例且是同一类规则——lexer 现在就在管"不允许前导零"，而 `BigInt::from_decimal_string("007")`
照样返回 `7`（还有测试钉着）；"SL 的字面量政策"与"BigInt 的解析宽容度"本来就分两层。其二，
`BigInt` 头文件自己立过规矩：它抛 `std::domain_error` 而不是 `MathError`，因为"不知道、也不该知道
SL 的异常类型体系"，65536 同理。其三，规则内容本身就是"手写不限、`e` 记法限死"，而 `BigInt` 拿到
的都是字符串，看不出、也不该关心它来自哪种写法。

**代价**：`decimal` 的 `str()` 在系数恰好一位数字时，科学计数法输出不带小数点（如 `1E+30`）——
这类输出粘贴回源码当字面量会被读成 int，不是 decimal，往返静默换类型。见 SL.md 4.2.6 `str` 那条
的说明；真要保住 decimal 类型，要么手动补一位小数（`1.0E+30`），要么走 `decimal(...)` 构造。

### decimal 的精度模型：抄 Python，每个运算都按上下文舍入

一度设计成"精确优先"（`+ - * // %` 恒精确，只有除不尽的 `/` 和无理运算才舍入），**否决了**：

1. **位数没有上限**。`x = x / 2` 放进循环，一千轮就是一千位，静默变慢变大；而除法恰恰是用户默认
   "结果不会变大"的地方。
2. **规则是锯齿状的**：`1/8` 精确、`1/6` 舍入、`1/5` 精确、`1/7` 舍入——精不精确取决于分母的质因数。

改成全舍入几乎不亏：`prec` 默认 28 时，"每个运算舍到 28 位"和"精确"在真实脚本里区分不出来
（`0.1 + 0.2 == 0.3` 照样为真，结果本来就只要 1 位），舍入只在 28 位以上才咬人。卖点没丢，
成本有了上限。

**构造不舍入、运算才舍入**：字面量、`decimal(x)`、int/bool 提升都精确保留全部位数。
`+x`/`-x`/`abs` 是运算，按上下文舍入；`+x` 不是恒等（IBM 规范如此，`BigDec::plus` 已按此实现）。

**标度是值的一部分，不做规范化**：`1.50` 与 `1.5` 值相等但 `str` 不同。一度想反过来（剥掉末尾零、
一个值一种形状），抄 Python 之后不这么干——"理想指数"规则让 `1.10 + 2.00` 得到 `3.10`，金额计算
不用补零，那是 decimal 最主要的用途。

### decimal 的上下文：全局可变 + 每个方法可传临时的

`decimal` 是**类**不是模块：`Context`、`getcontext`、`setcontext`、各信号类都是它的类属性；各舍入
常量挂在 `Context` 上（它们唯一用途就是当 `Context.rounding` 的取值，而挂在 `decimal` 上会从每个
decimal 实例上看得见）。

一度反对可变全局上下文（动态作用域、静默错值、机制过重），在"每个运算都舍入"定下来之后这些反对
不成立了：上下文管的是每一个运算，机制和范围就匹配了。代价照单收下——它确实是动态作用域，
`x / 3` 的结果取决于谁改过上下文。

**临时上下文走方法的可选末位参数**（`__op_div__(self, other, ctx=None)`），每个这样的 dunder 配一个
去掉 `__op_` 前缀和尾下划线的别名（`div`、`add`……），于是写 `a.div(b, ctx)`。**`Context` 不挂
`ctx.divide(a, b)` 那套算术方法**：那和 `a.div(b, ctx)` 是同一件事的第二种写法，两套等价 API 是净
负担（Python 两套都有是历史层积，它的 Context 早于 dunder 的 context 参数）。已知代价：左操作数是
int 时够不着，`1 / 3` 想换精度得写 `decimal(1).div(3, ctx)`。

**删掉的三个 Python 字段/类**：`capitals`（`E`/`e` 大小写是显示开关，算术环境里不该有显示选项）、
`clamp`（只为 IEEE 定宽交换格式服务，SL 的 decimal 没有定宽表示）、`FloatOperation`（专门拦截
Decimal 与二进制浮点混用，SL 没有这种混用）。

**保留了 `Infinity`/`NaN`/`sNaN`/负零**：traps 可配置，就必须有"不设陷阱时返回什么"，否则 traps 是
空壳。默认三个陷阱全开，正常用碰不到。附带好处：decimal 的 NaN 参与序比较是抛 `InvalidOperation`
而不是静默返回 `False`，排序不会得到无声的错误结果。

**`//` 不采纳 IBM 规范的 `divide-integer`（向零截断）**：SL 已明写"`//` 永远向负无穷"，跟着抄会把
Python 自己 `int` 与 `Decimal` 取整方向不一致的毛病引进来。

### 结果为 decimal 的常量折叠一律禁掉

它们按运行时的当前上下文舍入，编译期不知道那时的 `prec`/`rounding`，折了就可能与实际执行的结果
不一致。这跟 int 折叠**不是一回事**：int 用 `int64_t` 折、溢出就不折，是"保守但正确"；decimal 用
double 折 `0.1 + 0.2` 会得到 `0.30000000000000004`，那是**错值**，不是漏折。

**结果为 bool 的比较照折**：比较不舍入，它唯一查上下文的场合是 NaN 触发信号，而 NaN 只能由构造
调用产生，调用本身就不参与折叠。

`StaticEvaler` 里整套 float 折叠（`node_to_double`/`std::pow`/`std::fmod`/`make_float`）都要按这条
清理，不是改改名就完事。

### 反向运算符名用 `__rop_xxx__`，不是 Python 式的 `__op_rxxx__`

Python 的 `__radd__` 能忍，是因为正向名就叫 `__add__`；SL 前面多一段 `__op_`，`r` 就挤进了操作名
内部：`__op_rshift__` 是 `>>` 本身却长得像 "reverse shift"，`<<`/`>>` 的反向会变成
`__op_rlshift__` / `__op_rrshift__`。把 `r` 贴到 `op` 上，规则就是一句话：正向名把 `__op_` 换成
`__rop_`，操作名一个字母不动。

`__rop_*` 的参数顺序与方向统一，不给任何一个开特例：`type(b).__rop_sub__(b, a)` 算的是 `a - b`，
`__rop_cmp__(b, a)` 返回的是 `a` 相对 `b` 的符号。

### `__op_cmp__`：三路比较回退，省掉"每个有序类写 12 个方法"

六个比较运算符在每一侧的自有方法落空后，再试该侧的 `__op_cmp__`/`__rop_cmp__`，然后才换边、才
报错。它**不对应任何运算符**（不设 `<=>` 语法），返回 int（负/0/正）；`NotImplemented` 是弃权、
继续下一步——这条豁免必须有，否则 cmp 没法对不认识的类型弃权，回退链就断了；其他非 int 抛
`TypeError`，且这条只约束解释器的这次调用，手写 `obj.__op_cmp__(other)` 返回什么都行。

**连带改了 `object.__op_eq__`**：它原本按身份比较，于是 `==` 在 MRO 上永远命中它，`__op_cmp__`
这一步对 `==` 永远到不了——只写 `__op_cmp__` 的类会得到"`a < b` 假、`a > b` 假、`a == b` 也假"。
改成"是同一对象返回 `True`，否则返回 `NotImplemented`"，身份比较挪成 `==`/`!=` 整条链落空后的最终
兜底（`<`/`<=`/`>`/`>=` 落空仍抛 `TypeError`）。

**`!=` 多一条"`__op_eq__` 取反"**：最常见的类是只写 `__op_eq__` + `__hash__`、根本没有序的那种，
不加这条它们会静默失去 `!=`。互推只发生在 `==` 与 `!=` 之间——这两个是定义上的补；`<` 与 `>=` 只在
全序下才互补，偏序里 `not (a >= b)` 不等于 `a < b`，所以 **`<` 绝不退化成"不 `>=`"**。

### 不搬 C++ `<compare>` 那套

**`<=>` 运算符不要**：它在 C++ 里的价值是让编译器自动生成六个运算符，而这个价值 SL 用
`__op_cmp__` 回退已经兑现了；再加运算符只多买到"在源码里直接拿到符号"，却要占一个优先级档、起
名字、还要回答"`a <=> b <=> c` 算什么"（链式比较规则里它是异类）。真需要就加内置函数 `cmp(a, b)`，
不占语法位。

**三种序类别（strong/weak/partial）不要**：strong 与 weak 的区别在 C++ 里有消费者（模板、算法
契约），SL 里没有任何东西会读它——而 SL 遍地是 weak 的情形（`1 == 1.0`、`1.50 == 1.5`），纯文档、
零机制。

`partial` 的 `unordered` 倒能补上"`__op_cmp__` 只能表达全序"这个缺口，现在也不加：偏序类型少，
还得连带定义"不可比时 `<` 返回 `False` 还是报错"（decimal 的 NaN 选了报错，浮点传统选 `False`）。
**这道门是开着的**：现在 `__op_cmp__` 返回 `None` 落在"非 int → `TypeError`"里，以后拿 `None` 表示
不可比是纯放宽，不会让今天合法的程序改变行为。

### `raw_int` / `raw_float`：下个版本才加，设计已经定了

**定位**：逃生舱，只为速度和与 C/文件格式互通存在。行为几乎全部委托 C++——该 NaN 就 NaN、该回绕
就回绕、不主动报错。

**档位判据是"C++ 原生就有 + 宽度确定"**：`raw_int` 八档 `i8`/`i16`/`i32`/`i64`/`u8`/`u16`/`u32`/
`u64`（`<cstdint>` 定宽类型），`raw_float` 两档 `f32`/`f64`（IEEE binary32/binary64）。
`raw_int`、`raw_float` 本身是抽象基类，供 `isinstance` 用。

**不要 128 位、不要 `long double`**：`__int128`/`__float128` 是 GCC/Clang 扩展，MSVC 没有，而项目
要支持纯 `cl.exe`；自己软件模拟就不再是"委托 C++"，而且模拟出来的东西比现成的高精度 `int` 又慢又
不精确，需求接近零。`long double` 更直接——MSVC 上 64 位、GCC x86 上 80 位，宽度取决于平台，跟
raw 要的"行为确定"正好相反。哪天 128 位进了标准、或者项目不再管 MSVC，照这条判据再加不迟。

**字面量后缀 = 类名**：`1i32` 与 `i32(1)` 是同一件事，不用记两套。否决了 Windows 的
`y`/`w`/`d`/`q`（byte/word/dword/qword）+ `f`/`lf`：

- **决定性理由是十六进制冲突**：`d` 是十六进制数字，`0x1d` 究竟是 29 还是"十六进制的 1，dword"
  无解——两种解读都是整数后缀，没有类型能区分；而这套助记法必须用 `d`，换掉 `d` 助记就散了。
  `i`/`u` 都在 `a-f` 之外，天然没这个问题；`f` 虽是十六进制数字，但浮点后缀只用于浮点字面量、
  进制前缀只给整数，两者永不相遇。
- 其余理由：`u64` 自描述、不用查表；能扩展（真加 128 位时 `i128` 直接就有，`y/w/d/q` 得再发明
  字母）；那套助记法在浮点那半用不下去、只能改借 printf 的 `f`/`lf`，一套后缀混两种助记传统。
- 后缀前允许 `_`（`0xFF_u8`、`1_000_000_i64`），反正 `_` 分隔本来就在计划里。

**提升**：`raw_int → int`、`raw_float → decimal`，再照 int/decimal 已有的规则走；raw 之间则按 C++
的类型转换规则（有符号转无符号，`1ull < -1ll` 为真）。界线是"raw 之间用 C 的规则，那正是你要 raw
的原因；一掺 int/decimal 就升到精确类型用数学规则"。

**算术和比较必须同时提升**：只提升算术的话，`a - b > 0` 和 `a > b` 会给出不同答案——同一个问题
两种问法两个结果，是最难查的一类 bug。所以这里没有选择余地。

连带后果，别漏：

- `x + 1`（`x` 是 `u8`）结果是 **int** 不是 `u8`：普通字面量会把你踢出 raw 域，raw 代码里得写
  `x + 1u8`。已评估并接受——满屏魔数本来就不是好代码，raw 本来也不常用。
- 提升让 `1u8 == 1` 为真，于是 **`hash(1u8)` 必须等于 `hash(1)`**（`0.5f64` 与对应 decimal 同理），
  否则 `dict` 直接坏掉。
- 它们**进** `numbers` 塔（继承 `numbers.Real`）。早先倾向"raw 不进塔、不参与隐式提升"，被"算术和
  比较都提升"推翻了：一个能正确加减、能正确比较的数值类型，`isinstance(x, numbers.Real)` 返回假
  是错的答案。
- `0.1f64 == 0.1` 为 `False`，而且这是对的：double 的 0.1 精确转成 decimal 是
  `0.1000000000000000055511…`，跟十进制的 `0.1` 本来就不是一个数（Python 3 同）。转换必须精确、
  比较不舍入，所以这个结论是稳的。
- 跨族比较里的 NaN 跟着目标类型走：`nan_f64 < 1.0f64` 按 C 规则静默为 `False`，而
  `nan_f64 < decimal(1)` 提升成 decimal 的 NaN 后抛 `InvalidOperation`——"提升"的含义就是改用
  那个类型的语义。

**"稳定回绕、不 UB"是实现约束，不是白来的**。以下在 C++ 里是 UB 或平台相关，实现时必须显式处理，
不能真的一路 `a + b` 委托下去：

- 有符号溢出：转成对应的 unsigned 算完再转回来（C++20 起有符号整数保证补码，unsigned → signed
  的转换按模 2^N 良定义）；
- `INT_MIN / -1`、`INT_MIN % -1`：C++ 是溢出 UB，我们定为回绕（结果就是 `INT_MIN`）；
- raw_int 除以 0：没有"回绕"的答案可选，抛 `MathError`；raw_float 除以 0 则照 IEEE 出 inf/NaN、
  不报错——这正是"该 NaN 就 NaN"的意思，两者不对称是有意的；
- 移位量：**`x << n` 定义为等价于把 `x` 左移 1 位这个动作做 n 次**（右移同理）。这条定义一次性
  消掉两个 C++ UB——移位量 ≥ 位宽（于是左移和无符号右移得 0、有符号右移得全符号位，是**推出来
  的**而不是另外规定的，也就不会被 x86"按位宽取模"那个硬件行为带跑），以及有符号左移溢出（每一
  步各自回绕）。注意这是**规范**不是实现处方，实现照常直接短路，别真写成循环 n 次。
- 移位量为负：**待拍板，建议抛 `ValueError`，不做"反向移位"**。理由：上面那条定义支持不了它
  （"移 -1 次"没有意义，负数得另立一条规则，一条自洽的定义变成两条）；"反向"看着优雅是因为直觉上
  `<<` 与 `>>` 互逆，可它们本来就不互逆（右移丢低位，`(x << -1) << 1 != x`，对 `int` 也一样），
  心智负担并没省下、只是换了个地方付；而真实代码里负的移位量几乎总是算错了（下标算负、
  off-by-one），静默反向等于把 bug 变成看起来合理的错答案。收益面只有定点数换算
  `x << (a - b)` 那一类，而写定点数的人本来就该显式分支。用 `ValueError` 而不是 `MathError`：
  `x << -1` 数学上有意义（就是 `x / 2`），我们只是不接受这个实参，属于"值不合法"；`MathError`
  那批（除零、负数开偶次方根）是数学上无定义或非实数。

## 架构决策（不进 SL.md，但影响深远）

### 编译期 C++ 异常 vs SL 运行时异常对象：两层模型

`builtins/exceptions/SyntaxError.h` 的 `SyntaxError`（纯 C++ 异常）和 SL.md 文档化的、暴露给 SL
用户代码的异常类只是碰巧重名，不是同一个东西——这不是需要二选一的问题，是本来就该分层，类比
CPython `PyErr_SyntaxError` 这层 C API 跟 Python 层 `SyntaxError` 类。`SyntaxError` 编译期抛出，
其余异常运行时抛出；该编译期可能包含运行时（`eval`/`eval_isolated` 动态编译）。

必须打通两层的地方是 `eval(code)` 和 `eval_isolated(code)`：现场编译产生的语法错误必须变成能被 SL
`except (SyntaxError)` 捕获的运行时异常对象，内部 catch 住 C++ 异常、构造真正的 SL 异常对象再走
正常 `raise` 传播路径——不能让裸 C++ 异常类型泄漏到 `except` 类型匹配逻辑。以后 `EncodingError`/
`FileNotFoundError` 也要走这个"两栖"模式。

`InternalError`（AST 结构违反 Parser 自己的保证）能不能被 SL `except` 捕获，由"SL 层给不给它注册
对应的 SL 类"这一层决定，不由它继承哪个 C++ 基类决定——所以跟其他异常一样继承 `SLException`，复用
同一套构造/格式化逻辑。

### 字面量折叠用独立的、跟真正 VM 无关的静态求值器

不是偷懒抄近路，是 SL.md 本身"折叠不做常量传播，一掺变量就不折"这条约束逼出来的：定义域天生排除
名字查找/函数调用/副作用，`StaticEvaler` 完全不需要对象模型/方法分派/继承查找，可以先立好骨架不用
等 VM 写完。VM 具体走"编译到字节码"还是"直接树遍历执行"仍未决定，两种路线都跟这个结论不冲突。

### `numeric/BigInt`：手写、双路径，测试靠代数恒等式

**手写而非引库**（Boost.Multiprecision/GMP）：GMP 需要独立构建链接，Windows 下历来不省心；
Boost 头文件在严格编译选项下容易冒警告；`int` 四则运算是语言核心语义本身，值得完全自己掌握，不像
`nlohmann_json`/`doctest` 只服务测试。评估过的现成单头文件库（如 `faheel/BigInt`）不支持位运算、
除法/取模的符号语义没有文档——正是我们已经踩过坑的地方，换一个连这个都没说清楚的库等于把已知坑
换成未知坑。

内部表示是"小路径 `int64_t` / 大路径 limbs"二选一，不变量是"只要数值能装进 int64_t 就必然走小
路径"。每个操作套一层"先试原生运算 + 溢出检测，溢出或本来就有一方是大路径才提升成大路径走原算法"。

**测试方法论**：不手挑具体数字当预期值，改用一批边界值（0/±1、`int64_t` 边界内外、`2^63` 附近、
全 1 比特的 limb）两两/三三组合，批量验证数学上必然成立的恒等式（加法交换律/结合律、
`a == (a//b)*b + a%b`、位运算的补码恒等式、`pow` 的指数加法律）外加"规范化不变量"套件（同一个值走
不同运算路径算出来必须能用 `==` 判定相等）。**理由**：历史上的真实 bug 都是"某个函数假设输入已经
是规范形式，但被套了一层调用后规范形式被破坏"这一类模式（比如取负之后没有重新收缩到小路径）——这
类 bug 靠恒等式互相校验测得出来，靠盯着代码看或者手算几个常量测不出来。以后再碰这块代码，延续这个
测试策略。

`pow`/`operator<<` **没有结果规模上限**——`2 ** 10**9` 会真的去算一个十亿位的数，是明确决定不管
（"炸就炸呗，本来就是这么用的"），不是遗漏；真要限制留给以后接上 VM 时再谈。

溢出检测用 C++26 `<stdckdint.h>`（`ckd_add`/`ckd_sub`/`ckd_mul`）而不是 `__builtin_*_overflow`
或 SafeInt：后者是编译器专有名字，项目要支持的纯 `cl.exe` 前端不认；SafeInt 是抛异常的接口，跟
这个类"折不动一律返回信号、从不抛异常"的风格不合。

### `numeric/BigDec`：复用 BigInt，但"规范形式"跟 BigInt 不是一回事

`decimal` 的运行时表示是 `BigInt 系数（恒非负）+ int64_t 指数 + 独立的符号位 + 特殊值 tag`。
BigInt 已有的 `from_decimal_string`/`to_decimal_string`/`floor_div`/`mod`/`pow` 直接复用。

**符号为什么单独存**：`coeff_` 用 BigInt 自己的符号位就表示不出负零，而负零是要区分的（`-0` 与 `0`
数值相等但 `str` 不同，还决定后续运算结果的符号）。

**指数为什么是 int64_t 而不是 int32_t**：运算的中间结果（比如乘法的 `exp1 + exp2`）可以暂时越出
"构造得出来的范围"，`fix` 之后才必然落回 `[Etiny, Emax]`。于是约定：构造入口（`try_from_string`/
`from_parts`）把指数卡在 `±kMaxExponent`，中间结果不设限、但保证怎么算都溢不出 int64_t。
这样"指数越界"只在一处判，不用在每个算术步骤里操心。

**`kMaxExponent` 必须比 `Emax` 的上限宽一整个 `prec`**（现在取的是 `kMaxExp + kMaxPrec`）。次正规结果
的指数会被 `fix` 压到 `Etiny = Emin - prec + 1`，它比 `Emin` 自己的下界还低一个 `prec`；照着 `Emax`
的量级去卡，`Emin = -999999999` 配任何 `prec >= 2` 就能算出一个 `try_from_string` 读不回来的值，
"`try_from_string(x.to_string())` 恒等于 x" 这条不变量当场破掉。另一条路是在 `set_emin`/`set_prec`
里交叉校验，否决了：那会让"合法的 Emin"取决于当前 prec，两个字段之间凭空多出顺序依赖。

**最容易写错的地方**：BigInt 的不变量是"一个值只有一种表示"，BigDec **没有**这条——标度是值的
一部分，`1.5`（`15×10^-1`）和 `1.50`（`150×10^-2`）是同一个值的两种合法表示。所以 `==` 不能靠
结构相等，必须先对齐指数；哈希也得先归一到同一标度再算，否则相等的值哈希不同，`dict` 直接坏掉。
代码里"表示相等"和"数值相等"是两个不同的方法（`identical` vs `equals`），别混用。

### BigDec 的信号机制：条件 12 个、信号 8 个，抛的是 C++ 异常

SL.md 的异常树里 decimal 有 12 个异常类，但 `traps`/`flags` 只认 8 个——`ConversionSyntax`、
`DivisionImpossible`、`DivisionUndefined`、`InvalidContext` 都是 `InvalidOperation` 的细分，查陷阱、
记标志位时一律先折算成 `InvalidOperation`（`signal_of`）。折算这一步是照抄 Python 的 `_condition_map`；
但"抛出来的 DecTrapped 带细分条件"这层跟 CPython 的实际行为**不一致**——Python 抛的是折算后的基类
（`0/0` 抛 `decimal.InvalidOperation`，不是 `decimal.DivisionUndefined`）。带细分条件是刻意选的
"信息更多"版本：SL.md 自己把细分异常列成了类，executor 按 `condition()` 映射时让用户能按细分
异常去 catch，比 Python 的基类更有用。别把"抛细分条件"再当成"照抄 Python"。

陷阱触发时抛的是 `DecTrapped`（`numeric/` 自己的 C++ 异常），不是 SL 的 `decimal.XXX`——同 BigInt 抛
`std::domain_error` 的理由：`numeric/` 不认识、也不该认识 SL 的异常类体系，由调用方按 `condition()`
映射。上下文字段本身不合法（`prec = 0` 之类）走 `std::invalid_argument`，因为那是调用方的编程错误、
不是算术过程中的信号，跟 traps/flags 那套无关。

### `//` / `%` 的向负无穷取整：在截断结果上修正，且修正那一步必须走带上下文的加法

IBM 规范给的是向零截断的 `divide-integer`/`remainder`，SL 要的是向负无穷。实现是先照规范算出截断的
商和余数，再统一修正一次（余数非零且两操作数异号时，商减 1、余数加上除数）。三处坑：

1. **修正那一步不能"先精确相加再舍入"**：`1E-999999 % -1E+999999` 的精确余数有两百万位，真去构造
   会直接卡死。改成调带上下文的 `add`——它对齐操作数时用的粘滞位（把小到影响不了舍入的一方换成
   `1×10^exp`）本来就是为了保证"结果等于精确和的正确舍入"，所以值和信号都一样，代价是常数级。
   （这条被测试压着：把粘滞位那段短路掉，测试不是失败而是**挂死**。）
2. **`DivisionImpossible` 要按修正之后的商判位数**：截断商恰好 `prec` 位时，减 1 可能多出一位
   （`-99999.5 // 1` 在 prec 5 下就是），按截断商判会漏掉。
3. **`//` 单独用时不能顺手 `fix` 余数**：那会报出 `Inexact`/`Rounded`——那是余数被舍入才该有的
   信号，跟 `//` 的结果无关。所以公共部分只算到"截断商 + 截断余数 + 要不要修正"，加不加除数、
   舍不舍入由三个入口各自决定。
4. **商本身却必须过 `fix`**。一度以为"商是整数、位数又不超过 `prec`，fix 只会白报 Inexact/Rounded"
   就跳过了——前半句对（进不了舍入分支），后半句错：`fix` 还管指数域。`Emax` 小于 `prec - 1` 的上下文
   （合法，设得出来）下 `100000 // 1` 的商调整后指数是 5，超过 `Emax = 3`，该报 `Overflow`。
   `_pydecimal` 这里也不 fix，libmpdec 会——过 IBM 测试集的是后者。**位数够不代表指数域够，这是两条
   独立的检查**。

**两处零的符号**：`//` 的商为零时按两个操作数的符号异或（`0 // -3` 是 `-0`），跟 `*`、`/` 一致，
不让 `//` 成为唯一丢掉零符号的运算；`%` 的余数恰好为零时符号跟被除数走（`-6 % 3` 是 `-0`），这处
照抄规范——SL.md 写的恒等式 `x % y == x - (x // y) * y` 自己在零上也定不出符号（IBM 的加法规定
`a - a` 得 `+0`），换成"跟除数走"并不更有理有据，那就少一处偏离。

### BigDec 的测试：期望值来自 CPython 的 decimal，不手挑

`test/numeric/big_dec_cases.inc` 由 `gen_big_dec_cases.py` 生成，期望值（结果 + 触发了哪些信号）
全部来自 CPython 自带的 decimal——那是 C 写的 libmpdec，跟 BigDec 是两套独立实现，比手挑期望值强
得多。脚本带倍数参数，临时跑几十倍规模的差分测试很方便（做到 25 倍、约 47 万个断言全过）。

`//`/`%` 是我们偏离规范的地方，Python 的答案不能直接用。生成器的做法是**换一条推导路径**：先在超高
精度下拿到精确的截断商/余数，再整体修正，凡是超高精度下仍不精确的组合直接跳过不出题。两边只在数学
定义上一致，不共用代码路径——如果照着 C++ 的算法再写一遍 Python，测的就只是"我抄得一不一致"。

表里除陷阱全关的路径外，还有**陷阱开启的路径**（`kTrapped*` 四张表）：抛不抛、抛哪个条件、抛出时
flags 走到哪一步都是规范的一部分。陷阱表只要求两套 CPython 实现"抛出的条件名"一致——它们在抛出前
记 flags 的顺序不一致（1/3 在 Inexact 陷阱下，libmpdec 先记 Rounded、_pydecimal 先抛 Inexact），
抛出时的 flags 以 _pydecimal 为准（BigDec 是照它移植的）。值池里还刻意塞了带非零指数的零
（`0E+999999` 这类），专门压 fix 的零夹取、add 的零操作数、trunc_divmod 的量级短路这些路径。

**还没实现的**：`hash`（要先归一标度）和 `int(decimal)`（取整方向 SL.md 还没定）。SL.md 里 decimal
参与的运算符本身已经全了。

### 超越函数（`ln`/`log10`/`exp`/`sqrt`/`**`）：整数定点算法单独一层，"算到能定夺为止"是核心

这几个在任意精度下没法一次算准。做法照抄 Python `_pydecimal`：**先按 prec+3 位算一个近似值，看它
够不够定夺舍入方向，不够就再多算三位**，循环到够为止；判据是"末尾恰好是 5000…0 就说明正卡在两个可
表示值的正中间"（`is_roundable`）。因为已经算到任何舍入方式都给同一答案，最后那步 `fix` 固定用
HalfEven（`**` 除外，它尊重上下文的舍入方式，规范如此），算完靠 RAII 把上下文的 rounding 还回去——
不能写成"算完再赋值回去"，`fix` 会因为陷阱抛出去。

整数层的定点算法放在 `numeric/dec_math.{h,cpp}`：`ilog`/`iexp`/`dlog`/`dlog10`/`dexp`/`dpower`
以及 `div_nearest`/`rshift_nearest`/`sqrt_nearest`/`log10_digits`。这一层只跟 BigInt 打交道，不认识
BigDec、上下文和信号，好单独推敲。**里面那些常数（尤其是泰勒展开前的缩减深度 `kTaylorL`）是有误差
论证撑着的，动一个就会把上层那个循环的前提拆掉**，别随手调。`log10_digits` 带一份越算越长的静态
缓存，因此不是线程安全的。

**试过把 `big_dec_test.cpp` 里最耗时的两个 `TEST_CASE`（`**`、超越函数，合计占 numeric
测试总耗时的大头）用 `std::thread` 铺开跑、`log10_digits` 那份缓存另加锁保护，指望榨干本机
24 核——实测是反效果，而且不是"没提速"那种程度：2 线程就比单线程慢了 2.5 倍，24 线程慢了
8 倍多（5.9s → 49.8s）。根因大概率是 `run_test.bat` 固定用的 `/MDd` Debug CRT 堆：调试堆的
每次分配都要过一把全局临界区、外加链表式泄漏追踪的簿记开销，BigInt/BigDec
这种"每步运算都建一堆临时大数"的负载一并发就是灾难，线程越多锁竞争越狠。要验证这套账真能提速
得换 Release 构建，但那超出了"只改测试代码"的范围（`run_test.bat` 的构建类型是硬编码的），
所以这条路线整个撤回了，两个 `TEST_CASE` 照旧串行。以后如果构建方式变了（比如真的有了 Release
测试目标）想再捡起来，`log10_digits`/`dexp`/`dlog`/`dlog10`/`dpower` 这条链子仍然是唯一需要
额外加锁的地方——`sqrt` 和 `power_exact` 精确路径不碰它，天然线程安全。

**`**` 分三条路**：先用 `log10_exp_bound() + adjusted(y)` 粗筛掉必然溢出/下溢的（这一步同时替
`power_exact` 挡住了 `10^ye`、`xc^m` 之类会炸开的输入，别把它挪走）；再试 `power_exact`——把 y 写成
既约分数 m/n，检查 xc 是不是 n 次幂、xe 能不能被 n 整除，y 为负时还要求 xc 是 2 或 5 的幂；都不成
才走 `exp(y*log(x))`。

**指数不是整数而结果又恰好精确时**，规范要求照样报 Inexact（结果落进次正规区还要补 Underflow）。
`fix` 自己不会报，又不能在 `fix` 前后直接补——那会打乱规范规定的信号优先级。做法是先在一个陷阱全关、
标志位清空的上下文副本上 `fix`，再按优先级顺序把信号补报到真上下文上。

### 两处我们跟 libmpdec 不一致，都是故意站 `_pydecimal` 那一边

CPython 自带的两套 decimal 实现（C 的 libmpdec、纯 Python 的 `_pydecimal`）自己就有分歧——官方扩展
测试 `_decimal/tests/deccheck.py` 里的 `SkipHandler` 明写了这是已知情况。目前撞见两处，BigDec 两边
都跟 `_pydecimal`：

1. **非整数指数的 `**`**：规范只要求"按 `exp(y*ln(x))` 算"，**不保证正确舍入**。真值恰好可精确表示
   且用定向舍入时两边差 1 ulp：`9 ** 0.5` 在 ROUND_DOWN 下 libmpdec 给 `2.99`、`_pydecimal` 给
   `3.00`。选后者——真值精确就原样给出，`9 ** 0.5` 得 `2.99` 实在太不像话。
2. **`exp` 在 `Emin == 0` 时**：次正规判定该在舍入前还是舍入后做。`exp` 拿 `0.99…9`（调整后指数 -1）
   当近似值交给 `fix`，判成次正规，舍完却变回 `1.000…`（调整后指数 0，不次正规）。值一样，只差
   `Subnormal`/`Underflow` 两个 flag。规范原文写的是 "before any rounding"，字面上支持 `_pydecimal`。

**生成器因此对每一组用例都拿两套实现各算一遍，不一致就整组跳过**（默认规模下 pow 跳 21 条、超越函数
跳 8 条）。做成全表统一过滤而不是只挡这两处，是因为分歧点随参数漂移——尤其是 `Emin` 和舍入方式——
哪天有人往池子里加一档参数，不该因此得到一张 BigDec 永远过不了的表。我们这一支的行为由手写用例钉住。

### 整数/decimal 字面量禁止前导零

SL.md 一直没规定 `007`/`00` 合不合法，是真实的规范空白，已补上：不合法（单独一个 `0` 除外；decimal
整数部分同样受限，小数部分不受限）。理由：一是给以后要加的 `0x`/`0o`/`0b` 前缀预留解释空间——现在
放开，以后加前缀就是破坏性变更；二是避免"`0` 开头被当成八进制"这个 C 系语言的经典坑。

### 字节码 / `Code` 对象设计（供以后字节码化参考，不是当前实现）

分层 Lexer → Parser → Analyzer → Executor，字节码化以后要加但不是现在，先把树遍历语义定完整。这套
设计通过了"是否有可观察语言行为差异"的检验——换一种实现完全可以不这么做而不改变任何 SL 程序的可
观察行为，所以只记在这里，不进 SL.md。

**整体模型**：源码编译产出 `Code`（字节码 + 常量池），文件/函数体/类体建立各对应一个 `Code`，边界
等于帧的边界（`eval_isolated` 现编译出的是一份完整文件的 `Code`，正常压帧跑）。**`eval` 是这条
"边界=帧边界"的唯一例外**：它现编译出的是单个表达式的代码，且要在调用帧里跑，不能当成一份新文件；
真做字节码化时这里得单独设计（当前树遍历实现下不构成问题）。`Code` 对 SL 完全不可见，不通过 `getattr`/`attrs()` 暴露（不像 Python
`f.__code__`）——暴露就等于把字节码格式钉成可观察行为，以后想换实现就是破坏性变更。

`Code` 装：字节码；常量池（字面量、名字字符串、嵌套 `Code`）；行号映射 + 来源标识（非规范，纯为
报错）。函数体的 `Code` 额外带形参形状元数据。

**明确不装进 Code**：装饰器（建立完函数对象之后的独立步骤）；形参默认值/类型注解的具体值（外层
作用域、建立时求值，算出来挂在 Function 对象上，Code 只需要知道"有没有"）；捕获列表怎么捕获的
字节码在外层 Code 里，但**引用捕获了哪些名字必须作为函数体 Code 的持久元数据保留**（路由到定义帧
需要在运行期查"这个函数的引用捕获表里有没有这个名字"）。值捕获不受影响，就在 `_L` 普通字典里。

**"建立函数/类对象"指令（`MAKE_FUNC`）**：固定弹栈顶 6 项（捕获元组、形参注解/默认值元组、返回
类型注解、函数名、`Code` 常量、`doc`），弹几个必须编译期确定，不能运行时先查元信息才知道。引用
捕获不产生任何字节码指令——`MAKE_FUNC` 本来就在当前帧字节码里执行，天然知道当前帧是谁，直接抓一份
引用挂到新对象上。缺注解/缺默认值统一压一个纯内部、SL 层拿不到的哨兵值（不是 `object`，也不是
`None`——`None` 是合法真实默认值，拿它当哨兵会跟"默认值就是 None"撞车）。

**装饰器求值顺序**：`@deco func f(){}` 不能当 `deco(f)` 的语法糖去套用调用求值顺序——装饰器前缀是
func/class 自己产生式的一部分，根本不存在外层的 `deco(...)` 调用表达式。正式规则：先按从前到后对
各 decorator 求值，再进入捕获/形参/返回类型求值；装饰器的调用在建立完毕后按从近到远进行。命名
函数/类的绑定只在最终值确定后发生一次。

**Function 对象与 Code 的关系**：Code 编译一次可能复用多次（函数每次被调用新开帧但执行同一份
Code），但"建立"这个操作每次执行都必须构造全新的 Function 对象，不能因为 Code 复用就连带缓存
对象——`is` 比较的是对象身份，直接关系闭包正确性（循环里值捕获必须各自捕获到当次的值）。

## 悬而未决 / 需要以后回来处理

- `local` 保留字去留未拍板。
- `when` 完整语法语义未开始设计（`case` 暂留）。
- `assert` 只占保留字位置，行为未设计。
- 数字字面量扩展（二/八/十六进制整数、`complex` 字面量）故意拖后；`complex` 类本身已加
  （`numbers.Number` 子类）。科学计数法已经设计定型（见上面"科学计数法字面量"一节），
  lexer/parser 还没跟进实现。
- 完全没开始设计（用户明确的优先级顺序，"不属于语言本身的东西最后弄"）：文件 I/O；`set` 方法
  列表；字符串插值（已讨论并否决 f-string，打算用 `%` 运算符重载 + `.format()`）。
- 自定义模块系统：module/package 概念、多段名字的逐层导入 + 挂属性、`ImportError` 场景已定
  （见 SL.md `import` 一节），但"名字怎么定位到具体文件系统位置"（搜索路径）、循环 import、相对
  导入都还没设计——这跟"作用域隔离"是两回事，别混淆。
- VM 具体走"编译到字节码"还是"直接树遍历执行"未决定（两种路线都跟已有结论不冲突，见上面字节码
  一节）。
- 递归深度：SL 逻辑递归深度和 C++ 调用栈不是一回事，需要解释器显式 guard（对应
  `RecursionError`），具体阈值未定。
- `&`/`|`/`^` 对两个 `bool` 目前一律是 `TypeError`（位运算是 `int` 特有的）。要不要给 `bool` 单独
  补一套返回 `bool` 的逻辑运算（Python 那样 `True & False == False`）没定；现在只能写 `and`/`or`。
- `set`/`frozenset`/`dict` 等容器的方法列表尚未逐个列出（`d.pop(k)` 这类只在别处被引用过）。
- 内置类的构造/转换行为整片没定（`int(x)`、`str(x)`、`list(x)`、`tuple(x)` 等，只有
  `set`/`frozenset`/`frozendict`/`range` 写了）。其中 `int(decimal)` 的取整方向是真空白：截断还是
  向下取整？SL 的 `//` 已经定死"永远向负无穷"，`int()` 若选截断，语言里就有两种取整方向了。
- 科学计数法字面量的 lexer/parser 实现还没做（语法已经定型，见上面对应的决策一节）。`numeric/`
  两个类已经就位：`BigDec::try_from_string` 本来就按 IBM 语法收指数，`BigInt::from_decimal_string`
  也补上了。**int 指数上限 65536 归 lexer 管，那一半还没写**——现在 `BigInt` 那层是不设限的。
- 移位量为负时怎么办待拍板（`int` 和 raw 两边一起定）：建议抛 `ValueError`，不要"反向移位"，
  理由见上面 `raw_int`/`raw_float` 一节。
- `BigDec` 还缺 `hash`（要跟数值相等的 `int` 一致，得先归一标度）和 `int(decimal)`（取整方向 SL.md
  自己还没定，见下）。SL.md 里 decimal 参与的运算符本身已经全了，见上面 `numeric/BigDec` 几节。
- `sqrt`/`exp`/`ln`/`log10` 在 `BigDec` 上有了，但 **SL.md 还没规定它们怎么暴露给用户**——是挂成
  decimal 的方法，还是走一个 `math` 模块？`**` 是运算符，不受这个问题影响，先实现了。
- **`0 ** 0` 在 int 和 decimal 上不一样**：int 走 `BigInt::pow` 得 `1`，decimal 走 `BigDec::pow` 报
  `InvalidOperation`。这是照 Python 抄的（`0**0 == 1` vs `Decimal(0)**Decimal(0)` 报错），但 SL.md
  一个字都没写，等于把一处类型相关的行为差异留在了规范空白里。要么补进 SL.md，要么统一。
- `BigInt::pow` 没有上限，但没上限的具体后果是"挂死"而不是头文件写的"可能抛 `std::bad_alloc`"：
  指数大到一定程度，先被朴素 O(n²) 乘法拖到实际算不完（内存反而通常够，不会真的 OOM）。
  `operator<<` 的超大位移是干净的 `bad_alloc`，`>>` 有 O(1) 短路，两者都不受影响。这是 VM 层的资源
  guard 议题（要不要在解释器调用 `pow` 之前就卡一个指数上限），不是 `BigInt` 自己该管的，先记在这。
- `StaticEvaler` 里那整套 float 折叠（`node_to_double`/`std::pow`/`std::fmod`/`make_float`）还没清
  掉。按"结果为 decimal 的常量折叠一律禁掉"那一节的结论，这些不是改改名的事，要整段删；`decimal`
  接进前端时一起做。
- `decimal` 的 NaN 没有诊断信息（Python 的 `Decimal('NaN123')` 那种 payload），`BigDec` 直接把带
  payload 的字符串判为不合法。要不要补由以后需要时再说——静默丢掉比拒绝更糟，所以现在是拒绝。
