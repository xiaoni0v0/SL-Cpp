## 语言设计决策

### 动态作用域 → 显式捕获

标识符解析收窄成"只查当前帧 `_L`，查不到退回 `_G`"，不沿帧栈向外搜索（动机：模块内函数被外部调用时
不该意外搜到调用者的帧）。访问外层作用域需显式捕获：值捕获（建立时取值）、引用捕获 `&x`（只记
(定义帧, 标识符)，读写转发到定义帧）。捕获不跨层自动传递，中间每层必须显式转发。

`x op= expr` 的内部读取有特例：不适用"退回 `_G`"，未标记 global 时只查 `_L`，找不到直接
`NameError`——保证这一步的读写落在同一帧。因此 `x op= expr` **不等价于** `x = x op expr`。

**引用捕获内存模型**：定义帧字段是对帧对象的普通引用，走统一引用计数/拷贝规则；帧弹出时只把
自己那份局部字典的字段置为 `None`（不是把 dict 对象改成空字典，也不是把 dict 对象变成 `None`），
不管谁还持有该帧引用或那份 dict。判活/判死看帧上这个字段是不是 `None`。
`_G`/`_L` 字面量给出的就是那份 dict 本体，不是视图；函数 `return _L` 之后原帧死亡，相当于原帧
不再改它，外逃的 dict 内容停在放下那一刻（对象本身仍可变）。**否决过**：强引用整个帧对象
（帧永远不回收）；帧维护"谁引用了我"的通知列表、弹出时清空（对象拷贝时旁路账本不会自动同步）。

值捕获无生命周期限制但不能共享可变状态；引用捕获能共享但离开定义帧生存期后必 `NameError`——共享
可变状态用"值捕获 + 可变对象当盒子"，不加专门的 `Box`/`Wrapper` 类型（list-as-box 够用）。

### `finally` 跳转限制

`expr3` 里跳出这段范围的 `return`/`break`/`continue` 不合法。这项检查纯在编译期完成，不需要运行期
兜底：`expr3` 的内容编译期全部可见；唯一能在运行期往里塞代码的 `eval`，其 `code` 顶层不可能出现
这三者（见下），跳不出 `code` 自身；`eval_isolated` 编译出的代码只作用于它自己那份文件。

`raise` 允许。对齐 Python：`try`/`except` 里的 `return`/`break`/`continue` 以及待传播异常，都等
`finally` 正常结束再生效；`finally` 再抛则新异常取代待完成的跳转或原异常。语言没有
`__context__`/`__cause__`，不做异常链。

### `eval(code)`：共享调用帧，靠"空的静态外层环境"划出可用子集

绕了一圈：最初设计成完全内联 → 因下述几条整体删除、只留 `eval_isolated` → 现在以受限形式回归。

**回归的理由**：`eval_isolated(code, _L)` 顶替不了 `eval('x = 0')`。前者把 `_L` 当作一份新文件的
`_G`，其中的 `x` 只能是那份文件的全局变量；而内联的 `x = 0` 里，`x` 是局部变量、全局变量还是引用
捕获，只有调用帧当时的状态说了算，这件事没有任何写法能替代。

**定稿**：`code` 必须恰好解析出一个表达式（要多条自己写 `{ a; b }`，`{ }` 不引入作用域）。`eval`
跟任何调用一样压帧（执行器的 CALL 无特例），但它自己那一帧全程空着、对 `code` 不可见，`code` 在
调用帧（压 `eval` 这帧之前的栈顶帧）里求值——"等价于没有新帧"是 `eval` 的语义，不是压帧规则里挖洞。

**关键设计**：不列"禁止 `return`/`break`/`continue`"这三条禁令，而是规定 `code` 的**静态外层环境
为空**——不在任何 Program 内，也不在任何循环内。于是现有规则自己把子集切出来：`return` 要求有"离它
最近的 Program"，`break`/`continue` 要求外层有 `for`/`while`，都不满足 → `SyntaxError`；`raise`/
`global`/`import`/赋值/`del`/`try` 不要求任何外层构造 → 照常可用。好处是零新增规则，且嵌套情形
自动正确（`code` 里自己写的 `func` 体是 Program，里面的 `return` 合法；自己写的循环里 `break`
合法；但复合表达式不是 Program，`eval('{ return 1 }')` 仍非法）。

**当初的否决理由，逐条对照**：
- "内联要求'调用点'是编译期概念，但 `eval` 是一等函数值"——不成立了。调用帧是纯运行期概念（压
  `eval` 帧之前的栈顶帧），`f = eval` 照常可用，语义不含糊。
- "跳转信号要跨调用边界回传"——被空外层环境根除，`code` 顶层根本产生不了向外的跳转。
- "堵死'局部变量编译成槽位下标'这类未来实现"——**依然成立，是明知并接受的代价**。`_L` 必须始终是
  真字典（3.10.1 本来就这么规定），换取的正是 Python 做不到的"`eval` 里赋值真的生效"。
- "反面教材 Python `eval`/`exec`/`locals()`"——它烂恰恰是因为函数局部变量是编译期槽位、`locals()`
  只是快照。SL 没这个前提，所以不会重蹈。

**`eval` 是关键字，不是内置函数**（这条推翻过一次：先定成普通内置函数、可以 `f = eval` 传递，
后来改回关键字）。形态保留 `eval(code)`、括号强制、解析成专门的 `AstNodeEval` 节点，同 C 的
`sizeof`。

**改回来的决定性理由**，比"编译器一眼看出插了代码"更值钱：它把上面第三条"明知并接受的代价"收回来
了大半。`eval` 在**调用帧**里求值——只要它还是一等值，任何一次 `f(...)` 都可能是它的马甲，于是
**每一帧**的 `_L` 都必须永远是真字典；关键字化之后，"某一帧会不会被现场插进新代码"等价于"它自己
的 `Code` 里有没有 `eval` 点"，纯静态可判定，不含 `eval` 的函数（也就是绝大多数）就能把局部变量
编译成槽位下标。`code` 仍是运行期求值出来的 `str`，不要求字面量——需要静态可见的是 `eval` 点的
位置，不是它的内容。

代价是丢掉 `f = eval` / `map(eval, ...)`。当初为它辩护的"语义不含糊"没错，但不含糊 ≠ 有用：`eval`
的语义绑死在调用者的帧上，传来传去是陷阱，实际用例约等于零。另外 SL.md 给 `eval` 定的规则（恰好
一个表达式、静态外层环境为空、解析失败抛 `SyntaxError`）本来就全是编译期规则，挂在关键字上比挂在
运行期函数值上自然。

**形态为什么保留括号、不做成 `eval "code"` 这种无括号前缀**：`eval` 产出的值要参与外层表达式，跟
`return`/`raise`（值无意义、一定是整条表达式的全部）不是一类。做成最低优先级前缀的话
`eval "x" + 1` 就是 `eval("x" + 1)`，想要 `eval("x") + 1` 得写 `(eval "x") + 1`，外层括号变成常态，
等于没省；躲开这条又得给它单开一档高优先级，为一个罕用构造新增优先级不划算。

**`eval_isolated` 保持普通内置函数**。它跟帧无关、吃一个真 `globals` 字典，行为就是普通函数。这个
不对称是诚实的：`eval` 是穿着调用外衣的编译期构造，`eval_isolated` 是货真价实的函数。

**实参形状尽可能像一次真正的调用**：`eval(code)`、`eval(code='x')`、`eval(**{'code':'x'}) `
语法上都合法，`0`/`2` 个位置实参也不是 `SyntaxError`——恰好绑出一个叫 `code` 的形参是运行期按 3.5
的通用调用规则判定的事（绑定失败 `DispatchError`），跟普通函数调用的参数个数/类型从不在语法/语义层
校验是同一套道理，不给 `eval` 搞特殊待遇。`AstNodeEval` 因此和 `AstNodeCall`/`AstNodeImportCall`
共用 `CallArgs` 聚合体（不是公共基类——理由见 [architecture.md](architecture.md) 的"调用类节点共用
`CallArgs`"一条），`Parser::finish_call_args()` 三处调用方共用一份实参解析。

### `global` 作用在引用捕获上：运行期检查，`NameError` 不是 `SyntaxError`

**`global` 是一次名字表操作，不是函数体级别的静态声明**——跟 `del`/`import`/`try` 同一类"求值时
才生效、不要求任何外层构造"的操作（同 `eval(code)` 的"静态外层环境为空"模型，见上面一节）。因此
"`identifier` 是不是引用捕获"这条检查放在求值 `global identifier` 这一步（运行期），不是编译期；
报的异常是 `NameError`，不是 `SyntaxError`（3.11 规定 `SyntaxError` 只在编译期抛，这是既有约定
倒逼出的结果）。`global x` 执行后，该名字在当前帧里从引用捕获切换成模块全局，彻底断开跟原引用的
关联。机制上不需要新的运行期状态：VM 本来就要给每一帧维护引用捕获名集合（3.10.4 的读写删都要用），
执行时查一下这个集合即可。

### `eval` 的局部/全局帧：`in_local_scope` 从调用点传入，不是写死的

`eval(code)` 的静态外层环境为空这条模型漏了一处：`global` 合不合法不只取决于`code` 的 AST 形状，
还取决于**调用帧本身**是不是局部作用域（`func f() { eval('global x') }` 里 `code` 该在 `f` 的
局部帧求值，`global x` 该合法）。这条信息是纯运行期概念，`SemanticChecker`/`Analyzer` 静态分析阶段
无法从 `code` 的 AST 反推——只有执行 `eval` 那一刻的 VM 知道当前帧是什么。

**定稿**：`SemanticChecker` 构造函数、`Analyzer::analyze_single_expr` 都加一个
`bool in_local_scope = false` 参数（默认值保证 `check_program`/`analyze_program` 的整份 Program
入口不受影响，恒为顶层语义）。真正传入正确的值是未来 codegen/VM 编译 `eval` 调用点时的责任——
编译器天然知道这段代码此刻在哪一帧，把这个已知信息转发给 `analyze_single_expr` 即可，不需要反向
推断。当前没有 codegen/executor，这两个参数暂时只有测试在用。

`return`/`break`/`continue` 不受这条影响：判的是"AST 里有没有包一层 Program/循环"，是跟调用帧
局部/全局身份无关的静态性质。`global` 是目前唯一一个"合法性取决于调用帧"的构造。

### `==`/`!=` 的终局回退：解释器按身份兜底，序比较没有这条

3.8 原来把回退链写成「两侧的 eq/cmp 都未命中就报错」，六个比较运算符一视同仁。按这个字面读，
**任意两个「没为对方写过 eq」的对象比 `==` 都是 TypeError**——不只是 `() == []`，还包括
`object() == object()`（两个普通空对象）、`1 == None`。这显然不对，而且跟 SL.md 自己另外两处打架：

- **哈希契约**（4.3.2.3）：`__hash__` 默认按对象身份算，且要求 `__hash__` 与 `__op_eq__` 保持一致。
  默认哈希是身份哈希，默认相等就该按身份**给出一个值**，不是弃权到报错——否则键类型不齐一的
  `dict`/`set` 一旦哈希碰撞就没法比较。
- **`!=` 的推导**（3.8）：`__op_ne__` 未命中就「先试 `__op_eq__`、取其真值的逻辑非」。这条预设了
  `__op_eq__` 出值。

**病根是抄 Python 时漏了最后一步**。SL 这套（`object.__op_eq__` 不同一返回 `NotImplemented` +
两侧回退链）跟 CPython 的 `do_richcompare` 一模一样，但 CPython 在两侧都弃权后**只对 `==`/`!=`**
兜底成身份比较，其余四个序比较才抛 TypeError。所以 Python 里 `() == []` 是 `False`、`() < []` 是
`TypeError`。

**定稿**：补上这条终局回退——`a == b` 取 `a is b`，`a != b` 取 `not (a is b)`；`<`/`<=`/`>`/`>=`
没有兜底，两侧都弃权就 TypeError。

**兜底放在解释器层，不放进 `object.__op_eq__`**（否决过的方案）：如果改成 `object` 的 `__op_eq__`
不同一就直接返回 `False`，链子会在第一步就终止，**右操作数的 `__rop_eq__` 永远没机会跑**——左操作数
一路继承到 `object` 都没有自己的 eq 时（比如 `object() == MyThing()`），`MyThing` 写的 `__rop_eq__`
就失效了。所以 `object.__op_eq__` 保持返回 `NotImplemented`，兜底是解释器在回退链尽头的动作。

**对折叠器的影响：零**。折叠器本来就是这么做的（跨类型 `==` 折 `False`、跨类型序比较不折），
只是以前没有标准条文支撑，代码注释里只写了一句「其他不同类型的一定不等」。补完标准之后这句话
有了依据：不同类型的两个字面量不可能是同一个对象，所以身份兜底恒为假——**是精确结果，不是保守
近似**。这一轮顺带把折叠范围表的每一格都对着标准实测核了一遍（A/B/C/D/E/F 六组、一元行、
None/Ellipsis、嵌套容器递归、链式比较短路与部分折叠），没发现别的偏差。

### `StaticEvaler` 的数值折叠：不依赖高精度库，int 走 int64_t、decimal 彻底不折

**int**：`int64_t`，溢出/装不下就不折——这本来就是"保守但正确"，不是错的那一半，不用动。

**int 的科学计数法写法（`1e2`）**：不再"一律不折"，而是在折叠器内部（不是语法层）设一个**较小**的
指数上限（大致十几到二十几，具体数值要能覆盖住"展开完还有机会落进 int64_t"的情形，比如 19 附近，
只是个提前退出的效率阈值，不是正确性边界——超过它必然装不下 int64_t，跳过展开只是省一次字符串
拼接）：
- 指数超过上限：不折（原样留给运行期）；
- 尾数去掉符号后全是 `0`（如 `0e9999`）：不管指数多大，值恒为 `0`，直接特判折成 `0`，不用展开；
- 否则把尾数按指数补零展开成普通十进制数字串（`1e5` → `100000`），再走现有的
  `string_to_int64`/`from_chars` 那条路径正常尝试塞进 `int64_t`——装不下就不折，跟普通写法的
  int 字面量待遇完全一致。
- 展开这步复用 `ast_node_literals.cpp` 里已经写好的 `strip_sign`/`strip_exponent`（构造函数校验
  `raw_` 形状时就在做同样的拆分），不要在 `StaticEvaler` 里重新写一遍字符串手术——挪成两边都能调
  的共享辅助（放 `utils/` 或新开个小头文件），构造函数校验和折叠器的展开逻辑吃同一份代码。

**decimal**：彻底不折，一点都不折——算术、比较、真值，一概不折。之前"比较可以照折，因为比较不
舍入"那条判断依然成立，但既然都不打算碰 `BigDec` 了，"能不能照折"就不重要了：一条规则（decimal
恒不折）比两条规则（算术不折、比较折）更简单，没有理由为了"比较其实可以折"这一点点收益去链一份
`numeric/` 依赖进 `Analyzer`（也是这轮 numeric 测试被临时屏蔽、构建变慢的直接原因之一）。
`is_literal_pure` 仍然把 decimal 算作纯字面量（回答的是"有没有副作用、能不能当死代码剪掉"，跟
"知不知道它的值"是两个问题，`{ 1.5; 2 }` 里的 `1.5` 照样该被剪掉）。

**bool**：这次的结论不受影响，继续保留——算术/比较按 SL.md 4.2.5 把 bool 折算成 int（`is_int_family`）
复用 int 的实现；位运算和容器重复次数只认严格的 int（`is_int`），bool 没有位运算方法，
`True & 1` 运行期是 TypeError，不能折。

**`raw_` 不拆成尾数/指数两个字段**（用户第二次提议，讨论后决定不拆）。查过之后发现代价比想象中大：
`to_json.cpp` 把 `raw_` 原样吐进 JSON 的 `"raw"` 键，16 个测试文件的 `int_lit()`/`decimal_lit()`
辅助函数都按一整条字符串比对，拆了要么这些全部要改，要么 `to_json` 里现场把两段拼回一条——拼接
这步只是从"构造时"挪到"序列化时"，没有真正省掉。`BigDec::try_from_string` 吃的也是带 `e`/`E`
的完整字符串，不是拆好的两段，就算拆了喂给它之前还得拼回去（不过这轮 decimal 已经完全不折，这条
理由对 decimal 已经不重要了，纯粹是 int 这边收益不够）。真正该做的是把 `strip_sign`/
`strip_exponent` 这两个解析辅助函数收成一份两边共享的代码，而不是改数据形状——问题的根子是
"消费方各自现场解析、逻辑不共享"，不是"存成一条字符串"。

**`truthy`/`literal_equal` 返回 `std::optional<bool>`，不是 `bool`**：需要表达"判不了"这个第三态，
不能默认成真——`nullopt` 缺失时默认成真曾经让 `0e0` 的真值判断出错、被死分支消除留下了错误分支。
调用方（`fold_if`/`fold_for_cond`/`fold_not`/`fold_and_or`/`fold_compare`）一律把 `nullopt` 当
「不折」处理。**判定函数缺第三态，在折叠器里就等于埋了一个错误的默认值。**

decimal 的一元 `+`/`-` 不折，所以负的 decimal 整体不是纯字面量（`-1.5` 是 `OpUnary` 套一个字面
量），牵连到的比较、真值判断也一并不折——这不是漏洞，少折永远是安全的那一侧。

**为什么 decimal 折叠禁得这么死（连比较都不例外）**：用二进制浮点近似算 decimal 会产生错值，不是
漏折——`0.1 + 0.2` 折成 `0.30000000000000004`、跨量级比较得出错误结果、`0.0 ** 0` 把运行期该抛的
`InvalidOperation` 吞掉，这类错误比"该折的没折"严重一个量级，所以"decimal 一律不折"没有例外。

**中途走过一段弯路：改成 `BigInt`/`BigDec`，后来否决**。当时的想法：既然 `numeric/` 已经链进 `SL`
主目标，折叠器直接复用它，「编译期算的」和「运行期算的」就变成「本来就是同一份实现」，不再是「但愿
一样」；int 因此没有溢出边界，decimal 的比较也能精确参与折叠（不只是算术例外）。代价是
`BigInt::pow`/`shift_left` 自己不设上限，编译期算 `2 ** 一个超大指数` 会一路跑到天荒地老，
必须在折叠器里另外撑起一整套「事先估算结果规模」的逻辑（`nMaxIntDigits`，`*`/`**`/`<<` 三处都要
估）——这套估算是新代码，还真的估错过一次（`10 ** 4095` 那次，用「底数位数 × 指数」的保守上界
估的，实际分界因此偏到 2048 而不是 4095，得在测试里专门解释这个偏差）。

**否决理由**：`BigInt`/`BigDec` 是运行期的数值实现，折叠器是编译期的前端 pass，把两者绑在一起
违反分层；而**为了修一类 bug，引入了另一类需要精心维护的复杂度**（那套规模估算逻辑），划不来。
收益也小：换来的是 `10 ** 100`、`1e2 == 100`（当指数超出下面这条内部上限时）这类没人会写的表达式
能被折，日常代码几乎摸不到这条路径。最终定案：折叠器压根不引入高精度库，见上面的正文。

### `as`：`for` 迭代目标 + `except` 绑定目标，一个关键字两处用，但只有一种含义

原本这两件事分别由 `in`（`for (lvalue in iterable)`）和隐式注入的 `__except__` 承担，两处都割裂：

- **`in` 一身两责**：它既是可重载的成员测试运算符（`__op_contains__`），又是迭代 `for` 的判别依据。
  代价在 Parser 里看得最清楚——先按成员测试建出一个 `OpBinary(In)` 节点，再 `dynamic_cast` 把它拆开、
  重新解释成"循环头"。是**语义重解释**，不是分派。
- **`__except__` 是全语言唯一一处往用户作用域隐式塞变量的地方**（其余 dunder 全是属性：`__name__`/
  `__doc__`/`__return__`），而且规范为它写了一整套"保存原值 → 赋值 → 退出时恢复或 `del`"的
  shadow/restore 舞蹈。`global __except__` 直接把这套动作问到没词（该 shadow 全局的？该 `del`
  全局的？），except 体里定义的闭包引用捕获了它、活得比 restore 长也是同类的洞。

**定稿**：引入 `as` 关键字（`as` 本来就是保留字，提升成关键字跟当初 `in` 那次一样轻）。

- `for ⟦collect⟧ (iterable ⟦as lvalue⟧) expr`
- `except (Exc1, ... ⟦as lvalue⟧) expr`

**`as` 不是运算符**，只在这两处出现，含义都是"把左边的东西绑定到这个名字"——所以它没有"一身两责"
的问题，是一种含义用在两个构造里。这是解决问题的关键：`as` 一旦不是运算符，Parser 就变成"解析
表达式 → 看见 `as` → 消耗 → 解析目标 → 直接建节点"，`dynamic_cast` 和节点重解释整个消失。只把
`in` 改名叫 `as` 但仍做成运算符是白改。`in` 则退回纯成员测试运算符，不再兼任何循环职务。

**为什么 `as` 写在括号内部，而不是 `for (iterable) as i` / `except (E) as e`**：括号外会引进一个
现在没有的歧义。`as` 后面是完整表达式（之后才 check 成左值，因为要支持 `a[0]`、`a.b`、`(a,b)`、
`[a,*b]`——`$$` 收集模式的规范就依赖解构目标），而 body 紧跟其后也是表达式，中间没有分隔符；
`[` 和 `(` 既能续接前一个表达式（索引/调用）又能起头一个新表达式（列表字面量/分组），于是
`for (xs) as a [1, 2]` 会把 `a[1,2]` 贪心吃成索引左值，跟"目标是 `a`、body 是 `[1,2]`"撞车。
except 一模一样。放进括号里就保住了 SL 现在普遍成立的那条不变量：**头部完全被 `( )` 封死，body
紧跟 `)`**（`if`/`while`/`for`/`except` 无一例外），`)` 始终是"头部到此为止"的可靠信号。
两处的 `as` 位置因此是一致的，不存在不对称。

已知的观感瑕疵并接受：多异常类型时 `except (E1, E2 as e)` 乍看像 `e` 绑给了 `E2`。规则上没有歧义
（`as` 只能出现在头部末尾、绑定整个子句），且实际代码里绝大多数 except 只写一个类型，那时
`except (ValueError as e)` 和 `for (xs as x)` 读起来完全一致。

**`as` 整条可选**：`for (iterable)` 仍是迭代循环，只是每轮迭代出来的值直接丢弃；`except (E)` 就是
不关心异常对象。于是 for 头部的槽数规则简化成"3 个槽 → 步进，1 个槽 → 迭代"，1 个槽不再附带
"必须以 `in` 为根"这条额外要求——**任何表达式都能当可迭代对象**，能不能真迭代是运行期的事。
副作用：`for (x > 0) body` 从前是 `SyntaxError`，现在合法（迭代那个 bool，运行期才报 `TypeError`）。

**异常对象的绑定不做任何作用域魔法**：就是一次普通赋值，不 shadow 同名变量，except 体结束也不自动
解绑。Python 3 之所以自动 `del`，是为了断开 traceback 造成的引用环；SL 有 STW 全堆扫描处理循环
引用，没这个必要，于是整段 shadow/restore 规范直接删掉。附带后果：没有裸 `raise` 重抛了，要重抛
必须 `except (E as e) { raise e }`——显式，是好事。

### 链式比较

`< <= > >= != ==` 互相可链，`is` 单独一档优先级（比这六个松），不跟它们混链、也不共用节点类型。
**为什么 `is` 要分开**：`bool` 能跟 `int` 比大小（它实现了 `numbers.Real` 要求的比较，见下面
"`bool` 不再继承 `int`"），若和比较符混链，`a < b is c` 会解析成 `a < (b is c)`，把布尔值当数字比
大小——类型上合法、静默出错，是最危险的一类。拆开后 `a < b is c` 解析成 `(a < b) is c`，即便碰巧
不报错也是一眼假的写法。（注意这条理由不依赖"`bool` 是 `int` 的子类"，那层继承后来去掉了，理由
照样成立。）

### 开放式切片（`None..8` / `3..None`）

不加独立语法，靠 `..` 运算符 + `None` 表达开放端。`None` 本身不参与这个约定——是 `int` 的
`__op_range__`/`__op_rrange__` 把"另一侧是 None"识别成开放端，走普通运算符重载分派。

### 装饰器语法

`@decorator expr` 求值为 `decorator(expr)`；`@deco func f(){...}` 还需要把 `f` 重新绑定到装饰
结果。判断"该不该重新绑定"，否决过两条：①判断值有没有 `__name__`（鸭子类型）——`@staticmethod
outer` 会意外重新绑定 `outer`；②判断 `expr` 语法形状是不是直接的 `func`/`class`——嵌套装饰器
`@d1 @d2 func f(){}` 外层 `expr` 是装饰器表达式不是 func，外层不触发，`d1` 被丢弃。

**最终**：语法层面拆成两个东西，判据只看紧跟着的是不是 `func`/`class` 关键字：`@d1 @d2 ...
func/class ...` 属于 func/class 表达式自己语法的一部分（`decorators_` 是节点自己的字段）；
`@decorator expr`（expr 非紧邻 func/class）永远只是 `decorator(expr)`，无副作用。

**教训**：一个规则的触发条件要靠不断打补丁才能覆盖各种嵌套情况，往往说明从一开始就不该用同一个
语法形式表达两种意图，该在语法层拆开让解析器确定性判断，而不是语义层"猜"——跟"节点拆分原则"
（见 [architecture.md](architecture.md)）是同一条原则的两个应用。

### 命名决策：`match`/`case` → `when`

理由：`switch` 心智预期不对；`match` 常用词太易冲突；参考 Kotlin `when`，碰撞风险低。候选并否决：
`where`（LINQ/SQL 强关联过滤）、`given`（Scala 隐式参数）、`branch`（像名词）、`select`
（Go/SQL 已占用）、`pick`（太随意）。`case` 暂留，`when` 完整设计搁置。

### `++`/`--` 整体从语言里砍掉

没有后缀形式，丢了 C 系"真正好用"的场景（`arr[i++]`），剩下的前缀用法跟 `x += 1` 值语义完全一样，
纯粹少打两个字符换来专门一档优先级 + 专门节点 + 专门左值校验，投入产出不成比例。

### 空 `{}`：维持复合表达式语义，不是空字典

一度倾向改成空字典（`()`/`[]` 为空都优先当空字面量集合）。**否决**：空字典本来就是 `dict()` 写的，
不靠 `{}`；判别规则"要么 `**` 开头、要么第一个表达式后紧跟 `:`，否则复合表达式"统一适用，空的情况
自然落到"都不满足"分支。关键反例：`a = if (cond) {}` 里想表达"这个分支什么都不做"，如果 `{}` 是空
字典会让 `a` 变成空字典而不是 `None`，而空字典和 `None` 一样 falsy，这类错误会长期潜伏。要空操作
写 `None`，要空字典写 `dict()`，`{}` 不需要身兼二职。

这条只管**源码怎么写**，不该外溢成折叠器的约束。`for $$ (;False;)` 这类死循环消除一度因为"空字典
写不出字面量"就整个不折，那是错的：折叠器产出的是 AST 节点不是源码，`AstNodeLiteralDict` 的 `items_`
本来就可空，造一个空的完全合法，语义上也确实每次求值出一个新的空 dict（`is` 语义与循环真跑零轮一致，
不是 `*` 重复那种"克隆 vs 共享"的坑）。现在 `$$`/`$$ **` 一样折成空 dict 了。唯一残留的不对称是
`is_literal_pure` 对 dict 返回 `false`（dict 的相等/比较判不了），折出来的空 dict 不会再被
`prune_program` 当纯字面量丢掉，而 `$` 折出的 `[]` 会——这偏在安全侧，是少折不是折错。

### `if`/`while`/`for` 条件槽拒绝裸赋值 `=`

防 `if (x = 5)` 手误坑（SL 是动态类型，没有类型系统能免费防）。只限制 `if`/`while` 的 `cond`、
`for` 三槽形式中间槽；不限制 `for` 的 `init`/`inc`（这两槽存在的意义就是赋值）；只挡裸 `=`，不挡
`+=` 等复合赋值。真要在条件里赋值需要显式再套一层括号 `if ((x = y))`。

**因此"冗余括号没有任何效果"这个说法必须收窄**：冗余括号不改变值/类型/求值顺序，但它是实实在在写
在源码里的语法结构，凡是按**写出来的形状**给的语法限制都看它在不在——这条裸赋值限制就是唯一的现存
例子（`if (x = y)` 非法、`if ((x = y))` 合法）。以后再加这类纯语法限制，记得一并想清楚括号算不算。

`for (cond) body` 这种单槽纯条件形式**故意不提供**——`while $ (cond) body` 已经能做到完全一样的
效果，多一个入口只会削弱"`while` 是纯条件循环专用关键字"的区分。

### 类型注解设计

问题：没有泛型，没法表达"返回类型跟某个参数类型相同"；类型注解在类建立时求值，此刻类自己还没建好。
五版方案，否决前四个：

1. 内置单例 `Self`，类体收集属性那步替换成类对象——否，解出来的是基类自己建立那刻冻死的具体值，
   子类继承时协变做不到。
2. `Self` 读"绑定给第一个参数的值"的类型——否，绑定完成后这个信息早就丢了，且 SL 没有语法规定
   方法第一个形参必须是 `self`。
3. 用 `TypeVar` 顶替（`self: (T = TypeVar())`）——否，`MyInt.__op_add__("1", "2")` 这种不通过
   实例硬调的写法能通过检查，因为无约束 `TypeVar` 第一次出现只记基准，没人验证这个基准对不对。
4. `TypeVar` 加 `bound` 参数锚定到具体类——技术上能堵住上面的洞，但否决：`TypeVar` 该管的只是
   "多个位置类型互相一致"，混进"是不是某个特定类实例"，职责不单一。
5. 字符串注解惰性解析，推迟到第一次调用时按名字重新查找——技术可行，但否决：跟"建立时求值"两套
   时机并存不统一；按名字查找在"变量是引用语义"下不牢靠，名字随时可能被重新绑定。

**最终方案**：类型注解允许 `type | CompoundType | TypeVar`（正常检查）或 `str`（纯标签不参与
检查，等价无注解）。真正需要自引用/前向引用检查时，改为函数体内手动 `isinstance`（调用时才执行，
那时类早建好）。`TypeVar.bound` 只能是 `type | CompoundType`（不支持字符串，也不能是另一个
`TypeVar`——一致性检查按调用时形参顺序单趟扫描，`bound` 若指向另一个 `TypeVar` 会依赖两者相对
顺序，理解错了会悄悄放水）。

**牵出的更底层漏洞**：`class` 语法完全没有捕获列表（`func` 有），而"未捕获标识符只查当前帧与全局
帧"意味着类体、类体里任何方法体都够不到外层函数的局部变量——"局部定义一个类"这个模式完全走不通。
**修法**：给 `class` 补上跟 `func` 一样的捕获列表语法，放在基类之后（基类在类体帧建立前的外层帧
求值，捕获是新帧建立之后处理的，文本顺序对应求值顺序；且基类/捕获是两个毫不相关的概念，特意不
沿用 `func` 的 `[捕获](形参)` 视觉布局）。

**顺带化简**：引用捕获从"每个名字各存一份 (x, 定义帧)"改成"函数/类建立时无条件记住定义帧（不管
有没有捕获），引用捕获退化成只需要记名字集合"——一个函数/类只可能有一个定义帧，之前是重复存储。
这个"无条件定义帧"同时是让跨模块调用正确解析全局作用域的必要前提（见下面帧栈一节）。类的引用捕获
不会变成类属性（`_L` 只收集局部字典里的值捕获），类的引用捕获链式转发也不会有死帧问题（引用捕获
集合挂在函数/类对象自己身上，不是挂在帧上）。

### `import` 语义：module/package 概念仿 Python

多段名字（`import os.path`）原来写的"等价于 `os = import('os.path')`"站不住：按"`import()` 不
透明整串查找"这条流程，调用形态该返回叶子模块，绑给 `os` 就错了。中间讨论过一个更省事的方案：
loader 永远不解析点号，`a.b` 能不能访问纯靠 `a` 模块自己有没有挂对应属性——能自洽，但用户认为不如
直接照抄 Python 的 module/package 模型来得实在，否决。

定稿：module 对应文件、package 对应目录（内容是 `__init__.sl`；没有则视同空文件，不报错），两者
产出同一种模块对象，没有独立的 package 类型。多段名字从左到右逐段导入，逐层把子模块挂为上一级的
同名属性。调用形态返回**最后一段**（跟 `importlib.import_module` 一致）；关键字形态多段时只绑定
**第一段**（跟 Python `import` 语句一致）——这是两种形态在多段情形下唯一的差异，不是疏漏。完整
规则见 SL.md 对应章节。搜索路径、循环 import、相对导入仍未设计，故意搁置。

### `import` 的 AST 表示

两种语法形态**不**塞进一个节点里用 variant 分叉，拆成 `AstNodeImportKw`/`AstNodeImportCall` 两个
节点（理由见 [architecture.md](architecture.md) 的节点拆分原则）。

调用形态一度打算复用 `AstNodeCall`，被调对象填 `AstNodeIdentifier{U"import"}`——**否决**：这要求
运行期真的按名字查到一个 `import` 对象，但 `import` 是语言构造不是内置函数，既不在 4.1 里也不在
内置表里，这个标识符压根查不到；而且造出来之后 `_G['import'] = print` 就能把调用形态劫持掉
（内置名字本来就可以被 `_L`/`_G` 里的同名项 shadow），关键字形态不查名字、不受影响——同一个语言
构造两种写法一个能被劫持一个不能，这个分叉比劫持本身更坑。也考虑过给被调对象加个
零字段标记节点，同样否决：在"一切皆表达式"的语言里这个节点求值必须产出某个值（一个 4.1 里不存在
的"import 函数对象"）。

最终：`AstNodeImportCall` 没有被调对象槽位——`import` 是运算符本身，不产生这个中间值。

关键字形态存 `std::vector<std::u32string>`，不存 `AstNodeAttr` 链：`import os.path` 根本没对
`os` 做属性访问（是两次导入 + 一次 `os.path = <模块对象>` 赋值），存成属性链会让泛型递归的
`AstNodeAttr` 消费者把被绑定的 `os` 当成一次读取，语义反了。

换行规则：`import` 后无条件允许换行（跟 `global`/`del` 一致），两种形态一视同仁；段名之间的 `.`
跟属性访问 `x.y` 逐字对齐。调用形态的 `(` 不比 `global`/`del` 更严格（曾按"该像普通调用那样绑定"
判 `import\n(...)` 为错误，被否决：拆成独立节点之后 `(` 不再是接在某个被调表达式后面的后缀，而是
`import(...)` 整体的一部分）。

### `global`/`import`（关键字形态）目标收紧：不再参与外层运算符链

两者曾经都是"`parse_non_op` 只吃一个 token 就返回"——`global` 直接 `expect(IDENTIFIER)`，
`import` 手写一个 dot-loop 吃 `a.b.c`。问题是返回的节点会照常交回外层 `parse_expr_pratt` 的
中缀/后缀循环，跟标识符、字面量一视同仁地继续参与 `.`/`()`/`+`：`global x.y` 解析成
`Attr(Global(x),"y")`，`import a.b(x)` 解析成 `Call(ImportKw([a,b]),[x])`。这**不是**特意设计的
"一切皆表达式，别为它们特殊开洞"——`global` 的值恒为 `None`（3.4.4），`import` 的目标是模块对象、
模块对象恒不可调用（3.4.5 易错提醒）——两种拼法**保证**跑不通，编译期就能确定，只是实现从没堵。

**否决过的修法**：在 `check_terminator()` 那套机制上加一道"这个构造后面必须紧跟真正的终止符"的
检查。否决理由：终止符的合法集合随嵌入语境变（顶层是换行/`;`，函数实参里是 `)`/`,`，元组里是
`)`/`,`……），要把这些语境挨个枚举等于重新发明"什么token能合法跟在一个表达式后面"这件事，而这件事
`parse_expr_pratt` 自己的循环终止条件已经在处理，没必要另开一套。

**定稿**：目标改成整条 `parse_expr()`，吃完再校验形状——`global` 要求纯 `AstNodeIdentifier`；
`import` 要求 `AstNodeIdentifier` 或一路 `AstNodeAttr` 到底的链，展开进 `segments_`（复用属性
访问的 `.`/换行规则，不再手写一份"跟 x.y 保持一致"的复制品）。校验和析构都在 Parser 里做完，最终
字段形状不变（`identifier_: u32string`、`segments_: vector<u32string>`），不留一个宽泛的
`AstNodePtr` 给语义层。目标位置先用一次不消耗 token 的 `check(IDENTIFIER)` 探路，避免撞见
`global class`/`import as` 这类关键字时一头扎进它们自己的产生式、报出不相关的错。

判断标尺见 [parser-token-vs-expr-level.md](notes/parser-token-vs-expr-level.md) 新增的第三问。

### 真值统一到 `__bool__`

原文只列了一张"哪些内置对象为假"的清单，读起来像是真值由解释器写死的。改成：任意对象 `x` 的真值
就是 `type(x).__bool__(x)` 的返回值（必须是 `bool`，否则 `TypeError`）；`object` 自带一个无条件
返回 `True` 的 `__bool__`，所以任何对象都有真值，自定义类不重载就恒为真。原来那张清单降级成"部分
内置类型对 `__bool__` 的重载结果"。

`__bool__` 没有进协议那一章：那章的判定标准是"方法存不存在决定对象能不能参与某机制"，而 `__bool__`
因为 `object` 兜底永远存在，不存在"满足与否"的问题。也不属于运算符重载表（不对应任何运算符，`not`
明确不可重载）。

### 内置名字放在一张独立的"内置表"里，不放 `_G`

`print` 等内置名字原先没规定住在哪，塞进 `_G` 很不合适（每份文件的 `_G` 都得预先灌一份、还会被
`del` 掉）。定稿：单独一张固定、全局唯一、只读的**内置表**，只在按标识符**读取**且当前帧与它所属
全局帧都没有该名字时兜底（`_L` → `_G` → 内置表）。写和删永远不碰它：`print = x` 只是在 `_L`/`_G`
新建一项来 **shadow**，`del print`（没被 shadow 过时）照常 `NameError`。

**4.3 内置模块不在内置表里**：模块名只能靠 `import` 主动导入才绑定到标识符，没 `import` 过直接写
`numbers` 就是 `NameError`。（`import` 找不到同名源文件/目录时才去内置模块名里找，那是加载算法的
事，跟标识符解析是两回事。）

### `bool` 不再继承 `int`，改继承 `numbers.Real`

继承 `int` 会把位运算等一堆"只有 `int` 才讲得通"的东西带给一个只有两个值的类型，`isinstance(True,
int)` 成立也是 Python 被诟病过的历史包袱。改成继承 `numbers.Real`：混算行为几乎不变（`True == 1`、
`True + 1 == 2` 照旧），但不是靠继承白拿，而是 `bool` 自己实现 `numbers.Real` 要求的四则运算与
大小比较，参与运算前把 `True`/`False` 折算成 `1`/`0`，再复用 `int` 的实现；
结果类型与对应的 int 运算相同（不是 `bool`）。因此 `True + 1` 是 int，`True / 2` 是 decimal。

**没继承 `object` 而是继承 `numbers.Real`**：`bool` 确实能正确参与四则运算和比较，让
`isinstance(x, numbers.Real)` 对它成立符合通用数值代码的预期；要甩掉的只是 `int` 特有的那部分。

**连带后果（都是有意的）**：位运算 `~ & ^ | << >>`（SL.md 写的是"对于 int"）对 `bool` 变成
`TypeError`；容器重复次数（"非负的 int"）也不收 `bool`，`'a' * True` 是 `TypeError`；`FuncGroup`
分派时 `f(True)` 不再命中 `x: int` 那条候选。折叠器里对应地把"是不是 int"拆成 `is_int`（真 int）和
`is_int_family`（bool 或 int）两个谓词，强迫每个调用点显式选一次。

### 复合类型 `[]`：tuple 与 list 完全平行

`tuple[T1, T2, ...]` / `list[T1, T2, ...]` 定长、按位置检查；一个类型参数即定长 1（`list[int]`
不是任意长的 int 列表）。齐次用 `tuple[T, ...]` / `list[T, ...]`。`dict` 只有 `dict[K, V]`，
`set` 只有 `set[T]`。

### `unsupported` 从"打标记的内置函数"改成 `Descriptor` 子类

原设计 `unsupported(v)` 把 `v.__is_unsupported__` 置 `True` 再原样返回 `v`——一边骗
`isinstance`/协议检查说这个方法不满足，一边又保留 `v` 的可调用性，语义分裂；而且这个标记是"活的"
（每次协议检查都要重新扫），随时可能被 `attrs` 绕开。

改成内置类 `unsupported(name=None)`，`Descriptor` 子类，`get` 无条件抛 `AttributeError`。类体里写
`some_meth = unsupported`（收集属性那步自动补成 `unsupported(name)`，不用手写两遍名字）或
`unsupported('自定义消息')`，存进**描述器表**。于是"标记"和"行为"是同一个东西，不存在被绕开的窗口。

**优先级不用单独规定**：它进的是描述器表，自动遵守"MRO 上第一个命中的描述器表项获胜"，子类的
`unsupported` 正常盖住祖先类里的真实方法描述器。`protocols` 的鸭子类型检查也不再单独扫标记，改成
复用同一次 MRO 查找："查到的那一项是不是 `unsupported` 的实例"。

**`abstractmethod` 不跟着改**：它只在类建立那一刻被读一次、烤进 `__abstractmethods__` 就定型，
事后改标记没人再看，不存在 `unsupported` 那种被绕开的漏洞。两者还能正交组合：
`foo = abstractmethod(unsupported)` 天然表达"没有默认实现、子类必须重写"。

### 帧栈允许多个全局帧，`_G` 不再是"栈底"

原文写"栈底为全局帧"，跟已定稿的 `import`/`eval_isolated` 语义矛盾：这两者都会在栈的任意位置再压
一个文件级的帧，运行期同时存在多份 `_G`。

改法：帧显式分成**全局帧**（执行一份文件压入）与**局部帧**（函数调用、类体执行压入），每个帧再记
一条"所属的全局帧"——全局帧属于自己，局部帧属于"建立它的那个函数/类的定义帧所属的全局帧"。`_L` 是
栈顶帧的局部字典，`_G` 是当前帧所属全局帧的局部字典。

关键是这条链走**定义帧**、不走栈：一个函数不管从哪份文件里被调用，它的全局变量始终是它自己那份
文件的（等价于 Python 把 `__globals__` 绑在定义处的模块上）。若按"从栈顶往下找最近的全局帧"定义，
A 文件里的函数被 B 文件调用时全局变量会跑到 B 上去，是动态作用域灾难。定义帧这个概念本来就为引用
捕获而存在，直接复用，没有新增机制。

### 描述器移出类的属性表，单独一张描述器表

起因：属性协议一边把属性做成字典，一边靠描述器插一嘴、还兼着"防御"（方法描述器不实现 `set`，所以
`int.__op_add__ = f` 抛 `AttributeError`），但这层防御被 `attrs` 一扯就开——
`attrs(int)['__op_add__'] = f` 直接改掉 `int` 的行为。

比较过四条路：①黑名单锁住某些东西禁用 `attrs`（`__slots__`/`__dict__` 那套，无原则性答案）；②类的
属性表只读（"怎么只读"要新造只读视图类型，且挡住了合法的类级写入）；③`attrs` 返回一个继承 dict
但在 `[]` 上加检查的实例（继承 dict 却撒谎，破坏映射协议可替换性）；④**描述器全部搬到另一张表**。
选④，它顺带把②吃掉了：危险槽位根本不在 `attrs` 里，`attrs` 就能继续是一个诚实的、可读可写的普通
`dict`，类和实例一视同仁。

定稿：①描述器表只在类建立时确定，此后不变（类建立完之后再 `C.p = property(...)` 只是写进属性表、
成为普通类属性，不参与绑定）；②描述器表整体优先于属性表，同名时属性表那份是死项；③描述器表既不
通过属性名暴露，`attrs` 也取不到（唯一例外：`property.get` 经由类访问时故意返回自己供内省）。
因此实例不能用同名属性覆盖类上的方法：方法在描述器表里，写入走 `MethodDescriptor.set`，默认
`AttributeError`。不引入 Python 那套数据/非数据描述器区分。

实例侧不分两张表：查找规则只查 `type(o)` 的 MRO，实例属性表里放个描述器对象就只是个普通值——实例
属性表里没有任何解释器依赖的不变量，被旁路写也只会写出个被描述器遮蔽的死项。

**读/写/删三条规则的第 1 条必须对称**：都得先判"`o` 本身是类就查它自己 MRO 的描述器表"。曾经只有
读有这条特判，于是 `int.__op_add__ = f` 查 `type(int)`（即 `type`）的描述器表、查不到，静默写进
`int` 的属性表变成死项——那层"方法描述器不实现 `set` 所以报 `AttributeError`"的防御等于没有。

**`get(self, obj)` 不传属主类**（不像 Python 的 `__get__(self, obj, objtype)`）：靠
`isinstance(obj, type)` 一个判据区分经实例访问/经类访问。成立的前提是 `type` 是唯一元类且 final
（用户定义不出元类），因此"`obj` 是类"⟺"经类访问"；经实例访问时属主类就是 `type(obj)`，不用传。
**唯一的边界**：给 `type` 自己加需要绑定的普通方法或 `property` 会破坏这个等价（类是 `type` 的
实例，此时经实例访问的 `obj` 也是个类）。已在 SL.md 3.9.1.1 写死"别给 `type` 加这种成员"；运算符
方法不受影响，它们本来就是 `type(a).__op_xxx__(a, ...)` 显式传第一参数。

**描述器表的开放方式**：不新开 `descriptors()` 内置函数（用得极少却要长期占一个内置名字）；不做成
`cls.__descriptors__`（任何类在类体里定义同名的东西就会遮蔽它）。最终给 `attrs` 加参数
`attrs(obj, table='attributes')`，`table='descriptors'` 返回 `frozendict`（只读）。**`attrs` 保持
自由函数，不做成方法、也不给它配 `__attrs__` 钩子**：`attrs` 的全部价值在于它是唯一一扇不经过属性
协议的窗，做成方法就等于放回它本该绕开的机制里（能被 `__getattr__`/子类重载拦截）。

`frozendict` 只冻表、不冻值：拿到 `MethodDescriptor` 之后 `attrs(它)['func'] = evil` 照样能改
`int` 的行为。故内置描述器（`MethodDescriptor`/`property`/`classmethod`）持有的函数不放进自己的
属性表，走解释器内部引用；`staticmethod` 不在此列，它不是描述器，`v.func` 是货真价实的属性。

**函数对象的类和 `MethodDescriptor` 都不是内置名字**：类一定存在，但不进内置表，源码里写不出这个
名字。函数对象的类用 `type` 从任意 `func` 表达式的值上取；`MethodDescriptor` 只能通过
`attrs(cls, 'descriptors')` 拿到它的实例。

**改过一次**：原来的结论是"这种类干脆别写进 `SL.md`"，理由是 4.2/4.4 那两处是"内置表里有哪些名字"的
清单。后来发现这么做等于让规范整片缺一批真实存在的类——`type(某个函数)` 是什么、绑定方法是什么类的
实例，规范都答不上来。现在改成**单开 4.5「不入内置表的类」**：判据是"正常写 SL 时不应该、也没必要主动去动
它们"，成员有 `NoneType`/`SingletonType`/`CompoundType`（从 4.2 挪过去的）、`Function`/
`BuiltinFunction`/`Method`/`MethodDescriptor`。4.2 里那三个的小节号保留成一行重定向，**没有重排
编号**——`4.2.x` 在仓库里有八十多处引用，为消除三个空位去动它们不划算。

**类体收集方法不按 `protocols.Callable`**：只把函数对象和 `FuncGroup` 的实例包成 `MethodDescriptor`。
类、带 `__op_call__` 的实例等其它可调用对象进属性表、不绑定 `self`。装饰器也不先查 `Callable`，
直接按 3.5 调用。

`MethodDescriptor.get(self, obj)` 跟 `property`/`classmethod` 一样必须分 `isinstance(obj, type)`
两路：经由实例访问才把 `obj` 绑成第一参数，经由类访问（`C.method`）不绑定、直接返回持有的函数。
早期写成无条件绑定，会让 `C.method` 拿到"把类 `C` 绑成 self"的东西，已改正。

### 构造统一到 `__construct__`，不要 Python 的 `__new__` / `__init__` 两段式

`C(...)` 就是 `C.__construct__(...)`（`classmethod`，既分配也初始化，返回对象），见 SL.md 3.4.8。

**为什么两段式能合**。Python 分两段的四个真实理由，合并后各自都有着落：不可变类型的值必须在分配那
一刻定死（`__construct__` 返回对象，天然能直接造成品，这是合并的净胜项）；返回已存在的对象（驻留、
单例、缓存）同样靠"返回对象"支持；"造壳但不初始化"（反序列化、`copy`）降级成 `object.__construct__`
这一个根类原语，能力没丢，只是不再是每个类都要实现的协议的一半；协作式继承里 Python 的
`super().__new__(cls)` 漏传 `cls` 是经典 bug（`__new__` 是隐式 staticmethod，类型机制里的特例），
改成真正的 `classmethod` 后绑定自动带对。

**SL 尤其适合合**，因为 `type` 是唯一元类且 `__is_final_class__ = True`（SL.md 4.2.2）。Python 的
`C()` 真正是三层：`type(C).__call__` → `__new__` → `__init__`，第一层是留给用户元类的钩子。SL 没有
用户元类，那一层永远同一份实现，等于白留。所以 SL 本来就该是两层，合成一层之后"`C(...)` 就是
`C.__construct__(...)`"是真等价，规范一句写完。

顺带删掉的 Python 疣子：`__new__` 返回非 `cls` 实例时 `__init__` 静默不被调用；同一批实参被塞进两个
函数，逼 `__new__` 写一堆 `*args` 只为扔掉；"`__init__` 必须返回 `None` 否则 `TypeError`"；
`object.__new__` "子类重写了 `__init__` 就默默吞掉多余实参"的特判。

**"返回值必须是 `C` 的实例"是语言对构造路径的要求，不是 `__construct__` 的签名要求**。检查发生在
`C(...)` 这条路径上，直接写 `C.__construct__(...)` 只是一次普通的类方法调用，不检查。比 Python 严
（Python 是"不是就跳过 `__init__`"，不报错），代价是禁掉"`C()` 返回完全无关东西"的工厂写法——这是
故意的，"`C()` 必然返回 `C` 的实例"是个很值钱的不变式，要工厂就写普通 `classmethod`。

**`__abstractmethods__` 的检查挪进 `object.__construct__`**，不留在 `C(...)` 的三步里。留在三步里的话
直接调 `C.__construct__(...)` 就能绕过，上面那个等价就是假的。放在分配那一刻还有个好处：子类重写
`__construct__` 返回缓存对象时不报错，而这本来就对——压根没分配过抽象类的实例。

**`__construct__` 必须显式写 `@classmethod`**，类建立时收集属性那步检查，不是的就 `TypeError`。没有
仿照 Python 给 `__new__` 开隐式绑定特例：类体收集属性的规则（3.4.8）现在是一张干净的、不看名字的
表，为一个名字开洞不值。失败得响就够了——否则它会被存成 `MethodDescriptor`，经由类访问不绑定，
`C(x)` 把 `x` 当 `cls`，错得很隐蔽。

**认下的代价**：最常见的类（只想填几个字段）被迫关心分配，比 Python 的两行 `__init__` 多了取 `self`、
`return self` 两行样板，还多一个"忘了调 `super(...).__construct__()` 就返回 `None`"的失败模式（比忘调
`super().__init__()` 更致命，后者至少还有对象）。前面所有好处都是偶尔才用到的，这个成本每个类都付。
JS 靠 `super()` 隐式改写 `this` 躲掉了它，Smalltalk 没躲，Ruby 干脆保留 `allocate`+`initialize`、
只把 `new` 做成普通类方法。权衡后仍然选合并：偶发但真实的正确性问题（不可变类型、驻留、静默跳过
`__init__`）比每次多两行样板更值得治。

**配套改了 `super`**（SL.md 4.2.24）：第二个实参允许传类，是类就用它自己的 MRO，否则用 `type(obj)` 的。
`__construct__` 里手上只有 `cls` 没有实例，不放开就根本没法往上调。`get(obj)` 照旧原样传 `obj`，
绑不绑定由描述器按 `isinstance(obj, type)` 自己决定，跟 3.9.1.2 已有的两路规则完全一致，没有新机制。

### 调用的终点：`__op_call__` 必须有基础情形，四种"原语可调用"是它

`f()` 走 `type(f).__op_call__` 是条**递归**规则，原来的 SL.md 3.5 只写了递归那一支，没有终点——查到的
`__op_call__` 自己也得被调用。补上的基础情形是四种**原语可调用对象**：`Function`、`BuiltinFunction`、
`Method`、`FuncGroup`，解释器直接认得，不再查它们的 `__op_call__`。

**关键认识：基础情形是解释器里的一个判断，不是对象图里的某个节点。** 不可能靠"再定义一个
`__op_call__`"来终止。CPython 结构相同——`type(f)->tp_call` 是 C 函数指针，不是又一个 Python 对象。

类对象不是原语：`C(...)` 走 3.4.8 取 `C.__construct__`（classmethod → 绑定方法）落回原语。典型深度
是 2 跳（`a()` → `type(a).__op_call__` 绑定成 `Method` → 原语）。链**可以无限**：
`class A { __op_call__ = 某个 A 的实例 }`（按 3.4.8 第 7 条原样进属性表、不绑定）。按 bytecode.md
"C++ 栈不得随 SL 帧栈增长"的硬约束，这条链在主循环里走，吃的是 `RecursionError`，不会爆 C++ 栈。

### 函数对象：SL 函数与内置函数是两个 C++ 类、两个 SL 类型

C++ 侧拆开，判据就是"字段表不同"（跟 `NamedSingleton` 那四个合并的案例正好相反）：`Function` 持
`Ref<Code>` 等一串 GC 要遍历的引用；`BuiltinFunction` 持一个裸 C++ 函数指针，GC 不管、不占 SL 堆。

SL 侧也是两个类型（`Function` / `BuiltinFunction`，SL.md 4.5）。**不合并成一个**：合了之后 SL 层就得
回答"`print` 的函数体怎么内省"，只能是 `None` 或抛异常，凭空造一个半成品接口。有没有 SL 函数体是真实
差别，让类型如实反映它。

**三个函数类型（含 `Method`）都是 final**：`CALL` 指令靠比 `f->type()` **指针**决定是压 `ByteCodeFrame`、
调 native、还是去查 `__op_call__`。允许继承的话 `type(f)` 可能是子类，指针比较失效；放宽成 MRO 查找
会拖慢最热的指令。要包装可调用对象，用普通类加 `__op_call__`，这条路一直开着。

**内置函数走 3.5 那一套实参绑定，不另开一套**：代价是每个内置函数得声明形参与类型注解，换来的是槽位
填充/`*args` 收集/类型检查/`DispatchError` 措辞只有一份实现。CPython 是反面教材：`METH_VARARGS` /
`METH_FASTCALL` / argument clinic 三套并行，内置函数和 Python 函数的报错至今不一致。

`NativeFn` 的具体签名留到写 `executor/` 时定稿，因为它绑死在 `NativeFrame` 的形状上：纯计算型
（`len`/`abs`/`chr`）想直接返回 `ObjectRef`，回调型（`sorted(key=)`、`map`、`import` 加载算法）必须
返回"我压了这个帧"。统一成"永远建帧"会让 `len(x)` 白白堆分配一个帧对象，太亏。

### `for`/`while` 收集模式扩展：`$ *`、`$$`、`$$ **`

补上字典推导式的空缺。最好的说法不是"`$` 后面若有则必须是 `*`"这条规则，而是**两个记号各管一个
轴**：第一个（`$`/`$$`）定结果容器（list/dict），第二个（`*`/`**`）定每轮的值怎么进容器（整体一项
/ 展开一批）。配对约束是推出来的——展开方式必须跟容器种类匹配，复用展开语法里 `*` 对可迭代、`**`
对映射的既有分工。

**记号挂在 `for` 上而不是挂在被收集的表达式上**（不写成 `for $ (i in xs) *e`）。后者看着更贴合展开
语法的老位置，实际不行：`expr` 可以是 `{ ...; e }` 或 `if (c) a else b`，`*` 就得允许出现在复合
表达式末项、`if` 各分支里，规则变成"收集模式的 expr 及一切能成为它的值的子表达式"，非局部、难写
难查。挂在 `for` 上它就是这个循环的一个静态事实。代价：这个 `*` 不再是展开语法（没有操作数），是
模式修饰符。

**`$$` 每轮 `expr` 的形状定为"相当于 `(k, v) = expr`"**，即恰好产出 2 个元素的可迭代对象，不必是
`tuple`。决定性理由：迭代模式 `for ((k, v) in pairs)` 已经在按解构赋值规则拆每个元素了，同一个构造里
不能对"一对"有两套判定。已知后果并接受：两字符 str 会被当成合法 pair（同 Python 的
`dict(['ab'])`）。

### `float` → `decimal`：十进制、任意精度；二进制浮点降级成 `raw_float`

`int` 早就是高精度的，`float` 是数值塔里唯一"精度取决于硬件"的异类；而且字面量是十进制写的，
`0.1` 在词法分析那一刻就已经不是 `0.1`——这是所有浮点惊吓的源头。SL 定位是脚本、方便优先于速度，
于是换成十进制浮点 `decimal`（`符号 × 系数 × 10^指数`，系数任意精度）。原来的 double 以后以
`raw_float` 身份回来（跟 `raw_int` 一桌），价值只剩速度和与 C/文件格式互通。

**改名而不是沿用 `float`**：老 float 迟早以原生身份回来，两个类型不能都叫 float；而且各语言里
`float` 都背着"`0.1 + 0.2 != 0.3`"的包袱，这次改动的全部意义就是干掉这个默认假设。

**否决了有理数（分数）**：`1/3` 精确、`1/3*3 == 1` 成立，看着更"精确"，但显示两面派（打印 `1/3`
就不是小数类型了，打印截断小数又破坏往返）、无理运算照样得舍入（等于同时背两套精确性模型）、
分母静默膨胀（累加 `1/k` 几百项就是几千位的分母）。

**代价，别忘了**：超越函数得自己写。SL.md 允许 `x ** y` 的非整数指数，也就是 `2 ** 0.5` 必须算得
出来——任意精度下要靠牛顿迭代开方 + `exp(y·ln x)`，还得带保护位。精度固定这一点帮了大忙：保护位
数量有界，不用写通用实现。

### 科学计数法字面量：尾数带不带小数点决定 int 还是 decimal，纯语法判定不求值

语法：尾数（int 或 decimal 字面量）后面跟 `[eE][+-]?digits`，指数部分同样遵守"不允许前导零，
单独一个 `0` 除外"。`+` 可省略，`-` 不可省略。整体值是"尾数 × 10^指数"。

**类型只看尾数带不带小数点，不看指数正负、更不看数值算出来是不是整数**：尾数不带小数点时，
必须搭配非负指数，整体是 int（`1e9` 是 int，值 `1000000000`）；尾数带小数点时指数可正可负，
整体恒是 decimal（`1.0e9`、`1.0e-9`）。跟 `float → decimal` 一节同一个精神：类型是字面量写下的
样子决定的静态事实，不是运行时/编译期求值算出来的——`100e-1` 数值上恰好是整数 `10`，也不例外，
一律走"尾数不带小数点 + 指数为负 = 不合法"这条。

**尾数不带小数点、指数为负（如 `1e-9`）直接判成不合法，不是自动退化成 decimal**：曾经考虑过让
它退化成 decimal（跟 Python "只要有 `e` 就是 float" 一致，也更宽松），否决了——那样"是不是 int"
就得同时看两个信号（尾数带不带点 + 指数正负）才能判定，且两个信号还能互相覆盖（点决定，点没有
时指数说了算），概念上不干净；改成"不合法"之后，规则退化成一句话："尾数带小数点 ⟺ decimal"，
指数的正负只决定"这条 int 字面量合不合法"，不参与决定类型本身。代价是想写一个很小的 decimal
时不能省 `.0`（`1e-9` 不行，必须 `1.0e-9`），换来的是类型判定规则没有例外、不需要读指数才能确定
一个字面量是 int 还是 decimal。

**int 分支的指数上限定为 9999，decimal 分支不设限**：`decimal` 的系数指数分开存，指数再大也不会
真去材料化一个天文数字（`1.0e999999999` 不炸内存）；但 `int` 只有裸值，`1e999999999` 得真造一个
十亿位的 `BigInt`，那是小时级/爆内存。**一度决定"跟 `BigInt::pow` 一样不设上限、留给 VM 资源
guard"，后来推翻了**——`pow` 的操作数可以是变量、上限只能是运行时策略；而字面量的指数是写死在
源码里的静态常量，编译期就能判，没有理由拖到运行时。

**限制只针对 `e` 记法，手写的长字面量不受限**（`1` 后面手写 70000 个 `0` 合法，`1e70000` 不合法）。
这不是双标，是两种写法的代价本来就不对称：手写 n 位数，源码里就得有 n 个字符，长度即成本、
一眼看得见；`e` 记法几个字符就能要一个天文数字。

**数字定为 9999（不是最初量出来的 65536）**：lexer 里指数数字是 `u32string`，手写转成整数
要自己写循环；卡在 9999（4 位）上，判断退化成"位数 > 4 就不合法"，不用把指数解析成数值。
65536 是量过更大区间性能之后选的，但这个理由撑不住"改成 4 位数就能省一步手写转换"这个更简单
的实现收益——两者都远超实际用途，不值得为了那个理由多写一段解析代码。

**这条限制归 lexer 管，不下沉到 `BigInt`**（因此 `BigInt::from_decimal_string` 接受任意大的指数，
只在文档里注明风险）。理由有三条，都指向同一处：这是**源码形态的政策**，不是数值库的不变量。
其一，已有先例且是同一类规则——lexer 现在就在管"不允许前导零"，而 `BigInt::from_decimal_string("007")`
照样返回 `7`（还有测试钉着）；"SL 的字面量政策"与"BigInt 的解析宽容度"本来就分两层。其二，
`BigInt` 头文件自己立过规矩：它抛 `std::domain_error` 而不是 `MathError`，因为"不知道、也不该知道
SL 的异常类型体系"，9999 同理。其三，规则内容本身就是"手写不限、`e` 记法限死"，而 `BigInt` 拿到
的都是字符串，看不出、也不该关心它来自哪种写法。

**代价**：`decimal` 的 `str()` 在系数恰好一位数字时，科学计数法输出不带小数点（如 `1E+30`）——
这类输出粘贴回源码当字面量会被读成 int，不是 decimal，往返静默换类型。见 SL.md 4.2.6 `str` 那条
的说明；真要保住 decimal 类型，要么手动补一位小数（`1.0E+30`），要么走 `decimal(...)` 构造。

**decimal 字面量的指数 lexer 不设上限，是故意的**——上下文的 Emin/Emax 运行时可变，而构造不舍入，
词法期无从卡起。`1.0e2000000000` 这种超出 `BigDec::kMaxExponent` 的写法能过词法，到
`try_from_string` 才返回 `nullopt`，由转换那一层报 `SyntaxError`。不下沉到 lexer：`kMaxExponent`
是 numeric 的表示上限、不是源码形态的政策，抄一份到 lexer 会静默失配。

### decimal 的精度模型：抄 Python，每个运算都按上下文舍入

一度设计成"精确优先"（`+ - * // %` 恒精确，只有除不尽的 `/` 和无理运算才舍入），**否决了**：

1. **位数没有上限**。`x = x / 2` 放进循环，一千轮就是一千位，静默变慢变大；而除法恰恰是用户默认
   "结果不会变大"的地方。
2. **规则是锯齿状的**：`1/8` 精确、`1/6` 舍入、`1/5` 精确、`1/7` 舍入——精不精确取决于分母的质因数。

改成全舍入几乎不亏：`prec` 默认 28 时，"每个运算舍到 28 位"和"精确"在真实脚本里区分不出来
（`0.1 + 0.2 == 0.3` 照样为真，结果本来就只要 1 位），舍入只在 28 位以上才咬人。卖点没丢，
成本有了上限。

**构造不舍入、运算才舍入**：字面量、`decimal(x)`、int/bool 提升都精确保留全部位数。
`+x`/`-x`/`abs` 是运算，按上下文舍入；`+x` 不是恒等（IBM 规范如此，`BigDec::plus` 已按此实现）。

**标度是值的一部分，不做规范化**：`1.50` 与 `1.5` 值相等但 `str` 不同。一度想反过来（剥掉末尾零、
一个值一种形状），抄 Python 之后不这么干——"理想指数"规则让 `1.10 + 2.00` 得到 `3.10`，金额计算
不用补零，那是 decimal 最主要的用途。

### decimal 的上下文：全局可变 + 每个方法可传临时的

`decimal` 是**类**不是模块：`Context`、`getcontext`、`setcontext`、各信号类都是它的类属性；各舍入
常量挂在 `Context` 上（它们唯一用途就是当 `Context.rounding` 的取值，而挂在 `decimal` 上会从每个
decimal 实例上看得见）。

一度反对可变全局上下文（动态作用域、静默错值、机制过重），在"每个运算都舍入"定下来之后这些反对
不成立了：上下文管的是每一个运算，机制和范围就匹配了。代价照单收下——它确实是动态作用域，
`x / 3` 的结果取决于谁改过上下文。

**临时上下文走方法的可选末位参数**（`__op_div__(self, other, ctx=None)`），每个这样的 dunder 配一个
去掉 `__op_` 前缀和尾下划线的别名（`div`、`add`……），于是写 `a.div(b, ctx)`。**`Context` 不挂
`ctx.divide(a, b)` 那套算术方法**：那和 `a.div(b, ctx)` 是同一件事的第二种写法，两套等价 API 是净
负担（Python 两套都有是历史层积，它的 Context 早于 dunder 的 context 参数）。已知代价：左操作数是
int 时够不着，`1 / 3` 想换精度得写 `decimal(1).div(3, ctx)`。

**删掉的三个 Python 字段/类**：`capitals`（`E`/`e` 大小写是显示开关，算术环境里不该有显示选项）、
`clamp`（只为 IEEE 定宽交换格式服务，SL 的 decimal 没有定宽表示）、`FloatOperation`（专门拦截
Decimal 与二进制浮点混用，SL 没有这种混用）。

**保留了 `Infinity`/`NaN`/`sNaN`/负零**：traps 可配置，就必须有"不设陷阱时返回什么"，否则 traps 是
空壳。默认三个陷阱全开，正常用碰不到。附带好处：decimal 的 NaN 参与序比较是抛 `InvalidOperation`
而不是静默返回 `False`，排序不会得到无声的错误结果。

**`//` 不采纳 IBM 规范的 `divide-integer`（向零截断）**：SL 已明写"`//` 永远向负无穷"，跟着抄会把
Python 自己 `int` 与 `Decimal` 取整方向不一致的毛病引进来。

### 结果为 decimal 的常量折叠一律禁掉

它们按运行时的当前上下文舍入，编译期不知道那时的 `prec`/`rounding`，折了就可能与实际执行的结果
不一致。这跟 int 折叠**不是一回事**：int 用 `int64_t` 折、溢出就不折，是"保守但正确"；decimal 用
double 折 `0.1 + 0.2` 会得到 `0.30000000000000004`，那是**错值**，不是漏折。

**结果为 bool 的比较照折**：比较不舍入，它唯一查上下文的场合是 NaN 触发信号，而 NaN 只能由构造
调用产生，调用本身就不参与折叠。

`StaticEvaler` 里整套二进制浮点折叠（`node_to_double`/`std::pow`/`std::fmod`/`make_decimal`）都要
按这条清理，不是改改名就完事。**已清理完毕**：int 侧改用 `int64_t` 直接算、溢出就不折（不是接进
`numeric/BigInt`——折叠器故意不依赖高精度库，见下面"科学计数法字面量"一节附近的记录）；decimal 侧
按上一段的结论直接整个不折，不是"改用 `numeric/BigDec` 再折"。

### 反向运算符名用 `__rop_xxx__`，不是 Python 式的 `__op_rxxx__`

Python 的 `__radd__` 能忍，是因为正向名就叫 `__add__`；SL 前面多一段 `__op_`，`r` 就挤进了操作名
内部：`__op_rshift__` 是 `>>` 本身却长得像 "reverse shift"，`<<`/`>>` 的反向会变成
`__op_rlshift__` / `__op_rrshift__`。把 `r` 贴到 `op` 上，规则就是一句话：正向名把 `__op_` 换成
`__rop_`，操作名一个字母不动。

`__rop_*` 的参数顺序与方向统一，不给任何一个开特例：`type(b).__rop_sub__(b, a)` 算的是 `a - b`，
`__rop_cmp__(b, a)` 返回的是 `a` 相对 `b` 的符号。

### `__op_cmp__`：三路比较回退，省掉"每个有序类写 12 个方法"

六个比较运算符在每一侧的自有方法落空后，再试该侧的 `__op_cmp__`/`__rop_cmp__`，然后才换边、才
报错。它**不对应任何运算符**（不设 `<=>` 语法），返回 int（负/0/正）；`NotImplemented` 是弃权、
继续下一步——这条豁免必须有，否则 cmp 没法对不认识的类型弃权，回退链就断了；其他非 int 抛
`TypeError`，且这条只约束解释器的这次调用，手写 `obj.__op_cmp__(other)` 返回什么都行。

**连带改了 `object.__op_eq__`**：它原本按身份比较，于是 `==` 在 MRO 上永远命中它，`__op_cmp__`
这一步对 `==` 永远到不了——只写 `__op_cmp__` 的类会得到"`a < b` 假、`a > b` 假、`a == b` 也假"。
改成"是同一对象返回 `True`，否则返回 `NotImplemented`"，身份比较挪成 `==`/`!=` 整条链落空后的最终
兜底（`<`/`<=`/`>`/`>=` 落空仍抛 `TypeError`）。

**`!=` 多一条"`__op_eq__` 取反"**：最常见的类是只写 `__op_eq__` + `__hash__`、根本没有序的那种，
不加这条它们会静默失去 `!=`。互推只发生在 `==` 与 `!=` 之间——这两个是定义上的补；`<` 与 `>=` 只在
全序下才互补，偏序里 `not (a >= b)` 不等于 `a < b`，所以 **`<` 绝不退化成"不 `>=`"**。

### 不搬 C++ `<compare>` 那套

**`<=>` 运算符不要**：它在 C++ 里的价值是让编译器自动生成六个运算符，而这个价值 SL 用
`__op_cmp__` 回退已经兑现了；再加运算符只多买到"在源码里直接拿到符号"，却要占一个优先级档、起
名字、还要回答"`a <=> b <=> c` 算什么"（链式比较规则里它是异类）。真需要就加内置函数 `cmp(a, b)`，
不占语法位。

**三种序类别（strong/weak/partial）不要**：strong 与 weak 的区别在 C++ 里有消费者（模板、算法
契约），SL 里没有任何东西会读它——而 SL 遍地是 weak 的情形（`1 == 1.0`、`1.50 == 1.5`），纯文档、
零机制。

`partial` 的 `unordered` 倒能补上"`__op_cmp__` 只能表达全序"这个缺口，现在也不加：偏序类型少，
还得连带定义"不可比时 `<` 返回 `False` 还是报错"（decimal 的 NaN 选了报错，浮点传统选 `False`）。
**这道门是开着的**：现在 `__op_cmp__` 返回 `None` 落在"非 int → `TypeError`"里，以后拿 `None` 表示
不可比是纯放宽，不会让今天合法的程序改变行为。

### `raw_int` / `raw_float`：下个版本才加，设计已经定了

**定位**：逃生舱，只为速度和与 C/文件格式互通存在。行为几乎全部委托 C++——该 NaN 就 NaN、该回绕
就回绕、不主动报错。

**档位判据是"C++ 原生就有 + 宽度确定"**：`raw_int` 八档 `i8`/`i16`/`i32`/`i64`/`u8`/`u16`/`u32`/
`u64`（`<cstdint>` 定宽类型），`raw_float` 两档 `f32`/`f64`（IEEE binary32/binary64）。
`raw_int`、`raw_float` 本身是抽象基类，供 `isinstance` 用。

**不要 128 位、不要 `long double`**：`__int128`/`__float128` 是 GCC/Clang 扩展，MSVC 没有，而项目
要支持纯 `cl.exe`；自己软件模拟就不再是"委托 C++"，而且模拟出来的东西比现成的高精度 `int` 又慢又
不精确，需求接近零。`long double` 更直接——MSVC 上 64 位、GCC x86 上 80 位，宽度取决于平台，跟
raw 要的"行为确定"正好相反。哪天 128 位进了标准、或者项目不再管 MSVC，照这条判据再加不迟。

**字面量后缀 = 类名**：`1i32` 与 `i32(1)` 是同一件事，不用记两套。否决了 Windows 的
`y`/`w`/`d`/`q`（byte/word/dword/qword）+ `f`/`lf`：

- **决定性理由是十六进制冲突**：`d` 是十六进制数字，`0x1d` 究竟是 29 还是"十六进制的 1，dword"
  无解——两种解读都是整数后缀，没有类型能区分；而这套助记法必须用 `d`，换掉 `d` 助记就散了。
  `i`/`u` 都在 `a-f` 之外，天然没这个问题；`f` 虽是十六进制数字，但浮点后缀只用于浮点字面量、
  进制前缀只给整数，两者永不相遇。
- 其余理由：`u64` 自描述、不用查表；能扩展（真加 128 位时 `i128` 直接就有，`y/w/d/q` 得再发明
  字母）；那套助记法在浮点那半用不下去、只能改借 printf 的 `f`/`lf`，一套后缀混两种助记传统。
- 后缀前允许 `_`（`0xFF_u8`、`1_000_000_i64`），反正 `_` 分隔本来就在计划里。

**提升**：`raw_int → int`、`raw_float → decimal`，再照 int/decimal 已有的规则走；raw 之间则按 C++
的类型转换规则（有符号转无符号，`1ull < -1ll` 为真）。界线是"raw 之间用 C 的规则，那正是你要 raw
的原因；一掺 int/decimal 就升到精确类型用数学规则"。

**算术和比较必须同时提升**：只提升算术的话，`a - b > 0` 和 `a > b` 会给出不同答案——同一个问题
两种问法两个结果，是最难查的一类 bug。所以这里没有选择余地。

连带后果，别漏：

- `x + 1`（`x` 是 `u8`）结果是 **int** 不是 `u8`：普通字面量会把你踢出 raw 域，raw 代码里得写
  `x + 1u8`。已评估并接受——满屏魔数本来就不是好代码，raw 本来也不常用。
- 提升让 `1u8 == 1` 为真，于是 **`hash(1u8)` 必须等于 `hash(1)`**（`0.5f64` 与对应 decimal 同理），
  否则 `dict` 直接坏掉。
- 它们**进** `numbers` 塔（继承 `numbers.Real`）。早先倾向"raw 不进塔、不参与隐式提升"，被"算术和
  比较都提升"推翻了：一个能正确加减、能正确比较的数值类型，`isinstance(x, numbers.Real)` 返回假
  是错的答案。
- `0.1f64 == 0.1` 为 `False`，而且这是对的：double 的 0.1 精确转成 decimal 是
  `0.1000000000000000055511…`，跟十进制的 `0.1` 本来就不是一个数（Python 3 同）。转换必须精确、
  比较不舍入，所以这个结论是稳的。
- 跨族比较里的 NaN 跟着目标类型走：`nan_f64 < 1.0f64` 按 C 规则静默为 `False`，而
  `nan_f64 < decimal(1)` 提升成 decimal 的 NaN 后抛 `InvalidOperation`——"提升"的含义就是改用
  那个类型的语义。

**"稳定回绕、不 UB"是实现约束，不是白来的**。以下在 C++ 里是 UB 或平台相关，实现时必须显式处理，
不能真的一路 `a + b` 委托下去：

- 有符号溢出：转成对应的 unsigned 算完再转回来（C++20 起有符号整数保证补码，unsigned → signed
  的转换按模 2^N 良定义）；
- `INT_MIN / -1`、`INT_MIN % -1`：C++ 是溢出 UB，我们定为回绕（结果就是 `INT_MIN`）；
- raw_int 除以 0：没有"回绕"的答案可选，抛 `MathError`；raw_float 除以 0 则照 IEEE 出 inf/NaN、
  不报错——这正是"该 NaN 就 NaN"的意思，两者不对称是有意的；
- 移位量：**`x << n` 定义为等价于把 `x` 左移 1 位这个动作做 n 次**（右移同理）。这条定义一次性
  消掉两个 C++ UB——移位量 ≥ 位宽（于是左移和无符号右移得 0、有符号右移得全符号位，是**推出来
  的**而不是另外规定的，也就不会被 x86"按位宽取模"那个硬件行为带跑），以及有符号左移溢出（每一
  步各自回绕）。注意这是**规范**不是实现处方，实现照常直接短路，别真写成循环 n 次。
- 移位量为负：**已拍板，抛 `ValueError`，不做"反向移位"**。理由：上面那条定义支持不了它
  （"移 -1 次"没有意义，负数得另立一条规则，一条自洽的定义变成两条）；"反向"看着优雅是因为直觉上
  `<<` 与 `>>` 互逆，可它们本来就不互逆（右移丢低位，`(x << -1) << 1 != x`，对 `int` 也一样），
  心智负担并没省下、只是换了个地方付；而真实代码里负的移位量几乎总是算错了（下标算负、
  off-by-one），静默反向等于把 bug 变成看起来合理的错答案。收益面只有定点数换算
  `x << (a - b)` 那一类，而写定点数的人本来就该显式分支。用 `ValueError` 而不是 `MathError`：
  `x << -1` 数学上有意义（就是 `x / 2`），我们只是不接受这个实参，属于"值不合法"；`MathError`
  那批（除零、负数开偶次方根）是数学上无定义或非实数。已写进 SL.md 3.8「`x << y`, `x >> y`」。

## 架构决策（不进 SL.md，但影响深远）

### 编译期 C++ 异常 vs SL 运行时异常对象：两层模型

`cpp_exceptions/SyntaxError.h` 的 `SyntaxError`（纯 C++ 异常）和 SL.md 文档化的、暴露给 SL
用户代码的异常类只是碰巧重名，不是同一个东西——这不是需要二选一的问题，是本来就该分层，类比
CPython `PyErr_SyntaxError` 这层 C API 跟 Python 层 `SyntaxError` 类。`SyntaxError` 编译期抛出，
其余异常运行时抛出；该编译期可能包含运行时（`eval`/`eval_isolated` 动态编译）。

必须打通两层的地方是 `eval(code)` 和 `eval_isolated(code)`：现场编译产生的语法错误必须变成能被 SL
`except (SyntaxError)` 捕获的运行时异常对象，内部 catch 住 C++ 异常、构造真正的 SL 异常对象再走
正常 `raise` 传播路径——不能让裸 C++ 异常类型泄漏到 `except` 类型匹配逻辑。以后 `EncodingError`/
`FileNotFoundError` 也要走这个"两栖"模式。

`InternalError`（AST 结构违反 Parser 自己的保证）能不能被 SL `except` 捕获，由"SL 层给不给它注册
对应的 SL 类"这一层决定，不由它继承哪个 C++ 基类决定——所以跟其他异常一样继承 `SLException`，复用
同一套构造/格式化逻辑。

### 对象模型骨架落在 `runtime/`，不是扩 `executor/`

第 1 步动手前欠着的那个选择。定成新开 `runtime/`，理由是链接方向而不是口味：codegen 要直接造真 SL
对象塞进常量表，所以「codegen → 对象模型」；而虚拟机主循环因为 `eval` 要现场编译，所以
「executor → compiler」。对象模型如果放进 `executor/`，就成了 `executor ← compiler ← executor`
的环，CMake 层面直接过不去。这一条同时保证了以后拆 `sl_codegen` 时依赖方向不用回头改。

### 对象模型骨架里几个想清楚了才落的取舍

- **侵入式 `Ref<T>` 而不是 `std::shared_ptr`**：需要 GC 能读写引用计数、需要枚举整个堆，
  `shared_ptr` 的控制块两样都不给；顺带省掉每个句柄 16 字节和一次额外分配。计数是普通整数不是
  atomic——SL 没有线程。
- **构造恒 +1、析构恒 -1，不给 adopt/borrow 两套入口**：侵入式引用计数最经典的错法就是这两套入口
  混用。代价是"裸 `new` 出来不包 `Ref` 就必漏"，用 `make_ref` 兜住。
- **`trace()` 现在就定成纯虚，GC 自己的记账字段（全体对象链表、标记位）留到第 2 步**：判据是
  "跨类型的接口现在定，只动一个文件的内部字段以后加"。`trace()` 每加一个对象类型都要写一遍，
  留到第 2 步就是回头挨个补、还补不出编译错误；链表字段和标记位只动 `Object` 一个文件，一次加完
  即可，提前加反而是几个月没人用的死字段。
- **`Type::mro_` 存裸指针**：`mro_[0] == this`，用 `Ref` 会让每个类都自成一个环、引用计数永远
  归不了零。安全性由 `bases_` 兜着。
- **类型对象是普通堆对象，不是静态分配**：CPython 用静态 `PyTypeObject` + `PyType_Ready` 是因为
  它要在 C 层用聚合初始化写死一大堆槽位；这里没有那个需求，"建立时元类先留空、建完立刻回填"两行
  就把 object/type 互为对方类型的结解开了，还避开了静态初始化顺序问题。
- **`Runtime` 是进程级全局单例**：SL 没有"多解释器"，`import`/`eval_isolated` 建的是新的**全局
  作用域**而不是新运行时。把一个 `Runtime&` 穿过每个对象构造函数和每条指令，是在为一个 SL 根本不
  提供的能力付管道费。
- **`Runtime::shutdown()` 手工拆掉唯一的引用环**（每个类型强引用元类 `type`、而 `type` 的元类是
  自己），于是测试可以断言 `Object::live_count() == 0`。这不是洁癖：引用计数漏加漏减是静默的，
  这句断言是现阶段唯一能自动抓住它的东西。CPython 在这里选择直接不释放内置类型，代价是泄漏检查
  永远有底噪。

### 异常对象只存 `.args`，不额外造字段；跟 CPython 的选择一致，不是省事

`Exception`（`runtime/objects/Exception.h`）只有一个字段 `args_`，`BaseException` 全部子类共用
同一个 C++ 类。设计参照的是 CPython 的实际实现，不是简化版：CPython 的 `BaseException.args` 也是
C 结构体里的槽位，不走实例 `__dict__`；这里因为通用属性表机制还没落地，`.args` 现在只能从 C++
直接取（`Exception::args()`），等属性协议接上后再挂 `getattr(exc, 'args')` 这条路——不是临时糊弄，
是提前对齐了 CPython 本来就这么做的理由。

**没有 `__cause__`/`__context__`**：`raise` 的语法只有 `raise expr`，没有 `from` 子句，也不打算做
隐式的异常链记录（Python 那套是"处理一个异常期间又抛出新异常，自动记 `__context__`"）。这条写进了
`SL.md` 4.2.26，不是漏掉——加隐式链需要主循环知道"当前正在处理哪个异常"，那是执行期状态，现在还没有
执行期。

### `RaisedException` 信封：只在有界的、不回调 SL 的 C++ 代码里 throw/catch

不是 SL 异常跨帧传播的机制——那条路 `bytecode.md` 早就定死是主循环手写驱动的显式算法，C++ 原生异常
展开够不到别的 SL 帧（SL 帧是堆对象）。`RaisedException` 的用途窄得多：某个内置操作的 C++ 实现
（不回调 SL 的那种，比如 `int('abc')` 这类会失败的原生转换）决定"这一步该产生的结果是一个异常"，
throw 这个信封，由**紧邻它、不跨 SL 帧的调用方**立刻接住，翻译成 `Frame` 接口那句"接收沿栈传播的
异常"，之后就转回显式协议。生命周期严格不出那一段 C++ 调用，继承 `std::exception` 只是为了万一
真的漏接时还能兜底打印，不代表它可以像普通 C++ 异常一样随便展开。

### `HostErrorConversion` 现在没有调用方，仍然值得先写

`eval`、文件加载这些真正会用到它的地方都还没写（分别是第 5/7 步、还没排上号的模块系统）。提前写的
理由跟这几步一贯的做法一致：转换规则（哪个宿主异常对应哪个 SL 类、`.args` 塞什么）是设计决定，不是
实现细节，先钉死能避免以后临时拼凑；而且它足够独立，能在没有调用方的情况下单独验证正确性。
`EncodingError` 转换后落到 `IOError` 而不是它在 SL.md 里真正对应的 `exceptions.EncodingError`
（4.3.3），是因为 `exceptions` 模块还没有落脚处——记在代码注释里，模块建好后改一行就是了，不是被
遗忘的分歧。

### GC：按最大堆大小触发回收（`-Xmx` 语义），设计已定、实现推迟到主循环

用户提的方案：启动时给一个最大堆字节数（类似 Java `-Xmx`，有默认值，不设最小值——没有对象池，
用不上）；引用计数照常工作，一旦堆的总字节数超过上限就触发一次 STW 标记清扫（也可手动触发）；
回收完还是超，抛 `MemoryError`。**评估结论：思路可行，采纳，但落地时有三处必须跟已有设计对齐，
不能照字面直接实现**：

1. **必须按字节数，而且必须是"自报字节数"，不能是 `sizeof(T)`**。SL 的招牌是任意精度 `int`/
   `decimal`，它们的真实负载在 `BigInt`/`BigDec` 内部另一次堆分配里（limbs/系数），`Str` 的
   `u32string`、`Tuple` 的 `vector` 同理。只用 `sizeof(T)` 算的话，`2 ** 100000` 在账本上跟
   `2` 一样大，`-Xmx` 直接名存实亡。所以需要给 `Object` 加一个类似 `visit_own_refs()` 的钩子
   （比如 `size_bytes()`），默认 `sizeof(*this)`，`Int`/`Decimal`/`Str`/`Tuple`（以后还有
   `List`/`Dict`）覆写、把自己拥有的缓冲区大小加进去。这不是"以后再精确"的近似，是从设计上
   就该做对的地方。
2. **触发时机不能是"分配的那一刻"，必须推迟到安全点**。`Heap::collect()` 已经定死的前提是
   "C++ 调用栈上不能有任何存活的 `Ref`"，而分配（`make_ref`）经常发生在栈上还攥着别的 `Ref`
   的时候（比如拼一个 `Tuple` 的过程中）。所以分配时只能更新字节计数、标一个"超预算"的标志，
   真正的 `collect()` 调用推迟到虚拟机主循环的安全点——跟现有 `Heap::should_collect()`
   （按分配对象数算）是同一个模式，只是判断依据换成字节数。这意味着**这个功能的"触发"部分要等
   第 6 步（主循环）才能真正实现**，现在只能先把字节账本这半做好。
3. **"手动 STW"已经天然满足**：`Heap::collect()` 本来就是 public 的静态方法，随时能调，
   以后包成一个内置函数暴露给 SL 层（类似 Python 的 `gc.collect()`）就行，不需要额外设计。

`MemoryError` 已经加进 `SL.md` 4.2.26/4.4 的异常树（`Exception` 的子类，紧跟 `RecursionError`，
两者都是"解释器资源耗尽"类；没有放在 `SystemExit`/`KeyboardInterrupt` 那种直接挂 `BaseException`
下的致命错误里，因为应该允许 SL 代码 `except (MemoryError)` 自己兜底），`Type` 对象也已经建了
（`runtime/x_builtin_types.inc` 里的 `MemoryError`）——这两步现在做代价很低、跟其它异常类型的
处境一样（`RecursionError`/`DispatchError` 现在也都是"类存在、触发机制还没写"）。**没做的**：
`Object` 的字节计数钩子、`Heap` 里的总字节数账本、`Runtime::init()` 接受 `-Xmx` 参数、真正的
"超预算 → 安全点回收 → 仍超则抛 `MemoryError`" 这条流程，全部推迟到主循环落地（第 6 步）再回来做。

### `runtime/` 的类型名保持全局短名，不加 `Sl` 前缀、不开命名空间

审过一遍拍的板，别再来一遍。`runtime/` 往全局塞了 `Object`/`Type`/`Ref`/`Int`/`Str`/`Bool`/`Tuple`/
`Heap`，以后还会进 `Code`/`Frame`/`Function`/`Module`/`List`/`Dict`——确实是全项目第一批真会撞的通用名
（前面几层的 `Lexer`/`AstNodeFunc`/`BigInt`/`SemanticChecker` 本来就不会撞）。三个选项都掂量过：

- **不加 `Sl` 前缀**：`SL` 就是这个仓库的全部，前缀零信息量（同理 `BigInt` 也没叫 `SlBigInt`）；
  而且 C++ 类名与 SL 类名一一对应（`Object`↔`object`、`Int`↔`int`）本身有价值，加前缀会毁掉它。
- **不开 `namespace sl`**：项目零命名空间是既有风格，只给 `runtime/` 开会造成半个项目有半个没有的
  割裂，而 `compiler/codegen` 和 `executor` 恰恰会大量引用这些类型。
- 代价认了：读 codegen/executor 时 `Type *`、`Code *` 这类要靠上下文认。

顺带定死的两条命名：`Ref<T>` 是模板、`ObjectRef` 是 `Ref<Object>` 的别名，不是二选一（`Ref<T>` 作为
侵入式引用计数句柄的名字有 WebKit 的先例）；无负载单例那个 C++ 类叫 `NamedSingleton` 而不是
`Singleton`，是**故意跟 SL 的 `SingletonType` 岔开名字**：它覆盖 `None`（类型 `NoneType`）和三个
`SingletonType` 实例，比 SL 的 `SingletonType` 宽。类名说的是存储形状（零负载 + 一个显示名），叫
`Singleton` 会暗示一个并不成立的 1:1 关系，实际引起过误会。

**术语纪律**：SL 没有 `repr` 概念（只有 `str(x)`），别把 Python 的词带进来——`NamedSingleton` 上那个
字段叫 `name_`。

### GC 用"从根标记清扫"，不用 CPython 的 trial deletion

两条路都能处理环，选前者：

- **CPython 之所以必须用 trial deletion（对每个被跟踪对象减去内部引用数、剩余计数 > 0 的就是外部
  可达），是因为它的根集合根本枚举不出来**——C 栈上到处是借用引用，没有影子栈也没有 handle scope。
  这不是它觉得那个算法更好。
- **SL 这边根集合是可枚举的**：`bytecode.md` 那条"C++ 调用栈深度不得随 SL 帧栈深度增长、主循环不
  递归"的硬约束，意味着执行状态全在堆上的帧对象里；在主循环两条指令之间的安全点上，C++ 栈本来就是
  空的，根只有帧栈 / 模块表 / 各 `Code` 的常量表 / `Runtime` 持有的内置类型与单例。
- 既然根能枚举，标记清扫在正确性上好推理得多——trial deletion 那套"减内部计数、找残留、再把可达性
  传播回去"的中间状态很难在脑子里跑通，也很难测。

**代价是多了一条硬前提**："`collect()` 只能在安全点调用，C++ 栈上不能有活的 `Ref`"。所以分配动作
不许顺手触发回收（`make_ref` 里没有这种钩子），codegen 和内置函数实现的半途也不许调。这条前提直接
挂在那条主循环约束上——哪天想放松"主循环不递归"，先想清楚 GC 怎么办。

### 标记和清理共用一个 `visit_own_refs`，不拆成 trace + clear

CPython 是 `tp_traverse` + `tp_clear` 两个函数，每个类型各写一遍同样的字段清单。这里合成一个
`visit_own_refs(RefVisitor &)`：访问者拿到的是槽位的**引用**，标记阶段只读、清理阶段顺带置空。

理由是这两份清单一旦不一致，后果分别是提前回收（标记漏了字段）和永久泄漏（清理漏了字段），都极难
查；合成一个之后这种不一致在结构上就不可表达。顺带把每加一个字段要改的地方从两处降到一处。

`Object::type_` 这条边由基类的 `visit_all_refs` 统一报告/清理，不让每个子类重复写。

### 回收的五步流程里，第 3 步的"整批 +1"不是保险起见

`collect()` 是：标记 → 分离出未标记的垃圾 → **整批 incref** → 逐个放掉出边 → 整批 decref。

中间那次 incref 是必需的，不是防御性代码：垃圾之间互相持有引用，放边时谁的计数先归零谁就地析构，
而它的析构又要 decref 别的垃圾——那些可能已经删过了，就是 use-after-free。整批 +1 把生死统一推迟到
最后一步，析构顺序就不再是个问题。第五步里那句 `assert(refcount() == 1)` 守的正是这个不变量：
指向垃圾的引用要么来自垃圾（第 4 步放掉了），要么来自存活对象——而后者意味着它根可达、根本不该在
这批里。

### 全堆都进链表，不做"只跟踪可能成环的对象"

CPython 只把容器类对象挂进 GC 链表，`int`/`str` 这类叶子不跟踪，省下每对象两个指针和每轮扫描的
遍历。这里暂时全挂——叶子类型的 `visit_own_refs` 本来就是空的，正确性不受影响，而少一个"这个类型
到底算不算叶子"的判断就少一处能写错的地方（写错的后果是环永远漏掉）。

要加的时候加法是确定的：`Object` 的构造函数多收一个"要不要跟踪"的参数（不能做成虚函数——基类构造
期间虚分派不生效），叶子类型传 false。等主循环跑起来、能量出实际分配构成了再说。

### 撤销：`BootPhase` 有序相位被砍掉，`Runtime::instance()` 只剩一个空指针检查

第 3 步（bootstrap）刚做完时给 `Runtime` 配了个有序枚举 `BootPhase`
（`Uninitialized`→`Types`→`Values`→`Ready`），每个访问器声明自己要求的最低相位，`instance(required)`
统一拦截，理由当时写的是"防提前访问了还没建好的东西"。用户审这块代码时直接问：**这条防线拦的到底
是谁？** 逐个查了一遍所有 `instance(BootPhase::X)` 的调用点，发现**全部**来自 `Runtime` 自己生成的
公开访问器，没有任何一条来自真正意义上的"外部代码提前访问"。

深挖下去，"需要"区分 `Types`/`Values` 这两个状态的根源是自己造出来的：`build_singletons()` 当时
调用 `none_type()`、`Bool` 的构造函数当时硬编码调用 `Runtime::bool_type()`——都是**绕道公开的、
带相位检查的静态访问器**去拿自己所在阶段就该有的类型，而不是直接读 `Runtime` 自己的私有字段
`types_`，或者由调用方直接把 `Type*` 传进去。C++ 单线程同步执行，`Runtime::init()` 跑到一半时
根本不存在任何别的代码能观察到"类型建好了、单例还没建好"这个中间状态——这个状态只在 `init()` 那次
函数调用内部瞬间存在，出了这次调用要么是"完全没建"（`init()` 还没被调）要么是"完全建好"
（`init()` 正常返回）。**区分它俩的检查纯粹是自己在跟自己的实现细节较劲，不是真实存在的外部
需求**，是一个自我循环论证：检查存在的唯一理由是"有代码会被这个检查拦下"，而那些代码正是绕出去
又绕回来的自己。

修法：`build_singletons()` 直接读 `types_[index_of(BuiltinType::NoneType)].get()` 这类私有字段；
`Bool` 的构造函数改成跟 `NamedSingleton`/`Exception` 一样，接收调用方传来的 `Type*` 而不是自己反查。
改完之后 `Types`/`Values` 这两档在任何地方都不再被区分，`BootPhase` 整个枚举、`instance(required)`
那份带相位名的报错都删掉了，`Runtime::instance()` 现在只剩最初就该有的那一条：`g_runtime` 是否
为空。`ready()` 从 `phase() == BootPhase::Ready` 变成 `g_runtime != nullptr`——反正 `Ready` 那一档
从建出来那天起就没有任何代码要求过它，是提前为还没写的"内置函数表/模块表"占位，属于给假设中的
未来需求设计。

**教训**：加一层状态检查之前，先问"这个状态谁在外部会真的观察到、谁会真的需要区分"，而不是"这个
状态在概念上是不是存在"——`Types`/`Values` 在概念上确实是两个不同的完成度，但概念上存在不代表
有任何代码合法地依赖这个区分；真正的检查点只有"`init()` 有没有跑完"这一个二元状态。以后再遇到
"要不要拆更细的状态"这类设计冲动，先枚举一遍所有会读这个状态的调用点，看看它们是不是都是自己
写的、还绕得回去的内部实现。

### 字面量折叠用独立的、跟真正 VM 无关的静态求值器

不是偷懒抄近路，是 SL.md 本身"折叠不做常量传播，一掺变量就不折"这条约束逼出来的：定义域天生排除
名字查找/函数调用/副作用，`StaticEvaler` 完全不需要对象模型/方法分派/继承查找，可以先立好骨架不用
等 VM 写完。VM 具体走"编译到字节码"还是"直接树遍历执行"仍未决定，两种路线都跟这个结论不冲突。

### `numeric/BigInt`：手写、双路径，测试靠代数恒等式

**手写而非引库**（Boost.Multiprecision/GMP）：GMP 需要独立构建链接，Windows 下历来不省心；
Boost 头文件在严格编译选项下容易冒警告；`int` 四则运算是语言核心语义本身，值得完全自己掌握，不像
`nlohmann_json`/`doctest` 只服务测试。评估过的现成单头文件库（如 `faheel/BigInt`）不支持位运算、
除法/取模的符号语义没有文档——正是我们已经踩过坑的地方，换一个连这个都没说清楚的库等于把已知坑
换成未知坑。

内部表示是"小路径 `int64_t` / 大路径 limbs"二选一，不变量是"只要数值能装进 int64_t 就必然走小
路径"。每个操作套一层"先试原生运算 + 溢出检测，溢出或本来就有一方是大路径才提升成大路径走原算法"。

**测试方法论**：不手挑具体数字当预期值，改用一批边界值（0/±1、`int64_t` 边界内外、`2^63` 附近、
全 1 比特的 limb）两两/三三组合，批量验证数学上必然成立的恒等式（加法交换律/结合律、
`a == (a//b)*b + a%b`、位运算的补码恒等式、`pow` 的指数加法律）外加"规范化不变量"套件（同一个值走
不同运算路径算出来必须能用 `==` 判定相等）。**理由**：历史上的真实 bug 都是"某个函数假设输入已经
是规范形式，但被套了一层调用后规范形式被破坏"这一类模式（比如取负之后没有重新收缩到小路径）——这
类 bug 靠恒等式互相校验测得出来，靠盯着代码看或者手算几个常量测不出来。以后再碰这块代码，延续这个
测试策略。

`pow`/`operator<<` **没有结果规模上限**——`2 ** 10**9` 会真的去算一个十亿位的数，是明确决定不管
（"炸就炸呗，本来就是这么用的"），不是遗漏；真要限制留给以后接上 VM 时再谈。

溢出检测用 C++26 `<stdckdint.h>`（`ckd_add`/`ckd_sub`/`ckd_mul`）而不是 `__builtin_*_overflow`
或 SafeInt：后者是编译器专有名字，项目要支持的纯 `cl.exe` 前端不认；SafeInt 是抛异常的接口，跟
这个类"折不动一律返回信号、从不抛异常"的风格不合。

### `numeric/BigDec`：复用 BigInt，但"规范形式"跟 BigInt 不是一回事

`decimal` 的运行时表示是 `BigInt 系数（恒非负）+ int64_t 指数 + 独立的符号位 + 特殊值 tag`。
BigInt 已有的 `from_decimal_string`/`to_decimal_string`/`floor_div`/`mod`/`pow` 直接复用。

**符号为什么单独存**：`coeff_` 用 BigInt 自己的符号位就表示不出负零，而负零是要区分的（`-0` 与 `0`
数值相等但 `str` 不同，还决定后续运算结果的符号）。

**指数为什么是 int64_t 而不是 int32_t**：运算的中间结果（比如乘法的 `exp1 + exp2`）可以暂时越出
"构造得出来的范围"，`fix` 之后才必然落回 `[Etiny, Emax]`。于是约定：构造入口（`try_from_string`/
`from_parts`）把指数卡在 `±kMaxExponent`，中间结果不设限、但保证怎么算都溢不出 int64_t。
这样"指数越界"只在一处判，不用在每个算术步骤里操心。

**`kMaxExponent` 必须比 `Emax` 的上限宽一整个 `prec`**（现在取的是 `kMaxExp + kMaxPrec`）。次正规结果
的指数会被 `fix` 压到 `Etiny = Emin - prec + 1`，它比 `Emin` 自己的下界还低一个 `prec`；照着 `Emax`
的量级去卡，`Emin = -999999999` 配任何 `prec >= 2` 就能算出一个 `try_from_string` 读不回来的值，
"`try_from_string(x.to_string())` 恒等于 x" 这条不变量当场破掉。另一条路是在 `set_emin`/`set_prec`
里交叉校验，否决了：那会让"合法的 Emin"取决于当前 prec，两个字段之间凭空多出顺序依赖。

**最容易写错的地方**：BigInt 的不变量是"一个值只有一种表示"，BigDec **没有**这条——标度是值的
一部分，`1.5`（`15×10^-1`）和 `1.50`（`150×10^-2`）是同一个值的两种合法表示。所以 `==` 不能靠
结构相等，必须先对齐指数；哈希也得先归一到同一标度再算，否则相等的值哈希不同，`dict` 直接坏掉。
代码里"表示相等"和"数值相等"是两个不同的方法（`identical` vs `equals`），别混用。

### BigDec 的信号机制：条件 12 个、信号 8 个，抛的是 C++ 异常

SL.md 的异常树里 decimal 有 12 个异常类，但 `traps`/`flags` 只认 8 个——`ConversionSyntax`、
`DivisionImpossible`、`DivisionUndefined`、`InvalidContext` 都是 `InvalidOperation` 的细分，查陷阱、
记标志位时一律先折算成 `InvalidOperation`（`signal_of`）。折算这一步是照抄 Python 的 `_condition_map`；
但"抛出来的 DecTrapped 带细分条件"这层跟 CPython 的实际行为**不一致**——Python 抛的是折算后的基类
（`0/0` 抛 `decimal.InvalidOperation`，不是 `decimal.DivisionUndefined`）。带细分条件是刻意选的
"信息更多"版本：SL.md 自己把细分异常列成了类，executor 按 `condition()` 映射时让用户能按细分
异常去 catch，比 Python 的基类更有用。别把"抛细分条件"再当成"照抄 Python"。

陷阱触发时抛的是 `DecTrapped`（`numeric/` 自己的 C++ 异常），不是 SL 的 `decimal.XXX`——同 BigInt 抛
`std::domain_error` 的理由：`numeric/` 不认识、也不该认识 SL 的异常类体系，由调用方按 `condition()`
映射。上下文字段本身不合法（`prec = 0` 之类）走 `std::invalid_argument`，因为那是调用方的编程错误、
不是算术过程中的信号，跟 traps/flags 那套无关。

### `//` / `%` 的向负无穷取整：在截断结果上修正，且修正那一步必须走带上下文的加法

IBM 规范给的是向零截断的 `divide-integer`/`remainder`，SL 要的是向负无穷。实现是先照规范算出截断的
商和余数，再统一修正一次（余数非零且两操作数异号时，商减 1、余数加上除数）。三处坑：

1. **修正那一步不能"先精确相加再舍入"**：`1E-999999 % -1E+999999` 的精确余数有两百万位，真去构造
   会直接卡死。改成调带上下文的 `add`——它对齐操作数时用的粘滞位（把小到影响不了舍入的一方换成
   `1×10^exp`）本来就是为了保证"结果等于精确和的正确舍入"，所以值和信号都一样，代价是常数级。
   （这条被测试压着：把粘滞位那段短路掉，测试不是失败而是**挂死**。）
2. **`DivisionImpossible` 要按修正之后的商判位数**：截断商恰好 `prec` 位时，减 1 可能多出一位
   （`-99999.5 // 1` 在 prec 5 下就是），按截断商判会漏掉。
3. **`//` 单独用时不能顺手 `fix` 余数**：那会报出 `Inexact`/`Rounded`——那是余数被舍入才该有的
   信号，跟 `//` 的结果无关。所以公共部分只算到"截断商 + 截断余数 + 要不要修正"，加不加除数、
   舍不舍入由三个入口各自决定。
4. **商本身却必须过 `fix`**。一度以为"商是整数、位数又不超过 `prec`，fix 只会白报 Inexact/Rounded"
   就跳过了——前半句对（进不了舍入分支），后半句错：`fix` 还管指数域。`Emax` 小于 `prec - 1` 的上下文
   （合法，设得出来）下 `100000 // 1` 的商调整后指数是 5，超过 `Emax = 3`，该报 `Overflow`。
   `_pydecimal` 这里也不 fix，libmpdec 会——过 IBM 测试集的是后者。**位数够不代表指数域够，这是两条
   独立的检查**。

**两处零的符号**：`//` 的商为零时按两个操作数的符号异或（`0 // -3` 是 `-0`），跟 `*`、`/` 一致，
不让 `//` 成为唯一丢掉零符号的运算；`%` 的余数恰好为零时符号跟被除数走（`-6 % 3` 是 `-0`），这处
照抄规范——SL.md 写的恒等式 `x % y == x - (x // y) * y` 自己在零上也定不出符号（IBM 的加法规定
`a - a` 得 `+0`），换成"跟除数走"并不更有理有据，那就少一处偏离。

### BigDec 的测试：期望值来自 CPython 的 decimal，不手挑

`test/numeric/big_dec_cases.inc` 由 `gen_big_dec_cases.py` 生成，期望值（结果 + 触发了哪些信号）
全部来自 CPython 自带的 decimal——那是 C 写的 libmpdec，跟 BigDec 是两套独立实现，比手挑期望值强
得多。脚本带倍数参数，临时跑几十倍规模的差分测试很方便（做到 25 倍、约 47 万个断言全过）。

`//`/`%` 是我们偏离规范的地方，Python 的答案不能直接用。生成器的做法是**换一条推导路径**：先在超高
精度下拿到精确的截断商/余数，再整体修正，凡是超高精度下仍不精确的组合直接跳过不出题。两边只在数学
定义上一致，不共用代码路径——如果照着 C++ 的算法再写一遍 Python，测的就只是"我抄得一不一致"。

表里除陷阱全关的路径外，还有**陷阱开启的路径**（`kTrapped*` 四张表）：抛不抛、抛哪个条件、抛出时
flags 走到哪一步都是规范的一部分。陷阱表只要求两套 CPython 实现"抛出的条件名"一致——它们在抛出前
记 flags 的顺序不一致（1/3 在 Inexact 陷阱下，libmpdec 先记 Rounded、_pydecimal 先抛 Inexact），
抛出时的 flags 以 _pydecimal 为准（BigDec 是照它移植的）。值池里还刻意塞了带非零指数的零
（`0E+999999` 这类），专门压 fix 的零夹取、add 的零操作数、trunc_divmod 的量级短路这些路径。

**还没实现的**：`hash`（要先归一标度）和 `int(decimal)`（取整方向 SL.md 还没定）。SL.md 里 decimal
参与的运算符本身已经全了。

### 超越函数（`ln`/`log10`/`exp`/`sqrt`/`**`）：整数定点算法单独一层，"算到能定夺为止"是核心

这几个在任意精度下没法一次算准。做法照抄 Python `_pydecimal`：**先按 prec+3 位算一个近似值，看它
够不够定夺舍入方向，不够就再多算三位**，循环到够为止；判据是"末尾恰好是 5000…0 就说明正卡在两个可
表示值的正中间"（`is_roundable`）。因为已经算到任何舍入方式都给同一答案，最后那步 `fix` 固定用
HalfEven（`**` 除外，它尊重上下文的舍入方式，规范如此），算完靠 RAII 把上下文的 rounding 还回去——
不能写成"算完再赋值回去"，`fix` 会因为陷阱抛出去。

整数层的定点算法放在 `numeric/dec_math.{h,cpp}`：`ilog`/`iexp`/`dlog`/`dlog10`/`dexp`/`dpower`
以及 `div_nearest`/`rshift_nearest`/`sqrt_nearest`/`log10_digits`。这一层只跟 BigInt 打交道，不认识
BigDec、上下文和信号，好单独推敲。**里面那些常数（尤其是泰勒展开前的缩减深度 `kTaylorL`）是有误差
论证撑着的，动一个就会把上层那个循环的前提拆掉**，别随手调。`log10_digits` 带一份越算越长的静态
缓存，因此不是线程安全的。

**别用 `std::thread` 并行跑 `big_dec_test.cpp` 里 `**`/超越函数这两个最耗时的 `TEST_CASE`**：
验证过是反效果——`run_test.py` 固定用 `/MDd` Debug CRT 堆，每次分配都要过全局临界区，
BigInt/BigDec 这种"每步运算都建一堆临时大数"的负载一并发就是锁竞争灾难（2 线程比单线程慢 2.5 倍，
24 线程慢 8 倍多）。换 Release 构建可能是另一回事，但 `run_test.py` 的构建类型是硬编码的
Debug，验证不了。真要重拾这条路，`log10_digits`/`dexp`/`dlog`/`dlog10`/`dpower` 这条链子是唯一
需要加锁的地方——`sqrt`/`power_exact` 精确路径不碰它，天然线程安全。

**`**` 分三条路**：先用 `log10_exp_bound() + adjusted(y)` 粗筛掉必然溢出/下溢的（这一步同时替
`power_exact` 挡住了 `10^ye`、`xc^m` 之类会炸开的输入，别把它挪走）；再试 `power_exact`——把 y 写成
既约分数 m/n，检查 xc 是不是 n 次幂、xe 能不能被 n 整除，y 为负时还要求 xc 是 2 或 5 的幂；都不成
才走 `exp(y*log(x))`。

**指数不是整数而结果又恰好精确时**，规范要求照样报 Inexact（结果落进次正规区还要补 Underflow）。
`fix` 自己不会报，又不能在 `fix` 前后直接补——那会打乱规范规定的信号优先级。做法是先在一个陷阱全关、
标志位清空的上下文副本上 `fix`，再按优先级顺序把信号补报到真上下文上。

### 两处我们跟 libmpdec 不一致，都是故意站 `_pydecimal` 那一边

CPython 自带的两套 decimal 实现（C 的 libmpdec、纯 Python 的 `_pydecimal`）自己就有分歧——官方扩展
测试 `_decimal/tests/deccheck.py` 里的 `SkipHandler` 明写了这是已知情况。目前撞见两处，BigDec 两边
都跟 `_pydecimal`：

1. **非整数指数的 `**`**：规范只要求"按 `exp(y*ln(x))` 算"，**不保证正确舍入**。真值恰好可精确表示
   且用定向舍入时两边差 1 ulp：`9 ** 0.5` 在 ROUND_DOWN 下 libmpdec 给 `2.99`、`_pydecimal` 给
   `3.00`。选后者——真值精确就原样给出，`9 ** 0.5` 得 `2.99` 实在太不像话。
2. **`exp` 在 `Emin == 0` 时**：次正规判定该在舍入前还是舍入后做。`exp` 拿 `0.99…9`（调整后指数 -1）
   当近似值交给 `fix`，判成次正规，舍完却变回 `1.000…`（调整后指数 0，不次正规）。值一样，只差
   `Subnormal`/`Underflow` 两个 flag。规范原文写的是 "before any rounding"，字面上支持 `_pydecimal`。

**生成器因此对每一组用例都拿两套实现各算一遍，不一致就整组跳过**（默认规模下 pow 跳 21 条、超越函数
跳 8 条）。做成全表统一过滤而不是只挡这两处，是因为分歧点随参数漂移——尤其是 `Emin` 和舍入方式——
哪天有人往池子里加一档参数，不该因此得到一张 BigDec 永远过不了的表。我们这一支的行为由手写用例钉住。

### 覆盖率驱动补的窄路径，以及哪些分支是刻意不可达的

拿 clang 的 source-based coverage（`-fprofile-instr-generate -fcoverage-mapping` 单独编一份
`SL_Cpp_Numeric_Tests`，`llvm-cov show -show-branches=count`）量过一次 `numeric/`，据此补齐了几条
生成的用例表撞不到的路径。现在 `BigDec.cpp`/`BigInt.cpp`/`dec_math.cpp` 三个文件**行覆盖都是
100%**，剩下的只有分支级的未覆盖，而且**下面这些是刻意不可达的防御性代码，别再花时间去凑输入**：

- `power_exact` 里三处 `to_int64(...)` 失败的 `return nullopt`：`exp_` 有 `kMaxExponent` 卡着、
  `|y|` 又被外层 `pow()` 的溢出/下溢粗筛卡着，两者之积到不了 2^62。连带 `dec_math::to_int64`
  也就从来不会返回 `nullopt`（它只有这三个调用点会检查返回值，`dexp` 那处是直接 `.value()`）。
- `is_even_integer()` 的 `coeff_.is_zero()`：`pow()` 在更早的地方就把"指数为 0"处理掉了。
- `power_exact` 里 `while (!exponent.is_zero() && ...)` 的 `!exponent.is_zero()`：`xc == 1` 这一支
  要求底数数值不等于 1，于是 `xe != 0`。（Python 原版没这个判断，真喂 0 进去会死循环。）
- `dec_math::dpower` 里 `shift >= 0` 那一支：旁边的 `assert(shift < 0)` 已经写明恒等式，留着只是
  跟 Python 的写法保持一致。`dlog` 里 `p + extra < 0` 同理，从 `ln()`/`log10()` 那边推不出来。
- `BigInt` 里 `add_magnitude`/`mul_magnitude` 结果不会有多余高位 0、`shift_right_magnitude` 收不到
  `bits == 0`、`from_twos_complement` 收不到空 limbs、大路径的 `minus()` 收不到空 limbs——都是
  调用方的不变量保证的。

生成的用例表撞不到、需要手写窄路径覆盖的：`**` 的"不够定夺就多算三位"重试循环；`power_exact` 负
指数分支的三道上限；理想指数补零被 `p - 位数` 夹住那一档；`log10_digits` 缓存扩容的"再多算三位"和
"剥尾零"两条路径。

**`log10_digits` 的缓存是进程级静态、只增不减的**：新增测试要定向命中它的某条扩容路径时，选的 `p`
必须远高于其他用例已经摸到的量级（当前其他用例最高到 125 左右），否则命不命中取决于 doctest 跑
用例的顺序，覆盖会随机漂移。这是全项目唯一一处测试直接调 `dec_math`（不经 `BigDec::log10()`）——
从 `BigDec` 层没法定向命中某个具体的 `p`。

另外，**`**` 的"精确结果 + 非整数指数"补报信号那段跟陷阱的交互，只能靠手写用例**：24 组里有 9 组
libmpdec 跟 `_pydecimal` 不一致（前者把 `fix` 期间的 flags 全带上，后者只带补报到抛出点为止的），
生成器遇到分歧整组跳过，随机撞到也出不了题。跟上一节那两处一样，我们站 `_pydecimal`。

### `BigInt::from_decimal_string`：尾数为 0 时不去算 `10^指数`

`from_decimal_string` 的指数刻意不设上限（见 `BigInt.h`，9999 那条限制归 lexer 管），代价是
`"0e1000000"` 曾经要白算三秒多才返回 `0`，而这一步的代价只跟指数走、是 O(指数²)，再大一档就是
分钟级/爆内存。加了一条 `mantissa.is_zero()` 短路。**不要把它理解成"给指数加了上限"**——尾数非零
时照旧真去算，`2 ** 10**9` 那种"炸就炸呗"的决定没有变。

### `0 ** 0`：int 给 1，decimal 抛 InvalidOperation，两边故意不统一

SL.md 原先没规定，是真实的规范空白，已补进 3.4.2。用户拍板：`BigInt::pow` 保持 `0 ** 0 == 1`
（同大多数语言的整数幂约定，也同 Python 的 `int`），decimal 那边照 IBM 规范触发
`decimal.InvalidOperation`（默认陷阱开着，所以默认设置下是抛异常）。于是 `0 ** 0` 是 `1` 而
`0.0 ** 0` 抛异常——这个不对称是知情选择，不是漏掉：两条路各自跟着自己那套既有规范走，比为了
"看起来一致"去改其中一边更站得住。

同时把 `Context` 数值字段的取值范围写进了 SL.md 4.2.6.1（`prec` 最小 1 最大 999999999、`Emax`
最小 0 最大 999999999、`Emin` 最小 -999999999 最大 0，边界都算合法，越界抛
`decimal.InvalidContext`）。**这段是用文字写的，别改回 `1..999999999` 那种记法**——SL 自己的
`a..b` 左闭右开（同 Python 的 `range`），拿它写闭区间会把上界排除在外，意思正好说反。这个上界就是
`DecContext::kMaxPrec`/`kMaxExp`，取这个量级的理由见 `DecContext.h`——为的是 `etiny()`/`etop()`
以及 `exp ± prec` 这类中间算式在 int64_t 里怎么算都溢不出来。CPython 的 C 实现放到 10^18，我们
没跟：那要么把指数换成更宽的类型，要么在每个算术步骤里操心溢出，两样都不划算。

### 整数/decimal 字面量禁止前导零

SL.md 一直没规定 `007`/`00` 合不合法，是真实的规范空白，已补上：不合法（单独一个 `0` 除外；decimal
整数部分同样受限，小数部分不受限）。理由：一是给以后要加的 `0x`/`0o`/`0b` 前缀预留解释空间——现在
放开，以后加前缀就是破坏性变更；二是避免"`0` 开头被当成八进制"这个 C 系语言的经典坑。

### ~~`in` 升为关键字兼二元运算符，迭代 `for` 改用它，头部改成"数槽"~~（已被 `as` 取代）

**这个方案后来被推翻**：迭代 `for` 的判别依据改成了 `as` 关键字，`in` 退回纯粹的成员测试运算符，
不再兼任何循环职务，理由和定案见下面"`as`：`for` 迭代目标 + `except` 绑定目标"一节。这里保留
下面这段是因为它记录了在 `as` 之前那一版设计（把 `for` 迭代目标做成 `in` 表达式）解决了什么问题、
为什么当时觉得够用——后来发现"`in` 一身两责"（运算符 + 循环判别依据）本身也是个问题，才有了
`as` 那次进一步的推翻，两次决策叠在一起看才是完整的历史。

`for (x : iter)` 的 `:` 是个只在这一个位置出现的分界记号，parser 得先解析第一个槽、再前瞻（跨换行）
找 `:` 才知道是哪种模式，两条路的换行语义还不一样（迭代模式认出来之后整段"降级"成普通括号）。
换成 `in` 之后模式判定退化成两步纯后验的检查：把头部按槽切开，**槽数只能是 3 或 1**；是 1 就要求
那个槽以 `in` 为根，把它的两个孩子取出来当 `target`/`iterable`。前瞻、降级、`:` 分支全部消失。

`in` 本来就是保留字（`RW_IN`），升成关键字不破坏任何现有代码。

**优先级 55**，夹在比较组（60）和 `is`（50）之间。它就是个普通的左结合二元运算符，**不像比较组、
`is` 那样主动支持链式**：`a in b in c` 不报错，也不学 Python 隐式展开成 `and`，就是老老实实的
`(a in b) in c`（结果通常在运行期抛 `TypeError`，那是运行期的事）。选这一档的理由：`in` 结果是
布尔，属于"关系判断"那一片，和比较组、`is` 连成 60/55/50 一段；比 `not`（40）紧保证
`not x in y` 读作 `not (x in y)`；比 `and`（30）紧保证 `x in a and y in b` 不用加括号。

**重载方法叫 `__op_contains__`，定义在右操作数上，没有反向方法、没有回退**。这是全表唯一不走
"左 `__op_xxx__` → 右 `__rop_xxx__`"两步分派的运算符：`a in b` 该由容器 `b` 回答，若挂在左边，
每个类型都得认识所有容器。名字用 `contains` 而不是 `in`，就是为了让"谁实现它"从名字上看得出来——
读作"`b` 含不含 `a`"；叫 `__op_in__` 会跟"`__op_` 是左操作数的方法"这条约定打架。

**一处刻意的行为变化**：`in` 之后可以换行（`in` 已消耗，右操作数会跨行找），**之前不行**
（左边已完整，换行把它切成两槽）。`iterable` 里的换行也照槽的规矩切，不再享受 `:` 时代那种降级。
这跟同样两行写在块里的结果一致，是拿"少一条特例"换"长 iterable 得把运算符留在行尾或自己加括号"。

### 字面量 `raw_` 的形状校验归节点构造函数，且 AST 层面负数是合法字面量

两件事，同一个起因：`SemanticChecker` 原先管着 `AstNodeLiteralInt`/`AstNodeLiteralDecimal` 的
`raw_` 形状（纯数字、前导零、科学计数法后缀），而 `Analyzer` 的顺序是**先 check 后 fold、只 check
这一次**，于是 `StaticEvaler::make_int`/`make_decimal` 折出来的字面量节点从来没有任何人校验过。

**校验挪进构造函数**（`compiler/parser/ast_nodes/details/ast_node_literals.cpp`）。挑中这一处、而不是把
`SemanticChecker` 里那四十来处 `InternalError` 类断言一起搬，是因为它同时占齐三条：只看自己的字段、
构造之后 `raw_` 再也不会被改（`const`，全仓库无一处赋值），以及存在一个 `SemanticChecker` 看不见的
生产者。其余的搬不动：节点成员是 public 的，`ExprFolder` 拿着树里槽位的引用整棵子树往里换，构造
函数拦不住构造之后的赋值，检查最后还得在 `SemanticChecker` 留一份，变成两处都写。

分界线因此定为：**构造函数管"这个节点自己的字段合不合法"、且只有实现出 bug 才会违反的
（`InternalError` 类）；`SemanticChecker` 管"要看上下文"或者"是用户写错了"（`SyntaxError` 类）**。
重名、形参顺序、doc 槽位这几条虽然也是纯自省的，但它们是给用户看的诊断，留在 `SemanticChecker`——
让 AST 承担用户诊断等于把哑数据结构变成半个前端。

`InternalError` 要文件路径而节点只带行列，这里用 `"<file>"` 占位。不是拿不到，是不想让每个节点都
拖一份文件名；这类错误本来就写着"编译器自己有 bug"，行列足够定位。

**`raw_` 允许一个前导负号**。SL.md 说负数不是字面量，那是**文法**层面的话（词法阶段 `-1` 是一元
负号加上 `1`）；折叠之后 `-1` 就是一个 int 字面量节点，两句话不冲突。正号不接受——没有任何生产者
会写出来，收窄没成本。真正的不变量是 **`check(fold(x))` 必须过**：`check` 描述的是"一棵合法 AST
长什么样"，不是"Parser 刚吐出来的树长什么样"。这条不写进 SL.md（SL.md 描述语言，这是实现约定），
测试在 `test/analyzer/recheck_after_fold_test.cpp`。

顺带一提，除了 `SemanticChecker`，其余代码早就是这么认的：`literal_compare_int` 开头就判
`raw_[0] == U'-'`，`string_to_int64` 的注释写着"可以带一个前导 `-`"，折叠测试断言的就是
`int_lit("-1")`。

### 字节码 / `Code` 对象设计

VM 走"编译到字节码"这条路线，指令集/帧/`Code` 的完整设计在
[../compiler/codegen/bytecode.md](../compiler/codegen/bytecode.md)，不在这里重复。这套设计通过了"是否有可观察语言行为
差异"的检验——换一套指令集不改变任何 SL 程序的可观察行为，所以它属于实现契约、不进 SL.md。

这里只留跟**语言语义**绑定、字节码文档反过来要遵守的两条：

**装饰器求值顺序**：`@deco func f(){}` 不能当 `deco(f)` 的语法糖去套用调用求值顺序——装饰器前缀是
func/class 自己产生式的一部分，根本不存在外层的 `deco(...)` 调用表达式。正式规则：先按从前到后对
各 decorator 求值，再进入捕获/形参/返回类型求值；装饰器的调用在建立完毕后按从近到远进行。命名
函数/类的绑定只在最终值确定后发生一次。

**Function 对象与 Code 的关系**：Code 编译一次可能复用多次（函数每次被调用新开帧但执行同一份
Code），但"建立"这个操作每次执行都必须构造全新的 Function 对象，不能因为 Code 复用就连带缓存
对象——`is` 比较的是对象身份，直接关系闭包正确性（循环里值捕获必须各自捕获到当次的值）。

## 悬而未决 / 需要以后回来处理

- **匿名类没法调用 `super`**。`super(cls, obj)` 的第一个实参要写"定义这个方法的那个类"的名字，而匿名类
  没有名字。这个洞在合并构造之前就存在（匿名类重写任何方法都调不了 `super`），但 `__construct__` 让它
  从罕见变成常见——凡是要初始化字段的类都得调一次 `super`。可能的出路：给 `super` 加零参/单参形态
  （像 Python 的 `__class__` 闭包单元那样，由编译器把定义类填进去），或者别的。SL.md 3.10 那个栈的例子
  已经因此从匿名类改成了命名类 `Stack`。

- **`SL.md` 3.11「`SyntaxError` 在编译期抛出；其他所有异常均在运行时抛出」这句话的适用范围要收窄**。
  它的本意是：**编译器拿到一段完整的源码字符串之后**，若语法不正确，只抛 `SyntaxError`。但从命令行
  给 `SL.exe` 一个路径时，路径不存在、文件读不了、编码不合法这些在"拿到源码字符串"**之前**就会失败，
  抛的是 `FileNotFoundError` / `IOError` 之类，跟这句话并不矛盾——只是这句话没把那个阶段算进去。
  这一段（启动阶段的错误怎么报、算不算 SL 异常、能不能被捕获）还没设计，先记着别照字面理解。
- **`SyntaxError` 要不要在 `.args` 之外再暴露 file/row/col**（类似 CPython 的
  `SyntaxError.filename`/`.lineno`/`.offset`）还没拍板。现在的选择是不加：`BaseException` 只有
  `.args`，`HostErrorConversion.cpp` 转换时把位置信息揉没了、只留 `message()` 塞进 `args[0]`——
  这是刻意偏保守，没有替这个问题自作主张扩大 `SyntaxError` 的专属字段（那意味着要么破坏"整棵异常树
  共用同一个 C++ 类"这条现在成立的简单性质，要么等通用属性表落地才能挂"只有这一个子类多出来的字段"，
  两者现在都不想仓促定）。真要加，`file`/`row`/`col` 更像是走属性协议之后才该有的东西，不是往
  `Exception` C++ 类里加专属字段。
- `str(x)` 这类内置类的构造/转换函数、以及 `repr` 之类的函数，`SL.md` 还没写但很可能要有，
  见下面"内置类的构造/转换行为整片没定"那条。这也是为什么 `.args` 现在没有配套的字符串化规则
  （Python 的 `str(BaseException)` 那套"零个参数空串/一个参数就是它/多个参数是元组"）——那条规则
  依赖 `str()` 本身先有定义，不该在这之前单独为异常发明一套。

- **小整数/短字符串要不要做实例缓存**（Python 的 `-5..256` 那种），SL.md 没规定，`is` 的结果会
  被它影响。常量表去重已经保证同一份 `Code` 里的字面量 `1` 是同一个对象，跨 `Code` 则不保证；
  要不要再加一层全局缓存，等 VM 能跑起来、能实测收益时再说。
- **`object()` 目前造不出来**：`Object` 因为 `trace()` 是纯虚而抽象，而 SL.md 4.2.1 说 `object`
  可直接实例化。要等属性表落地（实例得有地方放属性）时一起补。
- `local` 保留字去留未拍板。
- `when` 完整语法语义未开始设计（`case` 暂留）。
- `assert` 只占保留字位置，行为未设计。
- 数字字面量扩展（二/八/十六进制整数、`complex` 字面量）故意拖后；`complex` 类本身已加
  （`numbers.Number` 子类）。科学计数法已经设计定型且 lexer/parser/analyzer 都已跟进实现完毕
  （见下面"科学计数法字面量"一节），不在此列。
- 完全没开始设计（用户明确的优先级顺序，"不属于语言本身的东西最后弄"）：文件 I/O；`set` 方法
  列表；字符串插值（已讨论并否决 f-string，打算用 `%` 运算符重载 + `.format()`）。
- 自定义模块系统：module/package 概念、多段名字的逐层导入 + 挂属性、`ImportError` 场景已定
  （见 SL.md `import` 一节），但"名字怎么定位到具体文件系统位置"（搜索路径）、循环 import、相对
  导入都还没设计——这跟"作用域隔离"是两回事，别混淆。
- 递归深度：SL 逻辑递归深度和 C++ 调用栈不是一回事，需要解释器显式 guard（对应
  `RecursionError`），具体阈值未定。
- `&`/`|`/`^` 对两个 `bool` 目前一律是 `TypeError`（位运算是 `int` 特有的）。要不要给 `bool` 单独
  补一套返回 `bool` 的逻辑运算（Python 那样 `True & False == False`）没定；现在只能写 `and`/`or`。
- `set`/`frozenset`/`dict` 等容器的方法列表尚未逐个列出（`d.pop(k)` 这类只在别处被引用过）。
- 内置类的构造/转换行为整片没定（`int(x)`、`str(x)`、`list(x)`、`tuple(x)` 等，只有
  `set`/`frozenset`/`frozendict`/`range` 写了）。其中 `int(decimal)` 的取整方向是真空白：截断还是
  向下取整？SL 的 `//` 已经定死"永远向负无穷"，`int()` 若选截断，语言里就有两种取整方向了。
- `BigDec` 还缺 `hash`（要跟数值相等的 `int` 一致，得先归一标度）和 `int(decimal)`（取整方向 SL.md
  自己还没定，见下）。SL.md 里 decimal 参与的运算符本身已经全了，见上面 `numeric/BigDec` 几节。
- `sqrt`/`exp`/`ln`/`log10` 在 `BigDec` 上有了，但 **SL.md 还没规定它们怎么暴露给用户**——是挂成
  decimal 的方法，还是走一个 `math` 模块？`**` 是运算符，不受这个问题影响，先实现了。
- `BigInt::pow` 没有上限，但没上限的具体后果是"挂死"而不是头文件写的"可能抛 `std::bad_alloc`"：
  指数大到一定程度，先被朴素 O(n²) 乘法拖到实际算不完（内存反而通常够，不会真的 OOM）。
  `operator<<` 的超大位移是干净的 `bad_alloc`，`>>` 有 O(1) 短路，`from_decimal_string` 的零尾数也
  短路了（见上面对应的决策一节），这几个都不受影响。这是 VM 层的资源
  guard 议题（要不要在解释器调用 `pow` 之前就卡一个指数上限），不是 `BigInt` 自己该管的，先记在这。
- ~~`StaticEvaler` 里那整套二进制浮点折叠还没清掉~~ **已完成**：int 侧改用 `int64_t`
  直接算、溢出就不折（折叠器不依赖 `numeric/BigInt`）；decimal 侧按"结果为 decimal 的常量折叠
  一律禁掉"一节的结论直接整个不折（不是接进 `numeric/BigDec` 再折）。没等 `decimal` 接进前端才做，
  是因为同一批 `double`/`raw_` 字符串逻辑还连带把 **int** 的科学计数法写法算错了（`0e0` 的真值判成真
  → 死分支消除留错分支），那条是会静默改语义的活 bug，等不了。
- `decimal` 的 NaN 没有诊断信息（Python 的 `Decimal('NaN123')` 那种 payload），`BigDec` 直接把带
  payload 的字符串判为不合法。要不要补由以后需要时再说——静默丢掉比拒绝更糟，所以现在是拒绝。
