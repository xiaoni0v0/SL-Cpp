## 语言设计决策

### 作用域、捕获与单元

**只查当前帧和全局帧，不沿帧栈向外找。** 标识符读取顺序是 `_L` → `_G` → 内置表，模块里的函数被外部调用时不会
意外读到调用者的帧。访问外层局部变量必须显式捕获，捕获不跨层自动传递，中间每层都要转发。

`x op= expr` 读旧值时不退回 `_G`，未标记 global 时只查 `_L`，找不到就 `NameError`，保证读写落在同一帧。所以
`x op= expr` 不等价于 `x = x op expr`。

**引用捕获是 Python 式的 cell，SL 叫单元。** 原设计是函数记住定义帧、读写转发过去，帧弹出即"死亡"，返回出去的
闭包一调用就 `NameError`，闭包没法逃逸，只能靠值捕获加盒子。改成单元后：

- 按变量一个单元，不按作用域一个闭包对象，捕获不同子集的闭包互不牵连。
- 建立闭包时由定义处的 `Namespace` 按名字取单元，已是单元就复用，所以同一作用域里 `[&n]` 的几个函数自动共享。
  不需要静态分析，`eval` 里定义的闭包也一样。名字尚不存在时建空单元。定义处的名字本身是引用捕获来的，直接转发
  那个单元。
- `Namespace` 透明穿过单元，外层照常按名字读写，内层直接拿单元。单元化对这个 `Namespace` 是永久的，`del` 清空值和声明，
  保留单元及名字与单元的关联，之后再赋值、声明仍作用于同一个单元，否则外层和闭包会分叉。
  无值的名字不作为字典项存在；声明独立于值存在，只有声明时也能 `del`，带 `const` 仍报 `TypeError`。
- 单元里同时放值和声明，`n: const int` 经捕获回写照样被拦。
- 空单元的读取退回 `_G` 和内置表。
- 复合赋值读取旧值只查写入所作用的位置，没有值就报 `NameError`；引用捕获、global 标记和普通局部名字都遵守这条规则。
- `global` 要清除局部的值和声明，包括只声明未绑定的名字；局部名字已单元化时清空单元内容，已有闭包仍持有该单元。
- 仍要用户写 `[&n]` 点明，不自动分析。语言里没有任何自动生成的捕获，注解懒求值用的是无捕获函数（见下）。
- 连带删掉"定义帧"和"帧死亡"两个概念。函数、类对象只记建立时的 `_G` 加单元；帧弹出后没人引用就能回收。
- 被引用捕获的名字多一层间接，其余名字不受影响。

**全局变量属于定义它的那份文件。** `import`、`eval_isolated` 会在帧栈任意位置压文件级的帧，运行期有多份 `_G`。
每个局部帧所属的全局帧取自函数、类对象建立时记住的 `_G`，不是从栈顶往下找最近的全局帧，否则 A 文件的函数被
B 文件调用时全局变量会跑到 B 上去。

**`class` 也有捕获列表**，放在基类之后：基类在类体帧建立之前求值，捕获在新帧建立之后处理。
捕获的值求值、引用单元的取得都作用于定义处所在作用域，结果装入新帧；压入类体帧不改变捕获的来源。
两者概念无关，所以不照搬 `func` 的 `[捕获](形参)` 布局。没有这个，局部定义的类和它的方法够不到外层局部变量。

**`global` 作用在引用捕获上是运行期检查，报 `NameError`。** `global` 是一次名字表操作，跟 `del` 一样求值时才生效，
不是函数体级别的静态声明；`SyntaxError` 只在编译期抛，所以这里只能是 `NameError`。

### `eval`

**`code` 在调用帧里求值，靠"静态外层环境为空"划出可用子集。** `code` 必须恰好解析出一个表达式，不在任何 Program、
任何循环内。于是 `return`、`break`、`continue` 自然是 `SyntaxError`，`raise`、`global`、`import`、赋值、`del`、`try`
照常可用，不需要逐条列禁令，嵌套情形也自动正确（`code` 里自己写的函数体里 `return` 合法）。`eval_isolated(code, _L)`
替代不了它：前者把 `_L` 当新文件的 `_G`，后者里 `x = 0` 落在哪由调用帧当时的状态决定。

**`eval` 是关键字，不是内置函数。** 这样"某一帧会不会被现场插进代码"等价于"它的 `Code` 里有没有 `eval` 点"，纯静态
可判定，不含 `eval` 的函数将来可以把局部变量编译成槽位下标。代价是没有 `f = eval`，而 `eval` 的语义绑死在调用帧上，
传来传去本来就是陷阱。保留括号形态 `eval(code)`：它的值要参与外层表达式，做成无括号前缀会让外层括号变成常态。
实参形状跟普通调用一致，能不能恰好绑出 `code` 形参是运行期按通用调用规则判定（失败 `DispatchError`）；
`AstNodeEval` 与 `AstNodeCall`、`AstNodeImportCall` 共用 `CallArgs`。`eval_isolated` 保持普通内置函数。

**`in_local_scope` 从调用点传入。** `global` 合不合法取决于调用帧是不是局部作用域，这只有执行 `eval` 那一刻知道。
`SemanticChecker` 和 `Analyzer::analyze_single_expr` 带一个默认 `false` 的参数，由将来编译 `eval` 的地方传入。
`global` 是目前唯一一个合法性取决于调用帧的构造。

### 类型系统

**声明是对名字的断言，不碰对象。** 写法是 Python 式 `x: T = v`、`x: T`。形参本来就是 `name: type = default`，返回类型
是 `): type`；C 式 `T x` 要改形参和返回类型，匿名函数 `func int (x)` 里的 `int` 还分不清是返回类型还是函数名。

- 声明之后名字若已绑定，当前值必须满足类型；`x: T = v` 先检查 `v`，失败则声明和绑定都不变；其余绑定方式按已有声明
  检查；`del` 连声明一起删。重新声明随时允许。
- 声明记在帧的 `Namespace` 里，检查落在表自己的写入口，所以 `_L['x'] = v`、`eval` 都绕不过。
- 声明不参与属性和方法解析：属性查找按运行期 MRO，`FuncGroup` 是运行期分派，参与解析等于引入静态编译阶段。
- 否决受检异常：任何调用、运算符、描述器、`eval` 都可能抛 `TypeError`、`NameError`、`DispatchError`，异常集合静态
  算不出来；退成运行期契约就得把未声明的异常包一层再抛，会改掉 `except` 的匹配语义。
- 否决 `x: auto = v`：声明是给读代码的人看类型的，`auto` 只给机器上锁；推导依赖运行时，`x: auto = None` 会锁成
  `NoneType`。类型太长就起别名，类型本来就是运行期对象。以后想加只需一个内置名字，不堵路。

**赋值和声明是同一个节点。** AST 上是 `target ⟦: ⟦const⟧ ⟦type⟧⟧ ⟦= value⟧`，类型和值可空但不同时为空，类型字段挂在
节点上（不挂在目标上），类型非空时目标只能是标识符。复合赋值保持独立节点，没有带类型的形式（`x: int += 1` 是
`SyntaxError`），它的读旧值规则也不同。

- `x: T` 的值是 `None`，跟 `del`、`global` 这类无值构造一致；"值取已有绑定"在未绑定时无法定义。
- codegen 约定：无值声明给存储指令推 `Missing` 哨兵，VM 遇到 `Missing` 只换声明不绑定。`Missing` 只能由
  `LOAD_INTERNAL` 产出，用户写不出来。要表达式的值时不能 `COPY` 那个 `Missing`，要另压 `None`。
- 四种赋值同属 `=` 那一档，右结合；`:` 左边按高于这一档解析，所以 `a or x: int` 是 `(a or x): int`，报错。
- 统一原则（用户定）：某处已有自己的语法时优先按那个语法解析，要就地声明就加括号，跟 `f(key=val)` 里 `=` 优先表示
  按关键字传参是同一个道理。字典分隔符换成 `->` 之后，只剩实参这一处：实参开头的 `identifier =` 表示按关键字传参，`=` 在这里
  不是赋值；其余赋值写法（`f(a.b = 1)`、`f(x += 1)`、`f(x: int = 1)`）一律禁止，要写就再套一层括号（用户定）。"加括号"指
  实参内部新开的任意一层括号，所以 `f(if (c) x = 1)` 也报错。否决放开 `f(x: int = 1)` 当"声明 + 位置实参"：它跟形参
  `func f(x: int = 1)` 长得一样，容易被读成给指定形参传值并附带类型；实际按位置把 1 绑到形参，调用方还多了个声明。
  禁止也给以后可能的按关键字传参时附带类型的写法留了位置。
- 索引允许零项、末尾逗号、多个 `*expr` 展开项，每一项按普通表达式解析，不允许按关键字传参或 `**expr` 展开。
  赋值、声明、复合赋值照常解析，不沿用调用的括号限制；`arr[x=1]` 先赋值，再以结果为下标。
  `arr[i:j]` 以声明 `i: j` 的值 `None` 为下标，声明的副作用照常，没有切片的专用写法。
  `x[]` 向索引方法传入零项，`x[()]` 传入一项空元组。各项从前到后求值，展开一项后才处理下一项；
  元素复合赋值只展开一次，读、写复用展开后的实参。
- 没有这种冲突的地方不特意禁，按声明照常解析，值和副作用都照常：
  - `except (e: E)` 的异常类就是声明 `e: E` 的值 `None`，运行期因为不是异常类抛 `TypeError`。`exc_type` 求值后紧接着
    检查 `issubclass(exc_type, BaseException)`，不满足就换成 `TypeError`、不再看后面的 `except`。只在真的轮到这个
    `except` 时检查，跟 `exc_type` 本身的求值时机一致，不提前到进入 `try` 时。理由：不检查的话 `except (None)`、
    `except (int)` 静默永远不匹配，原异常原样漏出去，看不出是 `except` 写错了；跟 `raise` 要求 `BaseException` 实例
    对称；只在异常路径上多一次 `issubclass`。原异常被丢弃，SL 没有异常链。
  - 单槽的 `for (x: int)` 迭代 `None`，运行期 `TypeError`。
  否决过在 Parser 里专门拦 `except (e: E)`：`as` 本来可选，括号里没写 `as` 时就是一个普通表达式，拦它是在给
  一种表达式开特例。
- `cond` 拒绝裸赋值这条只为防 `==` 手误写成 `=`，所以只管裸赋值 `target = expr`；带类型的赋值不可能是手误，放行。

**`isinstance` 只看类型，不看内容。** `isinstance(x, T)` 恒等于 `issubclass(type(x), T)`。原来 `isinstance(x, list[int, ...])`
既判类型又逐个检查元素，同一调用可能 O(1) 也可能 O(n)，空的普通 list 同时满足 `list[int, ...]` 和 `list[str, ...]`，
`FuncGroup` 分派结果取决于重载顺序。去掉 `__instance_check__`，只通过类型关系钩子扩展判定。实例检查钩子能拿到对象本身，
留着迟早有人在里面遍历内容；协议本来就定义在 `type(obj)` 的 MRO 上，鸭子类型不受影响。否决"去掉整个钩子机制"，
那会连协议一起废掉。代价是 `f([1, 2])` 调不了 `xs: list[int, ...]` 的形参，要用 `typed`（见下）。

类型关系钩子定为 `__is_subclass_of__`、`__is_superclass_of__`，两者必须是类方法。
`issubclass(X, Y)` 先问 `X.__is_subclass_of__(Y)`，弃权后问 `Y.__is_superclass_of__(X)`，最后查实际 MRO。
`True`、`False` 都是最终结论；没有方法或返回 `NotImplemented` 才继续，其他返回值是 `TypeError`，异常直接传播。
先问左侧，让复合类先拆开，再把具体分支交给右侧的协议或容器约束钩子，右侧不必自行处理复合参数。
Python 的子类检查钩子在元类上，SL 的钩子在参与判断的类自身上，名称直接写明接收者与参数的关系。
允许钩子改变与实际继承关系不同的类型判定，`isinstance(obj, type)` 因此进入类访问分支也是允许的行为；
不将它改成 `type(obj) is type`。右侧优先需要另行处理复合参数：现有协议钩子查复合类自身 MRO 会返回 `False`，
左侧便没有机会拆分。顺序仍保留左侧优先。

**带约束的容器类。** `tuple`、`list`、`dict`、`unordered_dict`、`frozendict`、`set`、`frozenset` 用 `[...]` 生成动态子类，
约束带在对象上，一切引入新元素的操作都检查。

- 同参数的类相等、哈希一致，不保证 `is`，只保证 `list[object, ...] is list`。保证 `is` 就得有一张缓存，永久持有会越积
  越多，弱引用缓存要多一套机制，还得把 `int | str` 和 `str | int` 规范化成同一条；`issubclass` 按结构比较，本来不依赖
  身份。Python 的 `list[int] is list[int]` 也是 `False`。实现可以自行缓存。
- 只有没有长度约束且元素类型全为 `object` 时才退回原容器类。`tuple[object, ...] is tuple`，
  `tuple[object]` 仍限制长度为 1，不能退回普通 tuple。
- 直接基类只有容器类本身，子类关系由 `__is_superclass_of__` 按元素类型协变判定。不按元素类型逐级生成基类，因为 `int?`、
  `A | B` 这类复合元素类型串不成类链。协变是安全的：写入永远查对象自己的约束，只会更严。
- 定长 tuple 的拼接、重复、切片等操作按结果长度与各位置的约束自动生成结果类，约束随元素位置一起拼接、重复或选取；
  来源容器没有约束的位置按 `object` 处理，空结果为 `tuple[]`，拷贝保留原类。这样结果长度改变后仍满足自己的约束。
  其余派生容器（`+`、`*`、切片、拷贝）保持自身类，否则 `x += [2]` 会悄悄把带约束的 `x` 换成普通 list。
- 声明不会把 `[1, 2]` 变成带约束的容器，`x: list[int, ...] = [1, 2]` 直接 `TypeError`（用户明确要求声明与对象脱钩）。
  否决"声明处的字面量自动建成带约束的容器"，那会让名字上的断言决定对象怎么创建。

**`typed` 方法。** `x.typed(*args)` 等价于"`x` 所属的内置容器类`[*args]`"从 `x` 构造，返回新对象。

- 选方法不选语法。否决 `字面量 as 类型`：只能做成静态语法，非字面量用不了，还要多一个关键字。方法静态动态都成立；
  折叠器见到"容器字面量 `.typed`"可以放心优化，因为字面量的类型恰是内置容器类，方法在描述器表里建类后不变。
  类型参数是名字、可能被遮蔽，仍要运行期求值，所以只能省掉中间那个普通容器，求值顺序同方法调用（先元素、再类型参数）。
- 复制，不就地改类型。就地改会悄悄破坏别处已成立的声明：`x: list! = ys` 之后把 `ys` 收紧成带约束的类，`x` 没经历
  绑定，声明却不成立了。声明、`isinstance` 结果、`FuncGroup` 分派都依赖"对象的类型终身不变"。
- 按值递归（用户要求）：元素不满足元素类型 `E`、但它是 `E` 所基于的容器类的实例时，递归转换。`E` 是复合类时恰有一支
  可转才转，复合类的检查顺序不作保证。按值递归，静态动态语义一致；深度受类型嵌套层数限制。
- 命名跟 `sorted(x)` / `x.sort()` 的约定一致，分词形式返回新对象。否决 `of`（Java 的 `List.of` 是用元素造列表）、
  `cast`、`as_type`（暗示同一对象强转）。`typed` 不改容器种类，冻结仍用 `frozenset(...)`。

**复合类。** 只剩 `|`、`!`、`?`，`[]` 归带约束的容器类。按结构比较相等，与书写顺序无关。子类判定把复合类展开成分支，
左边每一支都被右边某一支包含才算子类；`A!` 只有"恰为 A"一支。凡是要求类型的地方 `None` 都当作 `NoneType`
（`NoneType` 写不出来，原来 `int | None`、`func f(): None` 都写不了），`A?` 就是 `A | None`。

- 复合类直接动态建立为 `type` 的实例，以 `object` 为唯一直接基类，不继承分支的属性或方法。
  `CompoundType` 独立对象类型取消，声明类型只需接受 `type` 或 `str`。生成类持有不可变的内部结构，
  两个类型关系钩子都能用类方法绑定到具体复合类，无须给复合类另定实例方法协议。
- `!` 只接受具体类，操作数为复合类时抛出 `TypeError`，包括 `(A | B)!`、`A!!`、`A?!`。
  复合类仍可通过 `|`、`?` 组合，如 `A! | B!`、`A!?`。
  否决逐分支施加 `!`：精确类要求实际类型恰好是操作数，逐分支处理会改变这个含义；复合类本身又不允许实例化。
- 结构相等、哈希相同，不保证对象身份相同。类对象的比较走 `type.__op_eq__`，复合类自身的方法不能改变这个分派入口。
- 复合类不允许实例化，生成时 `__is_final_class__` 为 `True`。分配入口如何落实禁止实例化仍待确定；
  只让其 `__construct__` 抛异常不足以挡住 `object.__construct__(复合类)`。候选方案是分配时按内部复合结构拒绝，
  无须增加公开标志。不要为此伪造抽象方法，`finalclass` 现有规则不接受抽象类。

**属性声明不分类属性和实例属性。** 类体里的 `x: int = 0` / `x: int` 声明的是属性名的类型。读属性本来就是"实例属性表
→ 类属性表"回退，一个名字在两层是同一个东西。

- 没有单独的"声明表"概念。每个 `Namespace` 有两张独立的表：名字到值、名字到声明，键可以不一致、互不包含。类体帧
  `_L` 里的声明建类时成为 `attrs(类)` 的声明；有 `= v` 时 `v` 同时是类级默认值。
- 约束作用于 `attrs(o)` 的每一次写入，自定义 `__setattr__` 也绕不过。实例的属性表是另一个对象，自己没有类体里写的
  声明，所以声明要沿 MRO 继承：`o` 是类时取自己的 MRO，否则取 `type(o)` 的 MRO，自己的优先。
- 子类重声明就是普通的重新声明，整个替换基类的同名声明，新旧类型不必相关（用户定）：`class B(A) { n: const str = '1' }`
  在 A 有 `n: const int = 1` 时合法。子类不重声明、直接给同名属性赋值，收集属性时按普通写入检查继承来的类型和 `const`。
  收集时类体里声明过的名字连同声明原样存入，值在类体帧里已按该声明检查过，不再查，也不碰 MRO 上的同名声明。
- 否决"子类重声明须是父类声明的子类"：它让 A 的方法能认定 `self.n` 的类型，但 SL 里子类覆盖方法也不查签名，只给属性做
  里氏替换检查是孤例；类型懒求值，检查只能推迟到新声明首次求值，报错时机难以预料，挪到建类时又会让 `next: Derived?`
  这类前向引用 `NameError`。A 的方法往 B 的实例写 `self.n` 时仍按最派生的声明检查。
- 实例属性不单开语法，`self.x: T = v` 因冒号前只能是标识符而是 `SyntaxError`，类型只在类体里集中声明。
- 描述器仍优先，声明拦不了 `property`。

**`const` 挂在声明上，名字引用了对象之后只拦非声明的写入。** 写法 `x: const int = 1`、`x: const = 1`、`x: const`。
带 `const` 的名字已引用对象时，除声明以外的任何写入都抛 `TypeError`；还没引用对象时可以绑定一次。重新声明随时允许，
新声明整个替换旧声明，类型和 `const` 都不沿用。于是循环体里每轮 `y: const int = f(i)` 合法，没有块作用域带来的
"第二轮报错"。

- 只写声明也能去掉或加上 `const`：`x: const int = 1; x: int` 合法，此后 `x` 可以重绑；`x: int = 1; x: const int` 冻结。
  否决"只写声明不许去掉 `const`"：`x: int = x` 一样能去掉，拦了也不保护什么。`const` 防的是别处的普通写入，声明只能
  在名字所在的那一处写（`m.X: T = v` 是语法错误，属性只在类体里声明），不在它要防的范围里。

- "未绑定时可以写一次"是为了先声明后赋值：`x: const; if (c) x = 1 else x = 2`，以及类体里 `n: const`、构造时
  `self.n = v`。否决"`x: const` 只冻结当前绑定、未绑定时等于永远写不进"：那样 `x: const` 在未绑定时毫无用处，`const`
  属性只能在类体里给死值。相当于 Java 的 blank final，只是检查推迟到运行期。
- 属性的"已引用对象"跟查声明走同一条链（自己的表，再 MRO 上各类的表）。于是类体 `n: const = 1` 是真正的类常量，实例
  写不进去；类体只写 `n: const` 时每个实例各自写一次。否决只看自己那张表：那样 `a.X = 2` 会在实例上静默遮住类常量。
- 核心价值是别的模块改不了你的常量：外部只能 `m.X = v` 或 `attrs(m)['X'] = v`，都是非声明写入，`m.X: T = v` 是语法
  错误。唯一旁路是 `eval_isolated(code, attrs(m))`，那是明摆着的元编程，接受。
- 类属性的 `const` 跟类型一样沿 MRO 继承。注解（`: ⟦const⟧ ⟦type⟧`，至少写一个）在声明、形参、`for`/`except` 的绑定
  里写法一致，形参注解的 `const` 在函数体内生效。
- 返回值注解是唯一不能写 `const` 的地方：`const` 对返回值没有意义，而且 `func f(): const {}` 分不清 `{}` 是类型还是
  函数体（用户拍板）。
- 字符串类型的声明是完整的声明，不能理解成"没写类型"，唯一的区别是任何值都满足它（用户定）。SL.md 用"满足"这个词统一：
  `v` 满足 `T` 指 `T` 是 `str` 或 `isinstance(v, T)`，声明一节的规则都按"满足"写。字符串原样记进 `Namespace` 当声明的
  类型，`const` 照常，`x: 'doc'` 是一次重新声明，`x: const int = 1; x: 'doc' = '2'` 合法，跟别的重新声明一样整个替换。否决过"`x: '...' = v` 等价于 `x = v`、成功后再
  把字符串记进去"：那样带值的写法撞 `const` 报错，不带值的 `x: '...'` 却能记录、顺手去掉 `const`，两者不一致；
  要堵就得单开"字符串声明不能去掉 `const`"的特例，违背"声明加赋值恒允许"。
- 否决把 `const T` 做成复合类：`const` 管名字能不能重绑，类型管值属于哪个集合，是两个维度；做成复合类后
  `isinstance(1, const int)`、`list[const int, ...]` 处处要规定是忽略还是报错。别名给类型部分起即可。
- 否决 `const x = v` 前缀写法加"任何再绑定都报错"：没有块作用域时循环体里的 `const` 第二轮必然报错。

**形参注解进入局部作用域。** 带注解的形参，调用时以该注解在局部帧里加上声明，`func f(x: int) { x = 's' }` 抛
`TypeError`。调用时不匹配仍是 `DispatchError`（属于分派），函数体内违反声明是 `TypeError`，有意分开。字符串类型不检查。
值捕获进来的名字没有声明，捕获列表也不加类型写法。

**注解懒求值。** 注解在定义时求值太早，类体里 `__next: Node`、`func next(self): Node` 都会 `NameError`。C++ 式前向声明
做不了，SL 是引用语义，占位对象不是最终那个类。沿 PEP 649 的方向，但只让真正需要推迟的地方变懒：

- 函数的形参、返回注解和类体里的声明，类型编译成无形参、无捕获的函数，第一次检查时调用、验证、永久缓存。无捕获的
  函数只看得到 `_G` 和内置表，模块级的类和内置类型都在那里，常见写法够用。否决每次现场求值：两次调用之间类型可能变。
- 其余位置（函数体里、文件顶层、`for`/`except` 的绑定）就地求值，先 `T` 后 `v`，看得到局部变量。这些地方执行到时类
  早已定义；要是也走无捕获函数，`func f() { class P {}; p: P = P() }` 会因为 `P` 是局部的而 `NameError`。
- 类体里一律走无捕获函数，看不到类体局部名字（`class Outer { class Inner {}; x: Inner }` 要写 `x: Outer.Inner`），
  换来类体内部规则一致。
- 要用局部名字时，类型写成函数表达式并显式捕获，如 `func use(p: func [P]() { return P })`。最外层是函数表达式
  时不再包一层，在原本求类型的时刻求值，需要类型时以无实参调用。冗余括号不算，允许匿名或命名；命名函数照常绑定名字，
  类型位置不另设限制。函数对象本身不是合法类型，所以不会和"类型就是这个函数"冲突。
- 否决：表达式里的自由标识符自动引用捕获，那是隐式闭包换了个名字；"强制无捕获、没有逃生口"，局部定义的类就写不出
  带检查的注解；"所有注解都写成函数"，太啰嗦。
- `x: T` 而 `x` 未绑定时不做检查，所以不求 `T`，类体的 `__next: Node?` 由此成立。类体里 `__next: Node? = None` 要立刻
  检查，仍 `NameError`，已接受。
- 定义时"默认值符合注解"那条检查删掉，默认值在调用时和实参一样被检查。
- 字符串注解保留，作"写了但不检查"的逃生口。
- TODO：在 Analyzer 最前面加一遍注解转换，先于 `SemanticChecker` 和 `ExprFolder`。Parser 保留原始类型表达式，
  不生成隐式函数，也不因惰性求值而禁止注解中的赋值、声明、函数定义等表达式。
- 转换先复用 `AstNodeFunc`：非空、最外层不是函数表达式的惰性类型，替换为无形参、无捕获的匿名函数，
  body 为只含 `return 原表达式` 的 Program。给合成函数保留来源标记，区分隐式注解函数和源码中的显式函数。
  显式函数允许匿名或命名，直接使用；`const` 留在原 `Annotation` 上，类型省略时保持空指针，沿用默认 `object`。
- 按最终的函数边界递归转换：先包外层类型，再进入生成的函数体处理内部节点；其中的普通声明属于函数体，就地求值。
  函数的默认值、装饰器、捕获初始化等按定义所在环境处理，函数体进入函数环境；类体进入类环境。
  `for`/`except` 的绑定类型仍就地求值。最外层节点类型的判定在折叠前完成，不能在折叠后重新决定是否包装。
- 不引入 `AstNodeDeferredType`。现有 AST 通过 `AstNodePtr` 多态容纳节点，新节点本身不要求 C++ `variant`；
  但复用函数节点能沿用作用域、控制流检查和 codegen，暂时不增加专用节点和运行时求值对象的分支。
  第一版可每处注解生成一份 `Code`，同一源码处的 `Code` 重复建立函数时复用。后端若要减少对象数，按合成标记另行优化；
  共享代码仍须保持各次求值的局部帧和各条声明的缓存独立，不能提前求值其他注解。

**删掉 `TypeVar`。** 带约束的容器类要求元素类型是类或复合类，`list[T, ...]` 写不出来，`TypeVar` 只剩"多个形参类型一致"
"返回值类型跟某个形参一致"两种用途，动态语言里不常见，手动 `isinstance(r, type(a))` 就能替代。它是唯一带状态的注解，
跟懒求值、声明、分派都要单独处理；原规则记的是第一次遇到的值的精确类型，`max(1, True)` 会失败，结果还取决于形参
顺序。若保留，每次调用的记录只能放在帧的隐藏字段，不能放 `_L`；文件顶层和类体的声明还没有"这次调用"可依附。
以后真需要"返回同类"，单独设计一个更窄的东西。

### 语法

**`{}` 恒为复合表达式，字典和集合用 `${}`。** 字典 `${k -> v}`、集合 `${a, b}`、空字典 `${}`，空集合仍写 `set()`。`$` 与 `{`
是两个 token，由语法分析识别组合。原来"第一个表达式后跟 `:` 就是字典"的判别会把块首的 `{ x: int = 1 }` 吞成字典，
本身也是上下文相关的。否决类型名前缀 `dict{}`（与 `func f(): T {` 冲突）、`%{`、`~{`（运算符）、`@{`（装饰器）、
`#{`（注释）。已知瑕疵：收集模式里 `$` 是 list、`$$` 是 dict，而 `${}` 同时管 dict 和 set，两者语法位置不相交，不会混。
`a = if (c) {}` 里的 `{}` 表示"什么都不做"，值是 `None`，这正是不让 `{}` 当空字典的原因。

**字典的键值分隔用 `->`，`:` 只表示类型注解。** SL 尽量一个符号一个意思，`:` 原来同时是注解和字典分隔，块首、实参、
字典项里都因此要额外规定谁优先。`:` 表示类型在主流带类型的语言里几乎通用，声明、形参、返回值、`for`/`except` 的绑定都
用它，换注解的代价大；字典本来就已经是非主流的 `${}`，换分隔符代价小。`->` 读作"映射到"，Scala 的 `Map("a" -> 1)` 同理；
它不是运算符，只在 `${}` 的项里出现，`->` 在旧代码里会被切成 `-`、`>`，`>` 起不了表达式，所以不改变任何合法代码的含义。

- 否决 `=>`：留给以后可能设计的 JS 式 lambda `a => 3 * a + 1`（用户定，暂不进标准）。
- 否决 `=`（`${k = v}` 撞上"集合里放一个赋值"）、`${(k, v)}`（啰嗦）。注解换符号的方案（`::`、`as`、前缀 `int x`）都否决。
- 代价：以后若要函数类型的写法，不能再用 `(int) -> str`。

**控制头部用 `expr ⟦as binding⟧` 绑定。** `as` 是关键字，`from` 是保留字。主项在前，可选绑定在后；
不写绑定时主项保持原样。`binding` 是 `target ⟦annotation⟧` 的共用记号，定义在 SL.md 的“赋值与声明”一节。
未写注解时目标为左值，带注解时只能是标识符。

- `for` 绑定当前迭代元素，`except` 绑定匹配到的异常对象；具体绑定值由外层构造确定，`as` 不表示把左侧表达式的值
  直接赋给目标，也不作为通用运算符或类型转换。
- 目标在前与赋值、步进 for 更一致，但 `except` 的匹配条件及未来 `with` 的资源表达式是头部主项，让可选绑定作为后缀
  更便于阅读和扩展。`when` 的模式匹配另行设计，不能把匹配失败与赋值失败混为一谈。
- Parser 先按原有规则解析主表达式，再用 `parse_binding` 读取 `as binding`，返回 `Binding`。
  不需要把源表达式和可选绑定装进中间结构，也不需要拆出声明的头部和尾部。
- `except` 的多个异常类改用 `|` 拼成复合类。`: type` 是声明，`exc_type` 是匹配条件，两者独立，
  `except (A | B as e: Exception)` 成立。否决 `except (e: E)`：`x: T` 在别处是"只声明不赋值"，这里却在赋值。
- 否决 `in`：它是成员测试运算符，会回到"一身两责"的老问题（Parser 先建成员测试节点再拆开重解释）。
- 绑定记号写在括号里面，不写成 `for (iterable) as i`：括号外时 `for (xs) as a [1, 2]` 会把 `a[1, 2]` 吃成索引。头部完全
  被括号封死、body 紧跟 `)`，是 `if`/`while`/`for`/`except` 共同的不变量。
- 绑定可选：`for (iterable)` 丢弃每轮的值，`except (E)` 不关心异常对象。于是 `for` 头部的规则是"3 个槽是步进，1 个槽是
  迭代"，任何表达式都能当可迭代对象，能不能迭代是运行期的事。
- 异常对象的绑定就是普通赋值，不 shadow 同名变量，结束后不解绑。Python 自动 `del` 是为了断开 traceback 的引用环，
  SL 有全堆扫描，不需要。重抛写 `except (E as e) { raise e }`，没有裸 `raise`。
- `try` 正常完成时取保护体或匹配的处理分支的值。`finally` 正常完成保留此前的值、异常或跳转；抛出的新异常取代此前结果。
  匹配条件求值、异常类型检查、目标绑定中的异常同样进入 `finally`，不交给同一 `try` 的后续 `except`。
- 带 `: type` 时目标只能是标识符；`exc_type` 里的 `E1 | E2` 两侧都会求值，但仍只在发生异常之后。

**`cond` 拒绝裸赋值。** 防 `if (x = 5)` 手误：只限制 `if`/`while` 的 `cond` 和 `for` 三槽形式的中间槽，不限制 `init`、`inc`，
只挡裸 `=`。要赋值就再套一层括号 `if ((x = y))`。因此"冗余括号没有任何效果"要收窄：它不改值、类型和求值顺序，但凡是
按写出来的形状给的语法限制都看它在不在。以后再加这类限制，要一并想清楚括号算不算。`for (cond)` 单槽纯条件形式故意
不提供，`while` 已经能做。

按关键字传参时不允许名字重复，按 Python 的行为处理：显式写出的 `identifier` 重复时在编译期报 `SyntaxError`；涉及 `**` 展开的重复在运行期报错，
有 `**kwargs` 也不允许覆盖。运行期参数不匹配沿用 SL 的 `DispatchError`。`**` 的键必须是 `str`，否则 `TypeError`；
字符串不必是合法标识符，不能匹配普通形参时交给 `**kwargs`，没有该形参则 `DispatchError`。
字典字面量中的 `**` 仍允许后项覆盖前项，不能把这条覆盖规则套给调用。

**范围运算：`..` 左闭右开，`..=` 闭区间。** `..` 跟 0 起始的下标、切片配合最好，新运算符不改它的含义。只需两个：左端几乎
永远是闭的，真要左开写 `a + 1`。

- 选 `..=`：`=` 表示"等于也算"，跟方向无关，`1..=5`、`9..=0..-1` 都读得通。
- 否决 Kotlin 式"`..` 改闭区间、`..<` 表示左闭右开"：改了 `..` 的含义，`<` 还有方向，`9..<0..-1` 读起来是错的。否决
  `...`（`Ellipsis` 字面量）以及 `..^`、`..!`、`..|`（不表示含端点）。
- `..=` 长得像复合赋值，但 `..` 没有复合赋值形式，语法上无冲突。词法上是独立 token。
- range 对象带"是否包含 stop"的标志，不能把 `a..=b` 改写成 `a..(b + 1)`，负步长和 decimal 步长时会错。
- 三元形式的第二个运算符只能是 `..`，开闭沿用左边；stop 为 `None`（无上界）时两者相同。
- 开放式切片不加独立语法，靠 `None` 表达开放端，由 `int` 的 `__op_range__`/`__rop_range__`（及 `..=` 那一对）识别。
- `range(...)` 构造函数保持左闭右开，`closed=True` 得到闭区间。

**链式比较。** `< <= > >= != ==` 互相可链，`is` 单独一档、不跟它们混链。若混链，`a < b is c` 会解析成 `a < (b is c)`，
把布尔值当数字比大小，类型上合法、静默出错。

**`in` 运算符。** 优先级 55，夹在比较组和 `is` 之间，普通左结合，不主动支持链式。比 `not` 紧，`not x in y` 读作
`not (x in y)`；比 `and` 紧，`x in a and y in b` 不用括号。重载方法叫 `__op_contains__`，只在右操作数上查，没有反向
方法、没有回退：`a in b` 该由容器回答。名字用 `contains` 是为了让"谁实现它"从名字上看得出来。

**装饰器。** `@d1 @d2 func/class ...` 属于函数、类表达式自己的语法，`decorators_` 是节点字段，名字在最终值确定后绑定一次；
`@decorator expr`（后面不是紧邻的 `func`/`class`）永远只是 `decorator(expr)`。否决过"看值有没有 `__name__` 决定要不要
重新绑定"（`@staticmethod outer` 会意外重绑 `outer`）和"看 `expr` 形状是不是 func"（嵌套装饰器外层不触发）。触发条件要
靠打补丁才能覆盖嵌套情况时，说明该在语法层拆开，让解析器确定性判断。

**`++`/`--` 砍掉。** 没有后缀形式就没有 `arr[i++]` 这类真正好用的场景，前缀用法跟 `x += 1` 一样，却要专门一档优先级、
专门节点、专门左值校验。

**命名：`match`/`case` → `when`。** `switch` 心智预期不对，`match` 太常用易冲突，参考 Kotlin。否决 `where`、`given`、
`branch`、`select`、`pick`。完整设计搁置。

**`import`。** 照抄 Python 的 module/package：module 对应文件，package 对应目录（内容是 `__init__.sl`，没有则视同空文件），
产出同一种模块对象。多段名字从左到右逐段导入，把子模块挂为上一级的同名属性。调用形态返回最后一段，关键字形态多段时
只绑定第一段，这是两种形态唯一的差异。否决"loader 不解析点号、靠模块自己挂属性"。

- 两种形态拆成 `AstNodeImportKw`、`AstNodeImportCall` 两个节点。调用形态不复用 `AstNodeCall`：那要求运行期真能按名字
  查到一个 `import` 对象，而且 `_G['import'] = print` 就能劫持调用形态、关键字形态却不受影响。`AstNodeImportCall` 没有
  被调对象槽位。
- 关键字形态存名字段数组，不存属性访问链：`import os.path` 没对 `os` 做属性读取，存成属性链会让泛型递归的消费者把
  被绑定的 `os` 当成一次读取。
- `import` 后无条件允许换行，跟 `global`、`del` 一致。

**`global` 和关键字形态 `import` 的目标走整条表达式再校验形状。** 原来只吃一个 token 就返回，节点交回外层 Pratt 循环，
`global x.y`、`import a.b(x)` 会被解析成属性访问、调用。现在目标解析成完整表达式，`global` 要求纯标识符，`import` 要求
标识符或一路属性访问的链，在 Parser 里校验完再展开成最终字段。否决"这个构造后面必须紧跟终止符"：终止符的合法集合随
嵌入语境变，等于重新发明一遍 Pratt 循环的终止条件。判断标尺见 [notes/parser-token-vs-expr-level.md](notes/parser-token-vs-expr-level.md)。

**整数和 decimal 字面量禁止前导零**（单独一个 `0` 除外）。给以后的 `0x`/`0o`/`0b` 前缀留解释空间，也避开"`0` 开头是八进制"的坑。

**科学计数法：类型只看尾数带不带小数点。** 尾数不带小数点时指数必须非负，整体是 int；带小数点时整体是 decimal。
`1e-9` 不合法，不退化成 decimal，否则判定类型要同时看两个信号。int 分支的指数上限 9999，decimal 不设限：int 只有裸值，
`1e999999999` 得真造一个十亿位整数，而字面量的指数是静态常量，编译期就能判。限制只针对 `e` 记法，手写长字面量不受限，
长度即成本。上限取 4 位数，判断退化成"位数大于 4 就不合法"，不用把指数解析成数值。这条归 lexer 管，不下沉到 `BigInt`，
是源码形态的政策，不是数值库的不变量。decimal 的 `str()` 在系数只有一位时输出不带小数点（`1E+30`），粘回源码会被读成
int，这是已知代价。decimal 字面量指数超出 `BigDec::kMaxExponent` 时在转换那一层报 `SyntaxError`，不抄进 lexer。

### 对象模型与协议

**真值统一到 `__bool__`。** 任意对象的真值是 `type(x).__bool__(x)`，必须返回 `bool`；`object` 兜底返回 `True`。它不进
协议那章（因为永远存在，不存在满不满足），也不进运算符重载表（`not` 不可重载）。

**内置名字放在独立的内置表，不放 `_G`。** 内置表全局唯一、只读，只在读取且 `_L`、`_G` 都没有该名字时兜底。`print = x`
只是 shadow，`del print`（没被 shadow 时）照常 `NameError`。4.4 的内置模块不在内置表里，只能 `import` 后用。

**`bool` 继承 `numbers.Real`，不继承 `int`。** 算术和比较先把两个值按 1、0 折算成 int，复用 int 的实现，结果类型随对应运算，
除法可以得到 decimal，比较得到 bool，不把所有结果统称为 int。连带：位运算和容器重复次数不收 `bool`，
`FuncGroup` 里 `f(True)` 不命中 `x: int`。折叠器对应拆成 `is_int` 和
`is_int_family` 两个谓词，强迫每个调用点显式选一次。

索引的展开结果按位置传给索引方法。读取传入对象及索引各项，写入传入对象、值、索引各项，值排在索引之前。
因此写入方法可以采用 `(self, value, *indexes)`，零项、多项索引使用同一规则。参数排列不改变求值顺序：
元素赋值仍先对象、再索引实参的求值与展开、再右侧值；复合赋值读写复用展开结果。

`hash(obj)` 使用 `type(obj).__hash__(obj)`，与运算符、真值一样由所属类决定行为，类对象由唯一元类 `type` 处理。
经类访问普通方法不绑定，所以不能用 `obj.__hash__()` 作为这一规则，否则对类对象调用会缺少参数。

`frozendict` 恒满足 `Hashable`。键或值不满足 `Hashable` 时，计算该 frozendict 的哈希抛出 `TypeError`。
协议只看类上是否有方法，不检查方法能否成功；若按内容决定 `isinstance(x, Hashable)`，同一个类的实例会得到不同结论，
与 `isinstance` 只看类型的规则冲突。

**`unsupported` 是 `Descriptor` 子类。** 原设计是给 `v` 打 `__is_unsupported__` 标记再原样返回，语义分裂且能被 `attrs` 绕开。
现在 `get` 无条件抛 `AttributeError`，存进描述器表，"标记"和"行为"是同一个东西。优先级自然遵守"MRO 上第一个命中的
描述器表项获胜"；协议检查复用同一次 MRO 查找，看查到的是不是 `unsupported`。`abstractmethod` 不跟着改，它只在建类时
被读一次；`foo = abstractmethod(unsupported)` 表达"没有默认实现、子类必须重写"。

**描述器在类的另一张表里。** 起因是 `attrs(int)['__op_add__'] = f` 能直接改掉 `int` 的行为。比较过黑名单、类属性表只读、
`attrs` 返回撒谎的 dict 子类、描述器搬到另一张表，选了最后一个：危险槽位不在 `attrs` 里，`attrs` 就能诚实地可读可写。

- 描述器表只在建类时确定，此后不变；整体优先于属性表；不通过属性名暴露，只能 `attrs(cls, 'descriptors')` 取到
  `frozendict`。实例不能用同名属性覆盖类上的方法。不引入 Python 的数据/非数据描述器区分。实例侧只有属性表。
- 在一条 MRO 上查找时，先遍历描述器表，未找到时再遍历属性表。`super`、协议判定和抽象方法检查使用同一顺序，
  后两者只查表，不调用描述器的 `get`。读取类的普通属性时先沿类自身的 MRO 查属性表，再回退到元类的 MRO。
  写入、删除仍作用于对象自己的属性表，继承来的普通属性可以被自身的属性覆盖，但不能经子类或实例删除基类的项。
- 读、写、删三条规则的第 1 条必须对称，都先判"`o` 是类就查它自己 MRO 的描述器表"，否则 `int.__op_add__ = f` 会静默写进
  属性表成为死项。
- `get(self, obj)` 不传属主类，靠 `isinstance(obj, type)` 区分经实例访问和经类访问。前提是 `type` 是唯一元类且 final；
  给 `type` 自己加需要绑定的普通方法或 `property` 会破坏这个等价。
- `attrs` 保持自由函数，不做成方法、不配 `__attrs__` 钩子，它的价值在于是唯一不经过属性协议的窗口。
- 内置描述器持有的函数走解释器内部引用，不放进自己的属性表，否则 `attrs(md)['func'] = evil` 能改行为。
- 类体收集方法只看"是不是函数对象或 `FuncGroup`"，不按 `protocols.Callable`。`MethodDescriptor.get` 分两路，经类访问不绑定。
- 类体收集保留特定内置对象的处理顺序，其后先把一般的 `Descriptor` 实例直接收入描述器表，再判断是否需要包装函数或
  `FuncGroup`。自定义描述器由继承 `Descriptor` 决定，不额外按方法名做鸭子类型判定。
- `MethodDescriptor`、`classmethod` 建立时复制被包装对象的抽象标记，`property` 在任一提供的访问函数标为抽象时
  以 `True` 初始化自己的标记。标记仍可由 `abstractmethod` 显式设置，类建立时按收集后的表项计算抽象方法集合。
- 真实存在但名字不进内置表的类放在 4.3，规范要能回答 `type(某个函数)` 是什么。

**构造统一到 `__construct__`。** `C(...)` 就是 `C.__construct__(...)`（`classmethod`，分配并初始化，返回对象），不要 Python 的
`__new__`/`__init__` 两段式。合并后两段式的理由各有着落：不可变类型直接造成品，驻留和单例靠"返回对象"，造壳不初始化
降级成 `object.__construct__`，协作继承里绑定自动带对。SL 没有用户元类，`type.__call__` 那一层永远同一份实现，所以真等价。

- `C(...)` 路径要求返回值是 `C` 的实例，直接调 `C.__construct__(...)` 不检查。禁掉"`C()` 返回无关东西"的工厂写法是故意的。
- `__abstractmethods__` 检查放在 `object.__construct__` 里，否则直接调 `C.__construct__(...)` 能绕过。
- `__construct__` 必须显式写 `@classmethod`，建类时检查，不为一个名字开隐式绑定特例。
- 认下的代价：只想填几个字段的类要多写取 `self`、`return self` 两行，还多一个"忘调 super 就返回 `None`"的失败模式。
- `super` 的第二个实参允许传类（是类就用它自己的 MRO），否则 `__construct__` 里没法往上调。

**调用的终点。** `f()` 走 `type(f).__op_call__` 是递归规则，基础情形是四种原生可调用对象：`Function`、`BuiltinFunction`、
`Method`、`FuncGroup`。基础情形是解释器里的判断，不是对象图里的节点（CPython 的 `tp_call` 是 C 函数指针，同理）。
`class A { __op_call__ = 某个 A 的实例 }` 能造出无限链，在主循环里走，耗尽的是 `RecursionError`，不是 C++ 栈。

**SL 函数和内置函数是两个 C++ 类、两个 SL 类型。** 字段表不同：`Function` 持 `Ref<Code>` 等 GC 要遍历的引用，
`BuiltinFunction` 持 C++ 函数指针。合成一个 SL 类型的话，SL 层得回答"`print` 的函数体怎么内省"。三个函数类型（含
`Method`）都是 final，`CALL` 靠比 `type()` 指针分派。内置函数也走调用一节那套实参绑定，不另开一套（CPython 的
`METH_VARARGS`/`METH_FASTCALL`/argument clinic 三套并行是反面教材）。`NativeFn` 的签名等写 `executor/` 时定，因为它绑在
`NativeFrame` 的形状上：纯计算型想直接返回值，回调型要返回"我压了帧"。

**`==`/`!=` 的终局回退按身份兜底，序比较没有。** 两侧全部弃权后，`a == b` 取 `a is b`，`a != b` 取 `not (a is b)`；
`<`/`<=`/`>`/`>=` 抛 `TypeError`。不兜底的话 `object() == object()`、`1 == None` 都会报错，也跟"`__hash__` 默认按身份"和
"`!=` 由 `__op_eq__` 推导"矛盾。兜底放在解释器层，不放进 `object.__op_eq__`：后者若直接返回 `False`，右操作数的
`__rop_eq__` 永远没机会跑。折叠器跨类型 `==` 折 `False` 因此是精确结果。

**反向运算符名用 `__rop_xxx__`。** SL 前面多一段 `__op_`，Python 式的 `r` 会挤进操作名内部（`__op_rshift__` 本身就是 `>>`）。
规则是正向名把 `__op_` 换成 `__rop_`。`__rop_*` 的参数顺序统一：`type(b).__rop_sub__(b, a)` 算 `a - b`。

**`__op_cmp__` 三路比较回退。** 六个比较运算符在每一侧的自有方法落空后，再试该侧的 `__op_cmp__`，然后才换边。它不对应
任何运算符，返回 int，`NotImplemented` 是弃权，其他非 int 抛 `TypeError`（只约束解释器的这次调用）。连带：
`object.__op_eq__` 不同一时返回 `NotImplemented`，否则只写 `__op_cmp__` 的类会得到"`<` 假、`>` 假、`==` 也假"。`!=` 多一条
"`__op_eq__` 取反"，互推只在 `==` 与 `!=` 之间，`<` 绝不退化成"不 `>=`"（偏序下不成立）。

**不搬 C++ `<compare>`。** 不要 `<=>`：它的价值是自动生成六个运算符，`__op_cmp__` 已兑现；真需要就加内置 `cmp(a, b)`。不要
strong/weak/partial 三种序类别：SL 里没有消费者。以后要表达偏序，可以拿 `__op_cmp__` 返回 `None` 表示不可比，这是纯放宽。

### 数值

**`float` 换成 `decimal`。** 十进制浮点、系数任意精度，`0.1` 在词法阶段就不再失真。原来的 double 以后以 `raw_float` 身份回来，
价值只剩速度和与 C 互通。改名是因为两个类型不能都叫 float，而且 `float` 背着 `0.1 + 0.2 != 0.3` 的包袱。否决有理数：显示
两面派、无理运算照样舍入、分母静默膨胀。代价是超越函数要自己写。

**每个运算都按上下文舍入**（抄 Python）。否决"精确优先"：位数无上限，`x = x / 2` 循环一千轮就是一千位；精不精确取决于
分母的质因数。`prec` 默认 28 时，舍入只在 28 位以上才咬人。构造不舍入、运算才舍入，`+x` 也是运算。标度是值的一部分、
不规范化，"理想指数"让 `1.10 + 2.00` 得 `3.10`，金额计算不用补零。

**上下文全局可变，每个方法可传临时的。** `decimal` 是类不是模块，`Context`、`getcontext`、各信号类都是它的类属性，舍入常量
挂在 `Context` 上。全局可变上下文是动态作用域，代价接受。临时上下文走方法的末位参数（`__op_div__(self, other, ctx=None)`），
配无前缀别名，写成 `a.div(b, ctx)`；`Context` 不另挂 `ctx.divide(a, b)` 那套算术方法，两套等价 API 是负担。删掉 Python 的
`capitals`、`clamp`、`FloatOperation`。保留 `Infinity`、`NaN`、`sNaN`、负零：traps 可配就得有"不设陷阱时返回什么"。
`//` 永远向负无穷，不采纳规范的 `divide-integer`。

**`0 ** 0`：int 给 1，decimal 抛 `InvalidOperation`**，两边各跟自己的既有规范走，不对称是知情选择。`Context` 数值字段的范围
在 SL.md 里用文字写，别改回 `1..999999999` 这种记法（`..` 左闭右开，会把上界排除在外）。

**`raw_int` / `raw_float`：下个版本才加，设计已定。** 定位是逃生舱，只为速度和互通，行为委托 C++。

- 档位判据是"C++ 原生就有且宽度确定"：`i8`…`u64` 八档，`f32`、`f64` 两档；`raw_int`、`raw_float` 是抽象基类。不要 128 位
  （MSVC 没有）和 `long double`（宽度随平台）。
- 字面量后缀等于类名（`1i32`）。否决 `y`/`w`/`d`/`q`：`d` 是十六进制数字，`0x1d` 无解。后缀前允许 `_`。
- 提升：`raw_int → int`、`raw_float → decimal`；raw 之间按 C++ 规则。算术和比较必须同时提升，否则 `a - b > 0` 和 `a > b`
  答案不同。连带：`x + 1`（`x` 是 `u8`）结果是 int；`hash(1u8) == hash(1)`；它们进 `numbers` 塔；`0.1f64 == 0.1` 为 `False`
  （这是对的）；跨族比较的 NaN 跟着目标类型的语义走。
- "稳定回绕、不 UB"要显式实现：有符号溢出转 unsigned 算；`INT_MIN / -1` 回绕；raw_int 除零抛 `MathError`，raw_float 照
  IEEE 出 inf/NaN；`x << n` 定义为"左移 1 位做 n 次"，由此推出移位量 ≥ 位宽的结果；移位量为负抛 `ValueError`，不做反向移位
  （负移位量几乎总是算错了，静默反向会把 bug 变成看起来合理的错答案）。

### 解构赋值

解构先取出各层元素并完成全部个数检查，嵌套解构同样先检查，再向任何左值写入。个数不符抛出 `ValueError`，不写入左值。
检查通过后从前到后逐个写入，写入时检查已有声明的类型与 `const`。某次写入失败时保留此前已完成的写入，不回滚。
这样个数错误不会留下部分赋值，声明检查失败仍遵守普通赋值的效果。

### 循环

**收集模式：两个记号各管一个轴。** 第一个（`$`/`$$`）定结果容器，第二个（`*`/`**`）定每轮的值怎么进容器，配对约束复用展开
语法里 `*` 对可迭代、`**` 对映射的分工。记号挂在 `for` 上，不挂在被收集的表达式上：`expr` 可以是复合表达式或 `if`，挂在
表达式上规则会变成非局部的。`$$` 每轮的值相当于 `(k, v) = expr`，恰好产出 2 个元素即可，不必是 `tuple`，跟迭代模式拆元素
用同一套判定；两字符的 str 会被当成合法 pair（同 Python 的 `dict(['ab'])`）。

### 常量折叠

**`StaticEvaler` 不依赖高精度库。** int 走 `int64_t`，溢出就不折；decimal 彻底不折，算术、比较、真值一概不折，一条规则比
"算术不折、比较折"简单，也不用把 `numeric/` 链进 `Analyzer`。否决过"折叠器复用 `BigInt`/`BigDec`"：运行期数值实现和编译期
pass 绑在一起违反分层，还要为 `2 ** 超大指数` 撑起一套结果规模估算（估错过），收益只是 `10 ** 100` 这类没人写的表达式。
用二进制浮点近似 decimal 会产生错值（`0.1 + 0.2` 折成 `0.30000000000000004`），比漏折严重一个量级。

- int 的科学计数法写法：折叠器内部设一个十几到二十几的指数上限作效率阈值；尾数全 0 直接折成 0；否则补零展开再走普通
  int 路径。展开复用 `ast_node_literals.cpp` 的 `strip_sign`/`strip_exponent`，挪成共享辅助，不重写字符串手术。
- `raw_` 不拆成尾数、指数两个字段：JSON 输出和所有测试辅助都按一整条字符串比对，拆了只是把拼接从构造时挪到序列化时。
  问题根子是"消费方各自现场解析"，该收成共享辅助，不该改数据形状。
- `truthy`/`literal_equal` 返回 `std::optional<bool>`，`nullopt` 一律当"不折"。判定函数缺第三态，在折叠器里就是埋了一个
  错误的默认值（曾让 `0e0` 被判成真）。
- bool 的算术、比较按 int 折（`is_int_family`），位运算和重复次数只认真 int（`is_int`）。
- `is_literal_pure` 仍把 decimal 算纯字面量，它回答的是"能不能当死代码剪掉"，跟"知不知道值"是两个问题。

**`tuple`/`list` 的 `*` 重复：元素能进常量表就折。** 共享不必由 AST 表示：克隆出来的 n 份字面量在 codegen 里各自 intern，
结构相同就落在同一个槽，`x[0] is x[2]` 折叠前后都是真。判据是 `is_literal_const`（`is_literal_pure` 减去 `list`），不能复用
`is_literal_pure`，它会放过唯一该挡的那一类：`[[1]] * 2` 不折，`list` 每次求值都新建。

**`raw_` 的形状校验归节点构造函数，AST 层面负数是合法字面量。** `Analyzer` 先检查后折叠、只检查一次，折出来的字面量节点
没人校验，所以校验挪进构造函数。分界线：构造函数管"这个节点自己的字段合不合法、只有实现出 bug 才会违反"
（`InternalError` 类）；`SemanticChecker` 管"要看上下文"或"用户写错了"（`SyntaxError` 类）。其余断言搬不动：节点成员是
public 的，折叠器整棵子树往槽位里换，构造函数拦不住构造之后的赋值。`raw_` 允许一个前导负号（折叠后 `-1` 就是字面量），
真正的不变量是 `check(fold(x))` 必须通过，测试在 `test/analyzer/recheck_after_fold_test.cpp`。

## 架构决策（不进 SL.md，但影响深远）

### 编译期 C++ 异常与 SL 运行时异常对象分两层

`cppexceptions/` 的 `SyntaxError` 和 SL 层的 `SyntaxError` 类只是重名，类比 CPython 的 `PyErr_SyntaxError` 与 Python 层的类。
`eval`、`eval_isolated` 现场编译时要内部 catch C++ 异常、构造 SL 异常对象再走正常 `raise` 路径，裸 C++ 异常不能漏进 `except`
的匹配逻辑；`EncodingError`、`FileNotFoundError` 以后也走这个模式。`InternalError` 能不能被 SL 捕获，由 SL 层给不给它注册类
决定，跟它继承哪个 C++ 基类无关。

### 对象模型落在 `runtime/`，不是扩 `executor/`

理由是链接方向：codegen 要直接造 SL 对象塞进常量表（codegen → 对象模型），主循环因为 `eval` 要现场编译
（executor → compiler）。对象模型放进 `executor/` 会形成环。

### 对象模型的几个取舍

- 侵入式 `Ref<T>`，不用 `std::shared_ptr`：GC 要读写引用计数、要枚举整个堆。计数不是 atomic，SL 没有线程。
- 构造恒 +1、析构恒 -1，不给 adopt/borrow 两套入口，混用是侵入式计数最经典的错法。裸 `new` 不包 `Ref` 必漏，由 `make_ref` 兜住。
- `Type::mro_` 存裸指针：`mro_[0] == this`，用 `Ref` 会让每个类自成环。安全性由 `bases_` 兜着。
- 类型对象是普通堆对象，"元类先留空、建完回填"就解开了 object/type 互为类型的结。
- `Runtime` 是进程级单例：SL 没有多解释器，`import`、`eval_isolated` 建的是新的全局作用域，不是新运行时。
- `Runtime::shutdown()` 手工拆掉唯一的引用环（类型都强引用 `type`，`type` 的元类是自己），测试才能断言
  `Object::live_count() == 0`。引用计数漏加漏减是静默的，这句断言是现阶段唯一能自动抓住它的东西。

### 异常对象只存 `.args`

`BaseException` 全部子类共用一个 C++ 类，只有 `args_` 一个字段，跟 CPython 一样是结构体槽位，不走实例属性表。没有
`__cause__`/`__context__`，`raise` 没有 `from` 子句，也不做隐式异常链（那需要主循环知道"当前正在处理哪个异常"）。

### `RaisedException` 只在有界、不回调 SL 的 C++ 代码里 throw/catch

它不是 SL 异常跨帧传播的机制（那是主循环手写的显式算法，C++ 异常展开够不到堆上的 SL 帧）。用途是某个原生操作决定"这一步
的结果是一个异常"，由紧邻它、不跨 SL 帧的调用方立刻接住，翻译成帧接口的"接收传播的异常"。继承 `std::exception` 只是为了
漏接时能兜底打印。

### `HostErrorConversion` 提前写

转换规则（宿主异常对应哪个 SL 类、`.args` 放什么）是设计决定，先钉死免得以后临时拼凑，而且能单独验证。`EncodingError` 现在
落到 `IOError`，等 `exceptions` 模块有了落脚处再改一行。

### `compiler/` 门面：一个阶段一个函数

`read_source` / `tokenize` / `parse` / `analyze` / `compile`，函数名说"跑到哪一阶段为止"，参数类型说"从哪一阶段起步"，中间产物
就是返回值。每个重载都把起点到终点之间的阶段全跑完，不留缺口：`compile(AstNodeProgram &)` 会先原地分析再 codegen，
`AstNodeProgram &` 在 `analyze` 和 `compile` 两处表示同一个起点（解析完、未分析）。否决过让它收 `const AstNodeProgram &`
表示"已分析"：凭 const 区分起步阶段太隐晦，还凭空多出第四种起步点。要跳过阶段就直接调那一层的类。

- 否决过 `Hooks` 回调：为"打印"硬造的间接层，调用方拿不到产物本身。
- 门面一行 stdout 都不写，`eval` 将来走同一条流水线，不能往程序输出里掺东西。
- 阶段名由 `run_stage(name, stage)` 兜住：`SLException` 原样放过（那是用户代码的问题），其余包成带阶段名的 `InternalError`。
- `SyntaxError` 转 SL 异常对象那一层还没加，要等帧栈和主循环。

### 常量去重放在 `compiler/codegen/`

`ConstPool::structural_identical()` 判的是"该不该共用一个槽"，跟 SL 的 `==`/`hash` 好几处相反：`1`、`True`、`1.0` 必须各占
一槽（否则 `True is 1` 变真），`1.5` 与 `1.50`、`0` 与 `-0` 要分开，`NaN` 要复用同一槽。摆进 `runtime/` 等于在对象模型旁边
放一个长得像"对象相等"的函数。

- 元组必须自底向上规范化：先把元素 intern 成规范对象，再拿元素的对象身份当键；规范化后先 `find_tuple()` 查表，命中就不建
  新元组（编译期不 GC，扔掉的元组会攒到第一个安全点）。`structural_hash()` 和 `find_tuple()` 必须共用 `hash_tuple()`。
- 两边都要 `dynamic_cast`，不能靠"SL 类型相同"去 `static_cast` 另一边，那只是没人强制的隐含不变量。转不过去就当不相同。
- `take_table()` 不用 `&&` 限定，它拦不住"取完之后接着 intern"这个真正的危险；改成普通成员函数并显式清空。
- 哈希不缓存：`structural_hash()` 与 SL 的 `hash()` 语义错开，等 `hash()` 和 `dict` 定了再谈。

### `Code` 是 SL 对象

每份 `Code` 都有主（嵌套表、函数对象、模块），所以常量表不是 GC 根。但"有主"不等于"可追踪"：标记器只顺着
`visit_own_refs` 走，`Code` 若是普通 C++ 类型，追踪链在它这里断掉。做成 `Object` 后共享所有权、追踪、字节记账都免费
（CPython 的 code object 同理）。另一条路（普通类型加手动转发的 `visit_refs`）要重造生命周期、转发、记账三样，否决。

- 做成对象不等于暴露给 SL：`code` 类型不进内置表，没有任何属性或内置函数返回它。
- 不引入环：常量表只装字面量，嵌套 `Code` 是父到子的 DAG。
- 主构造函数不收 `Type*`，SL 层子类化不了它。

### GC

**按最大堆字节数触发回收（`-Xmx` 语义）。** 超过上限触发一次全堆标记清扫，回收后仍超就抛 `MemoryError`。必须按对象自报的
字节数（`size_bytes()`，纯虚），否则任意精度 `int` 的真实负载在账本上看不见。字节数只能由 `make_ref` 在构造完成后记
（`Heap::link()` 在基类构造期间调，问不到派生类大小），所以记的是分配压力；存活量在回收时重算。触发不能在分配那一刻，
只能标记"超预算"，等主循环的安全点再回收。账本已落地；`-Xmx` 参数和"超预算 → 安全点回收 → 抛 `MemoryError`"要等主循环。

**用"从根标记清扫"，不用 CPython 的 trial deletion。** CPython 用后者是因为根集合枚举不出来。SL 的执行状态全在堆上的帧对象
里，安全点上 C++ 栈是空的，根可枚举，标记清扫好推理得多。代价是硬前提："`collect()` 只在安全点调用，C++ 栈上不能有活的
`Ref`"，分配不许顺手触发回收。想放松"主循环不递归"之前先想清楚 GC 怎么办。

**标记和拆环共用一个 `visit_own_refs`。** CPython 的 `tp_traverse` + `tp_clear` 两份清单一旦不一致，后果分别是提前回收和永久泄漏，
合成一个之后不一致在结构上不可表达。访问者拿到的是引用本身（`RefBase &`），类型擦除靠继承，不手搓函数指针表。`RefBase::reset()`
是 `protected` + `friend class Heap`，`Ref<T>` 另开公开的 `reset()`，"放掉自己的句柄"和"放掉别人槽位里的引用"是两种能力。
否决在 `RefVisitor` 上挂 `should_clear()` 虚谓词。

**回收第 3 步的整批 incref 是必需的。** 垃圾之间互相持有引用，放边时谁先归零谁就地析构，再 decref 已删除的对象就是
use-after-free。整批 +1 把生死推迟到最后一步，第 5 步的 `assert(refcount() == 1)` 守的就是这个不变量。

**全堆都进链表**，不做"只跟踪可能成环的对象"：少一个"这个类型算不算叶子"的判断就少一处能写错的地方。要加时，`Object`
构造函数多收一个参数（不能用虚函数，基类构造期间虚分派不生效）。

**GC 根只有 `Runtime` 一处。** 原来的 `GcRootSource` 注册接口只有一个实现，剩下的根（帧栈、模块表、内部对象表）都是进程内
唯一、跟解释器同寿的东西，本来就该挂在 `Runtime` 上。代价是测试不能注册临时根。

**三张根表统一成"X-macro 清单 + 定长数组"。** 内置类型、单例、内部对象三张表形状一致，`visit_roots()` 是三个 for 循环，漏一行的
风险消失（漏了 GC 会悄悄清掉，症状是随机失效）。方向是单例向另两张看齐：`InternalObject` 的枚举值就是 `LOAD_INTERNAL` 的参数，
必须是数组加枚举。三张表不合并，存的东西和下标语义不同。

### `runtime/` 的类型名保持全局短名

不加 `Sl` 前缀（零信息量，且会毁掉 C++ 类名与 SL 类名一一对应），不开命名空间（项目零命名空间是既有风格）。C++ 对象类名等于
它覆盖的那棵子树的根的 PascalCase，所以异常树共用的类叫 `BaseException`；`NamedSingleton` 是唯一按存储形状命名的，它跨
`NoneType` 和 `SingletonType` 两棵树，叫 `Singleton` 会暗示不成立的一对一关系。SL 没有 `repr`，别把 Python 的词带进来。

### bootstrap：状态只有"有运行时 / 没运行时"两种

- 所有 `Type` 对象在 `init()` 里一次建完，不分批、不惰性。一个 `Type` 百来字节，全部几十 KB；分批会重新引入"有的建了有的
  没建"的中间态；惰性构造会让 `Runtime::type_list()` 这种热路径可能分配，跟 GC 的安全点前提冲突。
- 以后该惰性化的是内置函数和方法对象（几百个，多数程序碰不到），方法表存成静态 C++ 表、首次查找才物化。现在别把方法塞进
  `Type` 的构造函数。`attrs(cls, 'descriptors')` 要触发全量物化。
- 属于模块的东西（模块对象、`exceptions.EncodingError`、decimal 的信号类）等模块系统；`numbers.Number` 这类 Type 对象必须
  eager，`int` 的 MRO 指着它们。
- 不要按启动阶段划分相位。单线程同步执行下，`init()` 跑到一半的状态外部观察不到。曾经有过 `BootPhase` 枚举，所有检查点
  拦的都是 `Runtime` 自己绕出去又绕回来的访问器，删掉了。加状态检查之前，先枚举会读这个状态的调用点，看是不是都是自己。

### Program 的值只由 `return` 决定

复合表达式的值是最后一条，Program（文件、函数体、类体）的值只由 `return` 决定，走到末尾就是 `None`，所以 `func f() { 1 }`
返回 `None`。codegen 里 Program 每一条都按 `want_value=false` 编译，不补收尾指令，pc 走出字节码末尾等价于 `return None`。
否决"末尾补 `LOAD_CONST None` + `RETURN_VALUE`、以终止指令结尾为不变量"：在这套语义下走出末尾是正常结局，能抓 bug 的是
`CodeBuilder::build()` 核对"走出末尾时栈为空"和跳转两侧的栈深核对。代价是跳转目标可以等于指令总数、主循环取指前多一次
越界判断、函数体和类体走出末尾要走与 `RETURN_VALUE` 相同的收尾路径。

### 字节码

完整设计在 [../compiler/codegen/bytecode.md](../compiler/codegen/bytecode.md)。换一套指令集不改变 SL 程序的可观察行为，所以它是
实现契约、不进 SL.md。跟语言语义绑定、字节码要遵守的两条：

- 装饰器前缀是 func/class 产生式的一部分，不存在外层的 `deco(...)` 调用表达式。先从前到后求各装饰器，再进入捕获、形参、
  返回类型的求值；装饰器调用在建立完毕后从近到远；名字只绑定一次。
- `Code` 编译一次可复用多次，但每次"建立"都必须造新的函数对象，`is` 比的是身份，循环里的值捕获必须各自捕获当次的值。

实现取舍：

- `import` 调用形态不需要专门指令，加载算法包成内部函数对象，`LOAD_INTERNAL` 取出后普通 `CALL`。
- `eval` 必须是独立指令：它要现场编译，编译需要的 `in_local_scope` 来自调用帧；而且关键字化的意义就是让"有没有 `eval` 点"
  在字节码层面可判定。
- `finally` 的返回地址走帧上的小栈 `returns_`，不占操作数栈。原设计（压操作数栈）跟"`finally` 体只编译一份"冲突：四条进入
  路径里，压了返回地址的两条深度会比异常路径多一。挪进帧之后，四条路径的栈顶恒是"这条路径要带出去的值"（`break`/`continue`
  压 `None` 占位）。否决复制 `finally` 体（CPython 3.11 的做法，代码膨胀）和加 `STORE_RETURN`/`RETURN_STORED`（只解决 `return`）。

### codegen 拆成三层

`CodeGen` 只回答"这个节点发哪些指令"；`CodeBuilder` 不认识 AST，管标签回填、`EXTENDED_ARG` 定点迭代、栈深静态跟踪和四张表。
两者变化原因不同。`CodeBuilder` 在跳转两侧栈深对不上时当场断言，手写字节码最容易错的就是栈不平衡，而没有虚拟机时跑不出来。
反汇编器是 codegen 唯一的验证手段，输出完整版给人看、紧凑版给测试比对。测试写法见
[notes/codegen-test-conventions.md](notes/codegen-test-conventions.md)。

### `numeric/BigInt`

手写，不引 GMP、Boost：GMP 在 Windows 下构建麻烦，Boost 在严格选项下冒警告，现成单头文件库对除法和取模的符号语义没有文档。
内部是"小路径 `int64_t` / 大路径 limbs"，不变量是"能装进 `int64_t` 就必然走小路径"。

测试不手挑期望值，用一批边界值两两、三三组合验证数学恒等式，外加"同一个值走不同路径算出来必须相等"的规范化套件。历史上
的真实 bug 都是"假设输入已是规范形式、被套一层调用后破坏"，靠恒等式测得出来。以后碰这块延续这个策略。

`pow`、`operator<<` 不设结果规模上限，是明确决定；资源保护留给 VM。`from_decimal_string` 在尾数为 0 时短路，不去算
`10^指数`，这不是给指数加上限。溢出检测走 `common/overflow.h`，语义同 `<stdckdint.h>`（MSVC 没有这个头）；`cl` 下用 SafeInt
返回 bool 的自由函数，不用会抛异常的 `SafeInt<T>` 类。

### `numeric/BigDec`

表示是 `BigInt 系数（恒非负）+ int64_t 指数 + 符号位 + 特殊值 tag`。符号单独存，因为 `BigInt` 表示不出负零。指数用 `int64_t`：
中间结果可以越出构造范围，`fix` 之后才落回 `[Etiny, Emax]`，构造入口卡在 `±kMaxExponent`，中间不设限。`kMaxExponent` 必须比
`Emax` 上限宽一整个 `prec`，否则次正规结果 `to_string()` 后读不回来；否决在 `set_emin`/`set_prec` 里交叉校验（两个字段会凭空
多出顺序依赖）。

最容易写错的地方：`BigDec` 没有"一个值只有一种表示"的不变量，标度是值的一部分，`==` 必须先对齐指数，哈希要先归一标度。
"表示相等"和"数值相等"是两个方法（`identical` / `equals`），别混用。

**信号机制。** 12 个条件、8 个信号，细分条件查陷阱、记标志时先折算成 `InvalidOperation`（照抄 Python 的 `_condition_map`）。
抛出的 `DecTrapped` 带细分条件，这一点跟 CPython 不同（它抛折算后的基类），是刻意选的：SL.md 把细分异常列成了类，用户能按
细分异常 catch。陷阱抛 `numeric/` 自己的 `DecTrapped`，上下文字段不合法抛 `std::invalid_argument`，`numeric/` 不认识 SL 异常。

**`//`、`%` 向负无穷取整。** 先照规范算截断的商和余数，再统一修正一次。修正那一步必须走带上下文的 `add`（精确相加会构造两百万位
的数）；`DivisionImpossible` 按修正后的商判位数；`//` 单独用时不能 `fix` 余数（会误报 `Inexact`），但商本身必须过 `fix`（`fix` 还管
指数域，位数够不代表指数域够）。`//` 商为零时按两操作数符号异或；`%` 余数为零时符号跟被除数（照抄规范）。

**测试期望值来自 CPython 的 decimal**（`gen_big_dec_cases.py` 生成 `big_dec_cases.inc`），libmpdec 和 `BigDec` 是两套独立实现。
`//`、`%` 是我们偏离规范的地方，生成器在超高精度下换一条推导路径出题，不照 C++ 算法再写一遍。陷阱开启的路径也有表，以
`_pydecimal` 的 flags 顺序为准。

**超越函数。** 照抄 `_pydecimal`：先按 prec+3 位算近似，不够定夺舍入方向就再多算三位。最后的 `fix` 固定用 HalfEven（`**` 除外），
算完靠 RAII 还原 rounding。整数定点算法在 `numeric/dec_math.{h,cpp}`，只认识 `BigInt`；里面的常数（尤其 `kTaylorL`）有误差论证
撑着，别随手调。`log10_digits` 有进程级静态缓存，不是线程安全的。不要用 `std::thread` 并行跑最耗时的测试：Debug CRT 堆的全局锁
让 2 线程比单线程慢 2.5 倍。`**` 分三条路：粗筛溢出下溢（同时替 `power_exact` 挡住会炸开的输入，别挪走）、`power_exact`、
`exp(y*log(x))`。指数非整数而结果恰好精确时照样报 `Inexact`，在陷阱全关的副本上 `fix` 后按优先级补报。

**跟 libmpdec 不一致的两处，都站 `_pydecimal`**：非整数指数的 `**` 在定向舍入下（`9 ** 0.5` 在 ROUND_DOWN 下给 `3.00`）；`exp`
在 `Emin == 0` 时次正规判定在舍入前做。生成器对每组用例用两套实现各算一遍，不一致整组跳过，分歧点随参数漂移，所以全表统一过滤。

**覆盖率。** `BigDec.cpp`、`BigInt.cpp`、`dec_math.cpp` 行覆盖 100%。下面这些分支是刻意不可达的防御代码，别再凑输入：
`power_exact` 里三处 `to_int64` 失败；`is_even_integer()` 的零系数；`power_exact` 循环里的 `!exponent.is_zero()`；`dpower` 的
`shift >= 0`、`dlog` 的 `p + extra < 0`；`BigInt` 里几处由调用方不变量保证的分支。`log10_digits` 的缓存只增不减，新测试要定向
命中某条扩容路径时，`p` 要远高于其他用例摸到的量级（当前约 125），否则覆盖随用例顺序漂移。

## 悬而未决

- 匿名类没法调用 `super`：`super(cls, obj)` 的第一个实参要写类名。`__construct__` 让这个洞从罕见变成常见。可能的出路是零参或
  单参形态的 `super`，由编译器把定义类填进去。
- SL.md "编译期与运行期"一节 "`SyntaxError` 在编译期抛出、其他异常在运行时抛出" 没覆盖"拿到源码字符串之前"的阶段（路径不存在、读不了、编码不
  合法）。启动阶段的错误怎么报、算不算 SL 异常还没设计。
- `SyntaxError` 要不要在 `.args` 之外暴露 file/row/col 没拍板，现在不加；真要加也该走属性协议，不往 `BaseException` 里加专属字段。
- 内置类的构造、转换行为整片没定（`int(x)`、`str(x)`、`list(x)` 等），其中 `int(decimal)` 的取整方向是真空白（`//` 已定向负无穷）。
  `.args` 的字符串化规则依赖 `str()`，不单独为异常发明。
- 容器的方法列表没逐个列出。
- `sqrt`/`exp`/`ln`/`log10` 在 `BigDec` 上有了，SL.md 没规定怎么暴露（decimal 的方法，还是 `math` 模块）。
- `BigDec` 缺 `hash`（要跟数值相等的 `int` 一致）。
- 小整数、短字符串要不要做全局实例缓存（会影响 `is`），等 VM 能实测再说；同一份 `Code` 里的字面量已由常量表去重。
- `object()` 造不出来：`Object` 是抽象类，要等属性表落地。
- `local` 保留字的去留；`when` 的完整设计；`assert` 的行为；二、八、十六进制和 `complex` 字面量（`complex` 类已有）。
- 模块搜索路径、循环 import、相对导入。
- 资源与递归保护（讨论过、没决定做不做）：帧深度上限；深嵌套对象的 `==`、`hash`、`repr`、GC 标记以及超深嵌套源码的 Parser、
  Analyzer、CodeGen 递归，会撑爆 C++ 栈；`bad_alloc` 转 `MemoryError`；`10 ** 10 ** 10` 这类（`BigInt::pow` 实际会被 O(n²) 乘法
  拖到算不完）；迭代期间修改容器的版本号检测；测试加一套 ASan/UBSan 构建。
- 每次调用都要给带注解的形参加声明，注解在定义时已能共享，具体机制用户要重新设计。
- `decimal` 的 NaN payload（`Decimal('NaN123')`）现在一律判为不合法，静默丢掉比拒绝更糟。
- 文件 I/O、字符串插值（否决了 f-string，打算用 `%` 运算符加 `.format()`）放到最后。
