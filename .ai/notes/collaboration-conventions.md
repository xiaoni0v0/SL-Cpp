# 协作硬规矩

这些是用户明确要求过、贯穿整个项目始终有效的约束，不是某次任务的临时要求。新会话/新机器接手时
默认全部照办，不用再问一遍。

## 语言

全程用中文交流（对用户说的话）。代码注释也是中文，标识符/关键字本身用英文——这是这个项目一直以来
的既有风格，直接照抄现有代码的写法就行。

`.ai/context.md` 之外的所有地方（代码注释、`SL.md`、其他文档），**禁止出现引用"当前对话/会话"本身
的措辞**，比如"此次对话中""本次对话""刚刚加入""这次重构"之类——这些话会随时间失去意义（读者不知道
"这次"是哪次），而且代码/文档应该只描述"是什么"，不应该夹带"是怎么演变来的"这种过程性叙事。设计
决策的来龙去脉、被否决过的方案、bug 根因，这些确实有价值的"过程性记录"，专门写进 `.ai/context.md`
——**只有这一个文件豁免上述禁令**，可以自由使用"用户要求""之前尝试过""这次发现"这类语言，因为它
本来的定位就是给未来的 AI/开发者看的决策日志。

## git

**不准动 git**——不主动执行任何 git 命令（status/diff/log 只读命令也不例外，除非用户明确要求）。
这个项目当前的开发流程里，git 相关操作完全由用户自己把控。

## 并发编辑

用户会一边跟 AI 对话一边自己直接改代码；某些工具（linter/IDE 自动格式化）也可能同时在改文件。工具
调用结果里出现的"文件在你上次读取后被修改"之类的 system-reminder，遇到了就**默默按新内容继续干活
就行**——不要撤销/覆盖用户或 linter 刚做的改动，也不要在回复里特意提"我注意到文件被改了"这种话（除非
新改动跟当前任务直接冲突，需要用户澄清）。

## 汇报风格

用户是熟练的 C++/语言实现工程师，自己也在深度参与代码，经常并行做自己的重构。汇报进展/结论时：

- **直接给结论和证据，不要过程性流水账**。理想结构是"发现了什么 → 认真考虑过但否决了的方案（附
  具体理由）→ 最终选择的方案 → 验证结果（测试通过数字）"，跳过"我先做 A，然后做 B，接着……"这种
  纯粹按时间顺序的叙述。
- 用户会主动纠正方向、也会在方案合理时明确认可（"对，就是这个""可以"）——这些反馈要记住，不要下次
  又重新问一遍已经拍板过的问题。拿不准的、用户自己也说"这个我也没想清楚"的细节，交给 AI 自主判断即可，
  不用每个细节都反复确认。
- 用户经常要求"讨论/only answer，别动代码"——遇到这种明确说明的讨论回合，只回答、给理由，不要顺手
  改代码，即使觉得改了更好。
- 大规模改动前（比如这次"加强测试覆盖"这种开放式大任务），可以先用 `TaskCreate`/`TaskUpdate` 拆解
  成可跟踪的子任务，边做边勾，方便用户看进度，也方便自己不漏项。

## 测试

`test/parser/**`、`test/lexer/**` 下的测试文件按主题分组成目录，目录名用自己那套独立编号
（`01_literals`、`08_control_flow` 等，**不跟 SL.md 章节号绑定**，见
[no-section-numbers.md](no-section-numbers.md)），每个目录一个或几个 `*_test.cpp`，用 doctest 的
`TEST_SUITE`/`TEST_CASE`。
新增测试文件要记得同步加进 `CMakeLists.txt` 里对应的 `add_executable(SL_Cpp_Parser_Tests ...)` /
`SL_Cpp_Lexer_Tests` / `SL_Cpp_Analyzer_Tests` / `SL_Cpp_Numeric_Tests` 列表（这些列表是手写的
文件清单，不是 glob，漏加不会报错、只会静默不编译）。

正例用 `parse_json(...)`/`parse_program_json(...)` 转成 json 结构比对；反例（语法错误）用
`CHECK_THROWS_AS(..., SyntaxError)`，如果要断言具体是哪句报错、报错位置对不对，直接 `try { ... }
catch (const SyntaxError &e) { const std::string msg{e.what()}; CHECK(msg.find(...) != npos); }`——
`SyntaxError::what()` 的格式是 `"{file}:{row}:{col}:\nSyntaxError: {message}"`，位置信息是拼进消息
字符串的，没有单独暴露的字段，断言位置就是 `msg.find("row:col:")`。

用 `parse_json(...)` 结果做多次 `["field"]` 取值时的花括号初始化陷阱，见
[json-test-brace-init-trap.md](json-test-brace-init-trap.md)——非常容易踩、报错信息还很误导人。
